# Профиль и решение об оптимизации

Шесть последовательных release-прогонов: три до и три после локального изменения диагностики. Каждый пишет 64 × 524288 байт (32 МиБ) в новый физический каталог mktemp, затем отдельный процесс открывает и повторно проверяет чистый сегмент. Вход byte[i] = (i × 131) mod 256 и метаданные одинаковы. Параллельные проверки во время измерений не запускались. Другую активность машины и холодность дискового кэша не контролировали.

Среда: macOS 27.0 (26A5425a), arm64, Apple Swift 6.4 (swiftlang-6.4.0.30.4), swift-driver 1.168.6. Native SwiftPM, --jobs 2, -c release. Сборка вынесена из времени прогона. [Снимок до](исходники-профиля.json) и [снимок после](исходники-после-профиля.json) связывают внешние исходники с измерениями отдельно от отпечатка FUM в v4. Все production Swift-файлы финального результата совпадают со снимком после; позднее тест дополнен независимым oracle полного хэша.

## Решение

Первые три прогона показали RSS диагностического recovery 75153408 байт (71,67 МиБ) против около 8,5 МиБ writer. Два прохода FileHandle.read при вычислении SHA-256 удерживали временные буферы до конца области autorelease. Отдельная регрессия до исправления превысила выбранный локальный бюджет 64 МиБ: 75366400 байт. Это инженерный бюджет данной синтетической фикстуры, не универсальная гарантия API или пользовательский SLA.

Добавлен autoreleasepool вокруг чтения и SHA256.update каждого блока в диагностическом CLI. Ни формат, ни библиотечный файловый протокол, ни порядок sync не менялись. После — 9,27–9,28 МиБ: около 87% снижения пикового RSS диагностического процесса. Все хэши сегмента до/после в обеих сериях равны 3c504f55979ea006796597846cf070458efc38e9b0dd25d4364dbd2c7d0d104a. Тест дополнительно сверяет результат с независимым SHA-256 целого файла в родительском тестовом процессе.

Ускорение записи или восстановления не заявляется: запись использует прежний алгоритм, разброс времени и прогрев существенны. В исходной серии запись группы занимает примерно 54–59% времени ack, хэш входа — 23–25%; ни один из этих проверочных хэшей не убирается ради скорости. Повторный scan восстановления оставлен для перепроверки префикса непосредственно перед возможным truncate.

## Границы времени

Время записи охватывает 64 вызова добавить, включая sync; создание файла, генерация входа и печать JSON вне него. Ack-время — один вызов добавить до возврата квитанции. Профиль вложенный: время подтверждения включает дочерние стадии.

Время recovery — открытие/scan плюс явная повторная проверка/sync чистого файла; два диагностических SHA-256 вне этого времени, но внутри RSS. Кэш прогрет первым scan и hash. Ремонт хвоста, холодное чтение, перезапуск ОС и потеря питания здесь не измерялись. Неизменность байтов и восстановление усечённой фикстуры подтверждаются отдельными тестами, а не подменяются этим профилем.

## Воспроизведение

Из корня кодового репозитория:

```sh
swift build --package-path Packages/КонтейнерНаблюдений --build-system native --jobs 2 -c release
fum_profile_root=$(python3 -c 'import tempfile; from pathlib import Path; print(Path(tempfile.mkdtemp(prefix="fum-container-profile-")).resolve())')
Packages/КонтейнерНаблюдений/.build/release/профиль-контейнера записать "$fum_profile_root" 64 524288
Packages/КонтейнерНаблюдений/.build/release/профиль-контейнера восстановить "$fum_profile_root"
```

В текущей задаче каждый вызов и сборка выполнялись из назначенного FUM-дерева через v4-обёртку с абсолютным путём к пакету/бинарю, классом адресная и тайм-аутом 120 с (сборка — 180 с). Историю успешных и ошибочных запусков показывает [отчёт](../отчёт.md). Синтетические каталоги не являются пользовательской памятью и не включаются в Git.
