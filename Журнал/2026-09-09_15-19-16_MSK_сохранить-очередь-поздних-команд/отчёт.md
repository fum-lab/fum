## Проверки

Первый запуск в этой новой папке явно включил `--приёмочные-раунды`; все записи имеют v4, исходный порядок 1 и отсутствие перехода схемы. Первоначальный RED — отсутствие модуля. Следующий прогон выявил неправильную фикстуру пути macOS: временный путь /var проходил через symlink; фикстура стала использовать физический resolve, ограничение кода не ослаблялось. Затем девять основных сценариев дали GREEN.

Адресные поведенческие RED выявили пропуск дописанного во время callback сообщения, повреждённой оболочки и подмены именованного WAL. Исправления проверены повторно. Следующие RED рецензента доказали потерю хвоста при создании, перенос решения между очередями и пропуск payload без типа. Их закрыли сохранением всех уже наблюдённых байтов в начальном событии, расширением ссылки на область очереди/снимка/входа и строгой проверкой raw. Отдельный RED зафиксировал появление pending при чистом наблюдении. Сырые записи этих отказов не переписывались. Финальная проверка метки, инвентаря, режима и привязки выполнена до возврата и после последнего полного чтения WAL; все 27 тестов дали GREEN. Общий адресный набор затем прошёл целиком. Итоговое независимое read-only-ревью блокеров не обнаружило.

Аварийные тесты проверяют каждый из четырёх fsync, остановку дочернего процесса на четырёх границах, ENOSPC в середине события, короткую и нулевую запись, замену pending без удаления чужого файла, повреждение цепочки, неверный курсор и ссылку. Отдельно подтверждены повтор доставки после перезапуска, partial→complete ровно один раз, составное raw-сообщение, HookPrompt с «остановись», явная поздняя отмена, устаревший барьер и отсутствие расширения полномочий при подтверждении.

## Решения и ограничения

[Контракт](../../Инструменты/fum-snimki-indeksa/очередь.md) фиксирует Python API и явную доверенную границу. Начальный проверенный вход предоставляется вызывающим слоем; очередь сама не выполняет повторную Git-приёмку. Raw JSONL читается до склейки частей, вне публичного checkout. Живой callback отвечает на свежий nonce и доставляет типизированные решения; это не удостоверение личности или доказательство запуска hook. Неизвестное происхождение, незаконченный хвост и потеря канала запрещают барьер. Полученная runtime-отмена без законченной raw-строки должна немедленно блокировать вызывающий слой.

WAL, flock, pending и повторные проверки файлов дают долговечный сериализованный порядок. Проверка барьера — наблюдение конкретного поколения под блокировкой, без атомарного права последующего исполнения. Последующий отзыв может появиться после возврата API; исполнительный протокол здесь отсутствует. Полностью неисправное хранилище не позволяет гарантировать сохранение факта сбоя: любой неуспешный вызов прекращает рассмотрение действий. Полный откат каталога без внешнего якоря и враждебный процесс того же UID вне протокола не объявляются предотвращёнными. Нет автоматического ремонта, сброса или компактизации.

Чистый классификатор импортирован из разрешённого commit 002bb953671fa82b2144e7ec506d4975df977e3c с точным SHA-256 a3fdf3e04d9cb023489b60ecabe87428c652cfca92b6336f99a66bb55122fd23. Скопирован только модуль; чужой навык не прочитан и не импортирован. Собственные имена приведены к русским локальной токеновой автоматизацией после просмотра сухого плана; общие реестры и снимки не менялись.

Общая read-only-проверка связности завершилась отказом только по прежним причинам: одна неверная следующая ссылка запроса 11:39:26 и 282 ссылки на отсутствующий локальный `.obsidian/graph.json`. Собственная область этих ошибок не содержит. [Граница проверки](материалы/граница-связности.json) сохраняет категории и хэш полного вывода. Чужая навигация и пользовательский graph не исправлялись. Заключительные read-only-проверки связности, recency и exact diff выполняются как самонаблюдающий допуск контрольной точки по FUM-ПРАВИЛО-000188 вне обёртки; они не подменяют записанные адресные тесты.

## Ошибка отправки предыдущего коммита

После коммита 6612aac2879582f4d14bd2304a8c959f86963628 в прежнем сегменте агент вручную перепечатал назначение push и ошибочно использовал кириллическую `д` в суффиксе. Обычный push создал ранее отсутствовавший ref `refs/heads/codex/вход-снимка-индекса-01a07д3d` на этом OID. Затем тот же точный OID обычным push отправлен в правильный `refs/heads/codex/вход-снимка-индекса-01a07d3d`; Git подтвердил переход 48c0a98d→6612aac. Только ошибочно созданный ref удалён с точной lease на 6612aac2879582f4d14bd2304a8c959f86963628. Другие refs не менялись, commit оставался достижимым в правильной ветке.

Завершающий read-only-аудит через фактический `git symbolic-ref HEAD` и удалённый список подтвердил: правильная ветка содержит exact6612aac, ошибочный ref отсутствует, рабочее дерево чистое. Ошибка и коррекция были сообщены координатору. Этот интервал произошёл после прежнего commit и не включён задним числом в старый закрытый отчёт. Здесь он сохранён по новому явному поручению. Во всех новых Git-командах назначение берётся из фактического symbolic ref; вручную перепечатанные исторические refs выше являются только описанием происшествия.

## Происхождение и граница фиксации

Дословная команда восстановлена из завершённого raw JSONL текущей runtime-задачи 01a08592-8a01-7701-9386-78a0ae0553d7: только function_call_output с оболочкой codex_delegation и исходным input. Это явное делегирование корня 01a07d3d-d376-7ad2-aafc-67e4c25a67eb, а не притворное response_item человека. Сырые JSONL остались вне публичного checkout. После восстановления текущие HEAD, symbolic ref и AGENTS перечитаны, маршрут диалог включён; другой писатель этого дерева по доступным свидетельствам отсутствовал.

В первом update согласован компактный контракт: сырые позиции и происхождение сохраняются отдельно от типизированного решения; барьер связывает UUID снимка, подтверждения и поколение; новое событие делает старый барьер устаревшим. Два вызова start сначала неверно передали label/stem и получили отказ до записи; третий корректно создал новую папку. Предыдущие отчёты и истории не возобновлялись.

Собственная контрольная точка оставляет v4-отчёт открытым для интеграции. Общие правила, планы, реестры и обёртка не изменены; полный smoke и интеграция остаются у координатора. Точная фиксация, ordinary push и read-only-проверка OID выполняются после завершения документации; их время не входит в профиль.
