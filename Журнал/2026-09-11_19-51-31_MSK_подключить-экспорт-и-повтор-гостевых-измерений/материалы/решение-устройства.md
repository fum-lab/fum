# Устройство автоматизации Linux VM и границы подтверждения

Решение завершает выбор источников, профиля и устройства для работы `vm-01` [плана задачи](../../../Планирование/задачи/01a08fe2-d0c2-7ef3-b980-6bb5f8edbe97/план-этапа.json). Основание — четыре исходные команды в [запросе](../запрос.md) и [постановка](../../../Планирование/Linux-на-macOS.md). Реализация и окончательные испытания остаются отдельными работами `vm-02`–`vm-05`.

## Источник и профиль

Первая поддерживаемая конфигурация — Apple silicon, одна полноценная VM Apple Virtualization.framework, Ubuntu 24.04 arm64, 4 CPU, 8 GiB RAM и постоянный RAW-диск 32 GiB с EFI. QCOW2 используется как исходный формат. Intel, другие дистрибутивы, контейнеры, вложенная виртуализация, Linux GUI и полный профиль FUMA в эту поставку не входят. Общие каталоги хоста по умолчанию отсутствуют.

Закреплён выпуск Ubuntu `noble/release-20260826`, файл `ubuntu-24.04-server-cloudimg-arm64.img`, 619036160 байт, SHA-256 `afa139bac6f2629c1e1f2f8f34215f3a9ad9779801bcb945521ba1a45016743f`. При подготовке проверены первичный ключ `D2EB44626FDDC30B513D5BB71A5D6C4C7DB87C81`, подпись таблицы SHA256SUMS и все байты образа. [Реальное свидетельство и повтор без скачивания](../../2026-09-11_13-01-21_MSK_реализовать-настройку-Linux-VM/отчёт.md) относятся к этому источнику; их не требуется повторять при неизменных входах.

Ограниченный гостевой профиль закрепляет FUM `4dd5a7f33913b17f705e512be1826314da89a4c4`, клон на ext4, четыре Python-набора 8 + 4 + 25 + 21 тестов и два индекса. Он проверен на Ubuntu с Python 3.12.3 и Git 2.43.0. [Первичная готовность](../../2026-09-11_14-57-08_MSK_восстановить-настройку-и-проверить-Linux-VM/материалы/первичная-готовность.json) и [повтор](../../2026-09-11_14-57-08_MSK_восстановить-настройку-и-проверить-Linux-VM/материалы/повторная-готовность.json) относятся к кандидату 4; поздний манифест, импорт и наблюдатель в нём ещё не исполнялись.

## Разделение исполнения

| Часть | Ответственность | Состояние подтверждения |
| --- | --- | --- |
| Swift и Virtualization.framework | План, личное хранилище, VM, каналы управления и SSH, проверка готовности и импорт фаз | VM и доступ испытаны; новый обмен готовностью ещё подключается |
| Python-наблюдатель | Одна группа команд, срок, предел вывода, смерть родителя, очистка и неизменяемая квитанция | Настоящие subprocess-сценарии на macOS; точный ресурс принят из `0c0d1cf96e1dd46d2a0161a00974a04556c54f23` |
| Python-родитель упаковщика и гостя | Сохранение отправки, наследование замка, ожидание наблюдателя и проверка исхода | Фабрика упаковщика испытана; гостевое подключение впереди |
| Swift-родитель наблюдателя | Запуск того же ресурса через posix_spawn с явной средой исполнения | Принятое устройство; реализация и адресная приёмка впереди |

Используется один ресурс наблюдателя. Это обоснованно заменяет ограничение «Python только в госте» из [решения доступа предыдущего этапа](../../2026-09-11_14-57-08_MSK_восстановить-настройку-и-проверить-Linux-VM/материалы/решение-доступа.json): повторная реализация очистки групп на двух языках не нужна. Историческое решение сохраняется. Swift-процесс VZ/Foundation запускает наблюдателя через posix_spawn; отсутствие fork во всей цепочке не обещается: отдельный свежий Python запускает команду через Popen.

Упаковщик заранее требует CPython ≥3.13 с waitid/WNOWAIT и сохраняет выбранный runtime. Фабрика передаёт закреплённый путь отдельным параметром адаптеру и сверяет снимок до и после команды и перед установкой; исходный путь sys.executable не выбирается заново. Эта корневая дельта поверх принятого ресурса прошла RED/GREEN 20 проверок и прежние девять сценариев адаптера. На macOS waitid появился в Python 3.13; WNOWAIT позволяет сохранить лидера доступным для ожидания до последнего сигнала группе. [Контракт Python](https://docs.python.org/3/library/os.html#os.waitid). Для гостя остаётся штатный Python 3.12 закреплённого Ubuntu с проверкой тех же возможностей. Python не добавляется в список устанавливаемых VM-зависимостей `[qemu, gnupg]`: это отдельное условие сборки и поставки.

Наблюдателю передаются семь различных FD: описание, читающий конец жизни, удерживаемый замок, каталог, stdin, stdout и stderr. Пишущий конец жизни принадлежит только родителю. Команда не наследует замок; наблюдатель удерживает его до очистки и сохранения квитанции. CLI 0 наблюдателя подтверждает квитанцию, а успех команды проверяется отдельно. Точная среда, вход, исходник и выходы остаются в личном runtime вне Git. [Передача FD в Python](https://docs.python.org/3/library/subprocess.html#subprocess.Popen).

Swift передаёт собственный контекст каталога и действующего замка. SSH-восстановление из клиента без замка службы получает отдельную личную область попытки; гостевая запись дополнительно сериализуется своим замком. Фоновая служба VZ и интерактивный SSH сохраняют отдельный жизненный цикл. Наблюдатель не должен завершать VM при уходе вызывающего CLI.

## Доступ, повтор и пределы

Закреплённый SSH проходит через loopback → VSOCK 2222 → встроенный systemd-socket-proxyd → sshd. Новый NoCloud использует штатный прокси без установки socat. Из-за измеренного отказа прямого HTTPS через NAT команда готовности временно предоставляет обратный SOCKS только к `ports.ubuntu.com:443` и `github.com:443`; причина отказа NAT не приписывается VPN без доказательства. Восстановление собственных старых units выполняется автоматизацией через закреплённый NAT SSH, с резервными копиями и отказом при неизвестных изменениях.

Перед SSH сохраняется неизменяемый запрос с точными исходниками. После любого исхода забираются сырые начальные и конечные фазы, повтор объединяет их по UUID и точным байтам. Неполная пара остаётся неполной; сохранённая первичная ошибка не заменяется отказом экспорта. Состояние готовности должно опираться на полный профиль и соответствие фактическому ответу. Эта часть ещё ожидает подключённой реализации и испытаний.

Поддерживаемая граница прерывания — смерть родителя команды, срок, ограниченный вывод и потеря связи с сохранением собственных данных. Смерть самого наблюдателя, выход потомка из PGID, отказ носителя и непрерываемый ввод-вывод не дают обещания автоматического восстановления. Неочищенная группа может удерживать замок без успешного результата.

Одну окончательную поставку из чистого клона следует использовать для оставшихся реальных испытаний: свежий NoCloud, готовность, штатная остановка, повтор, ограниченное прерывание и восстановление. Профили холодного и повторного запуска имеют разные входы и не доказывают ускорение. Полная FUMA, исправление сети macOS и интеграция в master остаются вне этой задачи.
