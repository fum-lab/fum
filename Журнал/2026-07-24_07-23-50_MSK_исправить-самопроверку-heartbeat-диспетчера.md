# Отчёт 2026-07-24 07:23:50 MSK - Исправить самопроверку heartbeat диспетчера

Автозапуск следующего шага восстановлен без ослабления проверки занятости. Heartbeat больше не требует невозможного совпадения собственного runtime-статуса с `active`, но по-прежнему закрывает запуск при любой другой наблюдаемой активной задаче, неизвестном состоянии или недоступном host.

## Причина и исправление

Два последних тика завершались до Git-проверки, `show`, claim и создания задачи, потому что прикреплённая диспетчерская задача наблюдалась штатным списком как `idle`, а prompt требовал для собственного точного идентификатора только `active`. Локальный рабочий набор при этом оставался валидным и содержал готовый `FUM-STEP-0007`.

Первый и повторный recent-снимки теперь требуют ровно одну собственную запись в любом известном состоянии `active`, `idle` или `notLoaded`. После этого исключается только точное собственное совпадение; каждая другая запись проверяется на `active`. Эта формулировка закреплена в правилах репозитория, производной документации, контракте навыка и воспроизводимом heartbeat-шаблоне.

## Живая автоматизация

Существующая heartbeat-автоматизация обновлена штатным инструментом без создания дубля и без ручного редактирования локальной конфигурации. Целевая диспетчерская задача, пятиминутное расписание и статус `ACTIVE` сохранены; runtime prompt синхронизирован с репозиторным шаблоном. Во время обновления текущая рабочая задача сама считалась другой `active`-задачей и не позволяла диспетчеру создать параллельный шаг.

## Проверки

- Красный тест сначала подтвердил ошибочное требование `status=active`, затем отдельная красная фаза обнаружила остаточную неоднозначность второго снимка.
- После исправления целевой регрессионный тест и полный автономный набор из `59` тестов `fum-sleduyusjhij-shag-vetki` проходят.
- Штатный просмотр живой автоматизации подтверждает сохранённые идентичность, расписание и статус при новом prompt.
- Recency-метки, граф Obsidian, сессионная связность, `git diff --check` и повторный полный smoke-check проходят все `54` стадии. Первый идентичный процесс завершился, но вызывающая оболочка не сохранила его итоговый код и хвост вывода; поэтому для доказанного результата выполнен второй полный прогон.
