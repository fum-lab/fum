# План наблюдения macOS через Swift

FUM должен получать проверяемые наблюдения о среде macOS через системные API и передавать их агенту в единой форме. Текущая задача составляет план. Под FUMA предварительно понимается текущий проект FUM: отдельного сохранённого проекта с именем FUMA при осмотре не найдено.

## Команда пользователя

````text
Nauchisj videtj cherez vse API, kotoryiye predostavlyayet macOS. Ispoljzuj Swift v proyekte FUMA.
````

## Содержательный ответ

Планируется общий слой наблюдения macOS на Swift: доступные приложения и окна, семантическое дерево интерфейса, изображение экрана и распознанный текст, файловые изменения, устройства ввода, сеть и состояние системы. Основой станет уже существующее разделение переносимого ядра и платформенных адаптеров в клавиатурном прототипе. Затем слой подключается к инструментальному интерфейсу агента, чтобы полученные наблюдения были доступны в реальной рабочей сессии.

Запрос «все API» превращается в проверяемый реестр охвата SDK: для каждой области отмечаются реализованные источники, доступные данные, разрешения, минимальная версия macOS, ограничения и непокрытая часть. Единого разрешения на все данные и универсального API содержимого всех приложений план не предполагает. Swift используется для реализации системных адаптеров и ядра; запуск прототипа не подменяет подключение этой способности к агенту.

Другая пишущая задача работает в основном checkout. По последующему явному указанию текущая задача получила отдельный worktree и ветку: там сохраняются команды, ответы и планы и закрепляются правила поведения. Реализация нового Swift-наблюдателя остаётся следующим этапом планирования.

## Существующая основа

В `Прототипы/физические-состояния-клавиш/` уже есть библиотеки `FUMInputCore` и `FUMInputMac`, жизненный цикл источника start/stop, отдельные каналы событий и диагностики, нормализация временных меток и адаптеры IOHIDManager, GCKeyboard, CGEventTap и NSEvent. Это клавиатурный срез; он ещё не является общим наблюдателем macOS.

Ключевые точки кода: `Sources/FUMInputMac/MacKeyboardObservationSource.swift:27`, `Sources/FUMInputMac/MacInputEnvironment.swift:21`, `Sources/FUMInputCore/FUMInputCore.swift:68`. В инвентаре HID следует различить пустой список и ошибку открытия: сейчас оба случая могут возвращать пустой массив.

Прототип `агентное-чтение-сетевой-среды` моделирует движение агентов по арифметическому графу. Он не читает реальную сеть или состояние macOS и не подходит в качестве готового системного адаптера.

## Первая очередь источников

| Область             | API                               | Планируемый результат                                  |
| ------------------- | --------------------------------- | ------------------------------------------------------ |
| Приложения          | NSWorkspace, NSRunningApplication  | Снимок приложений, активное приложение, изменения.       |
| Семантика интерфейса | AXUIElement, AXObserver            | Доступные роли, атрибуты, элементы и события интерфейса. |
| Экран и окна        | ScreenCaptureKit, SCShareableContent | Выбранные окна и дисплеи, кадры с привязкой к источнику. |
| Текст изображения   | Vision                            | OCR с координатами и оценкой уверенности.               |
| Файловые изменения  | FSEvents                          | Изменения выбранных деревьев и основания пересканирования. |
| Сеть                | NWPathMonitor                     | Изменения доступного сетевого пути.                     |
| Питание             | IOPowerSources                    | Состояние источников питания и уведомления об изменении. |
| Физический ввод     | Существующие четыре адаптера       | Подключение клавиатурного среза без потери происхождения. |

NSWorkspace даёт сведения о приложениях, но отдельные уведомления запуска не покрывают фоновые приложения; для такого охвата Apple указывает наблюдение за runningApplications. Это должно быть отражено в тестах полноты. [Документация Apple](https://developer.apple.com/documentation/appkit/nsworkspace/didlaunchapplicationnotification).

AXUIElement позволяет запрашивать список доступных атрибутов и их значения, а также проверять доверие к процессу. Неподдержанный атрибут сохраняется как отдельный исход, а не пустое значение. [AXUIElement.h](https://developer.apple.com/documentation/applicationservices/axuielement_h), [получение нескольких атрибутов](https://developer.apple.com/documentation/applicationservices/1462051-axuielementcopymultipleattribute).

ScreenCaptureKit предоставляет выбор и захват экранного содержимого; SCShareableContent перечисляет доступные дисплеи, приложения и окна. Доступ к изображению и доступ к дереву Accessibility учитываются независимо. [ScreenCaptureKit](https://developer.apple.com/documentation/screencapturekit), [SCShareableContent](https://developer.apple.com/documentation/screencapturekit/scshareablecontent).

Vision распознаёт текст изображения; OCR сохраняется как результат распознавания с источником кадра, а не выдаётся за точное значение элемента Accessibility. [VNRecognizeTextRequest](https://developer.apple.com/documentation/vision/vnrecognizetextrequest).

FSEvents сообщает об изменениях наблюдаемого дерева. Перечень файлов уточняется по снимку; подписка начинается до первоначального обхода, а изменения во время него приводят к повторному чтению затронутых мест. Использован архивный официальный обзор; конкретные флаги и доступность нужно сверить с выбранным SDK при реализации. [Руководство Apple](https://developer.apple.com/library/archive/documentation/Darwin/Conceptual/FSEvents_ProgGuide/UsingtheFSEventsFramework/UsingtheFSEventsFramework.html).

NWPathMonitor наблюдает сетевой путь и его изменения; это не содержимое трафика всех процессов. IOPowerSources даёт состояние батарей и ИБП и уведомления об изменениях. [NWPathMonitor](https://developer.apple.com/documentation/network/nwpathmonitor), [IOPowerSources.h](https://developer.apple.com/documentation/iokit/iopowersources_h).

## Последовательность реализации

1. **Инвентарь охвата.** Зафиксировать установленную macOS, выбранный SDK, архитектуру и Swift toolchain. Составить конечный реестр публичных семейств API наблюдения и их доступности. Дополнительно обследовать процессные и ресурсные данные Darwin/Foundation, дисплеи, тома, аудио и видео, устройства IOKit, Bluetooth и прикладные интерфейсы. Для каждой области явно отметить, какие данные действительно наблюдаются. Правила доступа и требования entitlement проверять по официальной документации и фактическому SDK; недоступный источник остаётся видимым в реестре.
2. **Переносимое ядро на Swift.** Создать отдельный прототип `Прототипы/наблюдение-macOS/` с ядром, macOS-адаптерами и CLI. Новые собственные смысловые имена писать кириллицей. Общее наблюдение хранит источник и версию, идентичность объекта, время получения и предоставленное API время события, полезные данные, область охвата, свежесть и диагностику. Не расширять тип физического нажатия до универсального события.
3. **Первый сквозной сценарий.** Перечислить источники и текущий доступ; получить активное приложение, доступное дерево его интерфейса и выбранный кадр окна; связать результаты по приложению, окну, геометрии и времени. Не считать несколько последовательных API-вызовов атомарным снимком: фиксировать расхождения и повторять только необходимые чтения.
4. **Жизненный цикл и разрешения.** Для каждого адаптера реализовать снимок, подписку, остановку, тайм-аут и диагностические исходы «доступно», «нет разрешения», «не поддерживается», «источник исчез», «ошибка». Состояние доступа проверять без автоматического показа диалогов; запрос разрешения — отдельное явное действие интерфейса. Для стабильной повторной работы подготовить .app-оболочку с устойчивой идентичностью. Пользовательские события и изображения по умолчанию не становятся отслеживаемыми файлами репозитория.
5. **События и стоимость.** Использовать уведомления вместо постоянного полного опроса там, где API их предоставляет. Ограничить очереди, частоту кадров и объём дерева Accessibility. Учитывать потерю событий, переполнение, зависшее приложение, отключение устройства, сон и пробуждение. Для файловых изменений вести проверяемый снимок, а не считать поток уведомлений полным журналом содержимого.
6. **Инструментальный доступ агента.** Добавить стабильный Swift CLI с операциями «возможности», «доступ», «снимок», «подписка», «остановка» и версионированным машинным выводом. Затем подключить локальный инструментальный мост к рабочей среде агента и зарегистрировать его в реестре инструментов. Приёмка включает реальный вызов из агентской сессии; исполняемый пример сам по себе не означает, что агент уже получил новую способность.
7. **Расширение охвата.** После первого сквозного сценария последовательно подключать остальные семейства из реестра. Каждый новый источник получает собственный контракт доступности и регрессионные сценарии. Состояние «весь macOS поддержан» не использовать; полноту оценивать относительно конкретной версии реестра и SDK.

## Критерии приёмки

- Без разрешения источник сообщает точную причину; отказ или пустой список не выдаются за отсутствие наблюдаемых объектов.
- Изменения разрешений, исчезновение приложения и события сна не зависают и не подменяются устаревшими данными.
- Семантический текст и OCR сохраняют разное происхождение; расхождение остаётся наблюдаемым.
- Ограничены время запроса, память и очередь событий; остановка прекращает подписки.
- Автономные тесты воспроизводят записанные и синтетические ответы без живого захвата. Отдельная разрешённая приёмка проверяет настоящий macOS-источник и доступ через инструмент агента.
- Для каждого семейства API можно показать реализованный сценарий, требуемое разрешение, поддержанные версии и непокрытую часть.
- Код и системные адаптеры написаны на Swift; исходники, паспорт, точка запуска и ограничения сохранены в FUM после допуска к пишущей сессии.

## Долговременный журнал наблюдений

### Дополнение пользователя

````text
Vsyo eto nablyudeniye myi dolzhnyi byitj sposobnyi sokhranyatj v zhurnal v postoyannom zapominayusjhem ustrojstve.
````

### Принятый результат

Каждый подключённый вид наблюдения должен иметь сохраняемое представление на постоянном носителе: события, снимки, кадры, исходные ответы API в допустимой области, результаты OCR, сведения об источнике, разрешениях, ошибках и разрывах. Человекочитаемая запись задачи в репозитории связывается с этим журналом происхождением. Массивы пользовательских экранных и аппаратных данных хранятся в выбранном рабочем хранилище, чья ёмкость и доступность наблюдаемы.

### Формат и подтверждение записи

По сообщениям 32–33 выбран единый контейнер с JSON-заголовками и сырыми бинарными блоками. Это отдельный формат, отличный от исходного JSONL диалога Codex. [Подробный план контейнера](план-контейнера-наблюдений.md) задаёт границы, целостность, встроенные спецификации и сценарии восстановления.

- Версионированный сегмент содержит записи с длинами заголовка и нагрузки; переводы строк внутри бинарных данных не служат границей.
- Заголовок связывает данные с источником, порядком, временем, типом, версией и встроенной спецификацией. Неизвестный тип не препятствует сохранению исходных байтов.
- Крупные кадры и другие объекты включаются в тот же контейнер ограниченными фрагментами; фиксация группы связывает их порядок, общий размер и хэш. Внешнее хранилище больших объектов, предложенное первоначально, заменено этим выбранным вариантом.
- Единственный писатель полностью записывает и синхронизирует группу до подтверждения сохранения. Пакетная фиксация различает буфер и подтверждённые данные; потерянный ответ требует перечитать фиксацию по устойчивому идентификатору.
- Восстановление проверяет подтверждённый префикс и целостность. Незавершённый хвост и повреждение принятого префикса не обходятся поиском следующей сигнатуры.
- Индекс времени, источника, приложения и типа восстанавливается из контейнера. Если выбран SQLite, его роль и гарантии синхронизации задаются отдельно. [Документация SQLite](https://www.sqlite.org/wal.html).

### Переиспользование Swift-кода FUM

`ContentAddressedGenerationStore` в `Прототипы/воспроизводимое-пополнение-памяти/Sources/FUMReproducibleMemoryPopulation/ContentAddressedGenerationStore.swift` уже обеспечивает адресное поколение, staging, полную запись, fsync, публикацию без замещения и CURRENT с блокировкой. Метод фиксации начинается на строке 232; возврат после публикации и синхронизации — на строке 394. Этот схемонезависимый механизм следует проверить как основу публикации манифестов сегментов.

Нельзя переносить существующую доменную модель памяти без изменений: она рассчитана на remember/compose и ограниченное число событий, а непрерывному наблюдению нужны сегменты нового контейнера со встроенными бинарными группами. Проверенная гарантия существующего прототипа относится к аварии процесса; устойчивость к потере питания его паспорт не заявляет. В новом журнале отдельно задаются и проверяются границы аварии процесса, перезапуска ОС и потери питания для выбранного носителя.

Клавиатурный `GuidedCaptureRecorder` пригоден как пример формата JSONL, но не готов как постоянный надёжный журнал: синхронизация выполняется при закрытии карточки или сеанса. Редуктор меняется до append, а GUI при ошибке записи только показывает сообщение. До интеграции необходимы подтверждение фиксации и остановка либо диагностический разрыв при отказе.

### Ёмкость и проверка восстановления

- При нехватке места или I/O-ошибке запись не подтверждается; поток останавливается или явно фиксируется недоступный интервал. Если носитель уже не принимает даже сообщение об ошибке, ошибка возвращается вызывающему коду, а неопределённый разрыв отмечается при восстановлении. Нельзя обещать запись маркера на заполненный диск.
- Проверка свободного места полезна, но не заменяет обработку ошибок фактического write/fsync. Буфер ограничен; молчаливое удаление ранее подтверждённых наблюдений не применяется.
- Ротация разделяет сегменты; удаление, сжатие с потерями и сокращение срока хранения требуют явно выбранной политики. Резервная копия должна включать согласованный набор сегментов журнала со всеми фрагментами и спецификациями.
- Адресные сценарии охватывают частичный write, ENOSPC, ошибку fsync, прерывание до и после публикации указателя, повреждение сегмента, отсутствующий фрагмент, повтор подачи и повторное открытие. Последний подтверждённый префикс обязан восстанавливаться без изменения смысла.
- Приёмка включает запись на выбранный постоянный носитель, закрытие и повторное открытие другим процессом, чтение исходных данных и воспроизведение наблюдений. До такой проверки способность долговременного хранения не объявляется реализованной.

### Рабочий контракт

Исходный локальный JSONL текущей задачи Codex становится проверяемым источником для восстановления переписки. Точный сеанс определяется из CODEX_THREAD_ID и метаданных файла, а не по похожему заголовку. В этой задаче файл уже найден и прочитан; при первоначальном чтении восстановлены девять пользовательских сообщений. Последующие команды добавлялись по мере поступления; после переноса сообщений 32–35 текущий Журнал содержит 35 команд в исходной последовательности.

Чтение фиксирует полный завершённый префикс файла. Незавершённая последняя строка остаётся для следующего чтения. Для пользовательского диалога извлекаются только пользовательские сообщения и видимые ответы корневого ассистента; служебные инструкции среды, внутренние рассуждения, ответы инструментов и сообщения субагентов не переписываются в публикуемый журнал. У ответа через вопросник сохраняются точные текст вопроса и выбранный ответ без технических идентификаторов интерфейса.

После сжатия контекста и перед продолжением решения перечитываются первичные команды, их уточнения, принятые ограничения и незавершённые действия. Курсор содержит позицию, число завершённых строк и хэш прочитанного префикса; он записывается только после сохранения соответствующей выгрузки диалога. При усечении или изменении старого префикса требуется повторная сверка; одинаковые тексты отдельных сообщений не дедуплицируются по тексту.

Сводка может ускорять поиск, но её утверждения проверяются по исходным записям. Это восстанавливаемость контекста, а не отключение механизма сжатия Codex и не обещание бесконечного контекстного окна. Недоступный или повреждённый JSONL должен давать явную границу чтения. Постоянное закрепление этого порядка входит в уже согласованный пункт изменения канонических правил.

## Граница текущего результата

Для направления наблюдения выполнены статический анализ имеющегося Swift-кода и чтение официальной документации Apple. Новый прототип наблюдения не создан и не собирался; захват экрана и пользовательского ввода не запускался. Сборка Swift-преобразователя в проверке проекции относится к другому направлению. Работа по ускорению проекции и постоянному закреплению правил сохраняется.
