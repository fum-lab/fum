# План ускорения повторной пересборки проекции

Задача — сократить длительность повторных пересборок братиславской проекции, сохранив точные байты результата, независимую проверку и восстановление после прерывания. Оптимизация остаётся планом. По последующему указанию пользователя в собственной ветке реализованы профилировочные метки для измерения текущего алгоритма.

## Наблюдения и границы доказательства

Ссылки на номера строк ниже относятся к исходной версии a3bde39c84528848b13b0b2b415a7e6fd033b9a1 до добавления меток.

- В сохранённом отчёте соседней сессии `Журнал/2026-09-07_18-16-36_MSK_принять-модель-бетонных-глубинных-систем/отчёт.md` успешный документационный smoke-check занял 3141,242 с, то есть 52 мин 21,242 с. Предыдущая неуспешная попытка заняла 3118,355 с. Это время всего составного процесса; объявлять его временем одной транслитерации нельзя.
- Генератор при каждой отдельной CLI-команде создаёт новый временный корень, разворачивает закреплённые Git-архивы и задаёт новый SwiftPM scratch-path: `Инструменты/fum-bratislavskaya-proyekciya-pamyati/scripts/братиславская_проекция_памяти.py:5705`. В команде на строке 5766 отсутствует явный выбор Release; наблюдение другой активной задачи показывает исполняемый преобразователь из Products/Debug, работающий несколько минут почти с полной загрузкой одного ядра. Это основание измерить влияние конфигурации сборки, а не доказанный коэффициент ускорения.
- Даже ветка «без изменений» сначала формирует все выходы, строит контрольный план и вызывает внутреннюю независимую проверку: тот же файл, строки 4910–4942. Раннего дешёвого возврата до полного преобразования нет.
- Независимая проверка заново строит план и формирует полный ожидаемый набор выходов: строки 5250–5280. Сама независимость нужна; её стоимость необходимо измерять отдельно.
- При изменении канонических данных записывается полное новое поколение с синхронизацией каждого файла и каталогов: строки 4743–4819. Возможный вклад дисковых операций ещё не измерен.
- Стандартный smoke-check вызывает применение, затем отдельную проверку. После закрытия отчёта действующее правило FUM-ПРАВИЛО-000188 требует ещё одну такую пару. Это установленный порядок, а не случайный повтор, который можно молча удалить.
- Инвентарь включает новые неигнорируемые файлы. Добавление даже собственной карточки в `Журнал/` меняет снимок, который уже работающая пересборка обязана повторно сверить. Отсутствие конфликта слияния не гарантирует неизменности этого снимка.

## Уточнение по наблюдённому профилю и новым командам

Прогон 19 дал исходную стоимость: применение 1918,608 с, два преобразования содержимого 1788,628 с суммарно, отдельное третье преобразование 1116,120 с. Сначала нужны внутренние Swift-метки по документам и обработке регистра. В закреплённом LinguisticKit участок StringProtocol.swift:119–129 повторяет фильтрацию массива для каждого неоднозначного регистра и может иметь квадратичную стоимость; это статическая гипотеза, а не измеренный вклад функции. Оптимизация сохраняет фактическую семантику контекста и точные выходные байты.

Для каждого изменения исполняемого кода обязателен цикл из правила 000176. Работа сохраняется промежуточными коммитами в этой постоянной задаче. До следующей финальной приёмки нужна версионированная поддержка нескольких приёмочных раундов: прежний агрегатор запрещает два успешных полных запуска разных снимков; его изменение не должно ломать старые закрытые отчёты.

## Последовательность реализации

1. **Снять профиль на неизменяемом входе.** Разделить время подготовки и компиляции преобразователя, инвентаризации и хэширования, преобразования путей, разбора Markdown, транслитерации содержимого, записи поколения и независимой проверки. Сравнить холодный запуск, повтор без изменений, изменение одного документа и изменение только закрывающегося отчёта. Учитывать число файлов и байтов, вызовы преобразователя и переписанные выходы. Запуски выполнять в собственной допущенной пишущей сессии через штатную отчётную обёртку. В текущей ветке метки уже добавлены: они различают повторные и вложенные интервалы и сохраняют монотонное время. CLI-флаг `--профилировать` либо `FUM_PROJECTION_PROFILE=1` включает диагностику в stderr. Первый замер Swift остаётся общей стоимостью сборки, запуска и преобразования; дальнейшее разделение этих затрат требует дополнительных измерений.
2. **Проверить и внедрить малое ускорение исполнения.** Сравнить Debug и Release на одних входах, подтвердить побайтовое совпадение. Если выигрыш подтверждён, собирать изолированный Release-преобразователь один раз и вызывать готовый бинарный файл для следующих пакетов строк внутри процесса. Затем оценить повторное использование проверенной сборки между командами. Ключ должен учитывать дерево обёртки, закреплённую ревизию LinguisticKit, конфигурацию и флаги сборки, Swift toolchain, SDK и архитектуру. Произвольный HEAD без изменения этих входов не должен обнулять кэш.
3. **Убрать лишние вычисления при повторе.** Для неизменившегося поколения сравнивать актуальную идентичность входов и фактическое целевое дерево до дорогого формирования выходов. Полную независимую проверку оставить отдельным этапом. Для небольших изменений переиспользовать результаты только по доказанному ключу: байты источника, исходный и целевой пути, политика и версия генератора, версия преобразователя, зависимости ссылок и якорей. Изменение глобального контекста обязано инвалидировать зависимые записи. Первым этапом можно кэшировать только чистую транслитерацию точных входных строк; это меньше затрагивает семантику ссылок.
4. **Сохранить независимость проверки и атомарность установки.** Проверяющий процесс должен выводить ожидаемые байты из канонических входов, не доверяя паре редактируемых «манифест + целевой файл». На первом этапе не использовать кэш структурных выходов в независимом валидаторе. Новое поколение по-прежнему устанавливать атомарно; оптимизацию копирования и fsync рассматривать только по результатам профиля и с прежними аварийными гарантиями.
5. **Закрепить измеримый результат.** Сравнить полный и ускоренный пути на одном снимке: одинаковые пути, режимы, байты, манифест и восстановление после отказа. Повтор без изменений не должен заново транслитерировать все документы на стадии применения; изменение одного документа не должно требовать полной повторной транслитерации в генераторе, если глобальные зависимости не изменились. Независимую проверку учитывать отдельно. Численный бюджет времени выбрать по первому профилю и сохранить в регрессионном сценарии; ускорение в конкретное число раз сейчас не обещается.

6. **Закрепить поведение для будущих задач.** По последующим управляющим командам эта часть выполнена в собственной ветке текущей задачи: обновлены канонические правила и инвентарь, добавлены регрессии регистрации и изоляции. Основной checkout другой задачи остаётся доступен только для чтения. Фактические проверки и статус интеграции приведены в [отчёте](../../отчёт.md). Автоматизация карточки с записью только в собственную папку до выделения worktree остаётся возможным отдельным улучшением.

## Независимое уточнение плана

Read-only-анализ существующих тестов подтвердил приоритет: профиль, Debug/Release, кэш исполняемого преобразователя, затем инкрементальное преобразование. Один проход smoke-check сейчас формирует полный результат как минимум трижды: при применении, во внутреннем и во внешнем валидаторах.

Ранний возврат нельзя разрешать только по хэшам старого редактируемого манифеста. До успешного завершения `применить` должно сохраняться достаточное независимое доказательство корректности текущего дерева: повторное вычисление или отдельно обоснованный доверенный локальный кэш. Наружная проверка не делает безопасным уже возвращённый необоснованный успех самого применения.

Существующий тест идемпотентности на строке 2089 проверяет результат; дополнительно нужны счётчики реальных преобразований. Тест согласованной подмены выхода и манифеста на строке 1923 должен сохранять отказ на ускоренном пути. Тест удаления и переименования на строке 2172 необходимо дополнить изменением зависимых ссылок и якорей. Все три находятся в `Инструменты/fum-bratislavskaya-proyekciya-pamyati/tests/test_братиславская_проекция_памяти.py`.

## Регрессионные сценарии

- Повтор без изменений; изменение одного Markdown-файла; изменение только отчёта; чистое изменение Git HEAD при неизменных содержательных входах.
- Добавление, удаление и переименование источника; изменение режима; изменение целевого пути, заголовка или якоря документа, на который ссылаются другие документы.
- Смена политики, генератора, закреплённой зависимости, toolchain или конфигурации сборки; отсутствие, усечение и подмена записи кэша.
- Согласованная подмена манифеста и целевого файла; лишний выход; символическая ссылка; коллизия регистра или Unicode.
- Изменение источника во время чтения; прерывание до и после установки поколения; восстановление после частичной записи.
- Полное побайтовое совпадение ускоренного результата с независимым результатом без кэша.

## Граница текущей задачи

Команды пользователя и содержательные ответы сохраняются в собственных материалах этой задачи. Оптимизация генератора остаётся планом. Постоянные правила поведения и необходимые проверки по позднейшему явному указанию изменяются в собственной ветке; основная ветка другой активной задачи не изменяется. Изменение числа обязательных полных проходов потребует отдельного явного изменения правил с их валидатором; первый этап ускорения этого не требует.

## Продолжение после контрольного коммита

Коммит a521c41d не завершил согласованный объём. После выявления преждевременного завершающего ответа работа продолжается в той же задаче.

Следующая проверяемая часть — отдельный отпечаток фактического канонического содержимого. Он должен сохраняться после обычного или пустого коммита и изменения способа staging, игнорировать только разрешённые текущий отчёт, машинные записи и точную область Proyekcii, но меняться при содержательном изменении файлов, путей, режима или закреплённой зависимости. Прежний Git-отпечаток остаётся проверкой неизменности финального снимка.

Затем вводятся новая запись запуска v4 и снимок отчёта v3 с явной проверяемой границей миграции. Исторические v3-запуски не получают вымышленный содержательный отпечаток. Сохранённый старый префикс и его хэши защищаются от изменения; старые закрытые отчёты воспроизводятся прежней семантикой. Повтор полного запуска на уже проверенном содержимом отклоняется до запуска дочернего процесса, включая возврат A → B → A.

Новый промежуточный коммит сам по себе не является условием остановки: непосредственно после сохранения записи сбоя выполняется адресный RED/GREEN-сценарий отпечатка содержимого. Этот порядок даёт наблюдаемое свидетельство продолжения, но не считается универсальной машинной гарантией поведения агента.

## Проверяемые части перехода приёмочных раундов

1. Примитив содержательного отпечатка подготовлен и проверен отдельно; прежний Git-отпечаток не изменён. После профиля сокращён обход родителей, совпадение результатов подтверждено на одном входе.
2. Добавить строгий читатель запуска v4, проверяемую границу исходного префикса и отдельный план раундов на фикстурах. На этом этапе CLI ещё создаёт v3.
3. Добавить снимок отчёта v3 и его воспроизведение из сохранённого контекста; старые закрытые форматы сохраняют байты и вердикт. Проверить подготовленное закрытие и смежный читатель smoke-check.
4. Явно включить новую запись под действующим замком. Проверять оба отпечатка и запрет повторного полного запуска до создания дочернего процесса. Одновременно обновить применимые правила, инвентарь и регрессии.
5. После законченного перехода выполнить текущую финальную приёмку и штатную актуализацию проекции. Каждый промежуточный коммит сохраняет законченную часть, после него продолжается следующий разрешённый шаг.
