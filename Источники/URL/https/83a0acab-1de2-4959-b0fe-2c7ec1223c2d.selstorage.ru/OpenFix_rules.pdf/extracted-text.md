2.  Категории  задач
2.1  Переписывание  на  Rust
Разработка  безопасных  аналогов  на  языке  Rust  с  открытым  исходным  кодом.  Задачи  делятся
на

два

направления:

Задача  1:  переписывание  обвязки  XZ  на  Rust
xz —  это  широко  используемый  компрессор/декомпрессор  на  базе  lzma,  часто  применяемый  для  упаковки  архивов  (например,  .tar.xz).  Он  опирается  на  LZMA  SDK  от  7zip,  но  известен  рядами  критически  опасных  CVE.
Цель
Разработать  альтернативную  реализацию  утилиты  xz и  библиотеки  liblzma на  языке  Rust,  с
сохранением

совместимости,

повышенной

безопасностью

и

отказоустойчивостью.

Объём  работ
●  Реализация  CLI- оболочки  xz на  Rust;
 ●  Написание  нового  безопасного  парсера  .xz контейнера;
 ●  Обработка  аргументов,  флагов  и  потока  данных  (stdin/stdout);
 ●  Интеграция  с  оригинальной  библиотекой  lzma через  FFI  (если  не  реализуется  своя);
 ●  Экспортируемый  API  (аналог  liblzma)  через  FFI;
 ●  Возможность  линковки  как  системной  утилиты  и  библиотеки;
 ●  Разработка  модульных  и  интеграционных  тестов;
 ●  Документация.

Требования  к  реализации
●  Код  должен  быть  написан  на  Rust,  с  приоритетом  на  безопасные  идиомы;
 ●  Разрешено  использовать  FFI  для  связывания  с  lzma  SDK;



Страница 6
 ●  Код  должен  быть  оформлен  в  виде  2  артефактов:
 ○  CLI  (xz)
 ○  Библиотека  (аналог  liblzma);
 ●  Уязвимые  конструкции  оригинала  должны  быть  устранены;
 ●  Результат  должен  собираться  под  Linux  (Debian  или  SelectOS)  и  проходить
unit/integration

QA.


Критерии  приемки
●  Функциональное  соответствие  оригиналу;
 ●  Отсутствие  известных  CVE  в  коде-обвязке;
 ●  Покрытие  модульными  и  QA- тестами;
 ●  Проверка  код-ревью  и  аудитом;
 ●  Код  размещён  публично  под  лицензией  BSD  или  MIT.

Задача  2:  Переписывание  библиотеки  c-ares на  Rust
Описание
c-ares —  это  асинхронная  DNS- библиотека,  используемая  во  множестве  сетевых  приложений.
Цель
Разработать  полноправную  замену  c-ares на  Rust,  с  совместимым  C  API,  модульностью,
безопасным

управлением

ресурсами

и

возможностью

применения

в

других

проектах.

Объём  работ
●  Полноценный  DNS- резолвер,  поддерживающий:
 ○  A,  AAAA,  MX,  CNAME,  PTR,  SRV,  TXT  и  т.д.;
 ○  тайм-ауты,  ретраи,  отказоустойчивость;
 ●  Совместимость  с  асинхронными  и  многопоточными  приложениями;
 ●  Поддержка  C  API  (ares_*() функции);
 ●  Желательно  —  no_std и  минимальная  зависимость  от  внешних  crate;
 ●  Возможность  сборки  как  .so /  .a для  использования  в  C- проектах;



Страница 7
 ●  Покрытие  unit- тестами  и  API  QA.

Требования  к  реализации
●  Язык  реализации:  Rust  (желательно  #![no_std]);
 ●  API- совместимость  с  c-ares,  включая  заголовочные  файлы;
 ●  Без  использования  небезопасных  операций  (unsafe)  без  крайней  необходимости;
 ●  Сборка  под  Linux  x86_64 и  arm64;
 ●  Протестировано  под  Debian  или  SelectOS.

Критерии  приемки
●  Полная  функциональная  совместимость  с  c-ares;
 ●  Отсутствие  memory  leaks,  race  conditions;
 ●  Наличие  QA- интеграционных  тестов  на  каждую  функцию  API;
 ●  Публичное  размещение  исходников  под  лицензией  MIT  или  BSD.

2.3  Багхантинг

   https://bugs.launchpad.net/ или  https://www.debian.org/Bugs/)   и  подготовить  качественное  исправление,  которое  будет  принято  (замержено)  соответствующим  проектом.
Критерии  приемки
Для  признания  работы  по  багу  выполненной,  все  нижеперечисленные  условия  должны  быть
соблюдены:

1.  Баг  должен  быть  закрыт
 ○  Запись  в  баг-трекере  должна  быть  помечена  как  "closed",  "resolved",  "fixed"  и  т.п.;
 ○  Либо  в  комментарии/ merge  request  должно  быть  указано,  что  исправление
принято.

 2.  Исправление  должно  быть  доступно  для  просмотра  в  виде  diff /  pull  request /  patch
 ○  Патч/коммит  должен  быть  опубликован  и  содержать  конкретные  изменения;
 ○  Изменения  должны  быть  явно  связаны  с  описанным  багом.
 3.  Авторство  должно  быть  подтверждено
 ○  Участник  должен  быть  указан  как  автор  коммита  или  патча;
 ○  Организатор  вправе  проверить  авторство  Участника

Дополнительные  условия
●  Баг  может  относиться  к  любому  open  source- проекту,  желательно  популярному  и
активно

сопровождаемому;

 ●  Работа  должна  быть  оригинальной,  не  «rebase»  чужого  патча;
 ●  Приоритизация  багов,  связанных  с  безопасностью  (CVE),  стабильностью  и  сборкой  —
приветствуется.
