# Ветка · Strukturirovannye elementy FUM

Источник: <https://chatgpt.com/share/6a4dfd46-c6e4-83eb-8f27-8c91e25d6e01>

Полный структурный слой: [chatgpt-share.messages.json](chatgpt-share.messages.json).

## Диалог

### 1. Пользователь

Chelovek ili LLM vosprinimayut nestrukturirovannyij signal, a v kompjyutere sokhranyayut yego v cifrovom uzhe v strukturiruyemom vide v toj ili inoj stepeni. Vo vsyakom sluchaye eto kasayetsya porozhdayemoj informacii, naprimer, napisaniya programmnogo koda ili sozdaniye TeX-dokumenta, iz kotorogo porozhdayetsya PDF, k primeru. Tak vot togda cheloveku i LLM v kontekste FUM imeyet smyisl porozhdatj i sokhranyatj v pamyatj prostyiye strukturnyiye elementyi, znaniye o kotoryikh uzhe imeyetsya, i kotoryiye budut pomogatj avtomaticheski algoritmicheski strukturirovatj syiroj vkhodnoj potok, chtobyi pridavatj yemu strukturirovannuyu formu. Rechj mozhet idti, naprimer, o morfemakh, slovakh vmeste s ikh paradigmami, o boleye vyisokourevnevyikh konstrukciyakh, takikh kak slovosochetaniya s soglasovaniyem i celyiye predlozheniya.

### 2. Ассистент

Я рассматриваю вашу мысль как тезис о FUM-памяти: она должна накапливать элементарные структурные заготовки, помогающие автоматически распознавать, разбирать и оформлять сырой поток. Проверю прежний контекст термина FUM и затем сформулирую это как более строгую рабочую архитектурную схему.

### 3. Ассистент

Да, в контексте FUM это очень сильная мысль: **имеет смысл хранить не только готовую порождённую информацию, но и простые структурные элементы, которые затем работают как “крючки” для автоматического структурирования сырого потока**.

То есть память в FUM можно понимать не как архив «сырых данных», а как растущую систему структурных примитивов и правил их сборки.

Например:

**Сырой входной поток:**

> акустический сигнал, изображение текста, поток символов, поток токенов, жесты, код, TeX-разметка, визуальная сцена.

**Память FUM содержит уже известные структурные элементы:**

> морфемы, слова, парадигмы, синтаксические конструкции, шаблоны согласования, типовые фразы, фрагменты кода, TeX-команды, структуры документа, математические обозначения, схемы рассуждения.

**Тогда восприятие становится не просто записью сигнала, а его разбором через уже имеющиеся элементы.**

Например, поток:

> napisal bystro rabotayushchuyu programmu

можно разбирать не только как последовательность символов, а как набор распознанных элементов:

> `napis-al` → глагол, прошедшее время, мужской род
> `bystro` → наречие
> `rabotayushch-uyu` → причастие, женский род, винительный падеж
> `programm-u` → существительное, женский род, винительный падеж

И уже поверх этого можно строить более высокую структуру:

> субъект подразумевается, действие — “написал”, объект — “программу”, признак объекта — “работающую”, модификатор действия — “быстро”.

То есть FUM могла бы действовать примерно так:

```text
сырой поток
→ сегментация
→ сопоставление с известными элементами памяти
→ выделение новых устойчивых элементов
→ построение более крупной структуры
→ сохранение структуры и/или генеративного правила
```

Важный момент: такие элементы должны быть не просто “единицами хранения”, а **генеративными единицами**. То есть каждый элемент полезен в обе стороны:

```text
восприятие:   поток → структура
порождение:   структура → поток
```

Например, слово вместе с парадигмой — это не просто строка `"programma"`, а объект вида:

```text
лексема: программа
часть речи: существительное
род: женский
парадигма:
  именительный: программа
  родительный: программы
  дательный: программе
  винительный: программу
  ...
связи:
  может быть объектом глагола
  может согласовываться с прилагательным в роде/числе/падеже
```

Тогда при восприятии FUM легче распознаёт форму `"programmu"` как конкретную падежную форму. А при порождении она может выбрать нужную форму автоматически.

То же самое применимо к TeX:

```text
сырой замысел:
  "создать раздел с определением и формулой"

структурные элементы памяти:
  \section{}
  \begin{definition}...\end{definition}
$$
    ...
$$
  шаблон математического утверждения
  шаблон ссылки на формулу
```

Или к программированию:

```text
сырой замысел:
  "прочитать файл, распарсить строки, построить словарь"

структурные элементы памяти:
  функция
  цикл
  обработка исключений
  словарь
  split/parse pattern
  типовой шаблон чтения файла
  AST-конструкция
```

Получается, что FUM должна накапливать не только знания вида:

```text
"я знаю такой-то факт"
```

но и знания вида:

```text
"я знаю такую-то форму"
"я знаю такую-то парадигму"
"я знаю такой-то шаблон сборки"
"я знаю, как этот элемент распознаётся во входном потоке"
"я знаю, как этот элемент порождает выходной поток"
```

Это можно назвать **памятью структурирующих операторов**.

Хороший минимальный формат такого элемента мог бы быть таким:

```text
Элемент памяти E:

1. Каноническая форма
2. Набор наблюдаемых вариантов
3. Признаки / параметры
4. Условия распознавания
5. Правила порождения
6. Связи с другими элементами
7. Уровень абстракции
8. История подтверждений
```

Например для морфемы:

```text
E = {
  тип: морфема,
  форма: "-al",
  значение: прошедшее время / мужской род в русском глаголе,
  распознавание: встречается в глагольных формах после основы,
  порождение: добавляется к основе при образовании формы прошедшего времени,
  связи: глагол, время, род, число
}
```

Для синтаксического шаблона:

```text
E = {
  тип: конструкция,
  форма: "прилагательное + существительное",
  условие: согласование в роде, числе и падеже,
  распознавание: соседние элементы с совместимыми признаками,
  порождение: выбрать форму прилагательного по признакам существительного
}
```

Для TeX-документа:

```text
E = {
  тип: документная конструкция,
  форма: "теорема с доказательством",
  шаблон:
    \begin{theorem}
    ...
    \end{theorem}

    \begin{proof}
    ...
    \end{proof}
}
```

То есть FUM в таком виде становится системой, которая не просто отвечает или генерирует текст, а постепенно строит **многоуровневый словарь структур**:

```text
уровень 0: сырой сигнал
уровень 1: символы / звуки / штрихи
уровень 2: морфемы / токены / графемы
уровень 3: слова / команды / операторы
уровень 4: словосочетания / выражения / AST-узлы
уровень 5: предложения / функции / блоки документа
уровень 6: рассуждения / программы / статьи / документы
```

И тогда новая информация входит в память не хаотично, а через вопрос:

```text
какие уже известные элементы объясняют этот поток?
каких элементов не хватает?
какой новый элемент стоит создать?
как он связан с прежними?
как он поможет в будущем распознавать и порождать структуру?
```

Это особенно важно для LLM, потому что обычная LLM часто хранит знания распределённо и неявно. А в FUM, как я понимаю вашу линию, появляется дополнительный слой: **явная структурная память**, где можно хранить не только вероятностные ассоциации, но и воспроизводимые элементы формы.

И тогда главный принцип можно сформулировать так:

> FUM должна превращать повторяющиеся фрагменты сырого опыта в структурные элементы памяти, которые одновременно являются средствами распознавания, средствами сжатия и средствами порождения.

Или ещё короче:

> Память FUM — это не склад сигналов, а библиотека форм, через которые сырой сигнал становится осмысленной структурой.

### 4. Пользователь

Iznachaljno myi govorili o tom, chto FUM dolzhen byitj sposoben sam vyivoditj strukturu iz syirogo potoka, i v celom eto zhelayemoye svojstvo, no strukturiruyusjhiye operatoryi FUM eto v kakom-to smyisle forma khraneniya predvariteljnyikh znanij, i ona tozhe vpolne mozhet zadavatjsya i utochnyatjsya vruchnuyu chelovekom ili LLM. FUM dolzhen imetj pamyatj strukturiruyusjhikh operatorov, kotoraya mozhet popolnyatjsya i yavno kak zaraneye, tak i v processe analiza vkhodnogo potoka. Predvariteljno eto mozhet byitj realizovano tak, chto LLM dolzhnyi popolnyatj pamyatj strukturiruyusjhikh operatorov takim obrazom, chtobyi nailuchshim obrazom opisyivatj vkhodnoj potok. Yesli vyiyavlyayetsya nedostayusjhij strukturiruyusjhij element, to eto mozhet byitj kak svideteljstvom oshibki i netochnosti vo vkhodnom potoke, tak i svideteljstvom obnaruzheniya potrebnosti v novom strukturiruyusjhem operatore. Pokhozhe pamyatj strukturiruyusjhikh operatorov i yestj minimaljnoye yadro FUM, s realizacii kotorogo stoit nachatj. Eto pokhozhe na mekhanizm tipizacii v yazyikakh programmirovaniya. I zadacha etogo mekhanizma porozhdatj boleye kompaktnoye opisaniye potoka, v tom chisle s celjyu yego luchshego razmesjheniya v kontekstnom okne LLM.

Согласен: это уже выглядит как минимальное ядро FUM — пополняемая память операторов плюс процедура анализа, уточнения и сжатия входного потока. Я разложу это как архитектуру, включая развилку «ошибка входа или новый оператор».

### 6. Ассистент

Да. В такой постановке **память структурирующих операторов действительно выглядит как минимальное ядро FUM**.

Причём важный сдвиг здесь такой:

> FUM не обязан начинать с “чистого нуля”.
> Он может сам выводить структуру из потока, но также может получать заранее заданные структурирующие операторы от человека, LLM или другого FUM-модуля.

То есть FUM — это не только механизм **индукции структуры**, но и механизм **использования, проверки, уточнения и расширения уже имеющейся структурной памяти**.

## 1. Структурирующий оператор как аналог типа

Сравнение с типизацией очень точное.

В языках программирования тип помогает:

```text
сырой код → структурированное выражение → проверяемое значение
```

Например:

```text
x + y
```

само по себе является синтаксической конструкцией. Но если известно:

```text
x: Int
y: Int
+: Int × Int → Int
```

то выражение получает компактное и проверяемое описание:

```text
Add[Int](x, y)
```

А если известно:

```text
x: String
y: Int
```

то возникает конфликт. Этот конфликт может означать:

```text
1. ошибка в коде;
2. ошибка в типах;
3. нужна новая операция;
4. нужна неявная конверсия;
5. система неправильно поняла структуру.
```

Ровно так же в FUM:

```text
сырой поток → попытка структурирования через известные операторы → компактное описание
```

Если поток не укладывается в имеющиеся операторы, это не просто “ошибка”. Это **сигнал остатка**:

```text
residual = часть потока, не объяснённая текущей памятью операторов
```

И дальше FUM должен решить:

```text
это шум?
это ошибка?
это редкий частный случай?
это новый структурный элемент?
это уточнение старого оператора?
это конфликт между несколькими операторами?
```

## 2. Минимальное ядро FUM можно определить так

Я бы сформулировал минимальный FUM-0 так:

```text
FUM-0 =
  память структурирующих операторов
  + механизм применения операторов к потоку
  + механизм оценки качества структурирования
  + механизм выделения остатка
  + механизм предложения новых операторов
  + механизм сохранения/уточнения операторов
```

То есть не нужно сразу строить “полную интеллектуальную систему”. Достаточно начать с системы, которая умеет:

```text
1. принимать поток;
2. разбирать его через текущие операторы;
3. получать структурное описание;
4. видеть, что осталось необъяснённым;
5. предлагать новые операторы для лучшего объяснения;
6. сохранять эти операторы в явной памяти.
```

Это уже будет рабочее ядро FUM.

## 3. Оператор должен быть не просто шаблоном, а двусторонним элементом

Структурирующий оператор должен работать в две стороны:

```text
recognize: поток → структура
generate: структура → поток
```

Например, для морфологического оператора:

```text
Оператор: русское существительное женского рода 1-го склонения

recognize:
  "programmu" → lemma="programma", case=accusative, number=singular

generate:
  lemma="programma", case=accusative, number=singular → "programmu"
```

Для синтаксического оператора:

```text
Оператор: согласование прилагательного с существительным

recognize:
  "rabotayushchuyu programmu"
  → Adj agrees with Noun in gender=feminine, case=accusative, number=singular

generate:
  Noun(gender=feminine, case=accusative, number=singular)
  + adjective stem
  → adjective form with matching features
```

Для TeX:

```text
Оператор: theorem-with-proof

recognize:
  \begin{theorem}...\end{theorem}
  \begin{proof}...\end{proof}

generate:
  structure = Theorem(statement, proof)
  → TeX block
```

Для кода:

```text
Оператор: map/filter/reduce pattern

recognize:
  цикл с накоплением результата
  → higher-level operation

generate:
  higher-level operation
  → concrete loop / comprehension / function call
```

## 4. Хороший формат оператора

Минимально оператор можно хранить так:

```text
Operator {
  id
  name
  level
  input_domain
  output_structure
  recognizer
  generator
  constraints
  cost
  confidence
  examples_positive
  examples_negative
  links_to_other_operators
  provenance
  version
}
```

Где:

```text
level
```

указывает уровень:

```text
символы
морфемы
слова
словосочетания
предложения
документные блоки
кодовые конструкции
математические структуры
рассуждения
```

```text
recognizer
```

отвечает за распознавание во входном потоке.

```text
generator
```

отвечает за порождение обратно в поток.

```text
constraints
```

задают ограничения, похожие на типовые ограничения:

```text
прилагательное должно согласоваться с существительным
переменная должна быть объявлена до использования
TeX-блок должен быть закрыт
доказательство должно ссылаться на утверждение
функция должна возвращать значение нужного типа
```

```text
cost
```

задаёт цену использования оператора. Это важно, потому что FUM должен не просто “найти любую структуру”, а найти **компактное и полезное описание**.

## 5. Центральная функция: сжатие потока через операторы

Очень сильная формализация здесь такая:

```text
FUM пытается найти такое описание потока,
которое минимизирует длину описания при помощи известных операторов.
```

То есть:

```text
raw stream X
operator memory O
structured description S
residual R
```

И задача:

```text
найти S и R такие, что:

X ≈ decode(S, O) + R

и при этом:

length(S) + length(R) минимальна
```

Иными словами:

```text
хороший оператор = оператор, который уменьшает длину описания потока
```

Но не только механически уменьшает. Он также должен:

```text
сохранять воспроизводимость;
улучшать предсказание;
быть применимым повторно;
согласовываться с другими операторами;
не разрушать уже найденную структуру.
```

Это делает FUM похожим одновременно на:

```text
систему типов,
парсер,
компрессор,
грамматический индуктор,
память шаблонов,
механизм построения AST.
```

## 6. Остаток как главный источник роста

Ключевая сущность — это **необъяснённый остаток**.

Например, FUM имеет операторы для обычного предложения:

```text
Subject + Predicate + Object
```

И видит поток:

```text
"programmu bystro napisannyj rabotayet"
```

Система пытается разобрать, но что-то не сходится:

```text
"programmu" — винительный падеж
"napisannyj" — мужской род / именительный
"rabotayet" — глагол
```

Возникает остаток или конфликт.

Дальше возможны варианты:

```text
1. во входе ошибка;
2. транслитерация исказила форму;
3. нужна новая модель свободного порядка слов;
4. нужна модель эллипсиса;
5. нужна модель смешения русского и латинской записи;
6. текущий оператор согласования слишком жёсткий.
```

И вот здесь FUM не должен сразу “исправлять” поток. Он должен сохранить ситуацию как диагностическую:

```text
Residual {
  fragment
  failed_operators
  partial_matches
  conflict_type
  candidate_explanations
}
```

После этого LLM или человек может предложить новый оператор.

Например:

```text
Operator: loose transliterated Russian morphology
```

или:

```text
Operator: malformed-but-recoverable agreement
```

или:

```text
Operator: poetic/free word order
```

## 7. Когда создавать новый оператор, а когда считать это ошибкой

Это можно решать через несколько критериев.

Новый оператор имеет смысл создавать, если:

```text
остаток повторяется;
новый оператор заметно сжимает описание;
оператор объясняет не один фрагмент, а класс фрагментов;
оператор согласуется с уже имеющимися структурами;
оператор помогает порождать корректный выход;
оператор улучшает дальнейший разбор.
```

Скорее ошибка или шум, если:

```text
фрагмент единичный;
он не даёт повторно используемой структуры;
он противоречит сильным ограничениям;
его проще объяснить как опечатку;
создание оператора резко усложняет память;
оператор нужен только для одного случая.
```

Но это не бинарное решение. Лучше хранить статус:

```text
candidate_operator
hypothesis
low_confidence_operator
confirmed_operator
deprecated_operator
```

То есть новый оператор сначала может попасть в карантин:

```text
не использовать глобально,
но учитывать как гипотезу при анализе похожих потоков.
```

## 8. Роль LLM в пополнении памяти

LLM здесь не должна быть “истиной”. Она должна быть **генератором кандидатов**.

Схема может быть такой:

```text
1. FUM разбирает поток текущими операторами.
2. Возникают остатки и конфликты.
3. LLM получает:
   - исходный фрагмент;
   - текущий разбор;
   - список неудачных операторов;
   - остаток;
   - цель сжатия.
4. LLM предлагает:
   - новый оператор;
   - уточнение старого оператора;
   - исправление входа;
   - несколько конкурирующих гипотез.
5. FUM проверяет, даёт ли это лучшее описание.
6. Если да — оператор сохраняется с confidence/provenance.
```

То есть LLM работает как эвристический конструктор:

```text
residual → candidate operator
```

А FUM работает как проверяющая система:

```text
candidate operator → compression gain / consistency / reusability
```

Это важно: иначе память операторов быстро загрязнится произвольными объяснениями.

## 9. Контекстное окно LLM как причина для компактного описания

Очень важный практический мотив: **структурирование нужно не только ради понимания, но и ради размещения в контекстном окне**.

Сырой поток может быть большим:

```text
много текста
много кода
много TeX
много логов
много промежуточных рассуждений
много повторяющихся шаблонов
```

Но после структурирования его можно передать LLM компактно:

```text
Document {
  type: mathematical_note
  sections: [
    Definition(...),
    Lemma(...),
    Proof(...),
    Example(...)
  ],
  unresolved: [...]
}
```

Или для кода:

```text
ProgramSummary {
  modules: [...],
  functions: [...],
  data_flow: [...],
  type_conflicts: [...],
  repeated_patterns: [...]
}
```

Или для языкового потока:

```text
UtteranceStructure {
  intent: propose_architecture
  concepts: [FUM, operator_memory, type_system, compression, context_window]
  claims: [...]
  unresolved_terms: [...]
}
```

В таком виде LLM получает не 20 тысяч токенов сырья, а 2 тысячи токенов структуры. При необходимости FUM может восстановить детали через ссылки:

```text
node_17 → source span 1045:1290
operator_used → O.syntax.agreement.v2
residual → R23
```

То есть память операторов становится способом **семантической компрессии с обратной трассировкой**.

## 10. Важно различать lossless и lossy режимы

Для FUM нужно явно различить два режима.

**Lossless-структурирование:**

```text
структура + остаток позволяют полностью восстановить исходный поток
```

Это нужно для:

```text
кода,
TeX,
юридических документов,
математических доказательств,
логов,
данных,
ситуаций, где важна точность.
```

**Lossy-структурирование:**

```text
структура сохраняет смысл, но не все поверхностные детали
```

Это подходит для:

```text
резюме,
диалога,
планирования,
обобщения,
долговременной памяти.
```

В идеале FUM должен уметь хранить оба слоя:

```text
compact semantic structure
+
links to recoverable raw fragments
```

То есть:

```text
сжать для мышления,
но не потерять возможность проверки.
```

## 11. Минимальный цикл работы FUM

Можно описать ядро таким циклом:

```text
input_stream X

1. parse(X, operator_memory)
   → structured_description S
   → residuals R
   → conflicts C

2. score(S, R, C)
   → compression_score
   → consistency_score
   → usefulness_score

3. for each residual/conflict:
      propose candidate operators

4. evaluate candidates:
      does operator reduce residual?
      does it generalize?
      does it conflict with existing operators?
      can it generate examples?
      can it explain future/past fragments?

5. save/update operators:
      confirmed
      candidate
      rejected
      deprecated

6. reparse X with updated memory

7. serialize compact representation for LLM context
```

В псевдокоде:

```text
function FUM_ANALYZE(X, O):
    S, R, C = parse_with_operators(X, O)

    candidates = []
    for r in R:
        candidates += propose_operators(r, S, O)

    for op in candidates:
        gain = compression_gain(X, O, op)
        consistency = check_constraints(op, O)
        reuse = estimate_reusability(op, X)

        if gain > threshold and consistency ok:
            O.add(op, status="candidate")

    S2, R2, C2 = parse_with_operators(X, O)

    return {
        structure: S2,
        residuals: R2,
        conflicts: C2,
        operator_memory_updates: O.diff(),
        compact_context: serialize(S2, R2, O)
    }
```

## 12. Почему это действительно минимальное ядро

Потому что без памяти операторов FUM остаётся просто системой, которая каждый раз заново пытается понять поток.

А с памятью операторов появляется накопление формы:

```text
один раз выделили структуру
→ сохранили оператор
→ в следующий раз распознали быстрее
→ получили более компактное описание
→ нашли новый остаток
→ уточнили память
```

Это и есть фундаментальный цикл обучения FUM:

```text
поток → структура → остаток → новый оператор → лучшая структура
```

Или ещё короче:

```text
FUM = саморасширяющаяся система типизации сырого опыта.
```

Только “типы” здесь шире, чем в программировании. Это могут быть:

```text
морфологические типы,
синтаксические типы,
семантические роли,
жанры документов,
шаблоны кода,
математические конструкции,
риторические ходы,
ошибочные паттерны,
форматы данных,
процедуры рассуждения.
```

## 13. Хорошая итоговая формула

Можно сформулировать так:

> Минимальное ядро FUM — это память структурирующих операторов, с помощью которой сырой поток преобразуется в более компактное, проверяемое и порождающее описание.
> Необъяснённый остаток потока служит источником гипотез о новых операторах или об ошибках во входе.
> LLM может пополнять эту память, предлагая операторы, но FUM должен принимать их не по авторитету LLM, а по критериям сжатия, согласованности и повторной применимости.

И совсем компактно:

```text
FUM-memory stores forms.
FUM-analysis applies forms.
FUM-learning creates new forms from residuals.
FUM-context stores streams as references to forms.
```

На мой взгляд, именно с этого и стоит начинать реализацию: не с “полного мышления”, а с маленькой системы, которая умеет брать поток, разбирать его через библиотеку операторов, фиксировать остатки и расширять библиотеку так, чтобы следующее описание было короче, точнее и устойчивее.

### 7. Пользователь

Strukturiruyusjhiye operatoryi po suti zadayut derevo i iyerarkhiyu semanticheskikh svyazej. Nizkourovnevyiye strukturiruyusjhiye operatoryi, kak to operator suffiksa ili okonchaniya vpolne mogut byitj specifichnyimi dlya konkretnogo yazyika, dopustim, russkogo, i svyazyivatj, naprimer, lishj raznyiye formyi zapisi, k primeru zapisj kirillicej i latinicej. No vot boleye vyisokourovnevyiye i boleye semanticheskiye operatoryi uzhe mogut svyazyivatj v tom chisle strukturyi anglijskogo i russkogo yazyika mezhdu soboj.

### 8. Ассистент

Разверну это как многоуровневую архитектуру: нижние операторы остаются языко- и кодировочно-специфичными, а верхние образуют межъязыковые семантические связи. Полезно различить локальное дерево разбора потока и общую память операторов как граф смыслов.

### 9. Ассистент

Да, именно. **Структурирующие операторы задают не просто набор шаблонов, а многоуровневую иерархию семантических связей**. Причём чем ниже уровень оператора, тем сильнее он привязан к конкретной форме записи, языку или формату; чем выше уровень, тем больше он приближается к межъязыковой или даже внеязыковой семантике.

Я бы различил здесь три слоя:

```text
1. Формальные / поверхностные операторы
2. Языковые структурные операторы
3. Межъязыковые семантические операторы
```

## 1. Низкий уровень: операторы формы

На самом нижнем уровне оператор может связывать разные формы записи одного и того же или близкого элемента.

Например:

```text
кириллица: человек
латиница: chelovek
```

Оператор:

```text
TranslitRU {
  chelovek ↔ человек
}
```

Здесь почти нет высокой семантики. Это оператор соответствия между системами записи.

То же самое:

```text
programma ↔ программа
programmu ↔ программу
napisal ↔ написал
rabotayushchuyu ↔ работающую
```

Такие операторы специфичны для русского языка и для конкретной схемы транслитерации. Они помогают FUM понять, что:

```text
"programmu"
```

это не английское слово, а латинизированная форма русского:

```text
"программу"
```

Дальше уже подключается морфология.

## 2. Морфологический уровень: языкоспецифические операторы

Например:

```text
программа
программы
программе
программу
программой
```

связываются через оператор лексемы и парадигмы:

```text
LexemeRU {
  lemma: программа
  part_of_speech: noun
  gender: feminine
  paradigm: ...
}
```

Форма:

```text
программу
```

получает структурное описание:

```text
lemma: программа
case: accusative
number: singular
gender: feminine
```

Это уже не просто соответствие записей, а структурирование языкового материала.

В английском для похожей сущности будет другой низкоуровневый оператор:

```text
program
programs
```

Там нет падежной парадигмы как в русском, но есть число, артикли, порядок слов, предлоги и так далее.

То есть на низком уровне:

```text
русский оператор ≠ английский оператор
```

Например:

```text
RU: падежное окончание
EN: позиция в предложении / предлог / артикль
```

Но оба могут подниматься к одной и той же более высокой роли.

## 3. Синтаксический уровень: частично языковой, частично общий

Например, русское:

```text
я написал программу
```

и английское:

```text
I wrote a program
```

имеют разные поверхностные структуры:

```text
RU:
  "я" — именительный падеж
  "программу" — винительный падеж
  порядок слов относительно свободный

EN:
  "I" — subject position
  "program" — object position
  порядок слов более жёсткий
```

Но на более высоком уровне оба разбираются в одну структуру:

```text
Event {
  type: writing
  agent: speaker
  patient/result: program
  tense: past
}
```

И вот здесь появляются операторы более высокого уровня:

```text
SemanticRoleOperator {
  agent
  action
  object/result
  time
  manner
}
```

Они уже могут связывать русский и английский.

## 4. Высокий уровень: межъязыковые семантические операторы

Например:

```text
Я быстро написал работающую программу.
```

и:

```text
I quickly wrote a working program.
```

На поверхности они устроены по-разному.

Русская структура:

```text
я
быстро
написал
работающую
программу
```

Английская структура:

```text
I
quickly
wrote
a
working
program
```

Но FUM может построить общий семантический узел:

```text
Event {
  predicate: WRITE
  agent: SPEAKER
  object: PROGRAM
  object_property: WORKING
  manner: QUICKLY
  tense: PAST
}
```

Тогда русские и английские операторы оказываются не напрямую равными друг другу, а связанными через общий более высокий оператор:

```text
RU surface structure
      ↓
RU morphosyntax
      ↓
semantic event frame
      ↑
EN morphosyntax
      ↑
EN surface structure
```

Это очень важно: **английский и русский не обязательно нужно связывать напрямую слово-к-слову**. Лучше связывать их через промежуточную семантическую структуру.

## 5. Получается не только дерево, но и граф

Вы говорите “дерево и иерархия”, и это верно как первое приближение. Но, скорее всего, в полной FUM это будет не чистое дерево, а **многоуровневый граф**.

Почему?

Потому что один низкоуровневый элемент может участвовать в нескольких высокоуровневых структурах.

Например слово:

```text
работающая
```

может быть:

```text
1. причастием от "работать";
2. признаком объекта;
3. частью словосочетания "работающая программа";
4. семантическим свойством "functioning";
5. в другом контексте — частью метафоры.
```

То есть связи идут не строго вверх по одному пути, а расходятся:

```text
форма
 → морфология
 → синтаксис
 → семантическая роль
 → концепт
 → прагматическая функция
```

Поэтому минимально можно говорить об иерархии, но технически лучше думать о структуре как о DAG/графе:

```text
низкие операторы: ближе к сигналу
высокие операторы: ближе к смыслу
рёбра: связи объяснения, порождения, обобщения, перевода, уточнения
```

## 6. Межъязыковой оператор как “интерфейс”

Сравнение с типами здесь снова хорошо работает.

Низкоуровневые операторы похожи на конкретные реализации:

```text
RussianNounCaseSystem
EnglishWordOrderSystem
RussianVerbAspectSystem
EnglishTenseSystem
```

А высокоуровневые операторы похожи на интерфейсы:

```text
Agent
Action
Object
Property
Time
Cause
Goal
Condition
Modality
Negation
Quantification
```

Например:

```text
RU:
  "программу" в винительном падеже

EN:
  "program" после глагола "wrote"
```

оба реализуют более абстрактную роль:

```text
Patient / Object / Result of action
```

То есть:

```text
Russian accusative case
  implements SemanticObjectRole in certain constructions

English post-verbal noun phrase
  implements SemanticObjectRole in certain constructions
```

Это очень похоже на:

```text
class RussianAccusative implements ObjectMarker
class EnglishSVOPosition implements ObjectMarker
```

## 7. Пример структуры FUM для двух языков

Можно представить так:

```text
Raw input:
  "Ya bystro napisal rabotayushchuyu programmu"

Level 0: script/transliteration
  Ya → Я
  bystro → быстро
  napisal → написал
  rabotayushchuyu → работающую
  programmu → программу

Level 1: morphology
  Я → pronoun, 1st person, singular, nominative
  написал → verb, past, masculine/perfective
  работающую → participle/adjective, feminine, accusative, singular
  программу → noun, feminine, accusative, singular

Level 2: syntax
  subject: Я
  predicate: написал
  object: программу
  object_modifier: работающую
  manner: быстро

Level 3: semantics
  Event WRITE
    agent: speaker
    object: program
    property(object): working
    manner: quickly
    tense: past

Level 4: interlingual mapping
  English generation:
    "I quickly wrote a working program."
```

Здесь английская фраза не хранится как перевод каждой русской формы. Она порождается из более высокого семантического представления.

## 8. Поэтому память операторов должна быть стратифицированной

Для FUM полезно явно хранить уровень оператора:

```text
Operator {
  id
  level
  language_scope
  input_type
  output_type
  constraints
  links_up
  links_down
  examples
}
```

Например:

```text
Operator {
  id: RU_ACCUSATIVE_OBJECT
  level: morphosyntax
  language_scope: Russian
  input_type: RussianNounPhrase
  output_type: SemanticObjectRole
  constraints:
    - accusative case
    - compatible with transitive verb
}
```

Или:

```text
Operator {
  id: EN_POSTVERBAL_OBJECT
  level: syntax
  language_scope: English
  input_type: EnglishNounPhrase
  output_type: SemanticObjectRole
  constraints:
    - follows transitive verb in active SVO clause
}
```

Оба связываются с одним более высоким оператором:

```text
Operator {
  id: SEMANTIC_OBJECT_ROLE
  level: semantics
  language_scope: crosslingual
  input_type: event_participant
  output_type: role_in_event
}
```

## 9. Важное следствие для перевода

Тогда перевод в FUM — это не операция:

```text
слово на русском → слово на английском
```

а операция:

```text
русский поток
→ русская структура
→ межъязыковая семантическая структура
→ английская структура
→ английский поток
```

То есть:

```text
RU raw
→ RU operators
→ semantic operators
→ EN operators
→ EN raw
```

Это лучше, потому что многие вещи не переводятся один-к-одному.

Например:

```text
мне холодно
```

буквально:

```text
to me cold
```

но английская структура:

```text
I am cold
```

Семантический центр:

```text
ExperiencerState {
  experiencer: speaker
  state: cold sensation
}
```

Русский выражает experiencer через дательный падеж:

```text
мне
```

А английский — через подлежащее:

```text
I
```

Значит, FUM должен связать:

```text
RU_DATIVE_EXPERIENCER
```

и

```text
EN_SUBJECT_EXPERIENCER
```

через общий оператор:

```text
EXPERIENCER_ROLE
```

## 10. Ещё пример: русское “у меня есть”

Русское:

```text
У меня есть книга.
```

Английское:

```text
I have a book.
```

Поверхностно это разные конструкции.

Русская структура:

```text
у + genitive possessor
есть + possessed object
```

Английская структура:

```text
subject + have + object
```

Но семантически:

```text
Possession {
  possessor: speaker
  possessed: book
}
```

Соответственно:

```text
RU_U_MENYA_EST
  → POSSESSION_FRAME

EN_HAVE_CONSTRUCTION
  → POSSESSION_FRAME
```

Это типичный пример того, почему высокоуровневые операторы должны быть межъязыковыми.

## 11. Что это даёт FUM практически

Такое разделение даёт несколько преимуществ.

Во-первых, FUM может лучше сжимать поток:

```text
"Ya bystro napisal rabotayushchuyu programmu"
```

вместо хранения как строки можно хранить как:

```text
WRITE_EVENT(
  agent=speaker,
  object=PROGRAM(property=WORKING),
  manner=QUICKLY,
  tense=PAST
)
```

А поверхностную форму хранить только как ссылку или как восстановимый слой.

Во-вторых, FUM может связывать знания из разных языков:

```text
"я написал программу"
"I wrote a program"
```

становятся двумя выражениями одного семантического узла.

В-третьих, FUM может использовать один язык для уточнения другого. Например, если русская структура неоднозначна, английский перевод или англоязычная парафраза может помочь выбрать семантический разбор.

В-четвёртых, FUM может хранить знания не как текст на конкретном языке, а как структуру, которую затем можно порождать на разных языках.

## 12. Но полная межъязыковая нейтральность невозможна без потерь

Нужно оставить важную оговорку: высокоуровневые операторы могут быть межъязыковыми, но они не всегда будут полностью нейтральными.

Например, русский вид глагола:

```text
писал / написал
```

и английские времена/aspects:

```text
wrote / was writing / has written
```

не совпадают идеально.

Русское:

```text
я писал программу
```

и:

```text
я написал программу
```

различают процесс и завершённость.

В английском это можно выразить, но не всегда теми же средствами:

```text
I was writing a program.
I wrote a program.
I have written a program.
```

Поэтому межъязыковой оператор должен уметь хранить не только общий смысл, но и “семантические остатки”:

```text
common semantic frame
+
language-specific features
+
translation loss / ambiguity
```

Например:

```text
WRITE_EVENT {
  agent: speaker
  object: program
  completion: completed
  source_language_feature: RU perfective aspect
}
```

То есть FUM должен различать:

```text
универсальную семантику
```

и:

```text
языково-специфические смысловые оттенки
```

## 13. Итоговая архитектура

Можно представить память структурирующих операторов так:

```text
Level 0: raw signal operators
  звук, символ, пиксель, байт, токен

Level 1: notation operators
  кириллица, латиница, транслитерация, TeX, Markdown, Python syntax

Level 2: language-specific morphology
  русские окончания, английские plural forms, времена, падежи

Level 3: language-specific syntax
  русский свободный порядок слов, английский SVO, конструкции с предлогами

Level 4: semantic roles
  agent, patient, experiencer, instrument, goal, source, location

Level 5: frames/events
  possession, writing, perception, causation, comparison, definition

Level 6: discourse/rhetoric
  утверждение, доказательство, пример, возражение, уточнение, вывод

Level 7: task-level structures
  программа, документ, доказательство, план, объяснение, диалог
```

Низкие уровни могут быть специфичны:

```text
RU-only
EN-only
TeX-only
Python-only
```

Средние уровни частично общие:

```text
noun phrase
verb phrase
modifier
argument
predicate
```

Высокие уровни становятся межъязыковыми:

```text
event
role
cause
goal
state
definition
proof
decision
constraint
```

## 14. Главная формула

Можно сформулировать так:

> Низкоуровневые структурирующие операторы связывают разные формы записи и языковые реализации.
> Высокоуровневые структурирующие операторы связывают уже не формы, а смыслы, поэтому они могут объединять русские, английские и другие языковые структуры в общие семантические узлы.

И ещё короче:

```text
низкий уровень: разные записи одной формы
средний уровень: разные языковые формы одной роли
высокий уровень: разные языки как реализации одной семантической структуры
```

Именно такая иерархия делает FUM не просто парсером текста, а системой, которая может накапливать структуру смысла поверх разных форм записи, языков и форматов.
