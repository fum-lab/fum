# Требование записи следующего шага для терминальной ветки пула

Карточка сохраняет несовместимость репозиторного self-test следующего шага ветки с терминальным писателем worktree-пула. Общий smoke-check из выделенного слота ошибочно требовал переносимую selector-запись для runtime work-ref, хотя такой ref завершается квитанцией результата и не является обычной selector-driven веткой.

## Наблюдаемый сбой

Итоговый полный smoke-check дошёл до автономного набора `fum-sleduyusjhij-shag-vetki` и остановился на репозиторном тесте. Тест вызвал `validate` для фактически активного `refs/heads/codex/подузлы/сессия-…`, получил закрытый отказ об отсутствии ровно одной записи в `Планирование/следующие-шаги-веток/`, а затем не достиг собственных жёстко заданных ожиданий для `refs/heads/master`.

Производственный селектор сработал правильно: случайный вызов из ветки пула не получил полномочий или содержательного шага. Неверным было предположение self-test, что общий smoke всегда исполняется в ordinary-ветке с selector-записью.

## Граница повторения

К карточке относится запуск репозиторного self-test следующего шага из активного runtime work-ref пространства `refs/heads/codex/подузлы/`, когда переносимая selector-запись закономерно существует только для обычной целевой ветки. Общая мера должна одновременно проверить каноническую запись `master` и сохранить закрытый отказ прямых `validate` и `show` для ветки пула без записи.

Сюда не относятся обычная именованная branch FIFO, которой разрешено selector-driven продолжение, отсутствие или дубликат требуемой записи такой ветки, повреждённая карточка кандидата, exact-продолжение worktree-линии по её собственной FIFO и терминальная фиксация результата. Для обычной ветки прежнее требование ровно одной записи остаётся строгим.

## Ожидание и классификация

Действующие правила разделяют ordinary branch FIFO и worktree-пул. Переносимый набор следующего шага требуется только ветке selector-driven профиля, а терминальный писатель пула завершает назначение через `result_frozen` и освобождение чистого слота без новой задачи-продолжения. Поэтому требование selector-записи для runtime work-ref было недоработкой репозиторной проверки и слишком широких сопровождающих формулировок, а не отсутствующим плановым артефактом.

## Механизм и системное устранение

Репозиторный тест запускал CLI-команды относительно фактически активной ветки, но ниже проверял неизменные счётчики, кандидата и `step_id` канонической записи `master`. Пока smoke выполнялся в первичном checkout, две разные идентичности случайно совпадали; выделенный worktree впервые разорвал это неявное равенство.

Системное устранение делает границу явной. В active pool-ref self-test требует отсутствие собственной selector-записи и read-only проверяет канонический `master` через загрузку карточек и записей, проверку готового пула и детерминированный выбор. Отдельная временная Git-фикстура вызывает настоящие `validate` и `show` на ветке пула без записи и требует код `2` с точной диагностикой. Производственный селектор не получает prefix-bypass, а правила, требование, индекс веточных наборов и smoke-контракт различают ordinary `committed` и терминальный `result_frozen` с освобождением.

## Связанные шаги

Новые карточки шагов не создавались: первое проявление системно устранено и проверено в той же рабочей сессии. Runtime-ветка пула не превращалась в переносимую плановую линию ради прохождения теста.

## Критерии закрытия

- В активном `refs/heads/codex/подузлы/**` репозиторный self-test требует отсутствие selector-записи для текущего runtime ref.
- Тот же self-test проверяет ровно одну каноническую запись `refs/heads/master`, прежние счётчики `13/4/6/3` и выбор `FUM-STEP-0124` без переключения checkout.
- Изолированные `validate` и `show` на ветке пула без собственной записи остаются fail-closed с кодом `2`; production-селектор не получает исключение по префиксу.
- Полный автономный набор следующего шага ветки проходит внутри фактического worktree-пула.
- Правила и производные контракты явно исключают терминальные runtime work-ref пула из selector-driven профиля и признают квитанцию `result_frozen` с последующим освобождением допустимым терминалом писателя.
