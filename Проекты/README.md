# Проекты

Каталог является точкой подключения самостоятельных проектов к композиционной сборке [памяти FUM](../Глоссарий/память-FUM.md). В целевой архитектуре каждый проект имеет отдельный Git-репозиторий и подключается по пути `Проекты/<устойчивый-идентификатор>/` как submodule на точный проверенный commit. Это позволяет развивать проекты параллельно, не смешивая их историю, доступ и цели с общей веткой ядра FUM.

Корневой FUM остаётся описан в [главном README](../README.md) и не дублируется отдельным паспортом. `README.md` внутри репозитория проекта является его паспортом, а этот файл описывает общий контракт подключения. Наличие обычного вложенного каталога без gitlink не делает его проектом композиционной сборки.

## Паспорт проекта

Паспорт должен содержать:

- цель проекта и ожидаемый передаваемый результат;
- устойчивый идентификатор проекта, его репозиторий и полный ref основной ветки;
- границы разрешённых действий, доступа и публикации;
- опорные требования, документацию и источники;
- ссылку на выбранный [следующий шаг ветки](../Глоссарий/следующий-шаг-ветки.md), однозначно адресующий репозиторий и полный ref;
- способ проверки и условие завершения либо возврата результата в основную память.

Паспорт не заменяет исходные запросы, производную документацию, требования или журнал. Секреты, локальные учётные данные и непубликуемое машинное состояние в публичной памяти не сохраняются.

## Репозиторий, ветки и gitlink

Основная и рабочие ветки проекта живут внутри его собственного репозитория. Gitlink композиционной сборки не является живой веткой и не следует за remote автоматически: он фиксирует ровно один принятый commit проекта. Рекомендуемая ветка в `.gitmodules`, если она появится, остаётся только политикой обновления и не заменяет проверяемый выбор ревизии.

Перед подключением commit проекта должен быть опубликован или иначе надёжно сохранён и достижим из разрешённого источника. После проверки проектный commit и обновление gitlink фиксируются разными коммитами в разных репозиториях; между ними нет общей атомарной Git-транзакции.

## Параллельная работа

Каждая пишущая попытка шага работает в отдельном одноразовом клоне проектного репозитория и в уникальной step-ветке от точного базового commit. Параллельные исполнители не делят checkout, индекс или ветку. Принятие результатов в одну основную ветку проекта сериализуется, а локальная очередь одного checkout не считается координацией отдельных клонов.

Автоматическое разрешение конфликтов допускается только для проверяемых классов: непересекающихся изменений, структурных реестров, пересобираемых производных файлов и gitlink, где один дочерний commit является предком другого. Смысловой конфликт получает отдельный рабочий пакет и сохраняется как неустранённый, если проверки не дают достаточного основания для выбора.

## Границы доступа

Публичная композиционная сборка может подключать только публикационно допустимые репозитории и не должна раскрывать URL или имена приватных проектов. Проекты с закрытыми материалами подключаются в приватной сборке; наружу из них передаётся только явно разрешённый обезличенный результат.
