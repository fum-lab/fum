# Языконейтральный канонический протокол памяти

Канонические события и поколения памяти [FUM](../Глоссарий/FUM.md) имеют единственное нормативное байтовое представление. Профиль `fum.memory.canonical-json.v1` задаёт прикладное подмножество JSON Canonicalization Scheme: для каждого допустимого значения байты совпадают с JCS, а доменные ограничения исключают ненужные варианты чисел, `null` и Unicode-имена полей.

Профиль определяет preimage для SHA-256 и идентификаторов поколений. Исходная транспортная запись, порядок ключей декодера, `description`, `String.hashValue`, поведение Foundation и конечный перевод строки CLI в preimage не входят.

## Идентичность и область действия

Идентификатор профиля неизменяем: `fum.memory.canonical-json.v1`. Любое изменение правил, способное изменить байты или множество допустимых значений, требует нового идентификатора и явной политики совместимости.

Профиль применяется к объектам событий, записей, seed, журнала, снимка, трассы, модели представления, целого поколения и указателя `CURRENT`. Схема домена дополнительно определяет точные поля каждого носителя; байтовый профиль не заменяет доменную валидацию.

## Байтовая грамматика

| Аспект            | Норма `fum.memory.canonical-json.v1`                                                                                                    |
| ----------------- | --------------------------------------------------------------------------------------------------------------------------------------- |
| Кодировка         | Только строго корректный UTF-8 без BOM, CESU-8 и замены ошибочных последовательностей.                                                  |
| Корень            | Ровно один JSON-объект.                                                                                                                 |
| Глубина           | Корень имеет глубину `0`; глубина каждого дочернего значения на единицу больше. Максимум — `128`.                                       |
| Пробелы           | Не выводятся до, после или между токенами.                                                                                              |
| Завершение        | После конечной `}` нет байтов. `LF` или `CRLF` запрещены. CLI может добавить `LF` как внешний framing, но не хэширует его.              |
| Объекты           | Имена уникальны после раскрытия JSON-escape. Дубликат отклоняется до помещения в map.                                                   |
| Имена полей       | Только ASCII по шаблону `[a-z][a-z0-9_]*`.                                                                                              |
| Порядок полей     | Возрастание по беззнаковым ASCII-байтам имени. В этом подмножестве результат тождественен JCS-порядку по беззнаковым UTF-16 code units. |
| Массивы           | Сохраняют исходный порядок элементов.                                                                                                   |
| Булевы значения   | Только литералы `true` и `false`.                                                                                                       |
| Целые числа       | Только `0…9007199254740991`. Запись — `0` либо `[1-9][0-9]*`.                                                                           |
| Запрещённые числа | Отрицательные целые, `-0`, ведущий `+`, ведущие нули, дроби, экспоненты, числа выше `2^53−1`, `NaN`, ±`Infinity` и `BigInt`.            |
| `null`            | Запрещён. Необязательное поле отсутствует; неактивные поля вариантов `remember` и `compose` не выводятся.                               |

Диапазон целых чисел выбран из гарантированно точного межъязыкового диапазона I-JSON. Отрицательные и дробные числа в текущем домене памяти не используются: версии, порядковые номера и лимиты неотрицательны. Их запрет не теряет законных значений и не переносит в протокол сложную семантику ECMAScript-чисел.

## Строки и Unicode

Строка сохраняет точную последовательность Unicode scalar values. Профиль не применяет NFC, NFD, NFKC или NFKD: композиционно эквивалентные строки остаются разными свидетельствами и имеют разные байты и SHA-256.

Одиночные суррогаты, некорректные суррогатные пары и Unicode noncharacters `U+FDD0…U+FDEF`, `U+nFFFE`, `U+nFFFF`, где `n` — номер плоскости от `0` до `10₁₆`, запрещены. Корректные supplementary characters выводятся непосредственно в UTF-8, а не парой `\u`-escape.

Экранирование единственно:

- `U+0008`, `U+0009`, `U+000A`, `U+000C`, `U+000D` выводятся как `\b`, `\t`, `\n`, `\f`, `\r`;
- остальные `U+0000…U+001F` выводятся как `\u00xx` с четырьмя строчными hex-цифрами;
- `"` выводится как `\"`, а `\` — как `\\`;
- всё остальное выводится непосредственно, включая `/`, `U+007F…U+009F`, `U+2028`, `U+2029`, кириллицу и emoji.

## Канонический приёмник

Приёмник авторитетных байтов не полагается на мягкое поведение обычного JSON-декодера. Он:

1. Строго разбирает UTF-8 и JSON с сохранением числовой лексемы и возможности обнаружить дубликат до свёртки объекта.
2. Проверяет типы, диапазоны, Unicode и имена полей профиля.
3. Повторно сериализует значение по этому документу.
4. Требует полного побайтового равенства сериализованного результата и входа.
5. Только после байтовой проверки передаёт данные в типизированную доменную валидацию.

Поэтому корректные по RFC 8259, но неканонические записи с пробелами, другим порядком ключей, `\/`, лишним `\u`-escape, парой escape-суррогатов для emoji и конечным переводом строки отклоняются авторитетным контуром.

## SHA-256 и доменные идентификаторы

Текстовая форма SHA-256 равна `sha256:` и ровно 64 строчным hex-цифрам. Алгоритм получает только `canonicalBytes(value)` точного носителя:

| Поле или идентификатор                | Хэшируемое значение                                                                                                      |
| ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------ |
| `source_event_sha256`                 | Полное каноническое тело одного принятого события.                                                                       |
| `output_record_sha256`                | Каноническая запись памяти вместе с происхождением.                                                                      |
| `seed_sha256`                         | Канонический seed.                                                                                                       |
| `event_journal_sha256`                | Весь кумулятивный журнал принятых событий.                                                                               |
| `input_sha256`                        | Каноническая программа событий текущего перехода, а не сырые transport bytes.                                            |
| `snapshot_sha256`                     | Канонический снимок.                                                                                                     |
| `trace_sha256`                        | Каноническая трасса.                                                                                                     |
| `view_model_sha256`                   | Каноническая модель представления.                                                                                       |
| Адрес поколения (`generation_sha256`) | Полное каноническое поколение; его SHA-256 является адресом файла и значением `StoredMemoryGeneration.generationSHA256`. |

Принятые канонизатором записи одной программы событий — например, с другим порядком полей, разрешёнными пробелами или эквивалентным escape — получают один `input_sha256`. Это устраняет прежнее расхождение, при котором один путь хэшировал сырые входные байты, а другой — повторно закодированную программу.

## Версионирование носителей

Поколение схемы `3` содержит обязательное `canonical_profile: "fum.memory.canonical-json.v1"`. Указатель `CURRENT` схемы `2` содержит тот же идентификатор и точный SHA-256 поколения. Выходной артефакт прототипа также использует схему `3` и явно называет профиль.

Поколения схем `1` и `2` и указатель схемы `1` не мигрируются молча. Новый читатель отклоняет их без переопределения байтов новыми правилами и не перезаписывает хранилище. Мигратор старых поколений может быть добавлен только как отдельный версионный переход.

## Реализации и conformance

Продуктовая Swift-реализация использует собственные байтовые parser и writer. Канонический writer не вызывает `JSONEncoder`, `JSONSerialization`, форматтер чисел или `String(format:)`. SHA-256 вычисляется с помощью CryptoKit над уже готовыми байтами профиля; строчный hex строится побайтово. Foundation остаётся на границе `Data`, файловой системы, типизированного декодирования уже проверенных байтов и неавторитетного чтения номера прежней схемы перед явным отказом; она не определяет каноничность или preimage. Типизированная программа должна повторно дать те же байты собственного writer, иначе вход отклоняется, а `input_sha256` вычисляется непосредственно из байтов, полученных собственным parser до Foundation-декодирования.

Вторая реализация — узкий автономный verifier на Python из стандартной библиотеки. Он имеет собственные parser и writer, использует `hashlib` для SHA-256 и не вызывает `json.dumps` для байтов профиля. Он не заменяет Swift-runtime: не исполняет `remember` и `compose`, не строит снимок и не публикует `CURRENT`.

Обе реализации читают один неизменяемый corpus. Он содержит 12 положительных векторов, 38 отказов и 2 известных вектора SHA-256 — всего 52 проверки. Положительная часть закрепляет булевы значения, границы целых, глубины и размера `remember`, Unicode и escapes, различие NFC/NFD, обычные `remember` и `compose`, полную программу, начальное и продолженное поколения, `CURRENT` и точные SHA-256. Отказы покрывают превышение глубины, ошибочный UTF-8, оба класса Unicode noncharacter, дубликаты после раскрытия escape, запрещённые имена и значения, а также неканонические событие и `CURRENT`.

В положительном векторе `input_base64` может быть неканоническим транспортом, который обе реализации приводят к закреплённому `canonical_base64`. Вектор `mode: "noncanonical"` проверяет строгий приём: канонизация возможна, но исходные байты отклоняются. `mode: "invalid"` требует отказа самой канонизации.

Проверяемый автономный вызов:

```bash
swift test \
  --package-path 'Прототипы/воспроизводимое-пополнение-памяти' \
  --filter CanonicalMemoryProtocolConformanceTests
```

Тест Swift сам запускает Python в isolated mode, сверяет оба результата с одним manifest и дополнительно доказывает, что Swift-runtime сам порождает точные байты обоих поколений и `CURRENT`. Вызов не требует сети, секретов или внешних пакетов.

## Границы гарантии

Побайтовое совпадение двух реализаций и golden vectors доказывают переносимость конкретного профиля и набора. Они не доказывают безошибочность любой будущей реализации, истинность содержания, подлинность автора, полную durability хранилища или перенос продуктовой семантики FUM на Python.
