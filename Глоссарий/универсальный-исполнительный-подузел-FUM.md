# Универсальный исполнительный подузел FUM

Универсальный исполнительный подузел FUM — долговечный дочерний [подузел FUM](подузел-FUM.md), сохраняющий общий профиль способностей родительского узла: чтение памяти, планирование, декомпозицию, работу с разрешёнными инструментами, проверку, сохранение результата и передачу. Универсальность описывает класс доступных способностей, но не означает равные с родителем полномочия, доступ, секреты или право на внешние эффекты.

Все целевые FUM-агенты проектируются универсальными в этом смысле. Их специализация является [контекстной ролью](контекстная-роль-FUM-агента.md) назначения, а не необратимым урезанием способностей или отдельным видом агента. Роль направляет текущую работу и критерии качества; доступ, бюджеты и эффекты остаются самостоятельными ограничениями. Потенциальная способность выполнить работу также не заменяет доказательство фактической компетентности для конкретного класса задач.

Корень управляет таким подузлом через версионированное конечное назначение. В нём указаны точный репозиторий и исходный commit, полный рабочий ref и полный целевой ref, упорядоченный список карточек, область записи, доступ, внешние эффекты, бюджеты, параллелизм, глубина рекурсии, проверки, остановка, возобновление, ревью и форма интеграции. Подузел может сужать эти границы, но не расширять их; дальнейшая делегация по умолчанию запрещена и требует отдельного конечного разрешения.

Назначение может охватывать цепочку шагов, однако каждый содержательный переход выполняется отдельным [пишущим подузлом FUM](пишущий-подузел-FUM.md) как один контекстно посильный рабочий пакет с собственным commit, паспортом и типизированным исходом. Долговечная линейная цепочка самостоятельного репозитория закрепляется за одним физическим живым клоном и точным полным рабочим ref: корень создаёт только начальную host-задачу, а каждый коммитящий владелец заранее создаёт ровно одно продолжение того же checkout и ref. Локальная `self_line` FUM-STEP-0148 следует той же причинной форме внутри переиспользуемого linked worktree `Подузлы/слот-*`: долговечный FIFO-билет сохраняет за продолжением те же слот, ref и worktree, CAS `commit+handoff` создаёт непосредственный однородительский commit и передаёт очередь, а новый владелец после `reload_required` перечитывает фактический `HEAD` и подтверждает exact OID. Merge-коммиты внутри производящей цепочки запрещены. Состояние и квитанции точного повтора и восстановления сохраняются в Git, чтобы следующий процесс мог продолжить работу без скрытой истории чата.

Перед локальным резервированием обычная сессия строит exact committed routing snapshot с OID плановых источников, активными линиями и состоянием их FIFO. Новая линия лениво получает свободный слот, продолжение входит в существующую линию, а read-only-маршрут не занимает писательский слот. Одновременно активные писатель, независимый рецензент и интегратор занимают разные worktree-слоты; последовательные владельцы одной линии разделяют один слот строго по одному. Object database, Git common-dir и refs остаются общими.

Терминальный commit линии замораживается под устойчивым локальным result-ref; наличие ожидающего продолжения запрещает заморозку, а слот освобождается только после терминала всей линии и доказанной чистоты. Результат автоматически проходит независимое агентское ревью, отдельную агентскую интеграцию и при необходимости автоматическое разрешение допустимого конфликта; итог обязательно повторно ревьюируется независимым агентом. Только принятый объект через обычную FIFO основной ветки и exact-CAS двигает локальный `master`. Все result-ref сохраняются и после публикационного аудита отправляются без force в настроенный remote с точным readback; заблокированный результат остаётся отдельным ref, а сетевой отказ означает `publication_pending`. GitHub fork и pull request не входят в этот локальный маршрут.

Документальный эталонный CLI требует exact repo-root и `worktree_id` назначенного слота для содержательных и терминальных команд. Он не доказывает host-level перенос или возобновление workspace Codex Desktop и отсутствие автоматических чтений основного checkout до первого инструмента, поэтому локальный профиль не называется нативной изоляцией. Долговечный отдельный fork-репозиторий ниже остаётся самостоятельным архитектурным профилем.

Долговечный дочерний репозиторий регистрируется в отдельной [репозиторной композиции FUM](репозиторная-композиция-FUM.md) как Git submodule на точном принятом commit. Материализованный submodule является чистым detached-снимком, а каждая линейная цепочка ведёт запись в одном отдельном живом клоне с собственной очередью и точным рабочим ref; целевой ref не меняется до корневого ревью и интеграции. Корень проверяет точную вершину и всю последовательность результатов в отдельном клоне вне веточного владения цепочкой; только принятую цепочку или явно выбранный точный префикс можно передать в сериализованную CAS-интеграцию и последующее обновление gitlink. Между принятием в дочерний целевой ref и обновлением gitlink допустимо только явно записанное и идемпотентно возобновляемое промежуточное состояние.

Отдельный fork-репозиторий материализует [дочернего fork-агента FUM](дочерний-fork-агент-FUM.md). Каждая эфемерная [сессия шага FUM](сессия-шага-FUM.md) исполняет только один шаг его назначения и не является устойчивой идентичностью самого подузла: начальную сессию создаёт корень, а каждую следующую — предыдущий коммитящий владелец ветки. Продолжение восстанавливается из фактического `HEAD`, Git, паспортов и артефактов, а не из скрытой истории чата.

При отдельном разрешении линейный [ветвевой fork](ветвевой-fork-FUM.md) такого подузла может породить два дочерних fork. Каждый ребёнок получает собственные ref, checkout и линейную цепочку продолжений, а тот же родительский логический узел освобождает прежнюю сессию и сохраняется как восстанавливаемый модератор. Универсальность сама по себе не разрешает развилку: нужны конечные глубина, коэффициент ветвления, бюджеты, полномочия и критерии сравнения.

Универсальный подузел не является автоматически независимым свидетельством. Общая модель, поставщик, исходные данные, системный шаблон или инструменты остаются наблюдаемыми группами корреляции, а корневое ревью само по себе не превращает коррелированный результат во внешнюю проверку.
