# План комплекта Swift для macOS arm64

Первый конечный срез [FUM-STEP-0220](../карточки-шагов/🟡-FUM-STEP-0220-спланировать-полную-зеркальную-сборку-Swift-toolchain.md) сохраняет выбранный профиль, полный список 49 репозиториев схемы, разбор зависимостей и будущую приёмку. **Комплект пока не замкнут и не допущен к сборке.** Неизвестные входы перечислены в манифесте; успешная проверка этого плана не меняет их статуса. Clone, сборка, установка и изменение окружения этим срезом не выполнялись.

- [Манифест](манифест.json): полные OID, оригиналы, проекты адресов зеркал, 81 связь, 18 дополнительных входов и SHA-256 исходных свидетельств.

Более слабая запись ≥5.5 в соседнем README не используется как допуск. GettingStarted требует нативные arm64 зависимости без Rosetta, а минимальный Xcode отсылает к изменяемому CI. Поэтому совместимость этого изменения host должна быть проверена отдельно. Swift 6.4 текущей среды и прежнее предложение Xcode 16.4/SDK 15.5 не являются выбранными входами.

## Полный preset

Манифест закрепляет **весь** upstream `utils/build-presets.ini`, а не выписку. Цепочка включает `mixin_buildbot_install_components_with_clang`, `mixin_osx_package_base`, `mixin_osx_package_test`, `mixin_lightweight_assertions,no-stdlib-asserts`, `buildbot_osx_package` и `mixin_osx_package,macos_only`.

Сохраняются release-debuginfo, Apple vendor, Swift/stdlib/overlays, LLVM/Clang/compiler-rt, LLDB, llbuild, SwiftPM, SwiftDriver, SwiftSyntax, Swift Testing и его macros, PlaygroundSupport, IndexStoreDB, SourceKit-LSP, SwiftFormat и DocC с renderer. Сохраняются embedded stdlib cross targets: они не означают включение чужого Apple SDK. `install-static-linux-config` устанавливает конфигурацию; сам Linux SDK этим не предоставляется.

Установочные компоненты Swift: autolink-driver, back-deployment, compiler, clang-resource-dir-symlink, libexec, stdlib, sdk-overlay, static-mirror-lib, toolchain-tools, license, sourcekit-xpc-service, swift-remote-mirror, headers. LLVM: llvm-ar, llvm-ranlib, llvm-cov, llvm-profdata, IndexStore, clang, clang-resource-headers, compiler-rt, clangd, dsymutil, LTO, clang-features-file, lld. Полный файл остаётся определяющим источником при расхождении с этим обзором.

Upstream `macos_only` отключает iOS/tvOS/watchOS, но оставляет xros. Дополнение явно отключает и xros; задаёт `host-target=macosx-arm64`, `stdlib-deployment-targets=macosx-arm64`, `infer-cross-compile-hosts-on-darwin=false`. Параметры LLDB фиксируют SWIG/Python/libedit/curses/libxml2 и отключают LZMA/Lua/libfbsdvmcore. Случайно обнаруженные сторонние библиотеки не входят в допустимый результат.

Встроенные test/validation/long/stress и проверка installable package сохраняются. Однако upstream отключает LLDB tests/configuration и PlaygroundSupport tests; SwiftPM на macOS выставляет `SWIFTCI_DISABLE_SDK_DEPENDENT_TESTS=YES`, исключая часть Functional/Commands/InternalSupport. Это известные пробелы покрытия, а не выполненные тесты. Отдельная приёмка установленных продуктов ниже обязательна. `skip-build-benchmarks` не отменяет `toolchain-benchmarks`, который использует установленный SwiftPM.

## Граница исходников и зеркал

49 записей — **вся схема** `release/6.1` выбранного update-checkout. Она шире активной native сборки: 14 исходных продуктов, 14 транзитивных package-зависимостей, Ninja, integration tests и готовый renderer; CMake отдельно задаёт происхождение инструмента; ещё 17 репозиториев сохраняются как резерв схемы. У каждого записаны роль и условие. Смена preset, платформы или переменных требует повторного разбора.

Все прямые и транзитивные SwiftPM связи выбранного локального режима выписаны в обосновании. `SWIFTCI_USE_LOCAL_DEPS=1`; `SWIFTPM_LLBUILD_FWK` и `SWIFT_DRIVER_LLBUILD_FWK` отсутствуют. У SwiftPM bootstrap две стадии: CMake-зависимости и `swift-bootstrap`, затем новый bootstrap собирает SwiftPM. TSC использует SwiftSystem через CMake, хотя root Package.swift не объявляет внешнего пакета. Macros Swift Testing используют собранный SwiftSyntax через CMake; standalone `601.0.0-latest` сюда не подставляется. Versioned manifests также проверены.

Standalone Package.resolved не смешиваются с этим режимом: например, DocC lock содержит другие версии Crypto/NIO. DocC plugin, llbuild-analyze, сетевые integration tests и Linux/WASI/corelibs сценарии не активированы. `have-network` для lit отсутствует. macOS Foundation/Dispatch/XCTest берутся из принятого Apple комплекта; source pins corelibs не заменяют его SDK.

Darwin Crypto использует SDK CryptoKit, но `_CryptoExtras`, нужный X509, включает vendored BoringSSL. Его OID `7ae2b910c13017b63f1a8bd6c8decfce692869b0` и fiat-crypto `6ccc6638716d4632304baf1adbb5c47c3a12ea6f` закреплены отдельно; фактические изменённые файлы воспроизводятся из контейнерного SwiftCrypto OID. Полная регенерация CryptOpt/Fiat ещё не замкнута и не назначена. Vendoring-скрипты с загрузкой HEAD не запускаются. В llbuild .gitmodules пуст, gitlinks отсутствуют; BLAKE3, protobuf, abseil, jsoncpp, utf8_range, SwiftProtobuf и googletest/mock являются обычными вложенными файлами. Их байты закрепляет OID llbuild; отсутствие отдельного происхождения каждого файла не скрывается вымышленным upstream OID.

Проект зеркал использует существующие [правила и инструменты Git-зависимостей](../../Зависимости/README.md): оригинал становится `upstream`, подтверждённый форк рядом с FUM — `origin`, checkout и gitlink с полным OID находятся в `Зависимости/комплект-Swift/<имя>`. Имена соседних каталогов сохраняют ожидания SwiftPM. Зеркала, gitlinks и полные Git-байты в этом срезе **не созданы**; адреса в JSON — проект, а не подтверждение существования. Для BoringSSL/Fiat, SWIG/PCRE2 и test Python источники перечислены отдельно; их будущие форки/поставка проходят те же проверки прав и байтов. Готовые закрытые Apple входы Git-зеркалами не становятся.

Текущий FUM имеет один gitlink LinguisticKit `837e2ce107b97ee7b9d3344c9fe99142281fe393`, локальные SwiftPM пути и системную зависимость приложения mpv. Они не подменяют closure Swift. Codex CLI относится к общему инвентарю инструментов; существующее fum-lab/codex не дублируется. Новые русские исходные формы Swift/SwiftSyntax относятся к отдельной будущей постановке.

## Лицензии и недостающие входы

Снимки сохраняют реальные LICENSE/NOTICE/COPYING/COPYRIGHT с SHA-256: корни репозиториев, применимые вложенные LLVM/llbuild/IndexStoreDB notices, Unicode, BoringSSL и Fiat. Для BoringSSL сохранены также декодированные байты ответа Gitiles. Корневая лицензия Swift не заменяет OpenSSL/SSLeay/ISC/MIT/BSD/GPL notices вложенных компонентов. `config.guess` имеет собственный GPL-текст с исключением. Наличие корневого LICENSE не означает, что уже проверено право каждого будущего бинарного пакета; инвентарь включённых файлов и notices повторяется при упаковке.

Обязательные препятствия:

1. **Нативный host.** Нужна приёмка выбранного полного профиля на arm64; исторический cross build её не заменяет.
2. **Xcode/SDK/bootstrap.** Нет законно предоставленного точного экземпляра, SHA-256, подписи, receipt, SDKSettings и исторической лицензии Xcode 16.2 RC. [Текущий Apple SLA](https://www.apple.com/legal/sla/docs/xcode.pdf), разделы 2.2/2.5/2.7, не даёт общего права публичного размещения Apple Software. Нужна проверка применимых условий именно предоставленного экземпляра. CC0 FUM, зеркало или torrent сами не создают такого права.
3. **Нативный bootstrap.** CMake binary, Bison и его skeleton/M4/runtime, Python installer либо source build backends и фактически исполненные shell/упаковочные средства ещё не замкнуты. SWIG CMake-путь требует PCRE2 и Bison; Autoconf/Automake нужны альтернативному пути и не добавляются скрыто. Предложенные PCRE2 flags и точные OID сохранены в отдельных входах. Wheel hashes не доказывают пересборку wheel из Git.
4. **DocC renderer.** `swift-docc-render-artifact` `ab1a5ac593c757cc2f2fb5106c643b7fb5ec61b2` содержит готовый `dist`; product helper не собирает его исходники. Нет проверенной связи с исходным commit, Node/npm lock и всеми licenses. Продукт остаётся в составе, переход к полностью источниковой поставке закрыт.
5. **Integration tests.** В полном дереве `54d66724e83231ce6a9d83d5f64a129121bc249f` отсутствуют LICENSE/NOTICE/COPYING/COPYRIGHT; соседняя Apache-лицензия не присваивается. Нужно установить права и notices выбранных файлов.
6. **Фактическое автономное замыкание.** Чтение manifests выявляет декларации; native configure/resolve/exec/linker/packaging с запретом сети и чужих кэшей ещё не исполнялись. Неизвестный узел либо фактический внешний вызов должны закрывать приёмку, а не получать допуск по умолчанию.

Это остаток существующего шага, без новой постановки VM/backend или установки. Выбранные версии отвечают вопросу о первом кандидате; минимальная Xcode, полнота нативного состава, источник renderer и разрешённая доставка SDK остаются вопросами с указанными свидетельствами закрытия.

## Будущие команды и последовательность

[Команды JSON](команды.json) разделяют аргументы и подстановки. Они являются планом; значения в угловых скобках ещё должны быть предоставлены и приняты. Нельзя исполнять их с выдуманными путями или считать текущее окружение соответствующим профилю.

1. В отдельном назначении проверить публикационную организацию, отсутствие дублей форков, права и точные OID. Материализовать все 49 записей штатным механизмом Git-зависимостей в новом собственном checkout. Сохранить полный список origin/upstream/gitlink/OID, dirty/untracked/submodule состояние и пригодные к автономной передаче Git-объекты. Системные и бинарные входы получают отдельные digest/лицензии; отсутствие любого активного входа закрывает переход.
2. На копии точного update-checkout-config заменить значения repos схемы на сохранённые OID, а адреса — на принятые зеркала. До и после update-checkout сравнить **весь** набор имён и OID с манифестом. Исходный config содержит52 определения при49 именах выбранной схемы; производный config должен явно оставить только эти49 определений `repos`, поскольку dump обходит весь этот словарь. Выход dump не содержит `default-branch-scheme`, поэтому при его повторном использовании обязателен явный `--scheme`. `--dump-hashes-config` выдаёт `branch-schemes[scheme].repos`; `skip`, отсутствующий/лишний репозиторий, короткий SHA и расхождение запрещены. CMake с upstream `platforms=[Linux]` материализуется явно для происхождения инструмента, не теряется из полного списка. Один `--tag` недостаточен: confirm_tag_in_repo способен вернуться к ordinary update. Не использовать `--clean` либо сброс произвольного состояния; публикация чужих refs не относится к сборке.
3. Подготовить законный бинарный набор и все объекты онлайн. Передать его существующему плану VM FUM-STEP-0216 и [плану автономного комплекта FUM-STEP-0221](../карточки-шагов/🟡-FUM-STEP-0221-спланировать-офлайн-комплект-FUM-и-приёмку-в-macOS-VM.md), когда их принятые OID/интерфейсы будут доступны. На момент этого среза они не подтверждены. Передача включает digest источников/образа/дисков и явно разрешённые пути; новый VM backend здесь не реализуется.
4. В чистом госте проверить architecture, version/build, bootstrap executable, SDKSettings, native helpers, Python imports и их `__file__`. SDKROOT/DEVELOPER_DIR/CMake paths задаются явно. Пользовательские кэши и HOME не используются как источник зависимостей; чистый HOME задаёт будущий runner без изменения пользовательского состояния. Сеть для автономной фазы запрещена; наблюдение всех subprocess и linker inputs сравнивается с конечным инвентарём.
5. Штатный build-script получает **два** `--preset-file`: полный закреплённый upstream и собственное дополнение. Это исключает неявное чтение пользовательского `.swift-build-presets`. В режиме `--preset` произвольные обычные build flags после имени не поддерживаются; host/LLDB overrides находятся в INI. Все одиннадцать подстановок install/Info.plist и две native-подстановки заданы в JSON. Дополнение хранит INI в файле .txt; --preset-file не требует расширения .ini. Bootstrap выбирается через DEVELOPER_DIR и darwin-xcrun-toolchain=default со сверкой xcrun realpath. Нельзя глобально подставлять CMAKE_Swift_COMPILER или native-swift-tools-path: они изменяют выбор компилятора последующих продуктов. Сам build-script запускается принятым Python; bare python3 в PATH должен разрешаться в него же. Сохранить эффективные аргументы и CMakeCache перед исполнением, проверить их совпадение с профилем. Ни upstream исходники, ни SDK этим не переписываются.
6. Собрать и установить в отдельный префикс, выполнить штатную и дополнительную приёмку. Сравнить после операции весь список 49 OID и чистоту исходников. Сохранить состав результата, digest, licenses и статус завершения. Штатный Git dependency checker проверяет уже подключённые gitlinks; новый runtime gate замыкания ещё должен быть реализован и испытан до этой операции.

## Приёмка установленного набора

Пути всех запускаемых программ разрешаются внутри нового `.xctoolchain`; одного PATH либо `--version` недостаточно. Сначала проверить realpath, Mach-O arm64, `swift --version`, `swiftc --version`, `swiftc -print-target-info`, SDK path/build, динамические зависимости и фактические compiler invocations. Bootstrap используется только там, где он прямо объявлен сборочным входом; результат проверяется своим компилятором.

| PlaygroundSupport и остальные install components | Адресный пример импорта/исполнения; сравнение полного install manifest с заявленным набором, back-deployment, headers, remote mirror, embedded modules                             |
| Штатные integration tests                        | package-path на новый префикс, без have-network; обязательные pexpect/ptyprocess/psutil доступны из принятой среды; пропуски из-за отсутствующих обязательных инструментов — отказ |
| Benchmark                                        | Новый `swift-build` и сохранённый Package.swift без внешних пакетов; требовать exit code и свежий результат, поскольку helper может не передать код дочернего сбоя                 |

lit integration helper способен использовать `xcrun lldb`, если LLDB отсутствует в пакете. Preflight обязан отклонить это состояние. Аналогично отсутствие pexpect пропускает REPL, а отсутствие psutil ослабляет тайм-аут; зелёный итог при таком пропуске не принимается. Отключённые upstream LLDB/PlaygroundSupport/SwiftPM группы указываются в отчёте отдельно от адресной приёмки.

## Отказы, повтор и измерения

Будущие отказные фикстуры: отсутствующий tag и переход к ordinary update; неправильный полный OID; пропуск любого узла/лицензии/SDK; повреждённые bytes/digest; попытка fetch; внешний package/plugin; чужой SDK/Swift/LLDB из PATH; Rosetta/x86_64 helper; пропуск REPL; недостаток места; прерывание на configure/build/install. Для каждого ожидается ненулевой результат, различимый незавершённый статус и отсутствие квитанции готовности. Возобновление читает исходные digest и состояние этапа, сохраняет предыдущий журнал и не объявляет частичный префикс установленным продуктом.

Сравнить чистую сборку с пустыми build/cache каталогами, повтор в том же окружении без изменений и отдельную чистую повторную сборку. Зафиксировать версии/hardware/CPU/RAM, число параллельных jobs, свободное и пиковое занятое место, elapsed/user/sys time, peak RSS, сетевые обращения, кэши и hits/misses. Время получения/передачи входов, ожидания окна, сборки, тестов и упаковки измеряются отдельно. Результаты сравниваются по install manifest, исходным OID и нормализованным воспроизводимым полям; timestamps, подписи и недетерминизм объясняются, а не удаляются молча. Числовые бюджеты назначаются после измерения принятого профиля. Сейчас время/RAM/диск сборки неизвестны: сборка не проводилась.

## Локальная проверка этого плана

Из корня FUM, в своей отчётной обёртке:

```text
python3 -B Планирование/сборка-Swift/контроль_манифеста.py --корень . --манифест Планирование/сборка-Swift/манифест.json --повторов 3
python3 -B -m unittest discover -s Планирование/сборка-Swift/проверки -p test_манифест.py
```

Проверяются точное покрытие схемы, уникальность полей/узлов, полные OID и их связь с сохранёнными refs, SHA-256 снимков/профиля, лицензия либо явное ограничение, обязательные входы и известные концы рёбер. Код 0 означает целостный **план с препятствиями**. Код 2 означает повреждение/неполноту контракта. `--требовать-готовность` всегда возвращает 2 для этой плановой схемы; валидатор не удостоверяет байты SDK, выполнение сборки, лицензии или полноту автоматически обнаруженного графа. Для закрытого runtime допуска нужен отдельный испытанный контракт, связанный с тем же манифестом. Тестовые исходники и профиль валидатора хранятся рядом с результатом.
