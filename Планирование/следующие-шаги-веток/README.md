# Следующие шаги веток

Этот каталог хранит по одному выбранному [следующему шагу ветки](../../Глоссарий/следующий-шаг-ветки.md) для каждой автоматически развиваемой именованной [ветки работы](../../Глоссарий/ветка-работы.md). Он отделяет исполняемый выбор от общего пула [предложений о следующих шагах](../предложения-о-следующих-шагах.md), где одновременно могут оставаться десятки актуальных кандидатов.

Идентичность задаётся полным `branch_ref` внутри записи, а не именем файла. Для активной ветки должно находиться ровно одно совпадение. Файл `README.md` служит только описанием формата и не участвует в выборе.

## Формат записи

Запись начинается с TOML-блока:

```toml
+++
schema_version = 1
branch_ref = "refs/heads/project/пример"
step_id = "project-example-first-step-v1"
status = "ready"
project_path = "Проекты/пример/README.md"
+++
```

После блока располагаются один заголовок первого уровня и обязательные разделы `Задача`, `Критерии завершения` и `Источники`. Критерии задаются отдельными пунктами списка. HTML-комментарии вне fenced-блоков в исполняемой записи запрещены, чтобы скрытый для человека текст не попадал в агентский prompt. `project_path` является нормализованным путём к существующему паспорту проекта относительно корня репозитория: для `master` он равен `README.md`, а для `project/<имя>` — `Проекты/<имя>/README.md`.

Допустимые статусы:

- `ready` — шаг разрешён к однократному автоматическому запуску;
- `paused` — запуск временно приостановлен осознанным решением;
- `blocked` — продолжение требует нового входа, полномочия или внешнего изменения;
- `done` — у ветки нет следующего исполняемого шага.

`step_id` — устойчивый технический идентификатор конкретной версии выбора. Содержательное изменение задачи, критериев или статуса требует проверить, должен ли измениться `step_id`; новый исполняемый шаг всегда получает новый идентификатор.

## Жизненный цикл

Пятиминутный диспетчер Codex сначала проверяет recent-снимок до 50 задач и ничего не создаёт, если видит другую активную задачу, неизвестное состояние или недоступный host. Затем локальная автоматизация [fum-branch-next-step](../../Инструменты/fum-branch-next-step/SKILL.md) повторно проверяет активный ref и `step_id`, атомарно резервирует пару в общем Git-каталоге и разрешает создать обычную задачу Codex в локальном проекте.

Созданная задача до записи повторяет проверку ожидаемых `branch_ref` и `step_id`, полностью читает точные `record_path` и `project_path` и соблюдает границы действий, доступа, публикации и проверки паспорта. После успешной работы она обязана в том же коммите:

- заменить запись новым шагом со свежим `step_id`; либо
- явно установить `paused`, `blocked` или `done` с объяснением в теле записи.

Прежний `step_id` автоматически повторно не запускается. Claim не имеет TTL: после аварии он снимается только по предварительно наблюдённому `lease_id` и только после внешнего подтверждения, что прежняя задача больше не исполняется.

Проверка списка задач и создание новой задачи не образуют единой транзакции. Сам список не сообщает общее число или полноту и потому не доказывает состояние более старых задач за пределами recent-снимка. Повторная инвентаризация после claim, веточный барьер и проверка идентичности внутри созданной задачи сужают окно гонки, но не обещают абсолютную глобальную блокировку между разными host или клонами.

## Создание проектной ветки

Для новой ветки `project/<имя>`:

1. Создать `Проекты/<имя>/README.md` с паспортом проекта.
2. Создать в этом каталоге отдельную запись с точным `refs/heads/project/<имя>`.
3. Выбрать один шаг, критерии завершения, источники и новый `step_id`.
4. Запустить `python3 Инструменты/fum-branch-next-step/scripts/branch-next-step.py validate --repo-root . --json`.
5. Закоммитить паспорт и запись до разрешения фонового запуска.
