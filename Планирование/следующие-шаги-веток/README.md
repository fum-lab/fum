# Следующие шаги веток

Этот каталог хранит по одному версионному набору кандидатов [следующего шага ветки](../../Глоссарий/следующий-шаг-ветки.md) для каждой автоматически развиваемой именованной [ветки работы](../../Глоссарий/ветка-работы.md). Веточная запись не копирует задачи и критерии карточек: она связывает готового и отложенных кандидатов с актуальными [карточками шагов](../карточки-шагов/README.md) по устойчивым `card_id` и закрепляет точный хэш содержания каждой из них.

Идентичность ветки задаётся полным `branch_ref` внутри записи, а не именем файла. Для активной ветки должно находиться ровно одно совпадение. Файл `README.md` описывает формат и не участвует в выборе.

## Формат веточного набора

Запись начинается с TOML-блока схемы `3`:

```toml
+++
schema_version = 3
branch_ref = "refs/heads/project/пример"
state = "open"
project_path = "Проекты/пример/README.md"

[[candidates]]
step_id = "project-example-fum-step-0042-ready-v1"
status = "ready"
card_id = "FUM-STEP-0042"
card_content_sha256 = "sha256:<64 шестнадцатеричных символа>"

[[candidates]]
step_id = "project-example-fum-step-0043-blocked-v1"
status = "blocked"
card_id = "FUM-STEP-0043"
card_content_sha256 = "sha256:<64 шестнадцатеричных символа>"
resume_condition = "Получен требуемый внешний вход."
+++
```

После блока располагается ровно один заголовок первого уровня. Разделы `Задача` и `Критерии завершения` запрещены: они принадлежат карточке. Другие поясняющие разделы разрешены. HTML-комментарии вне fenced-блоков запрещены, чтобы скрытый для человека текст не попадал в агентский prompt.

Верхнеуровневый блок имеет ровно ключи `schema_version`, `branch_ref`, `state`, `project_path` и `candidates`. `project_path` является нормализованным путём к существующему паспорту проекта относительно корня репозитория: для `master` он равен `README.md`, а для `project/<имя>` — `Проекты/<имя>/README.md`. Значение `state` равно `open`, пока набор содержит хотя бы одного актуального кандидата, и `done`, когда кандидатов не осталось. Для `done` обязателен явный `candidates = []`; `open` без кандидатов недопустим.

Каждый элемент `candidates` содержит ровно `step_id`, статус диспетчеризации, `card_id` и `card_content_sha256`; для `paused` и `blocked` к ним добавляется только `resume_condition`. Поле `card_content_sha256` вычисляется по полному UTF-8-содержанию карточки после удаления только конечного служебного блока `FUM-MD-RECENCY`, удаления конечных пробельных символов и добавления одного перевода строки. Все `card_id` и `step_id` внутри одного набора уникальны, а связанная карточка имеет статус `active`.

Допустимые статусы кандидата:

- `ready` — закреплённая актуальная карточка разрешена к однократному автоматическому запуску;
- `paused` — запуск актуальной карточки временно приостановлен осознанным решением;
- `blocked` — продолжение по актуальной карточке требует нового входа, полномочия или внешнего изменения.

В открытом наборе может быть не более одного кандидата `ready` и любое число кандидатов `paused` и `blocked`. Для каждого отложенного кандидата обязательно непустое `resume_condition`, а для `ready` это поле запрещено. Корректные отложенные кандидаты остаются видимыми в наборе, но не мешают запуску единственного `ready`; если готового кандидата нет, запись корректна, однако диспетчер ничего не запускает. Недопустимая, устаревшая или повреждённая запись любого кандидата закрывает весь набор по принципу fail-closed.

`step_id` — устойчивый технический идентификатор конкретной версии кандидатной записи и claim-fence диспетчера. Смена карточки, её содержательного хэша, статуса диспетчеризации или условия возобновления требует нового `step_id`. Переход `paused` или `blocked` в `ready` всегда оформляется новой версией кандидатной записи; само выполнение условия возобновления не разрешает запуск старого поколения.

## Жизненный цикл

Пятиминутный диспетчер Codex сначала проверяет recent-снимок до 50 задач. Если он видит другую активную задачу, неизвестное состояние или недоступный host, то не резервирует шаг, не ставит плановую работу в локальную очередь и ничего не создаёт. Только при наблюдаемом простое локальная автоматизация [fum-branch-next-step](../../Инструменты/fum-branch-next-step/SKILL.md) проверяет активный ref, весь набор кандидатов и единственную запись `ready`, затем атомарно резервирует пару `branch_ref` и `step_id` готового кандидата в общем Git-каталоге и разрешает создать обычную задачу Codex в локальном проекте.

Резервация хранится как JSON blob под служебной Git-ссылкой физического checkout и меняется compare-and-swap. Она не требует POSIX-блокировок или ручного переноса файлов прежней реализации; проигравший CAS-вызов не может заменить конкурентно опубликованный другой `step_id` без новой проверки.

Созданная задача первым действием регистрируется в общей [FIFO-очереди checkout](../../Инструменты/fum-ocheredj-zadach-git-vetki/SKILL.md) и до собственного допуска только ждёт. После `admitted` она повторно проверяет ожидаемые `branch_ref` и `step_id`, полностью читает возвращённые `record_path`, `card_path` и `project_path` и соблюдает границы действий, доступа, публикации и проверки паспорта.

После успешной работы задача в том же атомарном commit+handoff переводит выполненную карточку в исторический статус с разделом `Результат`, удаляет её кандидатную запись и затем:

- сохраняет остальных актуальных отложенных кандидатов и выбирает не более одной другой актуальной карточки как `ready`, закрепляя свежие `card_content_sha256` и `step_id`; либо
- сохраняет открытый набор без `ready`, если все оставшиеся кандидаты корректно приостановлены или заблокированы; либо
- устанавливает для ветки `done` с пустым набором кандидатов.

Прежний `step_id` автоматически повторно не запускается. Claim не имеет TTL: после аварии он снимается только по предварительно наблюдённому `lease_id` и после внешнего подтверждения, что прежняя задача больше не исполняется.

Проверка списка задач и создание новой задачи не образуют единой транзакции. Сам список не сообщает общее число или полноту и потому не доказывает состояние более старых задач за пределами recent-снимка. Повторная инвентаризация после claim, FIFO-очередь checkout и проверка идентичности внутри созданной задачи сужают окно гонки, но не обещают абсолютную глобальную блокировку между разными host или клонами.

## Создание проектной ветки

Для новой ветки `project/<имя>`:

1. Создать `Проекты/<имя>/README.md` с паспортом проекта.
2. Создать актуальную карточку шага и включить её в [индекс карточек](../карточки-шагов/README.md).
3. Создать в этом каталоге открытый набор с точным `refs/heads/project/<имя>`, одной записью `ready`, `card_id`, хэшем карточки и новым `step_id`.
4. Запустить `python3 Инструменты/fum-branch-next-step/scripts/branch-next-step.py validate --repo-root . --json`.
5. Закоммитить паспорт, карточку, индекс и веточный набор до разрешения фонового запуска.
