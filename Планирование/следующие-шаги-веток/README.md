# Следующие шаги веток

Этот каталог хранит версионные наборы кандидатов [следующего шага ветки](../../Глоссарий/следующий-шаг-ветки.md) для обычных именованных [веток работы](../../Глоссарий/ветка-работы.md) selector-driven профиля branch FIFO. Набор не копирует задачи и критерии карточек: он задаёт конечный whitelist `automatic`, `paused` и `blocked`, связывает кандидатов с [карточками шагов](../карточки-шагов/README.md) по `card_id` и закрепляет точный хэш содержания. Готовность вычисляет непосредственно допущенная [задача-продолжение](../../Глоссарий/обязательное-продолжение-ветки.md) из нового `HEAD`.

Идентичность ветки задаётся полным `branch_ref`, а не именем файла. Для текущей ветки профиля селектора должно находиться ровно одно совпадение. Runtime work-ref пула в пространстве `refs/heads/codex/подузлы/` не является такой веткой, не получает переносимую запись и продолжается по exact FIFO назначения. Файл `README.md` описывает формат и не участвует в выборе.

Если ветка реализует конечную цепочку, её upstream служит [карточка цепочки шагов](../карточки-цепочек-шагов/README.md). Селектор не создаёт и не переключает ветку; отдельный ограждённый переход выполняется только между корневыми задачами при пустой FIFO и чистой рабочей копии.

## Формат веточного набора

Запись начинается с TOML-блока схемы `5`:

```toml
+++
schema_version = 5
branch_ref = "refs/heads/project/пример"
state = "open"
project_path = "Проекты/пример/README.md"

[[candidates]]
step_id = "project-example-fum-step-0042-automatic-v1"
dispatch = "automatic"
card_id = "FUM-STEP-0042"
card_content_sha256 = "sha256:<64 шестнадцатеричных символа>"
requires_completed_card_ids = []

[[candidates]]
step_id = "project-example-fum-step-0043-blocked-v1"
dispatch = "blocked"
card_id = "FUM-STEP-0043"
card_content_sha256 = "sha256:<64 шестнадцатеричных символа>"
requires_completed_card_ids = ["FUM-STEP-0042"]
resume_condition = "Получен отдельно подтверждённый внешний вход."
+++
```

Верхнеуровневый блок имеет `schema_version`, `branch_ref`, `state`, `project_path` и `candidates`. `project_path` — нормализованный существующий путь внутри репозитория. `open` требует кандидатов, `done` — точный пустой массив.

Кандидат содержит `step_id`, `dispatch`, `card_id`, `card_content_sha256` и `requires_completed_card_ids`; `paused` и `blocked` дополнительно требуют `resume_condition`. Хэш вычисляется по содержанию карточки без конечного блока `FUM-MD-RECENCY`. Все идентификаторы уникальны, а целевая карточка актуальна.

`automatic` означает предварительную допустимость для прямого продолжения при выполненных ALL-of-зависимостях. Только literal-статус `completed` удовлетворяет зависимости. `paused` и `blocked` не открываются из свободного текста, времени, сети, среды, секрета или вывода модели. Повтор, self-edge, цикл, устаревший хэш или небезопасный ready-payload закрывают весь набор.

Изменение пути или хэша карточки, `dispatch`, зависимостей либо `resume_condition` требует нового `step_id`. Переход в `automatic` всегда выпускает новую версию. Смена только статуса зависимости меняет вычисленную `selection.id`, но не объявление.

## Жизненный цикл

После commit+handoff ребёнок перечитывает новый `HEAD`, получает FIFO-допуск и вызывает:

```bash
python3 Инструменты/fum-sleduyusjhij-shag-vetki/scripts/branch-next-step.py validate --repo-root . --json
python3 Инструменты/fum-sleduyusjhij-shag-vetki/scripts/branch-next-step.py show --repo-root . --json
```

`ready` даёт одну карточку. `done` и `not_ready` заканчиваются `finish-clean`; коммита и следующего ребёнка нет. Периодический heartbeat, диспетчерский реестр, host-инвентаризация, reservation и claim не участвуют.

После успешной работы тот же коммит переводит карточку в исторический статус, удаляет её поколение и сохраняет остальные кандидаты либо `done`. До этого коммита задача создаёт ровно одно следующее продолжение, подтверждает его ожидающий билет и передаёт идентификатор очереди. Следующая задача выбирает заново; прежняя `selection.id` не является полномочием.

Политика `dynamic-readiness-source-history-first-parent-v2` ранжирует только вычисленный ready-пул по не более чем 16 first-parent-коммитам и устойчивой паре `card_id`, `step_id`. Она не обходит зависимости, режимы, полномочия или безопасность.

Корневой `./sbrositj.sh` не меняет селектор и не запускает карточку. После человеческого сброса работу начинает отдельный явный запрос. Исторические claim- и dispatcher-refs не являются активной частью жизненного цикла.

## Создание проектной ветки

1. Создать паспорт проекта.
2. Создать актуальные карточки и обновить их индекс.
3. Создать набор с точным полным ref, свежими хэшами, поколениями и зависимостями.
4. Запустить `validate`.
5. Закоммитить паспорт, карточки и набор по обычному протоколу обязательного продолжения.
