# Следующие шаги веток

Этот каталог хранит по одному версионному набору кандидатов [следующего шага ветки](../../Глоссарий/следующий-шаг-ветки.md) для каждой автоматически развиваемой именованной [ветки работы](../../Глоссарий/ветка-работы.md). Веточная запись не копирует задачи и критерии карточек: она задаёт конечный whitelist автоматических, явно приостановленных и заблокированных кандидатов, связывает их с актуальными [карточками шагов](../карточки-шагов/README.md) по устойчивым `card_id` и закрепляет точный хэш содержания каждой из них. Готовность автоматических кандидатов вычисляется во время каждого автозапуска, а не хранится заранее.

Идентичность ветки задаётся полным `branch_ref` внутри записи, а не именем файла. Для активной ветки должно находиться ровно одно совпадение. Файл `README.md` описывает формат и не участвует в выборе.

## Формат веточного набора

Запись начинается с TOML-блока схемы `5`:

```toml
+++
schema_version = 5
branch_ref = "refs/heads/project/пример"
state = "open"
project_path = "Проекты/пример/README.md"

[[candidates]]
step_id = "project-example-fum-step-0042-automatic-v1"
dispatch = "automatic"
card_id = "FUM-STEP-0042"
card_content_sha256 = "sha256:<64 шестнадцатеричных символа>"
requires_completed_card_ids = []

[[candidates]]
step_id = "project-example-fum-step-0044-automatic-v1"
dispatch = "automatic"
card_id = "FUM-STEP-0044"
card_content_sha256 = "sha256:<64 шестнадцатеричных символа>"
requires_completed_card_ids = ["FUM-STEP-0042"]

[[candidates]]
step_id = "project-example-fum-step-0043-blocked-v1"
dispatch = "blocked"
card_id = "FUM-STEP-0043"
card_content_sha256 = "sha256:<64 шестнадцатеричных символа>"
requires_completed_card_ids = []
resume_condition = "Получен требуемый внешний вход."
+++
```

После блока располагается ровно один заголовок первого уровня. Разделы `Задача` и `Критерии завершения` запрещены: они принадлежат карточке. Другие поясняющие разделы разрешены. HTML-комментарии вне fenced-блоков запрещены, чтобы скрытый для человека текст не попадал в агентский prompt.

Верхнеуровневый блок имеет ровно ключи `schema_version`, `branch_ref`, `state`, `project_path` и `candidates`. `project_path` является нормализованным путём к существующему паспорту проекта относительно корня репозитория: для `master` он равен `README.md`, а для `project/<имя>` — `Проекты/<имя>/README.md`. Значение `state` равно `open`, пока набор содержит хотя бы одного актуального кандидата, и `done`, когда кандидатов не осталось. Для `done` обязателен явный `candidates = []`; `open` без кандидатов недопустим.

Каждый элемент `candidates` содержит ровно `step_id`, `dispatch`, `card_id`, `card_content_sha256` и `requires_completed_card_ids`; для явных `paused` и `blocked` к ним добавляется только `resume_condition`. Поле `card_content_sha256` вычисляется по полному UTF-8-содержанию карточки после удаления только конечного служебного блока `FUM-MD-RECENCY`, удаления конечных пробельных символов и добавления одного перевода строки. Все `card_id` и `step_id` внутри одного набора уникальны, а связанная целевая карточка имеет статус `active`.

Допустимые режимы `dispatch`:

- `automatic` — карточка предварительно признана безопасной, полномочной и контекстно посильной при выполнении перечисленных машинных зависимостей;
- `paused` — запуск актуальной карточки приостановлен из-за условия, которое автоматизация не может доказать;
- `blocked` — продолжение по актуальной карточке требует нового входа, полномочия или внешнего изменения.

В открытом наборе может быть любое число кандидатов каждого режима. Для `automatic` поле `resume_condition` запрещено. Его `requires_completed_card_ids` является точной ALL-of-зависимостью: пустой массив даёт runtime-`ready` без карточечных предпосылок, а непустой — только если каждая перечисленная карточка имеет literal-статус `completed`. Статусы `active`, `absorbed` и `withdrawn` условие не выполняют и дают вычисленный `paused`; они не подменяются смысловым сходством. Явные `paused` и `blocked` требуют непустого `resume_condition` и никогда автоматически не открываются. Свободный текст, ссылки, часы, сеть, среда, секреты и модельный вывод не интерпретируются как разрешение.

Все обязательные `card_id` должны существовать в каноническом реестре; повторы, self-edge и циклы закрывают весь набор как недействительный. Корректные неготовые кандидаты остаются видимыми, но не участвуют в ранжировании и не мешают независимому runtime-`ready`. Если готового кандидата нет, запись корректна, однако диспетчер ничего не запускает. Недопустимая, устаревшая или повреждённая запись любого кандидата, включая проигравший выбор, закрывает весь набор по принципу fail-closed.

`step_id` — устойчивый технический идентификатор конкретной версии кандидатной записи и claim-fence диспетчера. Смена карточки, её пути или содержательного хэша, `dispatch`, массива зависимостей либо условия возобновления требует нового `step_id`. Путь входит в создаваемый агентский prompt, поэтому даже чистое переименование карточки при неизменных `card_id` и хэше выпускает новое поколение кандидатной записи. Переход явного `paused` или `blocked` в `automatic` всегда оформляется новой версией кандидатной записи. Изменение только жизненного статуса обязательной карточки не меняет объявление и `step_id`, но обязательно меняет вычисленный статус и `selection.id`.

## Жизненный цикл

Рабочий набор следующего шага остаётся специализированным источником карточочной работы и подключён первым адаптером [диспетчера автоматизаций FUM](../../Глоссарий/диспетчер-автоматизаций-FUM.md). Канонический общий реестр содержит ровно одно активное задание `master.next-step` с точными checkout и `refs/heads/master`, но его схема не заменяет схему `5`, `step_id`, содержательный хэш, вычисление готовности, `selection` и claim: адаптер следующего шага вычисляет и выбирает готовую карточку на границе запуска, а общий слой отдельно закрепляет поколение самого задания.

Пятиминутный общий тик Codex сначала проверяет recent-снимок до 50 задач, валидирует реестр заданий и структурно проверяет рабочий набор с вычислением runtime-готовности, но без ранжирования. Если он видит другую активную задачу, неизвестное состояние или недоступный host, то не резервирует задание, не ставит плановую работу в локальную очередь и ничего не создаёт. Только после второй успешной host-инвентаризации общий слой выбирает `master.next-step`, а локальная автоматизация [fum-sleduyusjhij-shag-vetki](../../Инструменты/fum-sleduyusjhij-shag-vetki/SKILL.md) повторно вычисляет пул, выполняет `show`, выбирает один runtime-`ready` на точном текущем `HEAD` и выполняет специализированный `claim` точных `branch_ref`, `step_id` и `selection.id`.

Политика `dynamic-readiness-source-history-first-parent-v2` сначала воспроизводимо вычисляет ready-пул из всего whitelist, а затем рассматривает не более 16 first-parent-коммитов. Контекст каждого готового кандидата состоит только из дедуплицированных нормализованных локальных ссылок раздела `Источники`; механические управляющие пути и собственная карточка исключаются. Сначала предпочитается кандидат, чей источник — изменённая завершённая или поглощённая карточка, затем кандидат с точно изменённым иным источником; внутри класса учитываются меньшая дистанция, большее число совпавших путей и устойчивый порядок `card_id`, `step_id`. При отсутствии свидетельств действует этот устойчивый порядок. Ранжирование остаётся мягким: оно не может обойти вычисленную неготовность, явные `paused`/`blocked`, безопасность, полномочия, явный выбор пользователя или контекстную посильность.

`show` возвращает выбранную карточку и вложенный объект `selection` с `id`, `policy`, точным `head`, `ready_count` и свидетельством `reason`, `commit`, `distance`, `matched_paths`. Идентичность хэширует объявления и вычисленные статусы всех кандидатов, их незавершённые зависимости, точные пути, жизненные статусы и хэши обязательных карточек, готовый пул, победителя и ранжирование. Поэтому новый `HEAD`, изменение результата зависимости, состава пула, карточки или свидетельства выпускают новое поколение даже при том же победившем `step_id`.

Общая и карточочная резервации хранятся раздельно под служебными Git-ссылками физического checkout и меняются compare-and-swap. Один свежий канонический UUID используется как клиентская попытка общего запуска и `lease_id` специализированного claim. Claim получает `--expected-selection-id`, повторно вычисляет выбор и одной транзакцией проверяет точную вершину полного `branch_ref` вместе с CAS служебной ссылки. Точный повтор тех же `selection_id` и `lease_id` после потерянного ответа идемпотентно подтверждает собственную резервацию; другой UUID получает `already_claimed` без чужого lease, а в пределах одной ветки прежний UUID нельзя использовать для нового поколения выбора. После подтверждённого создания UUID передаётся задаче только как непубликуемый runtime-fence.

Созданная задача первым видимым сообщением один раз называет назначенную карточку по машинно проверенным `card_id` и заголовку и сообщает об ожидании допуска. Первым инструментальным действием она регистрируется в общей [FIFO-очереди checkout](../../Инструменты/fum-ocheredj-zadach-git-vetki/SKILL.md) и во время неизменного ожидания больше ничего не сообщает. После каждого `admitted` задача сначала выполняет общие `bind-run` и `verify-run`, связывая резервацию с фактическим корневым `CODEX_THREAD_ID` и проверяя точные `generation` и `base_head` владельца очереди; предварительный `clientThreadId` из создания задачи этого не заменяет. Затем карточочные `bind-run` и `verify-run` связывают claim схемы `2` с тем же `task_id`, проверяют ожидаемые `branch_ref`, `step_id`, `selection.id`, `selection.head` и переводят claim в подтверждённую схему `4`. Только успешная проверка обоих уровней разрешает один раз объявить карточку взятой в работу, полностью прочитать возвращённые `record_path`, `card_path` и `project_path` и соблюдать границы действий, доступа, публикации и проверки паспорта. Любой новый коммит меняет поколение выбора. При mismatch работа не начинается, а владелец очереди снимается через `finish-clean`.

При явном полном откате собственной реализации задача внутри того же допуска сначала дожидается всех поздних писателей и доказывает чистое состояние на исходном `selection.head`. Затем привязанная к запуску операция `rearm` до `finish-clean` атомарно сверяет точные `task_id`, `generation`, `base_head`, ветку и claim схемы `4`; повтор идемпотентен только для той же попытки. После успеха разрешён только немедленный `finish-clean`. Сбой в промежутке оставляет прежнего FIFO-владельца и блокирует следующий heartbeat до возобновления той же задачи, не создавая второго писателя; после handoff `rearm` и `release` запрещены.

Факт создания задачи не завершает общий запуск. Следующий тик сопоставляет фактический `task_id` с точным `last_completion` FIFO: совпавший `committed` подтверждает успех, а `finished_clean` считается безопасным отказом только после host-доказательства окончательной остановки возможного исполнителя и подтверждённого `released` либо `unclaimed` карточочного claim. Иной исход остаётся неоднозначным и не допускает дубликат.

После успешной работы задача в том же атомарном commit+handoff переводит выполненную карточку в исторический статус с разделом `Результат`, удаляет её кандидатную запись и затем:

- сохраняет остальных актуальных `automatic`, `paused` и `blocked` и добавляет в whitelist все независимо допустимые карточки, закрепляя свежие `card_content_sha256`, `step_id` и точные `requires_completed_card_ids`, но не вычисляя при коммите победителя; либо
- сохраняет открытый набор без runtime-`ready`, если все оставшиеся автоматические зависимости ещё не завершены либо кандидаты явно приостановлены или заблокированы; либо
- устанавливает для ветки `done` с пустым набором кандидатов.

Прежнее поколение выбора автоматически повторно не запускается. Каждое входное сообщение heartbeat начинает новую логическую попытку и не наследует из истории прежнего тика UUID или признак уже вызванного `create_thread`. Повтор claim разрешён только той же логической попытке и только до первого вызова `create_thread`; после него неоднозначный результат не разрешает повторно создавать задачу в текущем тике. Успешный `create_thread` прежнего тика не блокирует новый `selection.id`, если прежний запуск уже терминализирован по очереди. Claim не имеет TTL. Успешно созданная живая задача не вызывает `release`: связанный claim схемы `3` или `4` при полном откате освобождается только её собственным `rearm`. Привилегированный внешний `release` любой читаемой схемы предназначен только для восстановления после host-подтверждения окончательной остановки возможного исполнителя; непрозрачные значения lease и внутренних поколений этих операций не публикуются.

Перед обычным выбором новый последовательный тик проверяет, не осталось ли за той же прикреплённой задачей чистое владение FIFO от уже завершившегося пользовательского `Stop` или `Start`. После доказательства точной собственной идентичности в профиле `schemaVersion=2` узкая read-only-команда `heartbeat-status` возвращает только `idle`, `own_owner` или `busy`, не раскрывая диагностические поля и непрозрачные идентификаторы очереди. Первичный `idle` точно означает пустые owner и waiting и явно разрешает продолжение независимо от исторических `last_completion` и `next_seq`; `busy` закрывает тик. `own_owner`, в том числе при ожидающих последователях, разрешает ровно один `finish-own-clean`, который сам захватывает поколение и сохраняет проверки неизменного `HEAD`, чистоты, индекса и CAS; после передачи повторная проекция продолжает тик только при `idle`. UI-закрепление диспетчерской задачи проверяется при установке отдельно и не выводится из единого recent-массива. Эта операция не является TTL, передачей приоритета или восстановлением чужой задачи. Она выполняется до раннего выхода из-за другой наблюдаемой `active`-задачи, чтобы ожидающий последователь не мог одновременно быть причиной и вечным блокиратором освобождения.

Штатные `Stop` и `Start` всего heartbeat сохраняют его цель, prompt, пятиминутное расписание и историю и не освобождают общий запуск или карточочный claim уже созданной задачи. Пользовательский ход в той же прикреплённой задаче не наследует исключение планового тика и при мутации проходит обычный корневой FIFO-контракт.

Проверка списка задач и создание новой задачи не образуют единой транзакции. Сам список не сообщает общее число или полноту и потому не доказывает состояние более старых задач за пределами recent-снимка. Повторная инвентаризация непосредственно перед claim, FIFO-очередь checkout и проверка идентичности внутри созданной задачи сужают окно гонки, но не обещают абсолютную глобальную блокировку между разными host или клонами.

## Создание проектной ветки

Для новой ветки `project/<имя>`:

1. Создать `Проекты/<имя>/README.md` с паспортом проекта.
2. Создать актуальную карточку шага и включить её в [индекс карточек](../карточки-шагов/README.md).
3. Создать в этом каталоге открытый набор с точным `refs/heads/project/<имя>` и одной или несколькими индивидуально допустимыми записями `automatic`, точными `requires_completed_card_ids`, `card_id`, хэшами карточек и новыми `step_id`.
4. Запустить `python3 Инструменты/fum-sleduyusjhij-shag-vetki/scripts/branch-next-step.py validate --repo-root . --json`.
5. Закоммитить паспорт, карточку, индекс и веточный набор до разрешения фонового запуска.
