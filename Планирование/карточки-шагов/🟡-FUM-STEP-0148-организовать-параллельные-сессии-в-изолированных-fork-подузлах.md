# Организовать параллельные сессии в изолированных fork-подузлах

[Карточка шага](../../Глоссарий/карточка-шага.md) сохраняет назначенный пользователем высший следующий приоритет отдельно от текущей завершительной сессии.

## Задача

Организовать действующий корневой контур так, чтобы каждая одновременно активная пишущая Codex-сессия получала отдельный зарегистрированный ветвевой fork FUM: собственную пару репозитория и полного рабочего ref, отдельный живой checkout, branch-scoped FIFO и линейное обязательное продолжение. Родитель закрепляет общую базу и назначения, активирует совместимые линии только после предактивационного барьера, а результаты возвращаются через проверяемый fork-маршрут — публикационно чистую ветку, push, pull request, отдельное ревью и ограждённую интеграцию — без совместной записи в один checkout или ref.

## Почему сейчас

Пользователь явно назначил эту работу наивысшим приоритетом сразу после текущего commit и разрешил создание fork, push веток и необходимых pull request. Общий checkout и ref вынуждают независимые сессии ждать одну FIFO и мешают безопасной параллельной работе. Локальные контракты универсального fork-подузла, дерева fork, host-привязок, ресурсного допуска, корневого ревью и интеграции уже созданы, но живой организационный маршрут отдельной сессии через собственный fork ещё не замкнут.

## Критерии завершения

- Каждая одновременно активная пишущая корневая или дочерняя Codex-сессия однозначно связана с отдельными идентичностью fork-подузла, репозиторием, полным рабочим ref, checkout, FIFO и поколением; две активные сессии не пишут в один checkout или ref.
- Корневая задача до активации ребёнка закрепляет точные исходную вершину, проект, роль, карточку или конечную цепочку, разрешённые пути и эффекты, целевой маршрут результата и проверяемую границу полномочий.
- Создание fork, ветки, checkout и задачи идемпотентно восстанавливается после потерянного ответа; неоднозначный host-, Git- или provider-исход закрывает активацию без второго создания и без совместного писателя.
- Предактивационный барьер допускает ребёнка только после подтверждения всех Git- и host-привязок; конфликтующие назначения сериализуются, а совместимые назначения действительно работают параллельно в независимых checkout.
- Каждый fork-подузел использует собственную branch-scoped FIFO и обязательное линейное продолжение; передача внутри fork не двигает исходную или целевую ветку и не наследует полномочия другой сессии.
- Публикационный маршрут создаёт публикационно чистую ветку, выполняет push и создаёт pull request с точными base/head, полными refs, поколением, паспортами и авторитетным readback без дубликата; пользовательское разрешение внешних эффектов не расширяется на секреты, расходы, иные репозитории или данные.
- Результат интегрируется только через корневое ревью и ограждённый fork-механизм: сдвиг base/head, цели, паспорта, критерия или поколения аннулирует принятие, а проигранный CAS не переписывает конкурентный результат.
- Принятый полный диапазон или точный префикс сохраняет все дочерние commit в происхождении; не принятое продолжение и дочерние refs не удаляются и не сворачиваются в одиночный коммит.
- Автономная приёмка поднимает не менее двух параллельных сессий в разных fork-подузлах, доказывает отсутствие взаимного вмешательства и интегрирует оба совместимых результата через проверяемые pull request и ревью; отрицательные сценарии покрывают общий checkout/ref, stale base/head, потерянные ответы и конфликт интеграции.
- Живой opt-in-прогон использует только явно разрешённые пользователем fork, push и pull request, сохраняет их точные URL и refs в отчёте и не объявляет успех до авторитетного readback и принятой интеграции.
- Правила рабочей сессии, очередь, веточный selector, дорожная карта, реестр планирования, документация универсальных подузлов и локальные проверки согласованно закрепляют новый маршрут; после завершения шага временно ожидающие кандидаты `master` снова вычисляются из нового `HEAD`.

## Граница результата

Карточка разрешает в своём будущем исполнении только необходимые для заявленного маршрута создание fork, push веток и pull request. Конкретные владельцы, удалённые URL, уровни доступа и состав публикуемых данных должны быть заново подтверждены preflight из фактического `HEAD`; новые секреты, платные сервисы, раскрытие пользовательских данных и несвязанные внешние эффекты из этого разрешения не следуют.
