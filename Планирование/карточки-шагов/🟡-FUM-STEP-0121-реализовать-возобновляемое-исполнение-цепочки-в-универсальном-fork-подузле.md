# Реализовать возобновляемое исполнение цепочки в универсальном fork-подузле

[Карточка шага](../../Глоссарий/карточка-шага.md) сохраняет один атомарный плановый шаг и его происхождение отдельно от веточного выбора.

## Задача

Расширить локальный runtime от одного заранее подготовленного пишущего пакета до линейной конечной цепочки в одном универсальном fork-подузле. Вся цепочка должна использовать один физический живой checkout и точный полный рабочий ref: корень создаёт только начальную host-задачу, каждый допущенный владелец выполняет один шаг с собственными проверками и перед осмысленным commit создаёт ровно одно продолжение того же checkout и ref, а `commit+handoff` атомарно продвигает ветку и строгую FIFO. Отдельные проверяющая и интеграционная задачи подключаются только после готовности диапазона и не владеют веткой между последовательными шагами. Готовый диапазон материализует точный локальный пакет передачи для заранее объявленного маршрута и только отмечает маршрут общего вклада fork — core без создания pull request.

Среда выполнения этой карточки намеренно остаётся линейной внутри одного [ветвевого fork FUM](../../Глоссарий/ветвевой-fork-FUM.md). Порождение двух дочерних fork и последующая модерация являются отдельными переходами, запланированными карточкой FUM-STEP-0145, и не изменяют правило одного продолжения на коммит.

## Почему сейчас

Существующий исполнитель создаёт ровно один commit от базы и не умеет передавать проверяемый диапазон. Дочерний runtime одного репозитория должен быть доказан до распределения цепочек по нескольким подузлам.

## Критерии завершения

- Детерминированный автономный адаптер выполняет не менее двух зависимых карточек без сети и живой модели в одном физическом живом checkout и на одном точном полном рабочем ref; отдельные клон и временный ref для последовательного шага не создаются.
- Каждый шаг имеет отдельную host-идентичность и сессию: корень создаёт только начальную задачу, а каждый следующий процесс появляется как заранее созданное продолжение коммитящего владельца, после допуска перечитывает фактический `HEAD` и восстанавливает работу без истории прежнего чата; сессия не становится устойчивой идентичностью fork-агента.
- Рабочий ref цепочки и целевой ref интеграции полны и различны, а продолжение обязано совпасть с владельцем по физическому checkout и точному рабочему ref; одноразовый клон и временный ref сохраняются только для независимого параллельного кандидата вне этой цепочки.
- Каждый шаг имеет отдельные пакет, commit или отрицательный исход, проверки и расход бюджета; состояние не перескакивает через незавершённую зависимость.
- Единый `commit+handoff` после машинного подтверждения ровно одного ожидающего продолжения продвигает рабочий ref только на непосредственного потомка прежней вершины и передаёт строгую FIFO без обхода более ранних билетов; отдельного интегратора шага нет, merge-коммиты внутри цепочки запрещены, поэтому диапазон от базы до вершины полный и линейный.
- Новый процесс восстанавливает точный следующий шаг, остаток бюджета и рабочую вершину только из фактического дочернего `HEAD`, Git-refs, машиночитаемых паспортов и прямого веточного selector.
- Адаптер живого контура строит доверенный контекст FUM-STEP-0120 из фактических карточек, Git/FIFO-допусков, снимка очереди, связанных commit-квитанций и `finish-clean`, затем исполняет обе закрытые схемы и семантический валидатор; сам паспорт не считается источником собственной авторитетности.
- Остановка после любого подготовленного перехода не создаёт двойного commit или второй задачи-продолжения; неоднозначный ответ создания запрещает commit и автоматический повтор, точный повтор уже подтверждённого `commit+handoff` восстанавливается идемпотентно, а изменённый запрос конфликтует.
- Суммарный паспорт подтверждает порядок всех commit, суммарный diff и отсутствие незаявленного расширения области.
- После готовности диапазона воспроизводимый пакет закрепляет точные базу, вершину и полный диапазон, но не двигает целевой ref и не объявляет цепочку принятой; отдельные ревью и интеграция выполняются вне последовательного владения рабочей веткой, а для общего вклада в core пакет лишь сохраняет точный признак будущего маршрута pull request.
