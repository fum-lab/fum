# Обновить README и реализовать его срез актуальности

## Задача

Обновить корневой README и реализовать первый исполняемый срез [проверяемой актуальности его пользовательских маршрутов](../../Требования/🟡-проверяемая-актуальность-маршрутов-README.md) на основе существующего [FUM-STEP-0165](🟡-FUM-STEP-0165-собирать-рабочий-контекст-задачи.md). Итог — короткая текущая инструкция и воспроизводимый вычисляемый JSON-сигнал потребности её обновления. Это поручение отдельной реализации, а не только последующего планирования.

Позднее поручение добавляет второе определение того же механизма — потребность интеграции веток. Оно исполняется тем же общим AutomationExecutor и не заменяет исходный README-сценарий.

## Почему сейчас

Человек прямо поручил обновить README, создать ощущение необходимости его обновления и реализовать с проверкой функциональную часть механизма. В текущей базе README не ведёт к сохранённым исходникам FUMA. Общая модель внимания, ДЕТЕКТОР-02 и сценарии зависимого устаревания уже спланированы; отсутствует исполняемая связь именно с актуальностью этой инструкции.

## Критерии завершения

- Сохранён полный первоначальный README-контракт и реализовано второе определение потребности интеграции по конечному контракту ниже; продемонстрированы раздельные ancestry/приёмка, прямой A/B на одних фактах и все отрицательные границы. Исходные v1 и регрессии проходят без подмены семантики.

- Выполнен конечный операторный контракт ниже: один общий бинарник, один наблюдаемый вход и два определения с разной целью дают доказанно разные результаты и трассы; generic-код не содержит специального оператора README, прежний v1 сохранён.

- Корневой README объясняет начало работы, обычный запрос, наблюдаемый результат, проверку, уточнение, продолжение и остановку. Сохранены ровно один `## Как использовать FUM сейчас`, прямая `Документация/README.md`, понятная прямая ссылка к `Приложения/FUMA/README.md` и предел 12 000 Unicode-символов с recency.
- README правдиво различает проверенные сборки, четыре самостоятельных пакета, ещё не подключённых к приложению, установщики с кодом 2 и недоказанные установленный переносимый `.app` и живые сенсоры. Свежие доказательства могут уточнить эти границы; ожидание не выдаётся за результат. Повторный перенос всех восьми пакетов не входит в работу.
- В монорепозитории сохранены исходники ограниченного сборщика/детектора, версионированная схема, конечные входы, открытые фикстуры, CLI и инструкции воспроизведения из чистого клона с объявленными зависимостями. Результат получается без скрытого API и без чтения частных данных по умолчанию.
- Вход явно задаёт одну задачу, один корневой README с версией, конечный набор наблюдаемых маршрутов, зависимости и версии оснований, время оценки и версию детектора. Выход фиксирует схему, причину, доказательства, неизвестность, состояние рассмотрения и подтверждение устранения. Допустимые состояния, переходы и критерии сброса конечны и документированы до проверки.
- Функциональный цикл проверяется целиком: наблюдение → значимость → внимание → выбор действия → проверка результата → изменение состояния. Потребность сохраняется до подтверждённого устранения расхождения относительно текущих оснований README. Просмотр и рассмотрение не снимают её и не дают новых полномочий; недоступный источник не превращается в состояние «всё актуально».
- Переиспользуются [ДЕТЕКТОР-02](../рабочий-контекст-задачи/детекторы.json), [КОНТЕКСТ-02–04](../рабочий-контекст-задачи/сценарии-приёмки.json) и [модель внимания](../рабочий-контекст-задачи/модель-внимания.md). Адаптеры 0177/0160 подключаются лишь при необходимости и по действительным контрактам; отсутствующий адаптер не выдумывается. Экранный attention/MCP допустим как представление готового сигнала, но не требуется для минимального CLI-среза.
- TDD сначала фиксирует независимые ожидаемые результаты: изменившийся значимый маршрут удерживает сигнал после просмотра и рассмотрения; подтверждённое исправление на текущих версиях снимает его; изменение постороннего источника не создаёт тревогу; недоступность сохраняется; старое подтверждение после новой версии недействительно; повтор и восстановление на тех же входах воспроизводимы. Сохраняются реальные RED/GREEN и измеряемый профиль на открытых сопоставимых входах.
- Существующие check-readme-index и recency используются по их фактическому назначению. Recency/hash сами не оценивают смысл; README не переписывается на каждый коммит. Итог объясняет стоимость чтения и вычисления, границы неизвестности и остаток 0165. Произвольный процент эффективности не назначается.

## Конечный контракт операторного среза

Первый минимальный проверяемый случай — прямая ссылка корневого README на принятый Приложения/FUMA/README.md. Адаптер извлекает реальные ссылки с привязкой к байтам README, OID/хэши выбранных источников, доступность, прежнее состояние и обратную связь; он не вычисляет заранее нужноОбновить, значимость или устранено. Значимость, удержание внимания и выбор следующего действия строятся на определении графа структурирующих операторов. Общий исполнитель 0208 получает ровно необходимые ограниченные структурированные вход/выход и общие операции сопоставления полей/вхождения в конечный список. Селекторы, условия, необходимые связи происхождения и исходы задаёт определение. Допустим конечный граф вход → сопоставление → результат без циклов и общего планировщика. В общем коде нет специального оператора README.

Доказанное отсутствие обязательной ссылки даёт расхождение. Изменение hash источника даёт повод пересмотреть, но не доказывает смысловое устаревание. Недоступность, нарушенная привязка или устаревший срез дают unknown; прежнее состояние при unknown не исчезает. Рассмотрено не означает устранено; снятие потребности требует проверенного нового свидетельства относительно текущих оснований.

Обязательный независимый тест прямо вызывает AutomationExecutor.выполнить с одним входом и тем же бинарником: определение А требует отсутствующую ссылку, Б отличается только целью и требует присутствующую. Различаются результат, хэш определения и трасса. Повреждение происхождения даёт unknown обоим определениям. considered при сохраняющемся расхождении не даёт resolved. Расширение имеет явную новую версию; прежние определения, наблюдения, поведение v1 и регрессии сохраняются. Полный язык графов, Metal и автономная фабрика не входят в этот срез.

Точные опоры: [контракт 0208](../../Прототипы/память-структурирующих-операторов/конечное-исполнение.md), [общий исполнитель](../../Прототипы/память-структурирующих-операторов/Sources/FUMStructuringOperatorMemory/ИсполнениеОператоров.swift) и [исходные тесты](../../Прототипы/память-структурирующих-операторов/Tests/FUMStructuringOperatorMemoryTests/ПроверкиЧистогоИсполнения.swift).

## Граница реализации и передачи

Достаточен конечный CLI-срез с двумя декларативными определениями, реальным README, исходниками, фикстурами, проверками и профилем. Полная реализация 0165, универсальный движок эмоций и доказательство субъективного переживания не заявляются. Новый постоянный запуск и внешние действия требуют самостоятельного основания.

Будущий исполнитель до первой записи штатно подтверждает точный коммит постановки в собственной native-задаче. Тяжёлое проверочное окно заранее согласуется с координатором; TDD и профиль ведутся через действующую отчётную обёртку. Текущий этап сохраняет лишь постановку и не выполняет native.

## Второе определение: потребность интеграции

Один общий AutomationExecutor с явной новой версией ограниченного расширения исполняет два декларативных определения: актуальность README и потребность в интеграции веток. Прежний v1, исходные определения, наблюдения и регрессии сохраняются. README-контракт, реальные ссылки с байтовой привязкой и прямой A/B-тест первого определения сохраняются полностью. Селекторы, условия, необходимые связи происхождения и исходы задаёт определение; адаптеры только извлекают факты. Общий исполнитель не получает специальных операторов README или «нужно интегрировать».

Вход второго определения содержит идентичность репозитория; точные исходные commit/tree; выбранную стадию маршрута через ведущую ветку fuma к master и её основание; точный наблюдённый target OID; ancestry и полноту истории; свидетельство приёмки с report/schema/commit и источником проверяющего; прежний сигнал, факт рассмотрения, квитанцию интеграции либо подтверждённую отмену. Наблюдённый target HEAD является версией свидетельства, а не новой идентичностью сигнала при каждом коммите. Идентичность области связывает репозиторий, исходную поставку и выбранную стадию маршрута. Стадия master принимает результат стадии fuma, а не перепрыгивает с исходной боковой ветки.

Конечные исходы второго определения:

- Проверенная поставка ещё не включена в выбранную цель — потребность интегрировать в этой области.
- Имеется только checkpoint либо предметная постановка — разобрать недостающий допуск, без утверждения готовности интеграции.
- Исходный commit уже ancestor цели, но подходящей квитанции нет — разобрать подтверждение включения; повторное слияние того же ancestor не предлагается.
- Вход отсутствует, имеет неподдержанную схему, противоречие, нарушенную связь OID либо неполную историю — unknown. Прежняя активная причина не стирается.
- Commit включён и квитанция интеграции совпадает с исходной поставкой, её приёмкой и выбранной областью — потребность снимается только в этой области.
- Подтверждённая отмена делает потребность неприменимой. Отметка considered сама по себе не означает resolved.

Ancestry не доказывает сохранность результата после revert. Утрата результата требует отдельного разбора, а не предложения повторно слить уже включённый ancestor. Статус приёмки не берётся из произвольной строки ready: связываются точные версии схемы, неизменяемые исходные файлы и хэши, результат проверяющего и его область. Первый срез явно поддерживает наблюдённый формат закрытого v3/report-v2; неподдержанный v4 не принимается по аналогии.

Независимые фикстуры включают чужую квитанцию и чужой OID, неполную историю, неподдержанный v4, ancestor без квитанции, подтверждённое включение, considered при сохранённой причине, отмену, revert и запрет перескока сразу в master. Прямой A/B-тест вызывает тот же AutomationExecutor.выполнить на одном входе и том же бинарнике: два определения отличаются только выбранной целью и дают разные result/hash/trace. При повреждении происхождения оба дают unknown с сохранением прежнего активного состояния.

Демонстрация читает фиксированные реальные Git-объекты и их существующие свидетельства; приёмка и ancestry показываются отдельно. Ни детектор, ни его пример не выполняют merge, push, запуск задач, выдачу новых полномочий или запись обработки 0177. Выбор действия является вычисленным предложением, а его исполнение требует самостоятельного разрешения. Полный язык графов, Metal, автономная фабрика, разбор шрифтов, сборка Swift/LLVM/Clang и зеркалирование зависимостей не входят в этот конечный срез.

## Настраиваемая чувствительность двух определений

Один общий исполнитель и два декларативных определения сохраняются. Чувствительность оценки задаётся настраиваемыми весами входных сигналов и порогами срабатывания. Параметры имеют явную версию, проверяемый хэш и конечную поддержанную область значений; они передаются как данные определения, а не прячутся в адаптере. Результат и трасса различают версии и хэши определения, параметров и фактических источников. Для каждого входного сигнала объясняются наблюдённое значение, применённый вес, вклад в оценку и связь с порогом; обязательное условие отдельно видно как обязательное, а не как произвольный численный вклад.

Веса регулируют чувствительность и приоритет рассмотрения, сохраняя доказанность фактов. Отсутствующая обязательная ссылка README остаётся расхождением, даже если её вес снижен. Нулевой вес не маскирует недоступность, нарушенное происхождение, устаревший срез, отсутствие обязательной приёмки либо иной обязательный неизвестный факт и не превращает unknown в успешный, разрешённый или устранённый исход. Рассмотрение и unknown не стирают прежнюю подтверждённую активную причину. Смена параметров сама по себе не является свидетельством устранения; снятие по-прежнему требует проверенного текущего основания соответствующего определения либо предусмотренной подтверждённой отмены.

Приёмка чувствительности включает прямые вызовы того же AutomationExecutor.выполнить на одинаковых фактах, одном бинарнике и неизменном определении с наборами параметров А и Б: различаются чувствительность, хэш параметров и объяснимая трасса. Для каждого из двух определений сохраняется хотя бы один такой воспроизводимый случай. Проверяются нулевой вес обязательного неизвестного факта, considered при сохраняющемся расхождении и смена порога при прежней активной причине: они не дают resolved. Недопустимые, отсутствующие либо неподдержанные обязательные параметры дают явный неуспешный исход по объявленному контракту, без молчаливого успешного значения по умолчанию.

Это дополнение входит в прежний конечный срез реализации с TDD, отдельными RED/GREEN, профилем и открытыми фикстурами. Оно не вводит третье определение, отдельный движок эмоций, субъективное переживание либо новые внешние полномочия. Прежний v1, оба A/B-теста смены определения, реальные маршруты README, стадии интеграции и все исходные отрицательные сценарии сохраняются.
