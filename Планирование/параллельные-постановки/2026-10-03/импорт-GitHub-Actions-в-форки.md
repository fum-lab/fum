## Первый проверяемый результат

Автоматизация в `Инструменты/fum-import-github-actions-v-forki/` по структурированному входу наблюдает состояние, строит сухой план, применяет объявленный набор workflows и разрешённых настроек к одному явно указанному доступному форку, затем подтверждает результат чтением. Тот же контракт проходит по списку форков с отдельным результатом каждого. Недоступный форк сохраняет отказ/неизвестность; он не получает фиктивный успешный статус.

Вход связывает repository ID и parent, точный upstream OID, манифест путей/SHA workflows, поддержанные настройки и локальные исключения. Унаследованные Git-файлы, серверное разрешение Actions, состояние отдельного workflow и успешный запуск CI — разные наблюдения. В исходном H `a990e2bf41d4a58075b9f048e9bd3786506e846a` `.github/workflows` нет; сначала нужен честно ограниченный канонический набор и проверенный API-контракт. Нельзя импортировать несуществующую конфигурацию и объявить её готовой.

Первый профиль CI использует воспроизводимую адресную проверку без выдуманного Codex UUID и не объявляется полной приёмкой постоянной сессии. Настройка macOS/Linux/Windows использует существующие платформенные постановки 0179–0181. Канонический workflow поставляется по фиксированным байтам и закреплённым зависимостям; пользовательские workflows не удаляются и не перезаписываются незаметно.

## План, применение и повтор

До изменений сохранить исходное состояние, diff и происхождение всех входов. Дрейф между планом и применением прекращает установку. Частичное применение или неизвестный сетевой исход требует адресного readback; повтор сопоставляет наблюдённое состояние с прежним намерением, не создаёт лишних коммитов и запросов. Реальные права и действующие официальные API GitHub проверяются отдельно от открытых фикстур.

Первый срез не переносит секреты, credentials, environments, runners и branch protection. Каждая дополнительная политика имеет собственный контракт и явный допуск. Внешние изменения в произвольных чужих форках не выдаются за разрешённые лишь по факту их принадлежности сети FUM. Подготовленный общий механизм остаётся применимым владельцем каждого форка.

RED/GREEN: пустой план при совпадении; отсутствующий файл; локальный конфликт; выключенный workflow при наличии файла; несовпадающий repository/parent; дрейф; частичный/неизвестный исход; повтор и readback. Измерить число API-вызовов, объём и время планирования/применения; сравнить с наблюдённой ручной последовательностью. Тестовые ответы не объявляются живой поставкой на GitHub.

## Хранение и восстановление

Полный восстанавливаемый комплект конфигурации хранится обычными отслеживаемыми файлами в памяти постоянной `fuma`: точные байты workflows, версионированное желаемое состояние поддержанных серверных настроек, исключения каждого форка и происхождение. Приватный операционный план и текущая конфигурация GitHub не заменяют этот комплект. Перенос на новую машину и восстановление форка не зависят от исходной сессии Codex.

Автоматизация восстанавливает или переустанавливает объявленный комплект из сохранённого состояния: наблюдение → сухой diff → применение в подтверждённой области → readback → повтор без изменений. Проверяемые сценарии: пустой доступный форк, частичная конфигурация, повреждённый или устаревший комплект, локальное исключение, дрейф и неизвестный исход. Откат и изменение версии имеют явные сохранённые входы, не выводятся из догадки. Секреты в публичный комплект не входят; сохраняются их необходимые имена и границы настройки, значения предоставляются отдельным приватным механизмом. Это уточнение существующего FUM-STEP-0178, а не создание второго направления; реализация и живая установка пока не подтверждены.
