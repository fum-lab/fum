## Принятая основа

Писатель одного expected принят ограниченной контрольной точкой PR237: слияние 4962e784f77800d5ff83dc3b9cb905b8c9a96df1. Хранение полных наблюдений, восстановление каталога новым процессом и чтение без API уже проверены. Принятый механизм не реализуется повторно.

## Назначение первого испытания

Принятая целевая схема постоянной ветки состояния — `<владелец>/<репозиторий>`; для нашего узла это `refs/heads/fum-lab/fum`. Один репозиторий или форк соответствует одному самостоятельному узлу с одной управляющей сессией. Дочерние чаты и рабочие ветки являются исполнителями внутри узла; новый самостоятельный узел получает свой форк. Устойчивый ID узла сохраняется в состоянии отдельно от имени и адреса репозитория, которые могут измениться.

Позднее уточнение этой модели подтверждено оригинальным ответом диалога от 2026-10-08 18:42:19 MSK. Действующая управляющая ветка пока остаётся `fuma`; новая постоянная ветка и перенос её назначения ещё не активированы. Отдельное временное испытание ниже проверяет механизм записи и доверия и не заменяет целевую схему именования.

ROOT назначает устойчивый ID узла fum-lab/fum и ID репозитория fum-lab/fum. Поколение полномочий конечного испытания: 2026-10-09-первое-живое-состояние. Путь одного expected: Память/конвейер/ожидаемое-состояние-узла.json.

Планируемый ref писателя: refs/heads/codex/dir/pamyatj--konvejyer--sostoyaniye-uzla--proba. Это отдельная ветка состояния: обычное продвижение fuma не выбирает новое поколение доверия. Физическое дерево и настоящий UUID видимого чата ещё не назначены. До независимого ACT, Git-назначения и открытого решения ROOT запись не допускается.

Первый перечень содержит одного явно выбранного живого исполнителя. Используются прежние expected, предпросмотр v2, ACT, решение ROOT, поставка и контейнер. Полнота перечня остаётся ложной; входные снимки равны null. Новый реестр задач не создаётся.

## Подготовка до эффекта

1. После принятия публикуемого назначения ROOT штатным start готовит обычную открытую пару Журнала будущего испытания и её навигационных соседей в своём дереве. Пара сохраняет корневой UUID в происхождении; будущий UUID исполнителя не выдумывается. Постановка, принятый код и открытая пара фиксируются исходным коммитом C.
2. Начать видимый чат из C в собственном дереве, первоначально только для чтения. Сверить настоящий native UUID, initial C, физический корень, ref, модель и effort. Назначить ровно один expected и конечный состав уже сохранённой пары.
3. Подготовить обычный ACT и открытое решение ROOT с реальными Git-источниками. После коммита решения D закрепить отдельный контрольный ref на D; сформировать кандидат и его raw SHA; Git-назначение A сохранить отдельно, не продвигая контрольный ref. Фикстура подтверждает отсутствие циклической ссылки.
4. Проверить публикационную границу принятой новой схемы назначения и точную привязку к физическому корню приватного входа. Не публиковать локальный адрес, не маскировать обязательное поле и не обходить строгую схему.
5. Передать независимый выбор опубликованного ACT писателю. Его .7 различает задачу ROOT и настоящего исполнителя: запрос и последний trailer содержат корневой UUID, история модели — наблюдённый UUID исполнителя. Первая runtime-база остаётся C с родителями [C]; первое_создание.коммит=C, доверие=null. ACT.постановка.коммит всегда сохраняет initial C, даже если более поздний разрешённый этап использует его потомка B. Дополнительный коммит ребёнка до ACT не допускается; закрытый снимок пары не возобновляется.
6. Назначить физические приватные каталоги контейнера и операции вне Git с устойчивым сохранением входа, UUID, намерения, .7/.9, квитанции и нового доверия. Временный каталог не доказывает восстановление после сбоя ОС.
7. Перед эффектом заново подтвердить актуальность ROOT-команд, владельца, источников, HEAD/ref, индекса и кандидата.

## Проверенные границы последовательности

Обычный дочерний читатель принимает закреплённый initial C и отдельную текущую базу этапа только при доказанном отношении предка. Создатель проверяет независимый ACT до подготовки и первых выходов, поэтому порядок C → UUID → коммит ребёнка B → ACT создаёт цикл допуска. Для первого испытания выбирается предварительная открытая пара ROOT в C, затем настоящий UUID и независимые ACT, D и A.

D фиксируется после ACT; отдельный control ref указывает на D. A выпускается после выбора точных байтов кандидата, независимо от writer ref. Ни публикация A, ни обычное продвижение fuma не сдвигают control ref или базу писателя. Новое доверие возникает только из успешной канонической квитанции и проверенного expected-коммита H; оно связывает точный writer ref с H. Установка файла сама по себе этого не доказывает.

Основания: [обычное дочернее поручение](../../../Инструменты/fum-svyaznostj-rabochej-sessii/обычное-дочернее-поручение.md), [создатель контрольной точки](../../../Инструменты/fum-svyaznostj-rabochej-sessii/scripts/создание_коммита.py) и [писатель expected](../../../Инструменты/fum-svyaznostj-rabochej-sessii/scripts/обновление_ожиданий_узла.py). Эти проверенные ограничения не являются свидетельством завершённого живого испытания.

## Конечные рубежи проверки

- Создать один expected, штатно проверить и зафиксировать его; прочитать сырой коммит и подтвердить удалённую доставку.
- Запустить новый процесс с прежним входом и каталогом операции; подтвердить повтор без второго коммита.
- Прочитать expected и прежние полные наблюдения новым процессом по явному новому доверию.
- Проверить, что обычное продвижение fuma не инвалидирует доверие неизменному state ref.
- Отказ прежнему действительному доверию после обновления требует второй отдельно разрешённой конечной операции либо настоящего предшествующего trusted expected. Первое создание этого не доказывает.
- Сохранить монотонные интервалы, число API/Git-вызовов, байты, результаты и SHA. Вложенные таймеры не складываются.
- Отправки команд восстановления и массовое возобновление сессий не входят в испытание.

## Условие первого эффекта

До живого запуска исправить [публикационный контракт назначения](публикуемое-назначение-писателя-ожиданий.md): реальный абсолютный корень .1 отклоняется действующим сканером. Отдельный контрольный ref устраняет циклические ссылки. Обычная открытая пара готовится ROOT до исходного C и не получает закрытого снимка проверок.

## Следующий рубеж

После принятого испытания подключить фактический ожидаемый перечень и новый живой цикл наблюдения. Затем проверять адресное восстановление существующего чата с учётом паузы, отмены, приёмки, неизвестных эффектов и поздних команд ROOT. Данные старого цикла остаются историческими.
