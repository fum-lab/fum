# Первое живое состояние узла

## Назначение

Проверить принятого писателя ожидаемого состояния на одной конечной живой операции. Используется существующий механизм из PR237 и PR238, принятый в `fuma` коммитом `bb0eeeb4822deead69ce9c92c3d91bc41d86cffe`; повторная реализация не нужна.

Исходный коммит C — точный коммит ROOT, содержащий эту постановку, принятый код и [открытую пару будущего испытания](../../../Журнал/2026-10-09_12-20-49_MSK_испытать-первый-expected-состояния-узла/запрос.md). Исполнитель начинает в отдельном видимом чате и собственном worktree строго из C. До настоящего UUID, физического корня, собственного ref и независимого допуска работа ограничена чтением; предварительный дочерний коммит не создаётся.

## Конечный состав

- Один файл ожидаемого состояния: `Память/конвейер/ожидаемое-состояние-узла.json`.
- Собственные запрос, отчёт, история модели и новые машинные записи проверок открытой пары испытания.
- Общие `Журнал/README.md` и индекс Markdown только в предусмотренной писателем сервисной границе. Соседние запросы и другие содержательные файлы ребёнок не меняет.

Корневой UUID — `01a07d3d-d376-7ad2-aafc-67e4c25a67eb`. Настоящий UUID, физическое дерево и окончательный полный ref исполнителя сохраняются в ACT после подтверждённого создания чата. Планируемая временная ветка — `refs/heads/codex/dir/pamyatj--konvejyer--sostoyaniye-uzla--proba`; она ещё не создана. Узел и репозиторий — `fum-lab/fum`; поколение полномочий — `2026-10-09-первое-живое-состояние`.

## Порядок допуска

1. ROOT фиксирует исходный C, затем создаёт чат из C и проверяет его реальные идентичности.
2. ROOT публикует независимый ACT и открытое решение D. Отдельный контрольный ref закрепляет D.
3. После выбора точных байтов кандидата ROOT сохраняет Git-назначение A с SHA кандидата. A не продвигает контрольный ref или базу писателя.
4. Перед первой записью писатель проверяет опубликованные ACT, D и A, собственный HEAD/ref/индекс и актуальность исходных команд. Его первая runtime-база — C с родителями `[C]`; `первое_создание.коммит=C`, доверие отсутствует. В ACT исходная постановка всегда связывается с C.
5. Один expected и собственный конечный состав создаются штатным писателем через принятые `.7`/`.9`, индекс, отчёт, проверки и квитанцию. Новый trust выбирается только после проверки сырого H и удалённой доставки.

## Свидетельства результата

Нужны фактические H, родители, дерево и точный состав изменения, подтверждённый удалённый OID, новый процесс повтора прежнего входа без второго коммита и новый процесс чтения expected с прежними полными наблюдениями по явному новому доверию. Отдельно проверяется сохранение доверия неизменному state ref при обычном продвижении `fuma`. Длительности, число вызовов и байты сохраняются с SHA; вложенные интервалы не складываются.

Первый перечень включает только одного явно выбранного живого исполнителя. Полнота остаётся ложной, входные снимки — `null`. Нового общего реестра не создаётся. Отказ прежнему действительному доверию после его обновления требует второй отдельно разрешённой операции и не заявляется по первому созданию.

## Границы

Пара испытания подготовлена ROOT до C, содержит действительные человеческие команды и корневой UUID. Она открыта, без закрытого снимка, собственной истории модели или вымышленных проверок ребёнка. Приёмка подготовки ROOT хранится в [отдельной паре](../../../Журнал/2026-10-09_12-18-00_MSK_подготовить-первое-живое-состояние-узла/запрос.md).

Целевая постоянная ветка состояния — `refs/heads/fum-lab/fum` по [принятой схеме](живое-состояние-задач-узла.md). Действующий управляющий ref пока `refs/heads/fuma`; production-переход требует отдельной проверки контракта. В испытание не входят массовое возобновление, отправки команд восстановления, D22, изменение общего допуска, новая разработка или повтор принятой `.2`.

Приватные входы, наблюдения, намерение, UUID операции, подготовка, квитанция и доверие сохраняются вне Git в устойчивых физических каталогах. Существование временного каталога само по себе не доказывает восстановление после сбоя ОС.
