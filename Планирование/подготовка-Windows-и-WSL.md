# Подготовка Windows и WSL

Первый срез FUM-STEP-0181 определяет конечную матрицу окружений, порядок обнаружения зависимостей и паспорт первого профиля. Это принятый для разработки план: установщик, автоматизированная подготовка и пригодность конкретного Windows-гостя ещё не подтверждены. Все команды ниже предназначены для будущей квалификации на выбранной системе; в этом плановом этапе они на Windows/WSL не исполнялись.

Нативный Windows и WSL используют разные клоны, исполняемые файлы и состояния. Наличие Windows, успешный запуск процесса или доступность пакета сами по себе не дают готовность FUM. Полная [постановка Windows VM](Windows-на-macOS.md) сохраняется вместе с этой матрицей; её будущие установка, управление и испытания не сокращаются до обзора совместимости.

## Состояния и граница результата

| Состояние          | Смысл и необходимое свидетельство                                                                                           |
| ------------------ | --------------------------------------------------------------------------------------------------------------------------- |
| План готов         | Определены конечные входы, границы, проверки и незаполненные поля паспорта; подтверждает только документационный результат  |
| Не проверено       | Комбинация допустима как кандидат, но нет реального протокола на точных байтах и версиях                                    |
| Незавершённо       | Известен необходимый следующий шаг: зависимость, права, ресурс, перезапуск, поставка или испытание; причина сохраняется     |
| Неподдержано       | Компонент исключён из данного профиля до действий; общий успех не скрывает исключение                                       |
| Готово для профиля | На объявленных OID, версии ОС и зависимостях завершились все обязательные проверки профиля, включая повтор и восстановление |

Переход к «готово для профиля» требует непустого конечного списка проверок, фактических исходов, отсутствия пропусков и незавершённых обязательных действий. Изменение входов снимает прежнюю готовность до новой проверки. Ошибка доступа, неизвестное значение и неподдержанный компонент различаются; ошибка не превращается в «отсутствует».

После окончания поддержки выбранного выпуска план требует нового решения, а не молчаливой подмены версии.

## Пути, репозитории и инструменты

| Область           | Нативный Windows                                                                               | WSL2                                                                                                         |
| ----------------- | ---------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Клон              | Собственный каталог на локальном NTFS, короткий путь, вне синхронизируемых и общих каталогов   | Другой клон внутри Linux ext4; Windows-монтирование диска не является рабочей областью первого POSIX-профиля |
| Git               | Проверенный git.exe выбранной архитектуры                                                      | Linux git; Windows git.exe через interop не используется для этого клона                                     |
| Python            | Проверенный существующий python.exe; Store alias и менеджер не принимаются за интерпретатор    | Linux python3 и отдельное venv; Windows venv не переносится                                                  |
| Shell             | Windows PowerShell 5.1 для обнаружения; PowerShell 7 — отдельная зависимость при необходимости | POSIX shell в выбранном дистрибутиве; cmd/PowerShell-команды не исполняются как Linux-команды                |
| Права и состояние | Windows ACL, блокировки и атомарная замена требуют отдельного адаптера                         | Linux UID/права/flock в собственной ext4; совместимость на смонтированных Windows-путях не предполагается    |
| Приватные данные  | Вне Git: ключи, лицензии, пользовательские конфиги, VM/EFI/TPM, журналы и временные сборки     | Вне клона: ключи, venv/кэши, частное состояние; не копируются из Windows-клона                               |

Репозиторий переносится Git-механизмом на точный OID, а не копированием работающего checkout вместе с индексом и кэшами. Профили не меняют глобальные `core.autocrlf`, `core.eol`, `core.ignorecase`, `core.longpaths`, `safe.directory`, имя, email, credential helper или SSH-настройки пользователя. Сначала читаются `.gitattributes`, `.gitmodules`, Git-конфигурация с происхождением, индекс и рабочая разница. Настройки конкретного нового клона возможны только как явные действия плана. Существующий грязный клон и чужое дерево сохраняются; `reset`, `clean`, перезапись конфигурации и присвоение чужого каталога не являются восстановлением.

## Инвентарь зависимостей и команды обнаружения

Сначала проверяется наличие команды и её точный путь; только затем исполняется уже существующий проверенный файл. Значения в угловых скобках ниже заменяются наблюдёнными значениями, это не готовые исполняемые команды. Неустановленный Python может автоматически загружаться новым менеджером при вызове `python`/`py`; поэтому голый `python --version` не считается безопасным обнаружением. Сначала `Get-Command`, затем `py list` для нового менеджера либо `py -0p` для старого launcher, затем версия явно найденного настоящего интерпретатора. Сетевые каталоги не опрашиваются как локальный инвентарь.

| Компонент                  | Источник и версия                                                                                            | Нативное обнаружение                                                                                               | WSL2 и граница                                                                                                           |

Git-обнаружение в своём клоне: `git --no-optional-locks status --porcelain=v1`, `git rev-parse HEAD`, `git symbolic-ref -q HEAD`, `git diff --stat`, `git diff --cached --stat`, `git config --show-origin --show-scope --list`, `git submodule status --recursive`. Конфигурация может содержать частные адреса и параметры; сырой вывод хранится локально и не переносится в публичный отчёт. Отсутствующий detached ref — отдельное наблюдение, а не повод переключать существующий клон.

`wsl --distribution <существующий-дистрибутив> --exec <команда>` уже может запустить гостя. Это следующий явно выбранный этап после обнаружения; он не входит в чтение состояния хоста. Версии дистрибутива читаются из его os-release и пакетного инвентаря после разрешённого запуска. `wsl --install`, `--update`, `--set-version`, `--unregister` не являются проверками и в этом срезе не выполняются.

## План подготовки, повтора и восстановления

1. Обнаружить точные ОС/архитектуру, инструменты, права, каталог и его владельца, свободный диск, состояние Git и текущие окружения. Отдельно установить возможность выполнения без администратора. Неизвестные поля остаются неизвестными.
2. Построить план без записи: требуемые и уже подходящие версии, точные источники/артефакты, лицензии, подписи/хэши, изменения файлов и переменных, права каждого действия, оценка диска и необходимость перезапуска. Версия «latest» не является закреплённым входом.
3. Перед будущей установкой проверить достаточность диска для всех одновременно существующих входов, распаковки, временной сборки и конечного результата плюс явно заданный резерв. Для VM учитываются ISO, drivers, answer media, EFI/TPM, рабочий диск, временные копии и снимки; для WSL — VHDX, клон, зависимости и кэши. Размер Windows-минимума не равен рабочему бюджету FUM.
4. В отдельном разрешённом этапе получить и проверить точные пакеты. Подходящие установленные версии переиспользуются; неизвестные источники и несовпавшие хэши дают отказ. Повышение прав и включение Windows-компонентов имеют отдельные этапы с объяснением действия. Пароли и лицензии не записываются в открытый план.
5. Создать собственный клон и отдельное окружение. Проверить точный gitlink и реальные LICENSE/NOTICE до использования зависимости. Сохранить прежние окружения и параметры Git. Незавершённость установки либо необходимость перезапуска сохраняются долговечно; автоматический перезапуск без отдельного действия не предполагается.
6. После перезапуска заново обнаружить состояние; сопоставить его с прежними входами и завершёнными действиями. Повтор не считает наличие каталога доказательством успеха и не запускает повторную установку вслепую. При изменении входа сначала новый план; при неизвестном исходе сначала сверка фактического результата.
7. Выполнить конечный набор проверок в обёртке выбранной ОС, затем повтор без изменений и сценарии прерывания. Итог показывает готовые, незавершённые и неподдержанные компоненты, команды продолжения и происхождение измерений. Удаление чужих данных и сброс Git запрещены как способ получить зелёный результат.

Будущие открытые фикстуры проверяют пробелы и кириллицу/ё в путях, длину пути, case-collision, UTF-8 и вывод консоли, LF/CRLF, executable bit, symlink/ACL, файл, удерживаемый другим процессом, атомарную замену, второго писателя, недостаток диска, отказ прав, неподходящую архитектуру пакета, остановку между установкой и квитанцией, перезапуск и повтор. Нормализация всего клона ради теста недопустима. RED/GREEN, профиль времени/памяти/диска и решение об оптимизации относятся к будущей реализации; плановый документ не является их заменой.

## Сохранённый план VM и первые проверки

До создания VM закрепляются версия и исходники UTM/QEMU, формат .utm, firmware и Secure Boot keys, ARM64 boot/network drivers, guest tools, единственный Autounattend.xml, редакция/язык/build/SHA-256 ISO и частный лицензионный вход. Временный URL ISO не является его идентичностью. Получение ISO и покупка лицензии этим планом не разрешаются.

Первое испытание создаёт новую собственную идентичность и EFI/TPM state, импортирует свежую конфигурацию, а затем подтверждает возможности из гостя. Кандидаты команд: `Get-ComputerInfo -Property BiosFirmwareType`, `Get-Tpm | Select-Object TpmPresent,TpmReady,TpmEnabled,TpmActivated`, `Get-CimInstance -Namespace root/CIMV2/Security/MicrosoftTpm -ClassName Win32_Tpm | Select-Object SpecVersion`, `Confirm-SecureBootUEFI`. Нужны фактические UEFI, версия TPM 2.0, готовность TPM и включённый Secure Boot; отдельно проверяются доверенные keys. Полный вывод Get-Tpm может содержать OwnerAuth и в публичный отчёт не переносится. Доступ администратора для этих проверок отражается в плане. `False`, отказ прав и «платформа не поддерживается» — разные исходы. Включённое поле конфигурации и загрузившийся установщик этого доказательства не заменяют.

После квалификации backend будущая реализация выполняет установку и перезагрузки, проверяет устройства/драйверы, архитектуру гостя и канал управления, затем конечный профиль FUM, штатную остановку, повтор с тем же диском/EFI/TPM и восстановление после прерывания. NoCloud, VZEFIVariableStore и Linux VSOCK не переносятся в Windows. WSL2 внутри VM, игры, GPU и полная переносимость FUMA остаются вне первого профиля. Parallels сохраняется альтернативой с отдельным выбором версии, CLI и лицензии, без предполагаемой покупки. При отказе UTM сохраняется препятствие; требования Windows не обходятся.

## Общий Linux lifecycle и поставка

Плановый цикл «проверить → план → подготовить → запустить → состояние/готовность → гостевой доступ → штатно остановить → повторить/восстановить» берётся из [Linux-постановки](Linux-на-macOS.md). Это семантическая общность операций, не обещание готового переносимого API.

Прочитан точный промежуточный Linux OID `0f62797675ddbcd3c68bceefe6793de95c5d20b8`, файл `Проекты/ВиртуальнаяМашина/README.md`. Наблюдаемый CLI: `проверить`, `план`, `подготовить --план … --до …`, `запустить`, `готовность`, `ssh`, `остановить`, `восстановить`. README сообщает реальные Linux-испытания ограниченного профиля из OID `4dd5a7f33913b17f705e512be1826314da89a4c4`, но также незавершённые упаковку, свежий NoCloud и прерывания. Этот CLI привязан к Apple Virtualization.framework и Linux. Он не является поставкой Windows-адаптера и не удостоверяет готовую общую библиотеку.

В базу `01b329cb49f4c5a5655fab4c16d7ea3a3ebf55a5` исполняемая общая библиотека из этой работы не доставлена; принятое координатором общее API для Windows пока не подтверждено. Импорт исходников и вызов Linux backend не выполнены. Перед переиспользованием требуются принятые OID/tree, точный путь и версия API, исходники/лицензии/ресурсы и протокол проверок. Тогда выбираются фактически общие проверка артефактов, владение состоянием, переходы, измерения и журнал, а платформенные операции остаются раздельными. Вторая Linux-реализация и новая универсальная библиотека этим срезом не создаются.

## Воспроизведение и лицензии

Принцип полного воспроизведения состояния применяется к этому срезу как различение принятых входов, точных исходных байтов, версии метода, восстанавливаемого результата и неопределённости. Хэш плана не доказывает воспроизводимость установленной ОС. Windows updates, сетевые каталоги, аппаратная конфигурация, подписи, частная лицензия и ключи требуют отдельных зафиксированных входов и границ. Повтор после изменения внешнего мира не объявляется тем же испытанием.

В монорепозитории сохраняются план, открытые профили, будущие исходники/фикстуры/команды и публикационно чистые свидетельства. Частные диски, EFI/TPM, ключи и токены остаются вне Git; результат восстанавливает структуру и проверяемое состояние, не публикуя секреты. Это не завершение сквозного принципа воспроизводимости FUM.

Windows, Windows SDK/Visual Studio и возможный Parallels имеют собственные лицензионные условия; CC0 FUM их не заменяет. Для Git for Windows учитываются GPL и лицензии комплекта, для CPython — PSF и включённые notices, для Swift — Apache-2.0 с Runtime Library Exception и notices, для UTM — Apache-2.0 и лицензии включённых компонентов, для QEMU — GPL и компонентные лицензии. Firmware, guest agent, SPICE/virtio-драйверы проверяются каждый на своей ревизии. Наличие LICENSE на upstream-странице не устанавливает лицензию будущего бинарного комплекта: до поставки нужны реальные LICENSE/NOTICE именно полученных артефактов. В этот срез сторонние бинарники и исходный код не включены.
