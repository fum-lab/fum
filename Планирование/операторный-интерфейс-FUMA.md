# Операторный интерфейс FUMA

Первый диагностический сценарий FUMA на Swift должен запускать Codex CLI, сохранять его доступный поток событий в памяти и показывать наблюдаемое состояние графически. Структурирующие операторы преобразуют это состояние в команды отрисовки Metal. GUI использует ту же память и определения операторов, что и остальная FUMA.

Это постановка дальнейшей работы. Она уточняет существующие требования и шаги; данный документ не подтверждает создание языка, запуск CLI из приложения, полноту записи API или работающий экран.

## Приоритет и существующее покрытие

Приоритет реализации — обработка контекста: [FUM-STEP-0165](карточки-шагов/🟡-FUM-STEP-0165-собирать-рабочий-контекст-задачи.md), [FUM-STEP-0177](карточки-шагов/✅-FUM-STEP-0177-возвращать-необработанные-сообщения-пользователя.md) и [FUM-STEP-0160](карточки-шагов/🟡-FUM-STEP-0160-накапливать-статистику-вызовов.md). Независимые ограниченные результаты могут разрабатываться параллельно; отдельный результат должен иметь собственные входы, критерии и границу последующего объединения.

GUI уточняет [FUM-REQ-0021 — проекцию внутренней памяти](../Требования/🟡-GUI-как-проекция-внутренней-памяти-и-исполнения.md), а Metal — [FUM-REQ-0002](../Требования/🟡-отрисовка-интерфейса-через-Metal.md). Общая платформенная область [FUM-REQ-0047](../Требования/🟡-графические-интерфейсы-FUMA.md) сохраняется. Первый сценарий macOS входит в [FUM-STEP-0182](карточки-шагов/🟡-FUM-STEP-0182-определить-платформенные-сборки-и-первый-сценарий-FUMA.md); хранение наблюдений связано с [FUM-STEP-0156](карточки-шагов/🟡-FUM-STEP-0156-реализовать-контейнер-наблюдений-с-бинарными-блоками.md).

Для языка сохраняется связь с ранее оформленными FUM-REQ-0067 и FUM-STEP-0208: [постановка чистого исполнения и UTF-32 в коммите b08b969c](https://github.com/fum-lab/fum/blob/b08b969c9c40bda90e53e8effee904f181dce7d6/Требования/🟡-чистое-исполнение-операторов-и-UTF-32.md). При слиянии принятой FUMA требование и [завершённый ограниченный интерпретатор FUM-STEP-0208](карточки-шагов/✅-FUM-STEP-0208-реализовать-интерпретатор-и-UTF-32.md) включены в текущее дерево. Прежняя ссылка сохраняет происхождение постановки. Доставка этого прототипа не закрывает универсальный язык или интеграцию основного runtime. Новые дублирующие идентификаторы не назначены.

## Язык описания структурирующих операторов

Предстоит определить способ описания операторов, их входов, выходов, композиции и наблюдаемого исполнения. Чистое вычисление отделяется от доступа к macOS: оператор получает явно сохранённый вход, а внешнее действие проходит через наблюдаемую Swift-прослойку.

Критерии будущего результата:

- Версионированное определение однозначно задаёт значения и порядок вычисления; неоднозначная конструкция, неизвестная версия и превышение ресурсов дают явный исход.
- Одни и те же определение и вход воспроизводят результат; происхождение связывает версию оператора, точные входные данные и наблюдение исполнения.
- Проверочные ожидания независимы от вычисления. Открытые положительные и отрицательные примеры покрывают композицию, ошибку и восстановление.
- Выбор текстового или структурированного представления, типов и пределов обоснован отдельным проектным решением; готовая универсальная грамматика сейчас не заявляется.

## Swift, macOS и память наблюдений

Swift-прослойка связывает API macOS, внутренний API интерпретатора операторов и наблюдаемый сигнал. Каждый вызов или наблюдение через API macOS, выполняемый FUMA, должен оставлять запись в её памяти. Эта область не означает перехвата всех вызовов всех сторонних процессов операционной системы.

Будущая приёмка должна подтвердить:

- вызов, вход, исход, ошибка или отмена различимы и связаны с породившей их операцией; недоступность API и отсутствие разрешения не выдаются за пустое успешное наблюдение;
- исходные доступные байты и интерпретированное представление связаны происхождением; потеря, усечение, разрыв и неизвестный формат видимы;
- подтверждённая запись восстанавливается другим процессом по контракту контейнера FUM-STEP-0156;
- перечислены границы наблюдаемого Swift-адаптера и фактическое покрытие API; полнота не выводится из одного успешного примера;
- определён способ учитывать служебные операции самого журнала без бесконечного самоописания и скрытых исключений;
- приватная рабочая память отделена от публикационно допустимых фикстур; полный рабочий поток не публикуется в Git автоматически.

## Codex CLI и диагностический GUI

Swift-приложение управляет процессом Codex CLI и сохраняет полный доступный ему поток событий. Отдельно учитываются выход процесса, диагностический поток, ошибка запуска, отмена и конец ввода. Порядок внутри каждого потока и фактически наблюдённое взаимное расположение событий различаются: недоказанный глобальный порядок не придумывается.

Для системы структурирующих операторов нужен адаптер API Codex CLI: типизированные команды и параметры, ответы, события и ошибки. Каждое обращение связывается с задачей, вызовом, версией протокола и сохранённым наблюдением. Фактически поддерживаемые операции определяются по конкретной поставке CLI; наличие процесса не доказывает доступности произвольного API. Воспроизведение читает сохранённые результаты и не повторяет внешние действия. Приёмка отдельно проверяет неподдержанную операцию, ошибку протокола и отличие воспроизведения от нового исполнения.

Операторы строят состояние диагностического интерфейса из сохранённых событий. Следующее преобразование формирует команды Metal. Обратное пользовательское действие возвращается в тот же событийный контур; ручное состояние renderer не становится отдельной доменной истиной.

Критерии первого вертикального сценария:

- известный поток воспроизводится из памяти без повторного запуска CLI; экранное состояние связано с его событиями и версиями операторов;
- живой запуск подтверждает фактические версию CLI и поддержанный формат событий; неизвестные события сохраняются, а неподдержанная интерпретация обозначается;
- проверены частичный ввод, большой поток, медленный потребитель, ошибка, отмена и восстановление; интерфейс не скрывает пропуски за сокращённым представлением;
- диагностический экран показывает наблюдаемые состояния, не выдавая их за доступ к скрытому внутреннему состоянию модели;
- происхождение хотя бы одного элемента и обратного действия проверяется сквозным сценарием; Metal-диагностика и проверка отображения имеют собственные свидетельства;
- исходники, открытые фикстуры и воспроизводимые команды хранятся в FUM; RED/GREEN, профиль и решение об оптимизации относятся к точному принятому снимку.

## Наблюдаемость и настройка для LLM

LLM должна видеть, что выполняется автоматически и каким способом: фактически выбранное правило, входы, текущее состояние, результат и происхождение. Для настройки используется язык описания структурирующих операторов. Представление отделяет наблюдаемое исполнение от желаемой конфигурации.

Компактный срез содержит точные указатели на полную трассу; детализация раскрывается адресно, чтобы наблюдаемость сама не переполняла контекст. Предложение настройки, её принятие и фактическое применение сохраняются как разные состояния. Отображение предложения не подтверждает, что оно уже влияет на исполнение. Приёмка должна проверить эту цепочку на успешном, отклонённом и ещё не применённом изменении, сохранив происхождение и поздние уточнения.

## Оболочка исходящих API Codex CLI

Уточнение «Оба потока» охватывает запросы CLI к API модели и инициированные CLI вызовы инструментов и ОС. Эти обращения должны проходить внутри управляемой оболочки FUMA на Swift с записью входа, результата, ошибки и отмены в память. Один запуск дочернего процесса и чтение его вывода ещё не доказывают охват исходящих обращений.

Перед реализацией требуется инвентарь точек обращения для закреплённой версии CLI: транспорт модели, встроенные инструменты, файловые и процессные операции, подключаемые инструменты и внешние сервисы. Для каждой точки указываются способ включения в оболочку, контролируемая граница, проверяемое свидетельство и непокрытые обходные пути. Неизвестное покрытие остаётся неизвестным; отдельный успешный адаптер не доказывает полноту всех потоков.

Приёмка связывает запрос к модели, порождённый вызов инструмента, его исход и следующий запрос единой трассой с версиями протокола и операторов. Отдельно проверяются ошибка транспорта, неподдержанный инструмент, отмена, разрыв записи и попытка обхода оболочки. Воспроизведение использует сохранённые результаты без повторения сетевого запроса или действия ОС. Конкретный способ встраивания и пределы вмешательства выбираются после проверки CLI; постановка не утверждает, что действующий CLI уже предоставляет все нужные точки подключения.

## Единый runtime и стоимость IPC

Целевая поставка — единый исполняемый бинарник FUMA, объединяющий пригодные для встраивания зависимости runtime; её назначение — минимизировать стоимость межпроцессного обмена. Предпочтительный горячий путь Codex → операторы → GUI следует исследовать как исполнение в одном процессе через прямые функции и общие буферы. Библиотека, загруженная в этот процесс, также не требует IPC для локального вызова; единственный файл поставки сам по себе не гарантирует единственный процесс.

[Сборка собственной реализации в FUM, FUM-STEP-0176](карточки-шагов/✅-FUM-STEP-0176-собрать-собственную-реализацию-в-FUM.md) задаёт доставку исходников и воспроизводимость. Она не подтверждает объединение runtime в один процесс. Это дополнительная цель выбора состава исполняемой системы, связанная с первым сценарием FUM-STEP-0182; существующие карточки данным уточнением не закрываются.

Критерии будущего решения:

- Для закреплённого сценария составлены схема фактических процессов и перечень переходов между ними; измерены число переходов, объём сериализации и копирования, задержки p50/p95 и пиковая память с указанными границами измерения.
- На одинаковых входах сравнены исходный вариант и доступный вариант прямых вызовов; пороги приемлемого улучшения и допустимой памяти заданы до сравнения, а отсутствие выигрыша не скрывается.
- Для каждого компонента указаны возможность встраивания, интерфейс прямого вызова, владение буферами, ошибки, отмена и необходимость изоляции; выбор подтверждён сборкой и профилем точного снимка.
- Системные frameworks и SDK не обещаны частью собственного бинарника. Сохраняемые отдельные процессы перечислены с причиной и измеренной ценой обмена. Вынужденное отклонение от единого бинарника остаётся явно незавершённой частью этой цели, пока отдельно не принято изменение требования; выигрыш IPC сам по себе её не закрывает.
- Пользовательский сценарий, наблюдаемость обоих потоков API и восстановление памяти сохраняются после изменения размещения компонентов; упаковка сама не считается доказательством результата.

Текущая поставка сохраняет цель и критерии, не выполняет встраивание Codex или объединение runtime.

## Порядок реализации и граница поставки

Сначала принимаются проверяемые контракты контекста и наблюдений. На общей версии данных можно независимо готовить язык операторов, Swift-адаптер процессов и macOS, а также GUI-проекцию с Metal-исполнителем. Их объединение проверяется одним сквозным сценарием; отдельный успех каждого компонента его не заменяет.

Точные версии CLI и SDK, формат обмена, ограничения ресурсов и пороги профиля предстоит закрепить перед реализацией. Старые прототипы и чужой незакоммиченный контракт не объявляются принятой поставкой. Текущий результат ограничен документационным checkpoint в постоянной ветке `planirovaniye`; реализация, полная приёмка и интеграция выполняются отдельно.
