# Добавить принимающий запуск обычного создателя

Независимая запись Журнала меняет Creator, READY и coherence. Контрольная точка кандидата должна использовать отдельный принятый Git-снимок K и считать рабочее дерево W данными. Обычные API существуют, но production consumer старого принятого контура поддерживает только писателя состояния U/G2. Этот пробел подтверждён двумя независимыми читающими обзорами.

Разработать ограниченный принимающий consumer для обычного дочернего maker .7 и prepared .9: подготовка, ready и create через существующие API. Новый код захватывает конечный состав K и ресурсы по точным Git-объектам, исполняется в свежем процессе -I -S -B через принятый Контур.исполнить. Закрытые входы выбирают точные K/manifest/ACT, физические пути и этап; собственная копия выбора не становится независимым основанием. Строгие проверки UUID, владения, native, модели, индекса, проверок, публикационной чистоты и READY сохраняются.

Перед файловыми эффектами и flock повторяются проверки принятого кода и выбранных данных. Popen имеет закрытый перечень; код W не компилируется, не исполняется и не импортируется. Recency callback исполняет проверку из K, сохраняя stock wrapper. Приватные выходы защищены от отложенной буферной записи. Точный повтор квитанции подтверждает прежний результат, не создаёт новый Git-коммит и не сбрасывает возраст READY.

Предметная область:

- Инструменты/fum-svyaznostj-rabochej-sessii/scripts/запуск_принятого_создателя.py
- Инструменты/fum-svyaznostj-rabochej-sessii/scripts/вход_принятого_создателя.py
- Инструменты/fum-svyaznostj-rabochej-sessii/tests/test_принятого_создателя.py
- Инструменты/fum-svyaznostj-rabochej-sessii/tests/профиль_принятого_создателя.py
- Инструменты/fum-svyaznostj-rabochej-sessii/принятый-создатель-коммита.md

Прежние engine, state launcher/entry, Creator/READY/coherence, normative-файлы, manifest state-контура, native bridge и runtime этим сегментом не меняются. Любая обнаруженная необходимая правка вне пяти путей сначала передаётся ROOT с точным основанием. Новый consumer сам себя не принимает: после отдельной приёмки ROOT выбирает его K и только затем разрешает bootstrap Журнала.

Три свежих профильных процесса одного закреплённого сценария с измерением подготовки, ready, создания и повторного чтения отдельно. Ни test fixture, ни профиль не объявляются настоящей приёмкой текущего Журнала.
