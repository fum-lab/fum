# Перейти на базу исправления N22

## Задача и текущая граница

Подготовлен конечный порядок замены исполняемой начальной базы ребёнка исторической совместимости Журнала после принятия ROOT исправления N22. Точный будущий коммит C пока не доставлен. Этот документ не является исполняемым поручением и не назначает C по текущему HEAD. Новый D, экспорт S, приглашение, native-сессия, предметный код и ACT этим этапом не создаются.

Основание — сообщение ROOT после отказа N22 до создания чата: JSON постановки сравнивался через Markdown splitter. ROOT сообщил о четырёх воспроизведённых смысловых отказах RED; GREEN и приёмка в момент постановки ещё выполнялись. Здесь эти исходы не воспроизводились и не принимаются. Ранее выбранный C `2ef854934d5f25e1237c6cd2d4e53b8739581f73` содержит старые helper, блокирующие приватное `.7 начало` и входы ребёнка. Необходим переход именно на исправление этого обнаруженного дефекта. Одно продвижение ROOT само по себе не требует синхронизации D/P/S.

Два изменённых тестовых файла не доказывают GREEN. После доставки C сверяется принятый Git-код, а не сохранённые промежуточные хэши W.

## Конечный порядок

1. **Принятый ROOT C.** Получить от ROOT полный OID, подтверждение принятия и обычной доставки, точный состав исправления и результаты RED/GREEN. Прочитать commit/tree/parents и требуемые исходники из этого C; подтвердить, что исполняемый контур ребёнка содержит принятый ремонт обоих helper. Текущий HEAD, сообщение «GREEN идёт» или наличие тестов C не заменяют.
2. **Неизменный P в новой читаемой основе.** Прочитать прежний путь P из C и потребовать те же 26711 байт/SHA. Сверить все девять обязательных исходников с пинами P. Если хотя бы одно равенство нарушено, остановить переиздание и передать ROOT конкретное несовпадение; не переписывать P ради допуска. При успехе внешний выбор P получает C, прежний путь и прежний SHA. Внутренний `кодовая_база` P сохраняется.
3. **Новый D-bootstrap.** Только после шагов 1–2 подготовить отдельный D в новой записи. Буквальная начальная база в поручении D374 меняется с C2ef на принятый C; пересчитывается `координация.хэш_поручения`, новое основание связывает этот переход с ремонтом N22. Точный структурный diff должен разрешать только необходимые поля, без глобальной замены OID. Встроенные байты P, 22 предметных пути, 12 наборов проверок, модель `gpt-6.1-sol`, усилие `ultra` и назначенный ref остаются прежними. Публикация D создаёт собственный точный селектор D; D374 сохраняется.
4. **Новый дочерний S.** ROOT экспортирует S для выбранной читаемой основы C/ref. Сохранить исходные байты отдельным носителем с полными C, путём, SHA, размером, меткой и свидетельством экспорта. Проверить заявленные Git-объекты/режимы/хэши; не утверждать повторную реконструкцию полноты выбора без отдельной проверки. Старые S не редактируются и не перепривязываются. ROOT-S(C1fb) из коммита `86913d1b7ac931d970b34aaae4d9f4e133a9caf1` имеет отдельную роль ROOT late/ACT и не становится новым child S автоматически.
5. **Предстартовые подготовка и приглашение.** ROOT заново готовит точные D/P/S, приглашение, предстартовое рассмотрение и необходимые заготовки входов по принятому контуру. Окончательные дочерние планы `.7` ещё не формируются: им нужны фактические UUID/nativebirth и собственный назначенный писатель ребёнка. Прежние планы не переименовываются в свежие; совпадение P не делает старое LIVE действительным.
6. **Новое native-начало.** Только при отдельном допуске ROOT создать новый старт ребёнка от C с буквальным новым приглашением. Проверить фактические initial `commit_hash`, UUID, физический cwd, модель/усилие, sole writer и ветку `refs/heads/codex/realizovatj-istoricheskuyu-sovmestimostj-zhurnala-n15`. Нужны равенства native initial C = внешний P.коммит = child HEAD; child ref = D.акт.ветка; S подтверждает эту же читаемую основу C/ref. Старое native-свидетельство не переписывается. Существующее занятое/неясное дерево или ref не сбрасывается и не мигрируется; конфликт передаётся ROOT.
7. **Собственное начало ребёнка.** После проверки nativebirth назначенный ребёнок готовит и выполняет своё приватное `.7 начало` на новом C и сохраняет частное свидетельство. ROOT не подменяет писателя ребёнка и не выпускает это свидетельство заранее.
8. **Позднее рассмотрение и ACT ROOT.** Получив проверяемое частное свидетельство, ROOT выполняет предусмотренное позднее рассмотрение, фиксирует его отдельным коммитом и получает отдельный действующий ACT после review. Свежие LIVE, входные/плановые хэши, пины контура, HEAD/ref/индекс и границы чтения должны соответствовать этим фактическим новым объектам. План и старые технические ограды не заменяют этот допуск.
9. **Собственные входы ребёнка.** Только после позднего committed review и отдельного ACT ROOT назначенный ребёнок готовит и выполняет свои `.7 входы` по текущему контуру. Дальнейший предметный эффект подчиняется своему отдельному допуску. Доставка плана, D/S, приглашение, созданный чат или успешный технический шаг не доказывают завершения исторической совместимости и интеграции.

## Что сохраняется

D95, D374, P, старый S(C3b), child S(C2ef), отдельный ROOT-S(C1fb), native-свидетельства прежних попыток, все RAW/отказы и закрытый отчёт C95 остаются неизменными. Новые свидетельства добавляются отдельными событиями с происхождением. STEP0243/#148 остаётся той же карточкой; новый STEP/issue не требуется.

## Критерий передачи

Готовый результат этого этапа — опубликованный документ с последовательностью, точными прежними входами и единственным недостающим внешним входом: принятый ROOT C с исправлением N22 и его проверочными свидетельствами. Переиздание D и новый native-старт остаются за этой границей. Предметный scope не расширяется; reader-перенос имеет собственную постановку и отдельно выбранного ROOT писателя/базу/результат.
