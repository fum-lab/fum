## Паспорт

- Статус: [MVP-кандидат](../../../Глоссарий/MVP-кандидат.md).
- Горизонты дорожной карты: [связная память проекта](../../дорожная-карта.md) и [воспроизводимые автоматизации](../../дорожная-карта.md).
- Пользователь: автор документации FUM, который добавляет новые понятия, обновляет тексты и поддерживает связность терминов.
- Минимальный результат: локальный контур, который помогает находить новые устойчивые термины, проверять статьи глоссария, обновлять индекс и расставлять полезные ссылки на уже заведенные термины.

## Продуктовая идея для запуска

Продукт: **Редактор связной документации FUM** - локальная проверка, которая помогает автору не ронять терминологическую сеть проекта.

Первый пользователь - автор документации, который перед коммитом хочет понять, где в измененных Markdown-файлах пропущены ссылки на уже заведенные термины, где появился новый устойчивый термин и не сломан ли индекс глоссария.

Первый сценарий запуска: пользователь указывает набор измененных файлов. Редактор строит отчет: найденные употребления терминов без ссылок, кандидаты в новые термины, статьи с неверным заголовком, отсутствующие строки в `Глоссарий/README.md` и битые ссылки.

Состав первого релиза:

- команда или сценарий `fum glossary check <files>`;
- чтение текущего индекса и статей `Глоссарий/`;
- отчет без автоматической правки файлов;
- предложения ссылок для склоняемых форм с сохранением исходного текста;
- минимальная фикстура с несколькими терминами, пропущенной ссылкой и новым словосочетанием.

Критерий готовности к запуску: автор может запустить проверку перед коммитом и получить понятный список действий по глоссарию без сетевых зависимостей и без автоматического закрепления случайных формулировок.

## Почему это может быть первым MVP

Глоссарий является языковым каркасом памяти FUM. Чем больше проект растет, тем важнее не терять смысл терминов, не плодить неявные синонимы и не оставлять документы без ссылок на уже определенные понятия.

Этот кандидат близок к текущей практике: глоссарий уже ведется как отдельный раздел, а локальный навык `fum-glossary` задает правила изменения терминов. MVP может сначала быть проверкой и отчетом, а не полноценным редактором.

## Проверяемый MVP

Минимальный вариант должен уметь:

- проверить, что каждый файл термина начинается с заголовка `# <Термин>`;
- проверить наличие термина в `Глоссарий/README.md`;
- найти в измененных документах употребления уже заведенных терминов без ссылок и выдать предложения;
- найти новые повторяющиеся словосочетания, которые похожи на устойчивые термины;
- проверить, что ссылки из глоссария и на глоссарий не битые;
- сформировать отчет, который агент или человек может принять, отклонить или использовать для правки.

## Критерии приемки

- Проверка работает локально без сети.
- Ложные срабатывания не меняют файлы автоматически.
- Для склоняемых форм предлагается ссылка на статью в именительном падеже, а текст ссылки сохраняет правильную форму.
- Новый термин создается только после явного решения, а не из-за одного случайного употребления.
- Индекс глоссария остается читаемым и предсказуемо упорядоченным.

## Не входит в первый вариант

- Автоматическое переписывание терминологических статей.
- Семантическое объединение терминов без участия человека.
- Полная онтология FUM или графовая база знаний.

## Зависимости

- `Глоссарий/README.md` и статьи терминов.
- `Инструменты/fum-glossary/SKILL.md`.
- Правило о ссылках на содержательные употребления глоссарных терминов из [AGENTS.md](../../../AGENTS.md).

## Риски

- Избыточное количество ссылок может ухудшить читаемость документации.
- Слишком агрессивное выявление терминов может закреплять случайные формулировки.
- Нужно различать полезную терминологическую связность и механическое превращение каждого слова в ссылку.

## Первый эксперимент

Сделать отчет для измененных Markdown-файлов: какие глоссарные термины уже употреблены без ссылки, какие новые словосочетания повторяются несколько раз, какие ссылки на глоссарий не проходят проверку. На первом шаге отчет не должен сам редактировать файлы.
