# Автономный клиент Telegram

Swift 6 пакет первого клиента FUMA для macOS arm64. Подтверждены синтетический контур через продукционные очередь, ядро и сериализатор, зашифрованный архив точного обмена и его чтение отдельным процессом. Настоящая загрузка TDLib и её профиль ещё не выполнены; полный сборочный комплект не готов. Это продолжающаяся реализация [FUM-STEP-0222](https://github.com/fum-lab/fum/blob/fe18610b813092b0ce52359533ebaf26d81f5d8c/%D0%9F%D0%BB%D0%B0%D0%BD%D0%B8%D1%80%D0%BE%D0%B2%D0%B0%D0%BD%D0%B8%D0%B5/%D0%BA%D0%B0%D1%80%D1%82%D0%BE%D1%87%D0%BA%D0%B8-%D1%88%D0%B0%D0%B3%D0%BE%D0%B2/%F0%9F%9F%A1-FUM-STEP-0222-%D1%80%D0%B5%D0%B0%D0%BB%D0%B8%D0%B7%D0%BE%D0%B2%D0%B0%D1%82%D1%8C-Swift-%D0%BA%D0%BB%D0%B8%D0%B5%D0%BD%D1%82-TDLib-%D0%B8-%D1%81%D0%B8%D0%BD%D1%82%D0%B5%D1%82%D0%B8%D1%87%D0%B5%D1%81%D0%BA%D0%B8%D0%B9-%D0%BA%D0%BE%D0%BD%D1%82%D1%83%D1%80-%D0%BA%D0%B0%D0%BD%D0%B0%D0%BB%D0%BE%D0%B2-FUM.md).

Текущий срез ведётся по [постановке Telegram](../../../../Планирование/параллельные-постановки/2026-09-30/telegram.md); [его отчёт](../../../../Журнал/2026-09-30_16-59-02_MSK_подготовить-клиент-Telegram-и-сборку-TDLib/отчёт.md) хранит результаты адаптации и незавершённые работы. Исторические ссылки закреплены на исходном коммите `fe18610b813092b0ce52359533ebaf26d81f5d8c` и не заменяют приёмку текущего среза.

## Собрать собственный код

Из корня FUM на macOS с Swift 6:

В примерах замените обозначения, начинающиеся с «путь/к», реальными абсолютными путями к выбранному кэшу или файлу.

```sh
python3 -B Приложения/FUMA/Packages/КлиентTelegram/Проверки/проверить-пакет.py --кэш /путь/к/кэшу-Swift
swift build --build-system swiftbuild --package-path Приложения/FUMA/Packages/КлиентTelegram --scratch-path /путь/к/кэшу-Swift --jobs 1 -c release
swift build --build-system swiftbuild --package-path Приложения/FUMA/Packages/КлиентTelegram --scratch-path /путь/к/кэшу-Swift -c release --show-bin-path
```

Последняя команда показывает каталог исполняемого файла `проверить-telegram`. Пакет зависит только от соседнего собственного `КонтейнерНаблюдений`; SwiftPM не загружает TDLib. Последний проверенный профиль использует macOS 27.0, Xcode 27.0 (27A266a), SDK 27.0 (26A425) и Swift 6.4.0.34.1. Исполнитель проверки получает developer directory через `xcode-select`, выбирает Swift Testing из установленного комплекта и передаёт его пути только дочерней команде; неполный комплект или ссылки за пределы developer directory отклоняются. На этом Xcode 27 `swift-test` является ссылкой на `swift-package`, поэтому runner сохраняет исходное имя запускаемого файла и не добавляет подкоманду `test`. Процедура подтверждена для Swift Testing и не доказывает XCTest. После дочернего процесса исполнитель выводит в stderr JSON `fum.исход-проверки-пакета.1`: обычный код сохраняется, сигнал возвращает код `128 + номер` и отдельные поля с исходным отрицательным кодом и номером сигнала. Поэтому SIGTERM различим с обычным выходом 143 по JSON. Внешняя отчётная обёртка видит 143 как обычный неуспех; прозрачная передача POSIX-сигнала ей не заявлена. Произвольный `--пакет` не получает гарантии автономности: SwiftPM может получать его внешние зависимости; проверенный местный граф этого клиента не распространяется на другие манифесты. Минимум macOS 15 в Package.swift не означает, что эта ОС отдельно проверена.

## Автономная команда

В каталоге собранных исполняемых файлов:

```sh
./проверить-telegram --help
./проверить-telegram --библиотека /путь/к/libtdjson.dylib \
  --квитанция /путь/к/квитанции-сборки.json \
  --sha256-квитанции SHA256_НЕЗАВИСИМО_ВЫБРАННОЙ_КВИТАНЦИИ --простой-секунд 15
```

Для второго запуска нужна отдельно собранная TDLib с закреплённого коммита `d1085f9cebc5a62379991ae1652673954f229c1f`. Локальный профиль фиксирует точные Git-объекты, отпечатки ключевых файлов, инструменты сборки и параметры arm64 Release. Исполнитель сначала требует зарегистрированную зависимость `Зависимости/TDLib`, точные mirror/upstream и чистый checkout на gitlink OID. Затем он создаёт две независимые копии только из локальных Git-объектов вне репозитория, собирает и устанавливает `tdjson` в каталоге с правами 0700, проверяет архитектуру, экспортируемые символы и совпадение SHA-256 библиотек. Команды Git используют локальный clone без hardlink и сетевого fetch; исходный checkout не меняется.

Текущая ветка пока не содержит записи TDLib в `.gitmodules` и точного gitlink. Поэтому исполнитель закрыто остановится до создания каталога и до сборки. Прежний отказ из-за различия имён зеркала `TDLib` и upstream `td` относится к исторической проверке; он не описывает текущий допуск добавления зависимости. Регистрация живой TDLib остаётся отдельным незавершённым результатом.

После принятой регистрации используйте новый абсолютный приватный каталог вне checkout и корень установленного OpenSSL 3.6.4:

```sh
python3 -B Приложения/FUMA/Packages/КлиентTelegram/Проверки/собрать-tdlib.py \
  --корень-репозитория . \
  --выход /путь/к/приватному-каталогу/сборка-tdlib \
  --openssl-root /путь/к/OpenSSL-3.6.4
```

Два прохода обязаны дать байтово одинаковую `libtdjson.dylib`. Это проверяет повторяемость на указанном хосте, но не поставляет Xcode SDK, zlib, OpenSSL с сертификатами или GNU gperf и не подтверждает сборку на чистой машине без этих объявленных системных зависимостей. Сейчас профиль содержит наблюдённую версию этих входов; полный их исходный bootstrap и лицензии остаются за границей этого результата. Закреплённая TDLib ещё не собиралась и не загружалась; измерения CLI получены только с синтетической заглушкой.

Команда загружает современные `td_create_client_id`, `td_send`, `td_receive`, создаёт клиента, ожидает коррелированный ответ `getAuthorizationState` со значением `authorizationStateWaitTdlibParameters`, измеряет простой и выполняет `close` с ожиданием фактического `Closed`. Параметры приложения, телефон и вход в аккаунт этому сценарию не нужны. До настоящего запуска утверждение об отсутствии обращений библиотеки к сети остаётся непроверенной границей.

Успех возвращает код 0 и JSON `fum.автономный-запуск-телеграма.1`; ошибка — код 2 и ограниченный код причины. Отсутствующие измерения не заменяются нулями. Измерение простоя включает процессорное время всех потоков и выборки RSS раз в секунду; две начальные секунды прогрева, запуск и закрытие исключены из CPU/wall интервала. Пиковый RSS относится ко всему процессу с момента его старта. Сетевая задержка этим измерением не определяется.

Приватный каталог запуска сохраняется и при ошибке, и после проверенного чистого закрытия; его путь выводится только в stderr. В нём находятся журналы и отдельный случайный ключ; вместе они позволяют прочитать сохранённое состояние и сырой обмен, включая секреты авторизации. Эти данные нельзя публиковать. Сохранение архива не является повторной отправкой намерений. [Проверка команды](Проверки/проверить-команду.py) охватывает неверные флаги, отсутствующую библиотеку, синтетические профили без TDLib и два отдельных процесса с временной ABI-совместимой динамической заглушкой. Последняя проверяет поля времени загрузки и закрытия, подтверждённый `Closed` и очистку потоков, но не является результатом для закреплённой TDLib. Ей передаётся абсолютный путь исполняемого файла.

## Архив точного обмена и привязка библиотеки

Перед загрузкой нужны абсолютный физический путь dylib, сырая квитанция сборки и независимо выбранный SHA-256 квитанции. Проверяются её исходные байты, строгая схема, параметры двух проходов, размер и SHA-256 библиотеки. Квитанция сборщика выводится в stdout: сохраняйте эти точные байты в приватный файл, отдельно выбирайте доверенное основание для SHA-256. Хэш, вычисленный только из произвольного найденного файла, не подтверждает его происхождение. Синтетическая C-библиотека проверок имеет отдельную схему без утверждения о сборке TDLib.

Связь квитанции и библиотеки сохраняется в архиве и удерживается процессом. Изменение квитанции или файла по прежнему пути закрывает повторное открытие. Проверка файла на диске не доказывает байты уже загруженного образа, отсутствие гонки перед `dlopen` или идентичность всех транзитивных библиотек, включая OpenSSL. Квитанция также не заменяет независимую проверку происхождения сборки.

[Архив](Sources/КлиентTelegram/АрхивОбмена.swift) сохраняет окончательные исходящие `Data`, включая `@extra`, до обращения к нижнему транспорту; [мост](Sources/КлиентTelegram/Мост.swift) передаёт те же байты и один терминальный NUL. Неверные UTF-8, внутренний NUL и недопустимый ID клиента отклоняются до записи. Входящие байты копируются, шифруются и синхронизируются до очереди и JSON-разбора. Поэтому повреждённый JSON, повторы и кадры неизвестного клиента остаются в архиве независимо от исхода разбора. Общий порядок, направление, поколение и привязка защищены одной последовательностью; её замок не удерживается во время блокирующего `receive`.

Каждая запись шифруется AES-GCM в отдельном сегменте каталога `обмен` с правами 0700; файл имеет 0600. Перед допуском следующей стадии синхронизируются файл и каталог. Ошибка записи или синхронизации запрещает исходящий send; при входящей ошибке запрещены передача парсеру и следующий receive. Переполнение C-буфера, при котором исходные байты не скопированы, сохраняется как явный разрыв без вымышленных данных. Незавершённый, повреждённый или чужой архив не исправляется автоматически. Пределы контейнера — 4096 записей и 256 МиБ; ротация пока отсутствует.

Архивное исходящее намерение не доказывает вызов C, принятие Telegram или доставку. Чтение архива не обращается к транспорту, не загружает dylib и не повторяет отправку. Старый семантический журнал не превращается задним числом в свидетельство сырого обмена. Ключ хранится отдельно от сегмента вне Git; stdout проверки содержит только размеры, хэши и метаданные кадров.

```sh
./проверить-telegram --проверить-архив /путь/к/приватному-архиву \
  --библиотека /путь/к/libtdjson.dylib \
  --квитанция /путь/к/квитанции-сборки.json \
  --sha256-квитанции SHA256_НЕЗАВИСИМО_ВЫБРАННОЙ_КВИТАНЦИИ
```

Для архива синтетического профиля три параметра библиотеки не нужны. [Проверки архива](Tests/ПроверкиTelegram/ПроверкиАрхиваОбмена.swift) наблюдают точные `Data` и устойчивую запись внутри Swift spy до нижнего send. Независимый Python-оракул сравнивает буквальные кадры в новом процессе. Отдельный побайтный C-свидетель входа send в этом срезе отсутствует.

## Синтетические измерения

Собранная Release-команда запускает конечные профили без библиотеки TDLib:

```sh
./проверить-telegram --профиль поток --кадров 1000
./проверить-telegram --профиль отмена --повторов 30
```

Архивный профиль воспроизводится отдельно:

```sh
./проверить-telegram --профиль архив --кадров 1000
python3 -B Приложения/FUMA/Packages/КлиентTelegram/Проверки/проверить-команду.py /путь/к/проверить-telegram --измерить-архив
```

Вторая команда выполняется из корня FUM. Она запускает подготовку и чтение архива в двух процессах, сравнивает все 1048 кадров с независимыми буквальными данными и проверяет неизменность шифротекста. [Результат 1 октября](Профили/2026-10-01-архив-обмена.json) получен на Debug-сборке: 32 прогревочных и 1000 измеряемых входящих кадров, затем 16 исходящих, по 4096 байт. Шифрование, запись, fsync и полный проход через очередь и разбор имеют отдельные счётчики и p50/p95. Это один локальный запуск без очистки кэшей ОС; он не является измерением настоящей TDLib или коэффициентом ускорения.

[Проверка команды](Проверки/проверить-команду.py) принимает абсолютный путь этого исполняемого файла; добавление `--измерить` запускает оба профиля в отдельных процессах с внешним тайм-аутом 45 секунд и выводит объединённый JSON. Сборка и запуск измеряются отдельно. [Сохранённый профиль](Профили/README.md) содержит результаты, хэши, границы измерения и решение об оптимизации.

Поток проходит копирование C-байтов, очередь и настоящее ядро с AES-GCM и журналом; генератор создаёт два вымышленных аккаунта. Задержка передачи включает ожидание обратного давления. Отмена проверяет кооперативный обработчик и весь четырёхкадровый хвост, без обещания принудительно прервать файловую синхронизацию. Сквозное сохранение аварийного хвоста фасадом и восстановление ядра проверены отдельными процессами; реальный idle TDLib остаётся в приёмке.

## Сквозной хвост и восстановление

При восстановлении допускается не более 256 уникальных черновиков и 256 уникальных попыток. Повторная запись существующей сущности не расходует новый слот. Черновик с прежним UUID должен сохранять точное содержимое, как и при обычном сохранении. Превышение предела или изменённый черновик отклоняются при открытии без изменения сегмента и без обращения к транспорту. Это ограничения числа сущностей, а не суммарного объёма их содержимого.

Журнал восстанавливается последовательно: одна запись расшифровывается и передаётся обработчику до расшифровки следующей. Ошибка обработчика немедленно прерывает проход. Ядро становится доступным только после успешного восстановления и сверки сохранённых исходов; при отказе открытый журнал закрывается. Массив всей расшифрованной истории больше не создаётся. Метаданные контейнера и итоговые модели по-прежнему удерживаются в памяти, поэтому это изменение само по себе не устанавливает общий предел памяти клиента и не меняет чтение контейнера при открытии.

Из корня FUM передайте абсолютный путь собранной Release-команды:

```sh
python3 -B Приложения/FUMA/Packages/КлиентTelegram/Проверки/проверить-восстановление.py /путь/к/проверить-telegram
python3 -B Приложения/FUMA/Packages/КлиентTelegram/Проверки/измерить-восстановление.py /путь/к/проверить-telegram
```

Первый исполнитель проводит повреждённый кадр через копирование C-байтов, приёмник, фасад и зашифрованный журнал. Новый процесс сверяет точный хвост, отказ чужого ключа, признак разрыва, отсутствие обращений к транспорту и неизменность сегмента. Отдельно проверяются отказ повторной подготовки и отсутствие автосоздания сегмента при восстановлении. Здесь повторно открывается ядро; перезапуск фасада поверх клиента в карантине не выполняется.

Второй исполнитель создаёт 16, затем 256 синтетических черновиков и незавершённых попыток. Для каждого объёма подготовка и восстановление идут в разных процессах; открытие ядра измеряется отдельно от проверки результата. Приватная квитанция версии 2 связывает исходные тела запросов, попытки и полные pending-события. Восстановление обязано вернуть точные данные с необходимостью разбора и без слепой повторной отправки. [Результаты и ограничения](Профили/README.md) включают объём входа, CPU, RSS и хэши.

Исполнители сами создают каталоги 0700 и случайный ключ 0600. Успешные временные каталоги удаляются только после проверок. При отказе путь сохранённого журнала и ключа выводится в приватный stderr; результаты завершённых фаз профиля остаются в JSON с кодом 2. Проверки не отключаются флагом Python -O. Каждый дочерний процесс ограничен 45 секундами. Новый процесс не означает холодный файловый кэш.

Проверка публикационной справки запускает собранную команду пять раз с `--help`, требует неизменные UTF-8 байты, успешный выход без stderr и отсутствие машинных путей. Она выводит хэши команды и справки, длительности отдельных процессов и медиану; код 1 означает найденные формы путей. Ей передаётся тот же абсолютный путь исполняемого файла:

```sh
python3 -B Приложения/FUMA/Packages/КлиентTelegram/Проверки/проверить-публикацию-справки.py /путь/к/проверить-telegram
```

Это измерение старта CLI, а не обработки Telegram. Оно использует локальный распознаватель путей из того же checkout; время сборки в него не входит. Первый запуск может включать работу системного кэша.

JSON версии 2 также содержит хэши исполнителя и распознавателя. Проверяются все пять объявленных режимов и требование абсолютных путей; пустой или посторонний вывод не считается справкой. Код 2 обозначает неполную справку или отказ процесса: уже полученные измерения остаются в JSON, а захваченный вывод направляется в stderr. Чтение бинарника для SHA перед первым измерением прогревает его файловый кэш.

## Библиотечный жизненный цикл

`СредаКлиента.открыть` создаёт ядро и единственного владельца receive в процессе. `добавитьКлиента` разрешён только до начала закрытия. Возвращённые C-байты копируются до следующего вызова API, затем ограниченная очередь передаёт их последовательно в actor. Клиенты разделяются по `@client_id`, ответы — по `@extra`.

`закрыть` выполняется один раз даже при конкурентных вызовах. Отмена ожидающего вызывающего не отменяет очистку. После остановки потоков неприменённый хвост сохраняется зашифрованным. Если `Closed` не подтверждён либо произошёл разрыв, результат требует разбора, а владелец библиотеки остаётся в карантине до конца процесса. Это исключает повторный receive поверх живого клиента. Успешно загруженный образ также сохраняется до завершения процесса: глобальный менеджер современной TDLib не допускает безопасного произвольного dlclose.

Тайм-аут закрытия ограничивает ожидание событий и кооперативного обработчика. Он не способен прервать зависший системный fsync либо чужой C-вызов. Нельзя считать `@extra`, `sending_id` или тайм-аут подтверждением идемпотентной доставки.

## Состояние, разрешения и хранение

Типизированная авторизация различает параметры, телефон, почту и коды, пароль, QR, Ready, отзыв доступа и закрытие. Полный текущий объект авторизации доступен в `СнимокКлиента.сведенияАвторизации`: интерфейс получает обновляемую ссылку QR, сведения о коде и подсказки 2FA. Регистрация, покупка Premium и неизвестное состояние не проходят автоматически; QR первого среза запрашивается только в ожидании телефона. Прикладные операции требуют Ready и подтверждения аккаунта через getMe. Обновления до этого подтверждения сохраняются до успешного применения каждого элемента.

`загрузитьЧаты` запрашивает основной список; конец загрузки отмечается по коррелированному 404. Позиции обновляются через `updateChatPosition`, `updateChatLastMessage` и `updateChatDraftMessage`. Нулевой `order` удаляет позицию списка, сохраняя объект чата. Серверный draft не изменяет собственный местный черновик. `прочитатьИсторию` возвращает отдельную страницу до 100 сообщений; параметры `от`, `смещение` и `толькоМестная` задаются явно, результат доступен через `взятьОтвет`. Короткая страница не объявляется доказанным концом истории.

Местные черновики не вызывают `setChatDraftMessage`. Отправка текста, документа, альбома и правки текста, подписи или медиа проверяют адресата, разрешение, права канала и применимые свойства сообщения. Перед отправкой сохраняются точное намерение, данные вложений и идентичность попытки. Неопределённая доставка после перезапуска требует явного вызова `сверить`: он читает историю TDLib и не повторяет send. Совпадающий текст под другим ID или отсутствие сообщения на странице не доказывают исход. Частичный отказ альбома сохраняет неизвестные исходы остальных элементов; после перезапуска они требуют разбора. Подтверждённая замена временного ID сохраняется и при поздних обновлениях этого ID.

Корень журнала, база TDLib и её файлы требуют собственных физических каталогов 0700 без расширенного ACL. Ключи — 32 байта; `прочитатьПриватныйКлюч` читает обычный файл 0600 с одной жёсткой ссылкой через удерживаемый дескриптор, проверяет ACL и неизменность метаданных. Каталог базы и каталог файлов должны физически различаться. Секреты авторизации не включаются в семантический журнал действий. Отдельный зашифрованный архив сырого обмена сохраняет исходные тела целиком, поэтому может содержать секреты авторизации.

Журнал шифрует содержимое AES-GCM поверх [контейнера наблюдений](../КонтейнерНаблюдений/README.md). Вложения сохраняются через openat с проверкой фактических дескрипторов и идентичности открытого корня журнала, затем синхронизируются до записи намерения. Само содержимое файлов вложений на диске не зашифровано: доступ ограничивают права и ACL. TDLib позже открывает эти файлы по имени; вызывающая сторона должна сохранять их неизменными. Защита от злонамеренного процесса того же пользователя, игнорирующего владение, не гарантируется.

## Граница приёмки

Синтетические проверки используют вымышленные аккаунты и сообщения. Авторизация реального аккаунта, подключение канала и публикация в Telegram не выполнены. Дальнейшая реальная проверка требует отдельно разрешённых аккаунта, адресата, содержимого и конкретных действий, а также защищённых api_id/api_hash. Переписка и секреты не должны попадать в Git, открытые фикстуры или профили.

Read-state, sponsored messages и полная обработка пользовательского контента остаются условиями будущего полного клиента. Передача чужой переписки модели не выполняется автоматически. CC0 собственного кода FUM не изменяет лицензии TDLib и сборочных зависимостей.

Происхождение перенесённого пакета: [исходный этап жизненного цикла](https://github.com/fum-lab/fum/blob/fe18610b813092b0ce52359533ebaf26d81f5d8c/%D0%96%D1%83%D1%80%D0%BD%D0%B0%D0%BB/2026-09-11_23-10-14_MSK_%D0%B7%D0%B0%D0%B2%D0%B5%D1%80%D1%88%D0%B8%D1%82%D1%8C-%D0%B6%D0%B8%D0%B7%D0%BD%D0%B5%D0%BD%D0%BD%D1%8B%D0%B9-%D1%86%D0%B8%D0%BA%D0%BB-%D0%BA%D0%BB%D0%B8%D0%B5%D0%BD%D1%82%D0%B0-Telegram/%D0%BE%D1%82%D1%87%D1%91%D1%82.md).

## Адресная проверка отказов автономной команды

После сборки команды выполните из корня FUM:

```sh
python3 -B -O Приложения/FUMA/Packages/КлиентTelegram/Проверки/проверить-команду.py /абсолютный/путь/проверить-telegram --проверить-отказы
```

Исполнитель компилирует четыре отдельные синтетические C ABI библиотеки: ответ с неверным `@extra`, ответ без `@extra`, коррелированный `authorizationStateWaitPhoneNumber` и повторяющийся `Closing` без `Closed`. Каждая запускается в отдельном процессе. Ожидаемый результат CLI — код 2 и JSON с причиной `требуется_разбор`. Код 0 самого исполнителя означает, что все четыре ожидаемых отказа и чтение их архивов подтверждены.

Поле `ожиданиеОтветаСекунд` измеряет только ожидание начального коррелированного ответа, включая его отказ. Связывание квитанции, загрузка библиотеки, простой и закрытие имеют отдельные интервалы. Два случая неверной корреляции проверяют внутренний предел ожидания 5 секунд; отсутствие `Closed` проверяет отдельный предел закрытия 5 секунд. Внешний предел каждого процесса — 45 секунд; его превышение считается отказом проверки.

Для каждого архива отдельный процесс сверяет привязку, семь кадров, точные размеры и SHA сырых байтов с независимыми литералами. Две исходящие отправки наблюдаются непосредственно в прежней C-фикстуре. Чтение не должно вызвать отправку или изменить файлы, их режимы и шифротекст. Все обязательные условия этого режима действуют под `-O`; неверные аргументы завершаются кодом 2 до прежнего набора.

Результат — JSON профиля; при неподтверждённой проверке исполнитель возвращает код 2, сохраняет завершённые измерения, фазу, её длительность и частичный stdout/stderr в приватном каталоге, указанном в stderr. Приватные архивы и ключи остаются вне Git. [Сохранённый профиль](Профили/2026-10-02-отказные-сценарии.json) и [его границы](Профили/README.md) относятся к синтетическому пути Debug. Реальная TDLib и общий набор тестов этим запуском не проверяются.

## Диагностика готовности TDLib до сборки

Из физического корня FUM:

```bash
python3 -B Приложения/FUMA/Packages/КлиентTelegram/Проверки/собрать-tdlib.py \
  --корень-репозитория . --только-проверить-зависимость
```

Режим не требует `--выход` и `--openssl-root`. Он возвращает JSON схемы `fum.готовность-зависимости-tdlib.1`: успех в stdout с кодом 0, отказ в stderr с кодом 2. Поля `этап`, `причина` и `пояснение` различают отсутствие регистрации, неверный gitlink, отсутствие локальной копии, изменённую копию, неверные источники и ошибки чтения. Неизвестные флаги и смешение с параметрами сборки дают `неверные_аргументы`.

Чтение сверяет обычный `.gitmodules` с HEAD и индексом, единственный gitlink с закреплённым OID и стадией 0 индекса, физическую локальную копию, её HEAD, чистоту, единственные origin/upstream, вложенные gitlinks, дерево, время коммита и отпечатки исходных объектов. Скрывающие флаги индекса, shallow и partial clone отклоняются. Все Git-чтения очищают `GIT_*`, отключают fsmonitor, optional locks и lazy fetch. Диагностика заканчивается до проверки выходного каталога, toolchain, clone, init/fetch и сборки.

JSON содержит монотонные интервалы профиля, регистрации и исходных объектов; завершённые интервалы сохраняются при отказе. Сообщения ограничены постоянным перечнем причин и не включают частные пути или произвольный Git stderr. Успех подтверждает только локальные входы: доступность зеркала, создание dylib, её загрузка и авторизация проверяются отдельно. В этой ветке TDLib пока отсутствует в `.gitmodules` и HEAD; фактический CLI возвращает `нет_регистрации`.

[Профиль 3 октября](Профили/2026-10-03-готовность-зависимости-TDLib.json) связывает исходники и 18 синтетических тестов под `-O`. Положительная фикстура подставляет свои OID, дерево, время и хэш исходника через API; это не положительная приёмка production CLI с закреплённой TDLib. Тесты сверяют неизменность файлов, режимов, индексов, refs, config и объектов временных репозиториев. Подготовка этих фикстур находится вне проверяемой операции.
