# Сборка и диагностика FUMA на Windows

Первый срез подготавливает нативный Windows-запуск общего Swift-runtime. Сейчас проверены локальные границы сборочной оболочки и чтение реальной Windows VM. Сам общий сценарий операторов и наблюдения на Windows ещё не собран: отсутствуют подготовленный toolchain и принятый Windows-адаптер общего контейнера.

## Проверить существующую VM

На macOS с установленным Parallels Desktop и уже работающей выбранной машиной:

```text
python3 -B Приложения/FUMA/Windows/диагностика.py --машина "Windows 11"
```

Вход — явное имя своей разрешённой VM. Выход — JSON `fum.windows.диагностика.1`: архитектура, версия ОС, разрешаемые в текущем PATH команды, наличие стандартного каталога SDK, статус активации, GPU/драйвер и наличие Vulkan loader. Каждый запрос имеет отдельные код, ошибку и монотонную длительность. `null` означает отсутствие полученного значения; его нельзя превращать в подтверждение готовности. Ненулевой код и ошибка сохраняются отдельно. Нулевой код самой программы означает формирование наблюдений, а не готовый toolchain.

Каждая гостевая команда ограничена 30 секундами. Передача UTF-16LE через `EncodedCommand` сохраняет кавычки и кириллицу. Скрипт не запускает и не останавливает VM, не устанавливает программы, не читает ключи и не меняет активацию. Тайм-аут управляющего процесса не доказывает прекращение команды внутри гостя. Диагностика ограничена разрешёнными командами чтения.

## Явные профили

| Профиль | ОС               | Процесс и Swift target                | Статус                              |
| ------- | ---------------- | ------------------------------------- | ----------------------------------- |
| ARM64   | Windows 11 ARM64 | ARM64; `aarch64-unknown-windows-msvc` | ОС наблюдалась, сборка не выполнена |
| x64     | Windows x64      | x64; `x86_64-unknown-windows-msvc`    | Среда не предоставлена              |

На 15 сентября 2026 года наблюдалась Windows `10.0.26200` в Parallels Desktop `27.0.1 (58670)`. Драйвер — Parallels Display Adapter `20.18.2701.58670`. Swift, Git, Python и WinGet не разрешились в окружении гостевой команды; стандартный каталог Windows Kits/10 не найден. Это ограниченная проверка системного окружения, не полный поиск пользовательских установок. `LicenseStatus=5` соответствует Notification; приобретённые права и активация не подтверждены. Наличие `vulkan-1.dll` не доказывает GPU, ICD, расширение поверхности или успешный рендеринг.

Официальная установка Swift публикует сборки x86_64 и ARM64 и требует C++ toolchain Visual Studio и Windows SDK. Перед установкой в существующую VM нужно закрепить выпуск Swift, точные компоненты MSVC/SDK, установочные хэши/подписи, подходящую лицензию и согласованное окно изменения VM. Эти входы ещё не получены; автоматической установки здесь нет. Вариант ARM64 не означает проверки x64-эмуляции, WSL или кросс-компиляции с macOS.

## Подготовить и исполнить сборку

`собрать.py` требует Python 3.10+; режим плана работает на хосте. Открытая фикстура хранится в [ожидании](фикстуры/ожидание.json) как точные hex-байты. Перед запуском сохраните их в отдельный бинарный файл вне checkout; например, внешняя команда Python принимает путь этого нового файла единственным аргументом:

```text
python -c "import pathlib,sys; pathlib.Path(sys.argv[1]).write_bytes(bytes.fromhex('0041d191f09f8ebb'))" <новый-файл-входа>
```

Полная справка:

```text
python3 -B Приложения/FUMA/Windows/собрать.py --help
```

Обязательные входы: `--пакет` (общий SwiftPM-пакет), `--продукт сценарий-runtime`, `--архитектура arm64|x64`, `--коммит` (полный OID чистого FUM), точная строка `--версия-компилятора` из принятого toolchain, новые непересекающиеся каталоги `--кэш`, `--контейнер` и `--выход` вне checkout, `--определение` внутри закреплённого checkout и `--вход`. Открытая фикстура входа имеет hex `0041d191f09f8ebb`; ожидаемый выход и повтор — `000000004100000051040000bbf30100`. Ожидание задано до запуска, а не вычислено из его результата. Без `--исполнить` выводится только JSON-план команд и `исполнено=false`.

С `--исполнить` программа требует настоящую Windows, чистый checkout на точном OID и совпадающий Swift target. Она последовательно выполняет release `swift test`, `swift build --product`, `swift run --skip-build`; ошибка прерывает цепочку. Каждая команда ограничена 900 секундами. Последняя команда передаёт четыре позиционных аргумента: определение, вход, корень контейнера, каталог результата. Контракт передан Android-исполнителем; точный принятый OID пакета `Приложения/FUMA/Packages/СценарийRuntime` ещё ожидается. Общие Package.swift эта оболочка не меняет.

После успешного запуска проверяются SHA-256 точных файлов `выход.bin` и `повтор.bin`; JSON содержит исходный OID, target, размер, SHA и раздельный профиль трёх команд. Полный контракт многофайлового контейнера и повторного открытия ещё не подключён. При отказе исходные сообщения процесса остаются в консоли, новые каталоги сохраняются для разбора; автоматический повтор и очистка не выполняются. Успех оболочки не заменяет проверки полного общего сценария и GPU.

## Проверки и профиль

```text
python3 -B -m unittest discover -s Приложения/FUMA/Windows/tests -p "test_*.py"
python3 -B Приложения/FUMA/Windows/tests/профиль.py
```

В агентской сессии команды запускаются через установленный учёт проверок. Проверки автономны: отказ чужой ОС/архитектуры, точные байты, прерывание последовательности, кавычки, неизвестное состояние и тайм-аут транспорта. Профиль измеряет только 5 серий по 1000 подготовок команд на хосте; стоимость компилятора и Windows-runtime не измерена. Исходный замер до уточнения позиционного CLI — 426667 нс на 1000 планов; окончательный замер хранится в отчёте с SHA реализации. Изменение алгоритма не обосновано: подготовка команд занимает менее миллисекунды, тогда как реальные диагностические гостевые вызовы занимают сотни миллисекунд и больше. Ускорение сборки этим не заявляется.

## Следующий проверяемый результат

См. [план подготовки инструментов](план-установки.md). Нужны согласованная подготовка инструментов в существующей VM и точный принятый OID общего ядра. Android-исполнитель готовит переносимость операторов и контейнера, но POSIX-адаптер не объявлен Windows-совместимым. После доставки нужно согласовать CLI, сохранить точный вход UTF-8, ожидаемый UTF-32LE и контейнер, собрать и повторно прочитать их на Windows ARM64. Vulkan выбран для будущего GUI; второй DirectX-рендерер в этот срез не входит. Проба реального Vulkan-устройства и `VK_KHR_win32_surface` остаётся отдельным обязательным графическим испытанием.
