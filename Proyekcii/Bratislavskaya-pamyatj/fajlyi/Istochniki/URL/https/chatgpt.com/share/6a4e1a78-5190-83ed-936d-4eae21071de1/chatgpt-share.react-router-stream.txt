Это естественное продолжение идеи FUM: **структурирующие операторы должны служить не только для внутреннего разбора текста, но и для построения человеко-читаемых визуальных интерфейсов знания**.\n\nТо есть один и тот же слой FUM может работать в двух направлениях:\n\n```text\nсырой поток\n→ структурирующие операторы\n→ семантическая структура\n→ компактное представление для LLM\n\nи одновременно:\n\nсемантическая структура\n→ визуальные операторы отображения\n→ графический интерфейс для человека\n```\n\nПричём это не просто “красивая визуализация”. Это может быть **рабочий интерфейс редактирования, проверки и объяснения знания**.\n\n## 1. Структурирующий оператор должен иметь визуальную проекцию\n\nРанее мы говорили, что оператор имеет примерно такие функции:\n\n```text\nrecognize: поток → структура\ngenerate: структура → поток\ncheck: структура → диагностика\ncompress: поток → компактное описание\n```\n\nК этому можно добавить ещё одну важную функцию:\n\n```text\nrender: структура → визуальное представление\n```\n\nТогда оператор становится единицей не только анализа и генерации, но и отображения.\n\nНапример:\n\n```text\nOperator: POSSESSION_FRAME\n\nsemantic structure:\n  Possession {\n    possessor: человек\n    possessed: объект\n  }\n\ntextual realization:\n  RU: \"У меня есть книга.\"\n  EN: \"I have a book.\"\n\nvisual realization:\n  [Человек] ──обладает──> [Книга]\n```\n\nИли:\n\n```text\nOperator: CAUSATION\n\nsemantic structure:\n  Cause(A, B)\n\nvisual realization:\n  [A] ──причина──> [B]\n```\n\nИли:\n\n```text\nOperator: DEFINITION\n\nsemantic structure:\n  Definition(term, meaning)\n\nvisual realization:\n  [Термин] ──определяется как──> [Смысл]\n```\n\nПолучается, что каждый оператор может иметь не только грамматическую и семантическую сторону, но и **визуальную грамматику**.\n\n## 2. Визуальный интерфейс как граф объяснённого знания\n\nЕсли память FUM — это память структурирующих операторов, то на экране можно показывать не просто текстовый ответ LLM, а **граф того, как знание организовано**.\n\nНапример для нашей текущей темы можно было бы построить такой граф:\n\n```text\n[FUM]\n  ├── [память структурирующих операторов]\n  │       ├── [распознавание]\n  │       ├── [порождение]\n  │       ├── [проверка]\n  │       ├── [сжатие]\n  │       └── [визуализация]\n  │\n  ├── [интерфейс человек ↔ LLM]\n  │       ├── [человеческое неявное знание]\n  │       ├── [нейросетевое неявное знание]\n  │       └── [символическая объяснимая форма]\n  │\n  └── [графический интерфейс]\n          ├── [узлы смыслов]\n          ├── [рёбра связей]\n          ├── [конфликты]\n          ├── [остатки]\n          └── [кандидатные операторы]\n```\n\nНо это дерево — только один вид. Та же структура может отображаться как:\n\n```text\nсемантический граф;\nиерархическое дерево;\nтаблица типов;\nкарта понятий;\nдиаграмма зависимостей;\nвременная шкала;\nAST-представление;\nграф доказательства;\nграф программы;\nграф перевода между языками;\nграф конфликтов и неопределённостей.\n```\n\nТо есть FUM должен хранить структуру независимо от конкретной визуальной формы, а интерфейс должен уметь строить разные проекции.\n\n## 3. Важно: интерфейс должен быть двусторонним\n\nСамое сильное следствие: визуализация не должна быть только выводом.\n\nОна должна быть редактируемой.\n\n```text\nFUM → строит граф → человек видит структуру\nчеловек меняет граф → FUM обновляет структуру\nFUM пересчитывает операторы → LLM получает уточнённый контекст\n```\n\nНапример, FUM показал:\n\n```text\n[LLM] ──создаёт──> [структурирующий оператор]\n```\n\nЧеловек может поправить:\n\n```text\nне “создаёт”, а “предлагает кандидат”\n```\n\nТогда граф меняется:\n\n```text\n[LLM] ──предлагает──> [кандидатный оператор]\n[алгоритм проверки] ──подтверждает/отклоняет──> [оператор]\n```\n\nИ это не просто косметическая правка. Это изменение структуры знания.\n\nЗначит, графический интерфейс становится способом **обучения FUM человеком**.\n\n## 4. Семантический zoom\n\nОчень полезной функцией будет семантическое масштабирование.\n\nНа верхнем уровне человек видит только крупные блоки:\n\n```text\n[FUM]\n  → [операторы]\n  → [структура]\n  → [объяснимость]\n  → [интерфейс]\n```\n\nПри приближении раскрываются детали:\n\n```text\n[операторы]\n  → recognizer\n  → generator\n  → checker\n  → renderer\n  → constraints\n  → examples\n  → residuals\n```\n\nЕщё глубже:\n\n```text\nRU_ADJ_NOUN_AGREEMENT\n  input:\n    adjective\n    noun\n\n  constraints:\n    gender equality\n    number equality\n    case equality\n\n  examples:\n    \"работающая программа\" — OK\n    \"работающий программа\" — conflict\n```\n\nТо есть человек может переходить от общего смысла к формальным правилам и обратно.\n\nЭто особенно важно, потому что одна из проблем LLM-интерфейсов — они обычно линейные: всё превращается в текстовый поток. А FUM-интерфейс может быть нелинейным:\n\n```text\nчеловек смотрит на карту смысла,\nа не на километры текста.\n```\n\n## 5. Визуализация остатков и конфликтов\n\nОсобенно ценным будет отображение не только подтверждённого знания, но и проблемных мест.\n\nНапример:\n\n```text\n[входной поток]\n   ↓\n[частично распознанная структура]\n   ↓\n[остаток R17]\n```\n\nНа экране это может выглядеть как узлы с разными статусами:\n\n```text\nподтверждённый оператор\nкандидатный оператор\nконфликт\nнеобъяснённый остаток\nошибка входа\nсомнительное соответствие\n```\n\nНапример:\n\n```text\n\"programmu bystro napisannyj rabotayet\"\n\n[programmu] → RU_NOUN_ACCUSATIVE\n[bystro] → ADVERB\n[napisannyj] → PARTICIPLE_MASC_NOM\n[rabotayet] → VERB_PRESENT\n\nКонфликт:\n  \"programmu\" ожидает modifier в feminine accusative\n  \"napisannyj\" имеет masculine nominative\n```\n\nГрафически человек сразу видит, где структура “ломается”. Это делает FUM не только системой представления знания, но и системой диагностики.\n\n## 6. Визуальный слой как часть памяти операторов\n\nМожно расширить схему оператора так:\n\n```text\nStructuringOperator {\n  id\n  name\n  level\n\n  recognizer\n  generator\n  checker\n  compressor\n\n  input_type\n  output_type\n  constraints\n\n  links_up\n  links_down\n\n  visual_schema\n  interaction_schema\n\n  examples\n  tests\n  confidence\n  provenance\n}\n```\n\nГде:\n\n```text\nvisual_schema\n```\n\nописывает, как оператор показывать человеку:\n\n```text\nузел;\nребро;\nконтейнер;\nтаблица;\nвременной интервал;\nиерархический блок;\nформула;\nкодовый блок;\nдиаграммный паттерн.\n```\n\nА:\n\n```text\ninteraction_schema\n```\n\nописывает, что человек может с ним делать:\n\n```text\nраскрыть;\nсвернуть;\nпереименовать;\nподтвердить;\nотклонить;\nсоединить;\nразделить;\nдобавить пример;\nдобавить контрпример;\nизменить ограничение;\nзапросить объяснение;\nзапросить генерацию текста;\nзапросить проверку.\n```\n\nТогда UI становится не отдельной “надстройкой”, а естественным продолжением оператора.\n\n## 7. Один смысл — много представлений\n\nОдин и тот же объект FUM можно показывать разными способами.\n\nНапример, структура:\n\n```text\nEvent WRITE {\n  agent: speaker\n  object: program\n  property(object): working\n  manner: quickly\n  tense: past\n}\n```\n\nможет отображаться как граф:\n\n```text\n[Speaker] ──agent──> [WRITE]\n[WRITE] ──object──> [Program]\n[Program] ──property──> [Working]\n[WRITE] ──manner──> [Quickly]\n[WRITE] ──tense──> [Past]\n```\n\nкак дерево:\n\n```text\nWRITE\n  agent: speaker\n  object:\n    PROGRAM\n      property: working\n  manner: quickly\n  tense: past\n```\n\nкак таблица:\n\n```text\nrole       value\nagent      speaker\nobject     program\nproperty   working\nmanner     quickly\ntense      past\n```\n\nкак русская фраза:\n\n```text\nЯ быстро написал работающую программу.\n```\n\nкак английская фраза:\n\n```text\nI quickly wrote a working program.\n```\n\nИ как компактный контекст для LLM:\n\n```text\nWRITE(agent=speaker, object=PROGRAM[working], manner=quickly, tense=past)\n```\n\nЭто означает, что FUM должен разделять:\n\n```text\nструктуру знания\n```\n\nи:\n\n```text\nпредставление знания\n```\n\nТогда текст, граф, таблица, дерево и код — это разные виды одной и той же внутренней структуры.\n\n## 8. Это особенно полезно для совместной работы человека и LLM\n\nLLM хорошо работает с текстом, но человеку часто удобнее видеть:\n\n```text\nкарту зависимостей;\nиерархию понятий;\nграф причин;\nструктуру аргумента;\nсхему программы;\nсеть конфликтов;\nцепочку доказательства.\n```\n\nFUM может быть переводчиком между этими режимами:\n\n```text\nLLM генерирует текстовое объяснение\n→ FUM извлекает структуру\n→ UI показывает граф\n→ человек исправляет граф\n→ FUM сериализует исправления\n→ LLM получает точный структурный контекст\n```\n\nТо есть человек не обязан писать длинное уточнение вроде:\n\n```text\n\"Нет, я имел в виду, что LLM не подтверждает оператор, а только предлагает его,\nа подтверждение делает алгоритмический слой...\"\n```\n\nОн может просто поправить ребро в графе:\n\n```text\nLLM ──creates──> Operator\n```\n\nна:\n\n```text\nLLM ──proposes──> CandidateOperator\nChecker ──validates──> Operator\n```\n\nА FUM сам превратит это изменение в текстовый контекст для LLM.\n\n## 9. Графический интерфейс как способ экономии контекстного окна\n\nВизуальный интерфейс также помогает экономить контекст LLM.\n\nЧеловек может работать с большим графом, но в контекст LLM передаётся только активный фрагмент:\n\n```text\ncurrent_focus:\n  node: CandidateOperator\n  neighborhood_depth: 2\n  visible_conflicts: [C12, C18]\n  user_edit:\n    relation changed from \"creates\" to \"proposes\"\n```\n\nТо есть LLM не нужно каждый раз видеть весь граф. Ей можно передавать только:\n\n```text\nлокальный подграф;\nизменения;\nконфликты;\nзапрос пользователя;\nрелевантные операторы.\n```\n\nЭто делает систему гораздо экономнее:\n\n```text\nполное знание хранится в FUM;\nчеловек видит его визуально;\nLLM получает компактный срез.\n```\n\n## 10. Фактически нужен язык визуальных операторов\n\nМожно ввести отдельный класс:\n\n```text\nVisualStructuringOperator\n```\n\nили шире:\n\n```text\nProjectionOperator\n```\n\nОн отвечает за переход:\n\n```text\nсемантическая структура → представление для человека\n```\n\nНапример:\n\n```text\nProjectionOperator: SEMANTIC_GRAPH_VIEW\n\ninput:\n  typed semantic hypergraph\n\noutput:\n  node-edge diagram\n\nrules:\n  entities → nodes\n  binary relations → edges\n  n-ary relations → event nodes\n  confidence → visual marker\n  conflict → diagnostic marker\n  residual → unresolved fragment\n```\n\nДругой оператор:\n\n```text\nProjectionOperator: TYPE_LATTICE_VIEW\n\ninput:\n  operators with type signatures\n\noutput:\n  hierarchy of types and subtypes\n```\n\nЕщё один:\n\n```text\nProjectionOperator: PROOF_GRAPH_VIEW\n\ninput:\n  statements, lemmas, dependencies\n\noutput:\n  proof dependency graph\n```\n\nТо есть визуализация тоже должна быть операторной, а не ad hoc.\n\n## 11. Главное архитектурное разделение\n\nЯ бы предложил такое разделение:\n\n```text\n1. Core FUM graph\n   Внутренняя структура знания: узлы, связи, типы, операторы, ограничения.\n\n2. Operator memory\n   Библиотека структурирующих операторов: распознавание, порождение, проверка.\n\n3. Projection layer\n   Операторы отображения: граф, дерево, таблица, временная шкала, AST, карта.\n\n4. Структурирующий оператор как единица объяснённого знания\n\nСтруктурирующий оператор — это не просто правило. Это минимальная единица знания, которая отвечает сразу на несколько вопросов:\n\n```text\nчто это за структура?\nкак её распознать?\nкак её породить?\nс чем она совместима?\nс чем она конфликтует?\nна каком уровне абстракции она работает?\nкакие примеры её подтверждают?\nкакие ошибки она помогает обнаруживать?\n```\n\nНапример, человек может интуитивно понимать, что в русском языке прилагательное согласуется с существительным. LLM тоже умеет часто правильно это делать. Но FUM должен вынести это в явный оператор:\n\n```text\nOperator: RU_ADJ_NOUN_AGREEMENT\n\nlevel: morphosyntax\ndomain: Russian\ninput:\n  adjective\n  noun\n\nconstraint:\n  adjective.gender = noun.gender\n  adjective.number = noun.number\n  adjective.case = noun.case\n\nrecognize:\n  \"работающую программу\"\n  → agreement(feminine, singular, accusative)\n\ngenerate:\n  noun(\"программа\", accusative, singular)\n  adjective(\"работающий\", feminine, accusative, singular)\n  → \"работающую программу\"\n\ndiagnostics:\n  \"работающий программу\" → agreement conflict\n```\n\nТакой оператор является объяснением сразу в нескольких смыслах:\n\n```text\nон объясняет, почему форма корректна;\nон объясняет, как её получить;\nон объясняет, почему другая форма ошибочна;\nон позволяет автоматически проверять новые случаи;\nон может быть понятен человеку;\nон может быть использован LLM как компактный контекст.\n```\n\nЭто уже не просто “знание внутри модели”, а **объяснённое знание**.\n\n## 3. FUM как общий язык представления знаний\n\nМожно сказать, что FUM-операторы образуют обобщённый язык представления знаний, но не в старом смысле “одной универсальной онтологии для всего”. Скорее это **многоуровневый язык структурирования**.\n\nОн должен уметь описывать:\n\n```text\nформы записи;\nморфологию;\nсинтаксис;\nсемантические роли;\nсобытия;\nпонятия;\nдоказательства;\nпрограммы;\nдокументы;\nпроцедуры;\nошибки;\nнеопределённости;\nпереводы между уровнями.\n```\n\nТо есть FUM-язык должен быть одновременно похож на:\n\n```text\nсистему типов,\nграмматику,\nонтологию,\nAST-представление,\nязык промежуточного представления компилятора,\nбазу правил,\nсистему доказательств,\nпамять примеров.\n```\n\nНо его отличие в том, что он не замкнут на один домен. Он описывает **структурирующие переходы**:\n\n```text\nсырой поток → форма → структура → смысл → действие\n```\n\nИ обратно:\n\n```text\nсмысл → структура → форма → поток\n```\n\n## 4. Человек и LLM как совместные авторы операторов\n\nЗдесь особенно ценна ваша мысль, что и человек, и LLM могут совместно объяснять свои знания в символической форме.\n\nЧеловек часто обладает знанием такого вида:\n\n```text\n\"я понимаю, что здесь что-то не так\"\n\"это звучит неправильно\"\n\"так обычно не говорят\"\n\"здесь не хватает определения\"\n\"эта программа нарушает инвариант\"\n```\n\nНо человек не всегда сразу формулирует это как алгоритм.\n\nLLM часто обладает знанием такого вида:\n\n```text\nможет привести много примеров;\nможет предложить правило;\nможет найти аналогии;\nможет переформулировать;\nможет обобщить;\nможет объяснить вероятную ошибку.\n```\n\nНо LLM тоже может галлюцинировать, быть непоследовательной или давать слишком мягкие объяснения.\n\nFUM должен играть роль третьей стороны:\n\n```text\nчеловек предлагает интуицию;\nLLM предлагает формализацию;\nFUM проверяет оператор на применимость, сжатие, согласованность и воспроизводимость.\n```\n\nТо есть цикл может быть таким:\n\n```text\n1. Человек или LLM замечает устойчивую структуру.\n2. LLM формулирует кандидатный оператор.\n3. FUM применяет его к корпусу примеров.\n4. Алгоритмы проверяют ограничения.\n5. Остатки и конфликты возвращаются человеку/LLM.\n6. Оператор уточняется.\n7. Подтверждённый оператор становится частью памяти.\n```\n\nЭто очень похоже на научный процесс в миниатюре:\n\n```text\nнаблюдение → гипотеза → формализация → проверка → уточнение → использование\n```\n\n## 5. Не просто объяснение, а проверяемое объяснение\n\nКлючевое отличие FUM-объяснения от обычного текстового объяснения LLM в том, что оператор должен быть **машинно применимым**.\n\nОбычная LLM может сказать:\n\n```text\n\"В русском языке прилагательные согласуются с существительными.\"\n```\n\nЭто полезно, но слабо.\n\nFUM-оператор должен позволять сделать:\n\n```text\ncheck(\"работающую программу\") → OK\ncheck(\"работающий программу\") → conflict\ngenerate(noun=программа, case=accusative, adjective=работающий)\n  → \"работающую программу\"\nparse(\"работающую программу\")\n  → structured NP with agreement features\n```\n\nТо есть объяснение становится не только словесным, но и операциональным.\n\nМожно сформулировать так:\n\n> Знание считается объяснённым в FUM не тогда, когда оно красиво описано словами, а тогда, когда оно стало структурирующим оператором, который можно применять, проверять, уточнять и использовать для сжатия потока.\n\n## 6. FUM как интерфейс между мозгом и LLM\n\nЧеловеческий мозг и LLM устроены принципиально по-разному. Но у них есть общая внешняя зона взаимодействия: **символические формы**.\n\nЧеловек не передаёт напрямую состояние мозга. Он говорит, пишет, рисует схемы, исправляет ошибки, приводит примеры.\n\nLLM не передаёт напрямую свои веса. Она генерирует текст, код, структуры, объяснения, примеры, классификации.\n\nFUM может собирать это в общий слой:\n\n```text\nhuman behavior / language\n        ↓\nsymbolic operators\n        ↑\nLLM behavior / generated explanations\n```\n\nПоэтому структурирующие операторы — это не буквальная карта мозга и не буквальная карта весов LLM. Это **согласованный внешний интерфейс смыслов**, через который разные носители знания могут взаимодействовать.\n\nБолее точная формула:\n\n```text\nFUM не обязан быть изоморфен мозгу или LLM.\nFUM должен быть совместим с ними на уровне объяснимого поведения.\n```\n\nЭто сильнее практически, потому что нам нужно не “увидеть мысль как она есть”, а сделать так, чтобы:\n\n```text\nчеловек понял;\nLLM могла использовать;\nалгоритм мог проверить;\nпамять могла сохранить;\nбудущий поток мог быть разобран компактнее.\n```\n\n## 7. Структурирующие операторы как “компилятор смыслов”\n\nМожно представить FUM как компилятор между разными представлениями:\n\n```text\nсырой текст\n→ языковая структура\n→ семантическая структура\n→ проверяемое знание\n→ действие / генерация / вывод\n```\n\nНапример:\n\n```text\n\"У меня есть книга.\"\n```\n\nРусский низкоуровневый разбор:\n\n```text\nу + genitive possessor\nесть + possessed object\n```\n\nВысокоуровневый оператор:\n\n```text\nPOSSESSION {\n  possessor: speaker\n  possessed: book\n}\n```\n\nАнглийское порождение:\n\n```text\n\"I have a book.\"\n```\n\nЗдесь FUM выступает как промежуточное представление:\n\n```text\nRU surface form\n→ RU operators\n→ semantic operator\n→ EN operators\n→ EN surface form\n```\n\nТакой же принцип применим к коду:\n\n```text\nсырой Python-код\n→ AST\n→ типовые структуры\n→ инварианты\n→ намерение программы\n→ проверка / рефакторинг / генерация\n```\n\nИ к математике:\n\n```text\nTeX-текст\n→ формулы\n→ утверждения\n→ зависимости\n→ доказательство\n→ проверяемая структура\n```\n\n## 8. Экономия ресурсов человека и LLM\n\nЗдесь FUM особенно полезен как система экономии внимания и контекста.\n\nБез FUM человек и LLM вынуждены снова и снова работать с сырым потоком:\n\n```text\nдлинный текст;\nдлинный код;\nдлинные рассуждения;\nмного повторяющихся шаблонов;\nмного неявных зависимостей.\n```\n\nС FUM поток превращается в компактное описание:\n\n```text\nDocument {\n  thesis: \"operator memory is the minimal core of FUM\"\n  concepts: [\n    structuring_operator,\n    explainability,\n    symbolic_interface,\n    compression,\n    type_system_analogy\n  ]\n  claims: [\n    operators externalize implicit neural and human knowledge,\n    residuals indicate either errors or missing operators,\n    algorithms verify and apply operators\n  ]\n  unresolved: [\n    exact operator schema,\n    validation protocol,\n    storage format\n  ]\n}\n```\n\nТакое описание можно поместить в контекст LLM гораздо дешевле, чем весь сырой поток. При этом оно не просто краткое, а структурно насыщенное.\n\nТо есть FUM выполняет три вида сжатия:\n\n```text\nсинтаксическое сжатие: убрать повторяющуюся форму;\nсемантическое сжатие: заменить текст структурой смысла;\nоперациональное сжатие: заменить множество случаев одним оператором.\n```\n\nПоследнее особенно важно:\n\n```text\n1000 примеров согласования\n→ один оператор согласования + исключения\n```\n\nИменно поэтому память структурирующих операторов экономит ресурсы не только LLM, но и человека.\n\n## 9. Алгоритмы как проверяющий слой\n\nЧтобы FUM не превратился в ещё одну коллекцию красивых, но непроверенных описаний, ему нужен алгоритмический слой.\n\nОн должен проверять хотя бы такие свойства:\n\n```text\nприменимость: оператор действительно распознаёт нужные фрагменты;\nсжатие: оператор уменьшает описание потока;\nсогласованность: оператор не ломает другие операторы;\nпорождаемость: оператор может генерировать корректные формы;\nдиагностичность: оператор выявляет ошибки;\nобобщаемость: оператор работает не только на одном примере;\nтрассируемость: понятно, откуда оператор взялся;\nобратимость: можно восстановить исходный поток или его существенную часть.\n```\n\nТогда LLM может предлагать гипотезы, но FUM не обязан им слепо верить.\n\nНапример:\n\n```text\nLLM: возможно, здесь есть новый оператор X.\nFUM: применим X к корпусу.\nFUM: X объясняет 37 фрагментов, но конфликтует с 4 сильными ограничениями.\nFUM: сохранить X как candidate_operator с confidence=0.62.\n```\n\nЭто резко повышает надёжность.\n\n## 10. Структурирующий оператор как договор между человеком, LLM и алгоритмом\n\nМожно сказать, что каждый подтверждённый оператор является договором:\n\n```text\nчеловек понимает его смысл;\nLLM может его использовать в рассуждении;\nалгоритм может его применять и проверять.\n```\n\nЭто очень важная тройственность.\n\nЧисто человеческое объяснение может быть понятно, но не алгоритмизируемо.\n\nЧисто нейросетевое знание может быть эффективно, но неявно.\n\nЧисто формальное правило может быть проверяемо, но семантически бедно.\n\nFUM-оператор должен соединять все три качества:\n\n```text\nпонятность;\nэффективность;\nпроверяемость.\n```\n\nИменно в этом смысле он является интерфейсом смыслов.\n\n## 11. Низкий уровень: операторы формы\n\nНа самом нижнем уровне оператор может связывать разные формы записи одного и того же или близкого элемента.\n\nНапример:\n\n```text\nкириллица: человек\nлатиница: chelovek\n```\n\nОператор:\n\n```text\nTranslitRU {\n  chelovek ↔ человек\n}\n```\n\nЗдесь почти нет высокой семантики. Морфологический уровень: языкоспецифические операторы\n\nНапример:\n\n```text\nпрограмма\nпрограммы\nпрограмме\nпрограмму\nпрограммой\n```\n\nсвязываются через оператор лексемы и парадигмы:\n\n```text\nLexemeRU {\n  lemma: программа\n  part_of_speech: noun\n  gender: feminine\n  paradigm: ...\n}\n```\n\nФорма:\n\n```text\nпрограмму\n```\n\nполучает структурное описание:\n\n```text\nlemma: программа\ncase: accusative\nnumber: singular\ngender: feminine\n```\n\nЭто уже не просто соответствие записей, а структурирование языкового материала.\n\nВ английском для похожей сущности будет другой низкоуровневый оператор:\n\n```text\nprogram\nprograms\n```\n\nТам нет падежной парадигмы как в русском, но есть число, артикли, порядок слов, предлоги и так далее.\n\nТо есть на низком уровне:\n\n```text\nрусский оператор ≠ английский оператор\n```\n\nНапример:\n\n```text\nRU: падежное окончание\nEN: позиция в предложении / предлог / артикль\n```\n\nНо оба могут подниматься к одной и той же более высокой роли.\n\n## 3. Синтаксический уровень: частично языковой, частично общий\n\nНапример, русское:\n\n```text\nя написал программу\n```\n\nи английское:\n\n```text\nI wrote a program\n```\n\nимеют разные поверхностные структуры:\n\n```text\nRU:\n  \"я\" — именительный падеж\n  \"программу\" — винительный падеж\n  порядок слов относительно свободный\n\nEN:\n  \"I\" — subject position\n  \"program\" — object position\n  порядок слов более жёсткий\n```\n\nНо на более высоком уровне оба разбираются в одну структуру:\n\n```text\nEvent {\n  type: writing\n  agent: speaker\n  patient/result: program\n  tense: past\n}\n```\n\nИ вот здесь появляются операторы более высокого уровня:\n\n```text\nSemanticRoleOperator {\n  agent\n  action\n  object/result\n  time\n  manner\n}\n```\n\nОни уже могут связывать русский и английский.\n\n## 4. Высокий уровень: межъязыковые семантические операторы\n\nНапример:\n\n```text\nЯ быстро написал работающую программу.\n```\n\nи:\n\n```text\nI quickly wrote a working program.\n```\n\nНа поверхности они устроены по-разному.\n\nРусская структура:\n\n```text\nя\nбыстро\nнаписал\nработающую\nпрограмму\n```\n\nАнглийская структура:\n\n```text\nI\nquickly\nwrote\na\nworking\nprogram\n```\n\nНо FUM может построить общий семантический узел:\n\n```text\nEvent {\n  predicate: WRITE\n  agent: SPEAKER\n  object: PROGRAM\n  object_property: WORKING\n  manner: QUICKLY\n  tense: PAST\n}\n```\n\nТогда русские и английские операторы оказываются не напрямую равными друг другу, а связанными через общий более высокий оператор:\n\n```text\nRU surface structure\n      ↓\nRU morphosyntax\n      ↓\nsemantic event frame\n      ↑\nEN morphosyntax\n      ↑\nEN surface structure\n```\n\nЭто очень важно: **английский и русский не обязательно нужно связывать напрямую слово-к-слову**. Лучше связывать их через промежуточную семантическую структуру.\n\n## 5. Получается не только дерево, но и граф\n\nВы говорите “дерево и иерархия”, и это верно как первое приближение. Но, скорее всего, в полной FUM это будет не чистое дерево, а **многоуровневый граф**.\n\nПочему?\n\nПотому что один низкоуровневый элемент может участвовать в нескольких высокоуровневых структурах.\n\nНапример слово:\n\n```text\nработающая\n```\n\nможет быть:\n\n```text\n1. причастием от \"работать\";\n2. признаком объекта;\n3. частью словосочетания \"работающая программа\";\n4. семантическим свойством \"functioning\";\n5. в другом контексте — частью метафоры.\n```\n\nТо есть связи идут не строго вверх по одному пути, а расходятся:\n\n```text\nформа\n → морфология\n → синтаксис\n → семантическая роль\n → концепт\n → прагматическая функция\n```\n\nПоэтому минимально можно говорить об иерархии, но технически лучше думать о структуре как о DAG/графе:\n\n```text\nнизкие операторы: ближе к сигналу\nвысокие операторы: ближе к смыслу\nрёбра: связи объяснения, порождения, обобщения, перевода, уточнения\n```\n\n## 6. Межъязыковой оператор как “интерфейс”\n\nСравнение с типами здесь снова хорошо работает.\n\nНизкоуровневые операторы похожи на конкретные реализации:\n\n```text\nRussianNounCaseSystem\nEnglishWordOrderSystem\nRussianVerbAspectSystem\nEnglishTenseSystem\n```\n\nА высокоуровневые операторы похожи на интерфейсы:\n\n```text\nAgent\nAction\nObject\nProperty\nTime\nCause\nGoal\nCondition\nModality\nNegation\nQuantification\n```\n\nНапример:\n\n```text\nRU:\n  \"программу\" в винительном падеже\n\nEN:\n  \"program\" после глагола \"wrote\"\n```\n\nоба реализуют более абстрактную роль:\n\n```text\nPatient / Object / Result of action\n```\n\nТо есть:\n\n```text\nRussian accusative case\n  implements SemanticObjectRole in certain constructions\n\nEnglish post-verbal noun phrase\n  implements SemanticObjectRole in certain constructions\n```\n\nЭто очень похоже на:\n\n```text\nclass RussianAccusative implements ObjectMarker\nclass EnglishSVOPosition implements ObjectMarker\n```\n\n## 7. Пример структуры FUM для двух языков\n\nМожно представить так:\n\n```text\nRaw input:\n  \"Ya bystro napisal rabotayushchuyu programmu\"\n\nLevel 0: script/transliteration\n  Ya → Я\n  bystro → быстро\n  napisal → написал\n  rabotayushchuyu → работающую\n  programmu → программу\n\nLevel 1: morphology\n  Я → pronoun, 1st person, singular, nominative\n  написал → verb, past, masculine/perfective\n  работающую → participle/adjective, feminine, accusative, singular\n  программу → noun, feminine, accusative, singular\n\nLevel 2: syntax\n  subject: Я\n  predicate: написал\n  object: программу\n  object_modifier: работающую\n  manner: быстро\n\nLevel 3: semantics\n  Event WRITE\n    agent: speaker\n    object: program\n    property(object): working\n    manner: quickly\n    tense: past\n\nLevel 4: interlingual mapping\n  English generation:\n    \"I quickly wrote a working program.\"\n```\n\nЗдесь английская фраза не хранится как перевод каждой русской формы. Она порождается из более высокого семантического представления.\n\n## 8. Поэтому память операторов должна быть стратифицированной\n\nДля FUM полезно явно хранить уровень оператора:\n\n```text\nOperator {\n  id\n  level\n  language_scope\n  input_type\n  output_type\n  constraints\n  links_up\n  links_down\n  examples\n}\n```\n\nНапример:\n\n```text\nOperator {\n  id: RU_ACCUSATIVE_OBJECT\n  level: morphosyntax\n  language_scope: Russian\n  input_type: RussianNounPhrase\n  output_type: SemanticObjectRole\n  constraints:\n    - accusative case\n    - compatible with transitive verb\n}\n```\n\nИли:\n\n```text\nOperator {\n  id: EN_POSTVERBAL_OBJECT\n  level: syntax\n  language_scope: English\n  input_type: EnglishNounPhrase\n  output_type: SemanticObjectRole\n  constraints:\n    - follows transitive verb in active SVO clause\n}\n```\n\nОба связываются с одним более высоким оператором:\n\n```text\nOperator {\n  id: SEMANTIC_OBJECT_ROLE\n  level: semantics\n  language_scope: crosslingual\n  input_type: event_participant\n  output_type: role_in_event\n}\n```\n\n## 9. Важное следствие для перевода\n\nТогда перевод в FUM — это не операция:\n\n```text\nслово на русском → слово на английском\n```\n\nа операция:\n\n```text\nрусский поток\n→ русская структура\n→ межъязыковая семантическая структура\n→ английская структура\n→ английский поток\n```\n\nТо есть:\n\n```text\nRU raw\n→ RU operators\n→ semantic operators\n→ EN operators\n→ EN raw\n```\n\nЭто лучше, потому что многие вещи не переводятся один-к-одному.\n\nНапример:\n\n```text\nмне холодно\n```\n\nбуквально:\n\n```text\nto me cold\n```\n\nно английская структура:\n\n```text\nI am cold\n```\n\nСемантический центр:\n\n```text\nExperiencerState {\n  experiencer: speaker\n  state: cold sensation\n}\n```\n\nРусский выражает experiencer через дательный падеж:\n\n```text\nмне\n```\n\nА английский — через подлежащее:\n\n```text\nI\n```\n\nЗначит, FUM должен связать:\n\n```text\nRU_DATIVE_EXPERIENCER\n```\n\nи\n\n```text\nEN_SUBJECT_EXPERIENCER\n```\n\nчерез общий оператор:\n\n```text\nEXPERIENCER_ROLE\n```\n\n## 10. Ещё пример: русское “у меня есть”\n\nРусское:\n\n```text\nУ меня есть книга.\n```\n\nАнглийское:\n\n```text\nI have a book.\n```\n\nПоверхностно это разные конструкции.\n\nРусская структура:\n\n```text\nу + genitive possessor\nесть + possessed object\n```\n\nАнглийская структура:\n\n```text\nsubject + have + object\n```\n\nНо семантически:\n\n```text\nPossession {\n  possessor: speaker\n  possessed: book\n}\n```\n\nСоответственно:\n\n```text\nRU_U_MENYA_EST\n  → POSSESSION_FRAME\n\nEN_HAVE_CONSTRUCTION\n  → POSSESSION_FRAME\n```\n\nЭто типичный пример того, почему высокоуровневые операторы должны быть межъязыковыми.\n\n## 11. Что это даёт FUM практически\n\nТакое разделение даёт несколько преимуществ.\n\nВо-первых, FUM может лучше сжимать поток:\n\n```text\n\"Ya bystro napisal rabotayushchuyu programmu\"\n```\n\nвместо хранения как строки можно хранить как:\n\n```text\nWRITE_EVENT(\n  agent=speaker,\n  object=PROGRAM(property=WORKING),\n  manner=QUICKLY,\n  tense=PAST\n)\n```\n\nА поверхностную форму хранить только как ссылку или как восстановимый слой.\n\nВо-вторых, FUM может связывать знания из разных языков:\n\n```text\n\"я написал программу\"\n\"I wrote a program\"\n```\n\nстановятся двумя выражениями одного семантического узла.\n\nВ-третьих, FUM может использовать один язык для уточнения другого. Например, если русская структура неоднозначна, английский перевод или англоязычная парафраза может помочь выбрать семантический разбор.\n\nВ-четвёртых, FUM может хранить знания не как текст на конкретном языке, а как структуру, которую затем можно порождать на разных языках.\n\n## 12. Но полная межъязыковая нейтральность невозможна без потерь\n\nНужно оставить важную оговорку: высокоуровневые операторы могут быть межъязыковыми, но они не всегда будут полностью нейтральными.\n\nНапример, русский вид глагола:\n\n```text\nписал / написал\n```\n\nи английские времена/aspects:\n\n```text\nwrote / was writing / has written\n```\n\nне совпадают идеально.\n\nРусское:\n\n```text\nя писал программу\n```\n\nи:\n\n```text\nя написал программу\n```\n\nразличают процесс и завершённость.\n\nВ английском это можно выразить, но не всегда теми же средствами:\n\n```text\nI was writing a program.\nI wrote a program.\nI have written a program.\n```\n\nПоэтому межъязыковой оператор должен уметь хранить не только общий смысл, но и “семантические остатки”:\n\n```text\ncommon semantic frame\n+\nlanguage-specific features\n+\ntranslation loss / ambiguity\n```\n\nНапример:\n\n```text\nWRITE_EVENT {\n  agent: speaker\n  object: program\n  completion: completed\n  source_language_feature: RU perfective aspect\n}\n```\n\nТо есть FUM должен различать:\n\n```text\nуниверсальную семантику\n```\n\nи:\n\n```text\nязыково-специфические смысловые оттенки\n```\n\n## 13. Это **сигнал остатка**:\n\n```text\nresidual = часть потока, не объяснённая текущей памятью операторов\n```\n\nИ дальше FUM должен решить:\n\n```text\nэто шум?\nэто ошибка?\nэто редкий частный случай?\nэто новый структурный элемент?\nэто уточнение старого оператора?\nэто конфликт между несколькими операторами?\n```\n\n## 2. Минимальное ядро FUM можно определить так\n\nЯ бы сформулировал минимальный FUM-0 так:\n\n```text\nFUM-0 =\n  память структурирующих операторов\n  + механизм применения операторов к потоку\n  + механизм оценки качества структурирования\n  + механизм выделения остатка\n  + механизм предложения новых операторов\n  + механизм сохранения/уточнения операторов\n```\n\nТо есть не нужно сразу строить “полную интеллектуальную систему”. Достаточно начать с системы, которая умеет:\n\n```text\n1. принимать поток;\n2. разбирать его через текущие операторы;\n3. получать структурное описание;\n4. видеть, что осталось необъяснённым;\n5. предлагать новые операторы для лучшего объяснения;\n6. сохранять эти операторы в явной памяти.\n```\n\nЭто уже будет рабочее ядро FUM.\n\n## 3. Оператор должен быть не просто шаблоном, а двусторонним элементом\n\nСтруктурирующий оператор должен работать в две стороны:\n\n```text\nrecognize: поток → структура\ngenerate: структура → поток\n```\n\nНапример, для морфологического оператора:\n\n```text\nОператор: русское существительное женского рода 1-го склонения\n\nrecognize:\n  \"programmu\" → lemma=\"programma\", case=accusative, number=singular\n\ngenerate:\n  lemma=\"programma\", case=accusative, number=singular → \"programmu\"\n```\n\nДля синтаксического оператора:\n\n```text\nОператор: согласование прилагательного с существительным\n\nrecognize:\n  \"rabotayushchuyu programmu\"\n  → Adj agrees with Noun in gender=feminine, case=accusative, number=singular\n\ngenerate:\n  Noun(gender=feminine, case=accusative, number=singular)\n  + adjective stem\n  → adjective form with matching features\n```\n\nДля TeX:\n\n```text\nОператор: theorem-with-proof\n\nrecognize:\n  \\begin{theorem}...\\end{theorem}\n  \\begin{proof}...\\end{proof}\n\ngenerate:\n  structure = Theorem(statement, proof)\n  → TeX block\n```\n\nДля кода:\n\n```text\nОператор: map/filter/reduce pattern\n\nrecognize:\n  цикл с накоплением результата\n  → higher-level operation\n\ngenerate:\n  higher-level operation\n  → concrete loop / comprehension / function call\n```\n\n## 4. Хороший формат оператора\n\nМинимально оператор можно хранить так:\n\n```text\nOperator {\n  id\n  name\n  level\n  input_domain\n  output_structure\n  recognizer\n  generator\n  constraints\n  cost\n  confidence\n  examples_positive\n  examples_negative\n  links_to_other_operators\n  provenance\n  version\n}\n```\n\nГде:\n\n```text\nlevel\n```\n\nуказывает уровень:\n\n```text\nсимволы\nморфемы\nслова\nсловосочетания\nпредложения\nдокументные блоки\nкодовые конструкции\nматематические структуры\nрассуждения\n```\n\n```text\nrecognizer\n```\n\nотвечает за распознавание во входном потоке.\n\n```text\ngenerator\n```\n\nотвечает за порождение обратно в поток.\n\n```text\nconstraints\n```\n\nзадают ограничения, похожие на типовые ограничения:\n\n```text\nприлагательное должно согласоваться с существительным\nпеременная должна быть объявлена до использования\nTeX-блок должен быть закрыт\nдоказательство должно ссылаться на утверждение\nфункция должна возвращать значение нужного типа\n```\n\n```text\ncost\n```\n\nзадаёт цену использования оператора. Это важно, потому что FUM должен не просто “найти любую структуру”, а найти **компактное и полезное описание**.\n\n## 5. Центральная функция: сжатие потока через операторы\n\nОчень сильная формализация здесь такая:\n\n```text\nFUM пытается найти такое описание потока,\nкоторое минимизирует длину описания при помощи известных операторов.\n```\n\nТо есть:\n\n```text\nraw stream X\noperator memory O\nstructured description S\nresidual R\n```\n\nИ задача:\n\n```text\nнайти S и R такие, что:\n\nX ≈ decode(S, O) + R\n\nи при этом:\n\nlength(S) + length(R) минимальна\n```\n\nИными словами:\n\n```text\nхороший оператор = оператор, который уменьшает длину описания потока\n```\n\nНо не только механически уменьшает. Он также должен:\n\n```text\nсохранять воспроизводимость;\nулучшать предсказание;\nбыть применимым повторно;\nсогласовываться с другими операторами;\nне разрушать уже найденную структуру.\n```\n\nЭто делает FUM похожим одновременно на:\n\n```text\nсистему типов,\nпарсер,\nкомпрессор,\nграмматический индуктор,\nпамять шаблонов,\nмеханизм построения AST.\n```\n\n## 6. Остаток как главный источник роста\n\nКлючевая сущность — это **необъяснённый остаток**.\n\nНапример, FUM имеет операторы для обычного предложения:\n\n```text\nSubject + Predicate + Object\n```\n\nИ видит поток:\n\n```text\n\"programmu bystro napisannyj rabotayet\"\n```\n\nСистема пытается разобрать, но что-то не сходится:\n\n```text\n\"programmu\" — винительный падеж\n\"napisannyj\" — мужской род / именительный\n\"rabotayet\" — глагол\n```\n\nВозникает остаток или конфликт.\n\nДальше возможны варианты:\n\n```text\n1. во входе ошибка;\n2. транслитерация исказила форму;\n3. нужна новая модель свободного порядка слов;\n4. нужна модель эллипсиса;\n5. нужна модель смешения русского и латинской записи;\n6. текущий оператор согласования слишком жёсткий.\n```\n\nИ вот здесь FUM не должен сразу “исправлять” поток. Он должен сохранить ситуацию как диагностическую:\n\n```text\nResidual {\n  fragment\n  failed_operators\n  partial_matches\n  conflict_type\n  candidate_explanations\n}\n```\n\nПосле этого LLM или человек может предложить новый оператор.\n\nНапример:\n\n```text\nOperator: loose transliterated Russian morphology\n```\n\nили:\n\n```text\nOperator: malformed-but-recoverable agreement\n```\n\nили:\n\n```text\nOperator: poetic/free word order\n```\n\n## 7. Когда создавать новый оператор, а когда считать это ошибкой\n\nЭто можно решать через несколько критериев.\n\nНовый оператор имеет смысл создавать, если:\n\n```text\nостаток повторяется;\nновый оператор заметно сжимает описание;\nоператор объясняет не один фрагмент, а класс фрагментов;\nоператор согласуется с уже имеющимися структурами;\nоператор помогает порождать корректный выход;\nоператор улучшает дальнейший разбор.\n```\n\nСкорее ошибка или шум, если:\n\n```text\nфрагмент единичный;\nон не даёт повторно используемой структуры;\nон противоречит сильным ограничениям;\nего проще объяснить как опечатку;\nсоздание оператора резко усложняет память;\nоператор нужен только для одного случая.\n```\n\nНо это не бинарное решение. Лучше хранить статус:\n\n```text\ncandidate_operator\nhypothesis\nlow_confidence_operator\nconfirmed_operator\ndeprecated_operator\n```\n\nТо есть новый оператор сначала может попасть в карантин:\n\n```text\nне использовать глобально,\nно учитывать как гипотезу при анализе похожих потоков.\n```\n\n## 8. Роль LLM в пополнении памяти\n\nLLM здесь не должна быть “истиной”. Она должна быть **генератором кандидатов**.\n\nСхема может быть такой:\n\n```text\n1. FUM разбирает поток текущими операторами.\n2. Возникают остатки и конфликты.\n3. LLM получает:\n   - исходный фрагмент;\n   - текущий разбор;\n   - список неудачных операторов;\n   - остаток;\n   - цель сжатия.\n4. LLM предлагает:\n   - новый оператор;\n   - уточнение старого оператора;\n   - исправление входа;\n   - несколько конкурирующих гипотез.\n5. FUM проверяет, даёт ли это лучшее описание.\n6. Если да — оператор сохраняется с confidence/provenance.\n```\n\nТо есть LLM работает как эвристический конструктор:\n\n```text\nresidual → candidate operator\n```\n\nА FUM работает как проверяющая система:\n\n```text\ncandidate operator → compression gain / consistency / reusability\n```\n\nЭто важно: иначе память операторов быстро загрязнится произвольными объяснениями.\n\n## 9. Контекстное окно LLM как причина для компактного описания\n\nОчень важный практический мотив: **структурирование нужно не только ради понимания, но и ради размещения в контекстном окне**.\n\nСырой поток может быть большим:\n\n```text\nмного текста\nмного кода\nмного TeX\nмного логов\nмного промежуточных рассуждений\nмного повторяющихся шаблонов\n```\n\nНо после структурирования его можно передать LLM компактно:\n\n```text\nDocument {\n  type: mathematical_note\n  sections: [\n    Definition(...),\n    Lemma(...),\n    Proof(...),\n    Example(...)\n  ],\n  unresolved: [...]\n}\n```\n\nИли для кода:\n\n```text\nProgramSummary {\n  modules: [...],\n  functions: [...],\n  data_flow: [...],\n  type_conflicts: [...],\n  repeated_patterns: [...]\n}\n```\n\nИли для языкового потока:\n\n```text\nUtteranceStructure {\n  intent: propose_architecture\n  concepts: [FUM, operator_memory, type_system, compression, context_window]\n  claims: [...]\n  unresolved_terms: [...]\n}\n```\n\nВ таком виде LLM получает не 20 тысяч токенов сырья, а 2 тысячи токенов структуры. При необходимости FUM может восстановить детали через ссылки:\n\n```text\nnode_17 → source span 1045:1290\noperator_used → O.syntax.agreement.v2\nresidual → R23\n```\n\nТо есть память операторов становится способом **семантической компрессии с обратной трассировкой**.\n\n## 10. Важно различать lossless и lossy режимы\n\nДля FUM нужно явно различить два режима.\n\n**Lossless-структурирование:**\n\n```text\nструктура + остаток позволяют полностью восстановить исходный поток\n```\n\nЭто нужно для:\n\n```text\nкода,\nTeX,\nюридических документов,\nматематических доказательств,\nлогов,\nданных,\nситуаций, где важна точность.\n```\n\n**Lossy-структурирование:**\n\n```text\nструктура сохраняет смысл, но не все поверхностные детали\n```\n\nЭто подходит для:\n\n```text\nрезюме,\nдиалога,\nпланирования,\nобобщения,\nдолговременной памяти.\n```\n\nВ идеале FUM должен уметь хранить оба слоя:\n\n```text\ncompact semantic structure\n+\nlinks to recoverable raw fragments\n```\n\nТо есть:\n\n```text\nсжать для мышления,\nно не потерять возможность проверки.\n```\n\n## 11. Минимальный цикл работы FUM\n\nМожно описать ядро таким циклом:\n\n```text\ninput_stream X\n\n1. parse(X, operator_memory)\n   → structured_description S\n   → residuals R\n   → conflicts C\n\n2. score(S, R, C)\n   → compression_score\n   → consistency_score\n   → usefulness_score\n\n3. for each residual/conflict:\n      propose candidate operators\n\n4. evaluate candidates:\n      does operator reduce residual?\n      does it generalize?\n      does it conflict with existing operators?\n      can it generate examples?\n      can it explain future/past fragments?\n\n5. save/update operators:\n      confirmed\n      candidate\n      rejected\n      deprecated\n\n6. reparse X with updated memory\n\n7. serialize compact representation for LLM context\n```\n\nВ псевдокоде:\n\n```text\nfunction FUM_ANALYZE(X, O):\n    S, R, C = parse_with_operators(X, O)\n\n    candidates = []\n    for r in R:\n        candidates += propose_operators(r, S, O)\n\n    for op in candidates:\n        gain = compression_gain(X, O, op)\n        consistency = check_constraints(op, O)\n        reuse = estimate_reusability(op, X)\n\n        if gain > threshold and consistency ok:\n            O.add(op, status=\"candidate\")\n\n    S2, R2, C2 = parse_with_operators(X, O)\n\n    return {\n        structure: S2,\n        residuals: R2,\n        conflicts: C2,\n        operator_memory_updates: O.diff(),\n        compact_context: serialize(S2, R2, O)\n    }\n```\n\n## 12. Почему это действительно минимальное ядро\n\nПотому что без памяти операторов FUM остаётся просто системой, которая каждый раз заново пытается понять поток.\n\nА с памятью операторов появляется накопление формы:\n\n```text\nодин раз выделили структуру\n→ сохранили оператор\n→ в следующий раз распознали быстрее\n→ получили более компактное описание\n→ нашли новый остаток\n→ уточнили память\n```\n\nЭто и есть фундаментальный цикл обучения FUM:\n\n```text\nпоток → структура → остаток → новый оператор → лучшая структура\n```\n\nИли ещё короче:\n\n```text\nFUM = саморасширяющаяся система типизации сырого опыта.\n```\n\nТолько “типы” здесь шире, чем в программировании. Это могут быть:\n\n```text\nморфологические типы,\nсинтаксические типы,\nсемантические роли,\nжанры документов,\nшаблоны кода,\nматематические конструкции,\nриторические ходы,\nошибочные паттерны,\nформаты данных,\nпроцедуры рассуждения.\n```\n\n## 13.
