Остаток как главный источник роста\\n\\nКлючевая сущность — это **необъяснённый остаток**.\\n\\nНапример, FUM имеет операторы для обычного предложения:\\n\\n```text\\nSubject + Predicate + Object\\n```\\n\\nИ видит поток:\\n\\n```text\\n\\\"programmu bystro napisannyj rabotayet\\\"\\n```\\n\\nСистема пытается разобрать, но что-то не сходится:\\n\\n```text\\n\\\"programmu\\\" — винительный падеж\\n\\\"napisannyj\\\" — мужской род / именительный\\n\\\"rabotayet\\\" — глагол\\n```\\n\\nВозникает остаток или конфликт.\\n\\nДальше возможны варианты:\\n\\n```text\\n1. во входе ошибка;\\n2. транслитерация исказила форму;\\n3. нужна новая модель свободного порядка слов;\\n4. нужна модель эллипсиса;\\n5. нужна модель смешения русского и латинской записи;\\n6. текущий оператор согласования слишком жёсткий.\\n```\\n\\nИ вот здесь FUM не должен сразу “исправлять” поток. Он должен сохранить ситуацию как диагностическую:\\n\\n```text\\nResidual {\\n  fragment\\n  failed_operators\\n  partial_matches\\n  conflict_type\\n  candidate_explanations\\n}\\n```\\n\\nПосле этого LLM или человек может предложить новый оператор.\\n\\nНапример:\\n\\n```text\\nOperator: loose transliterated Russian morphology\\n```\\n\\nили:\\n\\n```text\\nOperator: malformed-but-recoverable agreement\\n```\\n\\nили:\\n\\n```text\\nOperator: poetic/free word order\\n```\\n\\n## 7. Когда создавать новый оператор, а когда считать это ошибкой\\n\\nЭто можно решать через несколько критериев.\\n\\nНовый оператор имеет смысл создавать, если:\\n\\n```text\\nостаток повторяется;\\nновый оператор заметно сжимает описание;\\nоператор объясняет не один фрагмент, а класс фрагментов;\\nоператор согласуется с уже имеющимися структурами;\\nоператор помогает порождать корректный выход;\\nоператор улучшает дальнейший разбор.\\n```\\n\\nСкорее ошибка или шум, если:\\n\\n```text\\nфрагмент единичный;\\nон не даёт повторно используемой структуры;\\nон противоречит сильным ограничениям;\\nего проще объяснить как опечатку;\\nсоздание оператора резко усложняет память;\\nоператор нужен только для одного случая.\\n```\\n\\nНо это не бинарное решение. Лучше хранить статус:\\n\\n```text\\ncandidate_operator\\nhypothesis\\nlow_confidence_operator\\nconfirmed_operator\\ndeprecated_operator\\n```\\n\\nТо есть новый оператор сначала может попасть в карантин:\\n\\n```text\\nне использовать глобально,\\nно учитывать как гипотезу при анализе похожих потоков.\\n```\\n\\n## 8. Роль LLM в пополнении памяти\\n\\nLLM здесь не должна быть “истиной”. Она должна быть **генератором кандидатов**.\\n\\nСхема может быть такой:\\n\\n```text\\n1. FUM разбирает поток текущими операторами.\\n2. Возникают остатки и конфликты.\\n3. LLM получает:\\n   - исходный фрагмент;\\n   - текущий разбор;\\n   - список неудачных операторов;\\n   - остаток;\\n   - цель сжатия.\\n4. LLM предлагает:\\n   - новый оператор;\\n   - уточнение старого оператора;\\n   - исправление входа;\\n   - несколько конкурирующих гипотез.\\n5. FUM проверяет, даёт ли это лучшее описание.\\n6. Если да — оператор сохраняется с confidence/provenance.\\n```\\n\\nТо есть LLM работает как эвристический конструктор:\\n\\n```text\\nresidual → candidate operator\\n```\\n\\nА FUM работает как проверяющая система:\\n\\n```text\\ncandidate operator → compression gain / consistency / reusability\\n```\\n\\nЭто важно: иначе память операторов быстро загрязнится произвольными объяснениями.\\n\\n## 9. Контекстное окно LLM как причина для компактного описания\\n\\nОчень важный практический мотив: **структурирование нужно не только ради понимания, но и ради размещения в контекстном окне**.\\n\\nСырой поток может быть большим:\\n\\n```text\\nмного текста\\nмного кода\\nмного TeX\\nмного логов\\nмного промежуточных рассуждений\\nмного повторяющихся шаблонов\\n```\\n\\nНо после структурирования его можно передать LLM компактно:\\n\\n```text\\nDocument {\\n  type: mathematical_note\\n  sections: [\\n    Definition(...),\\n    Lemma(...),\\n    Proof(...),\\n    Example(...)\\n  ],\\n  unresolved: [...]\\n}\\n```\\n\\nИли для кода:\\n\\n```text\\nProgramSummary {\\n  modules: [...],\\n  functions: [...],\\n  data_flow: [...],\\n  type_conflicts: [...],\\n  repeated_patterns: [...]\\n}\\n```\\n\\nИли для языкового потока:\\n\\n```text\\nUtteranceStructure {\\n  intent: propose_architecture\\n  concepts: [FUM, operator_memory, type_system, compression, context_window]\\n  claims: [...]\\n  unresolved_terms: [...]\\n}\\n```\\n\\nВ таком виде LLM получает не 20 тысяч токенов сырья, а 2 тысячи токенов структуры. Важно различать lossless и lossy режимы\\n\\nДля FUM нужно явно различить два режима.\\n\\n**Lossless-структурирование:**\\n\\n```text\\nструктура + остаток позволяют полностью восстановить исходный поток\\n```\\n\\nЭто нужно для:\\n\\n```text\\nкода,\\nTeX,\\nюридических документов,\\nматематических доказательств,\\nлогов,\\nданных,\\nситуаций, где важна точность.\\n```\\n\\n**Lossy-структурирование:**\\n\\n```text\\nструктура сохраняет смысл, но не все поверхностные детали\\n```\\n\\nЭто подходит для:\\n\\n```text\\nрезюме,\\nдиалога,\\nпланирования,\\nобобщения,\\nдолговременной памяти.\\n```\\n\\nВ идеале FUM должен уметь хранить оба слоя:\\n\\n```text\\ncompact semantic structure\\n+\\nlinks to recoverable raw fragments\\n```\\n\\nТо есть:\\n\\n```text\\nсжать для мышления,\\nно не потерять возможность проверки.\\n```\\n\\n## 11. Минимальный цикл работы FUM\\n\\nМожно описать ядро таким циклом:\\n\\n```text\\ninput_stream X\\n\\n1. parse(X, operator_memory)\\n   → structured_description S\\n   → residuals R\\n   → conflicts C\\n\\n2. score(S, R, C)\\n   → compression_score\\n   → consistency_score\\n   → usefulness_score\\n\\n3. for each residual/conflict:\\n      propose candidate operators\\n\\n4. evaluate candidates:\\n      does operator reduce residual?\\n      does it generalize?\\n      does it conflict with existing operators?\\n      can it generate examples?\\n      can it explain future/past fragments?\\n\\n5. save/update operators:\\n      confirmed\\n      candidate\\n      rejected\\n      deprecated\\n\\n6. reparse X with updated memory\\n\\n7. serialize compact representation for LLM context\\n```\\n\\nВ псевдокоде:\\n\\n```text\\nfunction FUM_ANALYZE(X, O):\\n    S, R, C = parse_with_operators(X, O)\\n\\n    candidates = []\\n    for r in R:\\n        candidates += propose_operators(r, S, O)\\n\\n    for op in candidates:\\n        gain = compression_gain(X, O, op)\\n        consistency = check_constraints(op, O)\\n        reuse = estimate_reusability(op, X)\\n\\n        if gain \u003e threshold and consistency ok:\\n            O.add(op, status=\\\"candidate\\\")\\n\\n    S2, R2, C2 = parse_with_operators(X, O)\\n\\n    return {\\n        structure: S2,\\n        residuals: R2,\\n        conflicts: C2,\\n        operator_memory_updates: O.diff(),\\n        compact_context: serialize(S2, R2, O)\\n    }\\n```\\n\\n## 12. То есть каждый элемент полезен в обе стороны:\\n\\n```text\\nвосприятие:   поток → структура\\nпорождение:   структура → поток\\n```\\n\\nНапример, слово вместе с парадигмой — это не просто строка `\\\"programma\\\"`, а объект вида:\\n\\n```text\\nлексема: программа\\nчасть речи: существительное\\nрод: женский\\nпарадигма:\\n  именительный: программа\\n  родительный: программы\\n  дательный: программе\\n  винительный: программу\\n  ...\\nсвязи:\\n  может быть объектом глагола\\n  может согласовываться с прилагательным в роде/числе/падеже\\n```\\n\\nТогда при восприятии FUM легче распознаёт форму `\\\"programmu\\\"` как конкретную падежную форму. А при порождении она может выбрать нужную форму автоматически.\\n\\nТо же самое применимо к TeX:\\n\\n```text\\nсырой замысел:\\n  \\\"создать раздел с определением и формулой\\\"\\n\\nструктурные элементы памяти:\\n  \\\\section{}\\n  \\\\begin{definition}...\\\\end{definition}\\n  \\\\[\\n    ...\\n  \\\\]\\n  шаблон математического утверждения\\n  шаблон ссылки на формулу\\n```\\n\\nИли к программированию:\\n\\n```text\\nсырой замысел:\\n  \\\"прочитать файл, распарсить строки, построить словарь\\\"\\n\\nструктурные элементы памяти:\\n  функция\\n  цикл\\n  обработка исключений\\n  словарь\\n  split/parse pattern\\n  типовой шаблон чтения файла\\n  AST-конструкция\\n```\\n\\nПолучается, что FUM должна накапливать не только знания вида:\\n\\n```text\\n\\\"я знаю такой-то факт\\\"\\n```\\n\\nно и знания вида:\\n\\n```text\\n\\\"я знаю такую-то форму\\\"\\n\\\"я знаю такую-то парадигму\\\"\\n\\\"я знаю такой-то шаблон сборки\\\"\\n\\\"я знаю, как этот элемент распознаётся во входном потоке\\\"\\n\\\"я знаю, как этот элемент порождает выходной поток\\\"\\n```\\n\\nЭто можно назвать **памятью структурирующих операторов**.\\n\\nХороший минимальный формат такого элемента мог бы быть таким:\\n\\n```text\\nЭлемент памяти E:\\n\\n1. Каноническая форма\\n2. Набор наблюдаемых вариантов\\n3. Признаки / параметры\\n4. Условия распознавания\\n5. Правила порождения\\n6. Связи с другими элементами\\n7. Уровень абстракции\\n8. История подтверждений\\n```\\n\\nНапример для морфемы:\\n\\n```text\\nE = {\\n  тип: морфема,\\n  форма: \\\"-al\\\",\\n  значение: прошедшее время / мужской род в русском глаголе,\\n  распознавание: встречается в глагольных формах после основы,\\n  порождение: добавляется к основе при образовании формы прошедшего времени,\\n  связи: глагол, время, род, число\\n}\\n```\\n\\nДля синтаксического шаблона:\\n\\n```text\\nE = {\\n  тип: конструкция,\\n  форма: \\\"прилагательное + существительное\\\",\\n  условие: согласование в роде, числе и падеже,\\n  распознавание: соседние элементы с совместимыми признаками,\\n  порождение: выбрать форму прилагательного по признакам существительного\\n}\\n```\\n\\nДля TeX-документа:\\n\\n```text\\nE = {\\n  тип: документная конструкция,\\n  форма: \\\"теорема с доказательством\\\",\\n  шаблон:\\n    \\\\begin{theorem}\\n    ...\\n    \\\\end{theorem}\\n\\n    \\\\begin{proof}\\n    ...\\n    \\\\end{proof}\\n}\\n```\\n\\nТо есть FUM в таком виде становится системой, которая не просто отвечает или генерирует текст, а постепенно строит **многоуровневый словарь структур**:\\n\\n```text\\nуровень 0: сырой сигнал\\nуровень 1: символы / звуки / штрихи\\nуровень 2: морфемы / токены / графемы\\nуровень 3: слова / команды / операторы\\nуровень 4: словосочетания / выражения / AST-узлы\\nуровень 5: предложения / функции / блоки документа\\nуровень 6: рассуждения / программы / статьи / документы\\n```\\n\\nИ тогда новая информация входит в память не хаотично, а через вопрос:\\n\\n```text\\nкакие уже известные элементы объясняют этот поток?\\nкаких элементов не хватает?\\nкакой новый элемент стоит создать?\\nкак он связан с прежними?\\nкак он поможет в будущем распознавать и порождать структуру?\\n```\\n\\nЭто особенно важно для LLM, потому что обычная LLM часто хранит знания распределённо и неявно.
