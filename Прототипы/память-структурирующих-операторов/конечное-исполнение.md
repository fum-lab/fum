# Конечное исполнение операторов

Тот же `AutomationExecutor`, который обслуживает прежние сценарии [прототипа](README.md), исполняет отдельное определение над типизированным входом. Чистый метод `выполнить` возвращает наблюдение и не принимает ожидаемого ответа. Прежний `AutomationFixture` служит проверочным адаптером: переводит шаги в определение, вызывает общий метод, затем сравнивает итог с `expectedOutput` и формирует прежнюю трассу.

## Запуск

Команды выполняются из корня FUM. Для отдельного исходного байтового входа:

```sh
printf '\321\221' | ./Прототипы/память-структурирующих-операторов/запустить.sh исполнить \
  --определение Прототипы/память-структурирующих-операторов/Sources/FUMStructuringOperatorMemory/Определения/UTF-8-в-UTF-32LE.json \
  --вход байты
```

Результат содержит скаляр `1105` (U+0451) и байты `[81,4,0,0]`. Для UTF-32BE следует передать отдельный JSON с `порядок: "BE"` последнего шага; результат — `[0,0,4,81]`. Выбор порядка обязателен и не зависит от архитектуры машины.

Первый самостоятельный пример нормализации текста:

```sh
printf '  ИСПРАВЬ   ОТЧЁТ  ' | ./Прототипы/память-структурирующих-операторов/запустить.sh исполнить \
  --определение Прототипы/память-структурирующих-операторов/Sources/FUMStructuringOperatorMemory/Определения/нормализация.json \
  --вход текст
```

Наблюдаемый результат — `исправь отчёт`. Имя примера означает преобразование регистра и пробелов; это не Unicode NFC/NFD.

Параметры `--определение` и `--вход` обязательны; повторы, неизвестные параметры и лишние аргументы отклоняются. Режим `байты` передаёт stdin без преобразования в `String`; `текст` требует корректный UTF-8; `скаляры` принимает JSON-массив целых Unicode-скаляров. Пробник читает только явно указанный файл определения и конечный stdin, пишет наблюдение в stdout, диагностику — в stderr. При отказе частичный результат не выводится, код завершения равен 1. Сетевых запросов, записи пользовательских файлов и исполнения кода из определения нет. Точка входа SwiftPM создаёт лишь служебную сборку вне Git.

## Закрытое определение

Схема `fum.определение-оператора.1` требует ровно поля `схема`, `идентификатор`, `версия`, `правила`, `шаги`. Каждый шаг содержит ровно `идентификатор`, `оператор`, `аргументы`. Полный пример хранится в [нормализации](Sources/FUMStructuringOperatorMemory/Определения/нормализация.json), байтовые правила — в [UTF-8 → UTF-32LE](Sources/FUMStructuringOperatorMemory/Определения/UTF-8-в-UTF-32LE.json).

| Оператор          | Вход → выход     | Точные поля аргументов                              |
| ----------------- | ---------------- | -------------------------------------------------- |
| `обрезать`        | текст → текст    | пустой объект                                      |
| `нижний-регистр`  | текст → текст    | пустой объект                                      |
| `сжать-пробелы`   | текст → текст    | пустой объект                                      |
| `заменить`        | текст → текст    | `старое`, `новое`: строки; старое непустое           |
| `префикс`        | текст → текст    | `текст`: строка                                    |
| `повторить-правила` | байты → скаляры | `правила`: непустой массив уникальных имён          |
| `упаковать-слова` | скаляры → байты  | `ширина`: 1, 2 или 4; `порядок`: `LE` либо `BE`      |

Именованное правило содержит `идентификатор`, массив `байты` из включительных диапазонов `{от,до}` и массив `поля` из `{байт,маска,сдвиг}`. Номер байта отсчитывается от начала совпадения с нуля; маска применяется до левого сдвига; результаты соединяются побитовым OR. Проверка запрещает выход за границы правила, нулевые маски, переполнение 32 бит и перекрытие выходных битов. Повтор сопоставляет конечные диапазоны и обязательно продвигает курсор на положительную длину правила. Пересекающиеся и префиксные альтернативы отклоняются до исполнения; порядок не служит скрытым разрешением неоднозначности.

Разбор отклоняет неизвестные и повторные поля, включая повтор через JSON-экранирование, неверные типы, повторные идентификаторы, неизвестные операторы и ссылки, неправильные аргументы. Числа только целые; `true`, `false`, `null`, дроби и экспоненты не входят в схему. Пустой список шагов возвращает вход как результат с обычной проверкой пределов. Несоответствие типа очередному оператору даёт явный отказ исполнения.

## Строгий UTF-8 и UTF-32

Определение содержит девять альтернатив из таблицы 3-7 Unicode 17.0.0: `00–7F`; `C2–DF 80–BF`; `E0 A0–BF 80–BF`; `E1–EC 80–BF 80–BF`; `ED 80–9F 80–BF`; `EE–EF 80–BF 80–BF`; `F0 90–BF 80–BF 80–BF`; `F1–F3 80–BF 80–BF 80–BF`; `F4 80–8F 80–BF 80–BF`. Длины, диапазоны и маски — данные определения, а сопоставление, извлечение битов, повтор и упаковка — общие конечные операции.

Сначала получается массив Unicode-скаляров: U+0000…U+10FFFF без U+D800…U+DFFF. Отдельная упаковка шириной 4 возвращает UTF-32 в выбранном порядке. Никакой исправляющий стандартный декодер исходного UTF-8 внутри этого пути не вызывается. Независимые тесты содержат буквальные ожидаемые скаляры и байты для обеих сериализаций.

Избыточные кодировки, отдельные продолжения, неправильные продолжения, суррогаты, значения выше U+10FFFF и оборванный конец отклоняются. `позицияБайта` — абсолютный индекс с нуля первого несовместимого байта по наиболее длинному совпавшему префиксу; при нехватке байта он равен длине входа. `началоПоследовательности` отдельно указывает начало неудачного сопоставления. Например, `41 D1` даёт позицию 2 и начало 1, а `41 E0 9F 80` — позицию 2 и начало 1.

Нормализация Unicode не выполняется. U+FEFF и noncharacters принимаются как скаляры и сохраняются; новый BOM не добавляется, входной U+FEFF не удаляется. Сочетание `е` и U+0308 остаётся двумя скалярами. Упаковка шириной 1 или 2 — общий оператор слов с проверкой вместимости, а не UTF-8 или UTF-16.

## Пределы и наблюдение

| Объект                    | Верхняя граница                                         |
| ------------------------- | ------------------------------------------------------- |
| Файл определения          | 65 536 байтов UTF-8; глубина JSON 16; 8 192 узла          |
| Идентификатор / версия    | 128 байтов без управляющих скаляров / 1…1 000 000        |
| Шаги / правила            | 32 / 32                                                 |
| Байты и битовые поля правила | по 1…8                                               |
| Строковый аргумент        | 4 096 байтов UTF-8                                       |
| Отдельный вход API        | 262 144 байта; скаляр учитывается как 4 байта             |
| Результат каждого шага    | 1 048 576 байтов; скаляр учитывается как 4 байта          |
| Счётчик общих операций    | 16 777 216                                              |
| События правил / следы шагов | 256 / 32                                              |

API позволяет только уменьшать пределы входа, результата, операций и событий. CLI сначала ограниченно читает stdin до 262 144 байтов; для режима `скаляры` дополнительно действуют пределы общего JSON-разбора 65 536 байтов и 8 192 узла. Это конечная обработка всего принятого ввода. Порции чтения `FileHandle` не являются потоковым декодером с сохранением неполного состояния.

Предел результата не равен пределу памяти процесса или размера JSON-отчёта: наблюдение включает результат, промежуточные скаляры и трассу, сериализация временно выделяет память. Текстовые операции используют конечные строки и таблицы Swift/Foundation; промежуточное выделение `lowercased`/обрезки может предшествовать проверке уменьшенного предела результата. Счётчик операций ограничивает шаги, сопоставления, поля, упаковку и явные строковые циклы; он не измеряет инструкции стандартной библиотеки, разбор, хэширование или время CPU. Ограничение памяти процесса и дедлайн исполнения не заявлены. Unicode-версия текстового регистра зависит от runtime; версия 17.0.0 закреплена для нормативных правил байтового определения.

Наблюдение схемы `fum.наблюдение-оператора.1` связывает хэш канонического определения, его версию, тип входа, SHA-256 точных исходных байтов, результат, полученные скаляры и следы шагов. Для входа `скаляры` хэшируются четыре байта BE на скаляр; для текста — его UTF-8. Хэш определения учитывает идентификатор, версию, аргументы, правила и порядок шагов, но не пробелы оформления JSON. Разные определения с одинаковым итогом сохраняют различную идентичность.

События правил сохраняются до предела; остаток отражён в `пропущеноЗаписей`. `хэшНаблюдения` — SHA-256 точного канонического JSON с временно пустым значением этого поля. Канонический кодировщик сохраняет имена ключей, сортирует их и не экранирует слеши. Хэши не архивируют входные данные и не подтверждают их истинность; для последующего воспроизведения вызывающая сторона сохраняет исходник отдельно. Пробник этого файлового эффекта не выполняет.

## Проверки и профиль

Проверка пакета описана в [README](README.md). [Новые автономные тесты](Tests/FUMStructuringOperatorMemoryTests/ПроверкиЧистогоИсполнения.swift) покрывают 23 положительных вектора в обоих порядках, 26 отрицательных векторов с точными позициями, закрытую схему, бюджеты, неоднозначность правил, изменение поведения данными и независимость от ожидания. Прежние сценарии проверяются тем же адаптером; полное наблюдение сравнено побайтно с базой `3fdcb39ce8822102fe8823ee8bf483be2d6581c3`. Совместимость доказана для сохранённых сценариев и отдельных пустых/повторных шагов; произвольные прежние входы за новыми конечными пределами не обещаны.

Флаг `--профиль` оставляет наблюдение детерминированным и пишет JSONL стадий в stderr: загрузка определения и stdin, разбор, повторная проверка типизированного определения, исполнение и трасса. Трасса включает хэши и канонизацию для хэша наблюдения; финальная сериализация stdout и запуск процесса находятся вне стадий. На отказе загрузки или разбора профиль может быть неполным; выполненные стадии проверки/исполнения помечают исход. Все длительности представлены JSON-целыми; единица — наносекунда.

Для воспроизведения профиля собрать Release с `swift build -c release --package-path Прототипы/память-структурирующих-операторов --scratch-path <внешний-каталог-сборки>`, получить путь командой `swift build` с теми же параметрами и `--show-bin-path`, затем запустить:

```sh
python3 -B Прототипы/память-структурирующих-операторов/Проверки/проверить-и-измерить.py \
  --бинарник <путь-к-FUMStructuringOperatorMemoryProbe> \
  --выход <путь-к-профилю-json>
```

[Скрипт](Проверки/проверить-и-измерить.py) проверяет CLI и делает по пять повторов шести фиксированных входов, включая предельный ASCII, смешанный UTF-8, кириллическую замену и большой графемный кластер. Для проверки профиля используется независимый кодек Python, а не исполнитель Swift. Сохраняются версии среды, хэши исходников, бинарника, скрипта, определений, входов и результатов, все замеры и медианы. Скрипт явно пишет выбранный отчёт как проверочный инструмент; это не операция языка определения.

В [профилях до и после](../../Журнал/2026-09-11_07-43-37_MSK_реализовать-интерпретатор-и-UTF-32/отчёт.md) устранение промежуточных массивов сериализации уменьшило медиану трассы предельного ASCII с 375,0 до 49,7 мс; байты наблюдений совпали на всех шести входах. Точные исходники обеих серий восстанавливаются [открытыми проверочными патчами](Проверки/эталоны-профиля/README.md). Это измерение конкретной среды, а не обещание производительности на других системах.
