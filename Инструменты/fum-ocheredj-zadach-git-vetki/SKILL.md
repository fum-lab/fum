# Очередь задач Git-ветки

Очередь допускает к записи в один физический checkout именованной линии только одну корневую задачу. Билеты exact-продолжений получают возрастающий `seq` первым успешным Git compare-and-swap; приоритетов, TTL, перестановки и принудительного обхода нет. Независимые пишущие линии могут исполняться параллельно в разных слотах, а read-only-задача не создаёт FIFO-билет только ради чтения.

Обычный осмысленный коммит последовательной именованной линии является узлом её причинной цепочки. До промежуточного коммита worktree-линии уже существует ровно один первый exact-билет: его могла зарегистрировать самостоятельно открытая задача либо, при отсутствии билета, одна задача, созданная владельцем. Обычная branch FIFO, включая `master`, требует предварительно созданную владельцем задачу и передаёт её идентификатор в `commit`. Терминальные commits результата, ревью и интеграционного кандидата пула, а также `finish-clean`, продолжения не создают.

## Граница двух runtime-профилей

Инструмент содержит два отдельных runtime-профиля и общий read-only-маршрутизатор перед ними. Обычная очередь `ocheredj-zadach-git-vetki.py` сериализует последовательные сессии `master` и других обычных именованных линий в одном физическом checkout через `join` и `commit+handoff`. Пул `пул-worktree-подузлов.py` лениво выделяет независимым линиям разные linked worktree и полные refs, сериализует продолжения каждой линии собственной FIFO слота и передаёт замороженные результаты через независимые ревью и интеграцию.

Профили не подменяют друг друга. Exact-продолжение worktree-линии входит в FIFO пула именно этого слота, полного ref и checkout и не получает новый worktree; `master` использует обычную branch FIFO в первичном checkout. Терминальное назначение писателя, рецензента или интегратора заканчивается квитанцией результата, ревью либо интеграционного кандидата и обязательного продолжения не создаёт. Одна задача не превращается между классами по догадке.

## Доверенная маршрутизация новой задачи

Обычная новая задача Codex начинает из первичного checkout с read-only route, загруженного из актуального закоммиченного `HEAD`. Она передаёт точный корневой `CODEX_THREAD_ID`; маршрутизатор перечитывает актуальный план, полные refs и неизменяемые квитанции активных линий и возвращает ограждённый снимок вариантов. Агент оценивает роль задачи и выбирает один класс:

- read-only-задача получает только право чтения и не резервирует писательский слот;
- независимый писатель атомарно резервирует в состоянии пула, затем идемпотентно переиспользует либо материализует `Подузлы/слот-NNNN` с новым полным ref;
- exact-продолжение выбирает одну линию из exact-снимка; ограждённая команда создаёт неизменяемую квитанцию намерения и регистрирует task в FIFO той же линии, ref и worktree без второго checkout;
- рецензент и интегратор входят только по отдельным exact-назначениям с закреплёнными объектами проверки.

Намерение продолжения может создаться как по exact родительскому prompt перед commit+handoff, так и по самостоятельному выбору новой задаче из свежего снимка активных линий. После создания оно становится одноразовым exact-доказательством: отсутствующая, использованная, stale или несовпавшая квитанция закрывает маршрут отказом и никогда не становится независимым выделением. Имя чата, cwd, похожий ref, один `HEAD`, родительский текст или наличие свободного слота не доказывают класс. `refs/heads/master` является явным исключением размещения: его доказанное продолжение использует первичный checkout, но независимый писатель, открытый из этого каталога без такой квитанции, получает новый ref и слот.

Резервация Git-состояния и создание каталога worktree не образуют одну файловую транзакцию. Поэтому слот сначала получает недоступное другим задачам состояние материализации, а exact повтор после потерянного ответа продолжает ту же резервацию; право содержательной работы появляется лишь после полного физического readback и `admitted`. Сформированный второй bootstrap закрепляет exact относительный путь слота и требует, чтобы все содержательные команды передавали его как `repo-root`.

Первый read-only-вызов обычной новой задачи из чистого первичного checkout:

```text
<HEAD-bootstrap-пула> маршрутизировать \
  --task-id "${CODEX_THREAD_ID:?CODEX_THREAD_ID is required}" \
  --целевая-ссылка refs/heads/master \
  --json
```

Ответ содержит `хэш_маршрутизации`, exact OID каждого обязательного планового источника, активные линии с их FIFO-readback и свободные слоты. Задача обязана перечитать указанные exact-объекты и явно выбрать один класс. Фиксация любого пишущего выбора одной Git-транзакцией CAS-проверяет target, объект пула и все queue OID снимка и сохраняет единственный маршрут exact `task_id`; конкурентный выбор двух линий не может создать две связи. Read-only-класс не создаёт route-ref, не получает право поздней записи и завершается без писательского состояния. Дополнительный неизменяемый ref `refs/fum/task-runtime-routes/<sha256(task_id)>` является общей границей обычной branch-scoped FIFO, bootstrap-перехода `перейти-на-цепочку` и worktree-пула: он атомарно появляется только вместе с первым ticket либо переходной FIFO-записью соответствующего маршрута, навсегда закрепляет exact branch/worktree/queue либо `assignment_hash`, а иной профиль получает закрытый отказ. Параллельная линия резервируется только с тем же хэшем:

```text
<HEAD-bootstrap-пула> зарезервировать-себя \
  --task-id "${CODEX_THREAD_ID:?CODEX_THREAD_ID is required}" \
  --хэш-маршрутизации <sha256:...> \
  --решение параллельная_линия \
  --шаг <exact-step> \
  --разрешённый-путь <path> \
  --json
```

После `worktree_reserved` задача переносит рабочий каталог в exact `путь_worktree` и из него исполняет сценарий из возвращённого `доверенная_ревизия_протокола`, а не из текущего slot `HEAD`:

```text
<bootstrap-пула-из-protocol_oid> подтвердить-и-войти \
  --task-id "${CODEX_THREAD_ID:?CODEX_THREAD_ID is required}" \
  --json
```

Для `последовательное_продолжение` новая задача указывает exact линию и тот же снимок; команда создаёт неизменяемое намерение и FIFO-ticket, но не новый worktree:

```text
<HEAD-bootstrap-пула> присоединиться-к-линии \
  --task-id "${CODEX_THREAD_ID:?CODEX_THREAD_ID is required}" \
  --идентификатор-назначения <assignment-id> \
  --хэш-маршрутизации <sha256:...> \
  --решение последовательное_продолжение \
  --json
```

Полученный `хэш_продолжения` вместе с exact `task_id` идёт в `войти-в-линию-и-ждать` из старого слота. Владелец передаёт первому FIFO-ticket командой `передать-линию --task-id … --поколение … --хэш-продолжения … --файл-сообщения …`. До объекта коммита отдельная CAS закрепляет в дополняемой карте assignment закрытое намерение: логический ключ handoff, exact task и поколение, ref, родителя, дерево, SHA-256 сообщения, Git-идентичности и реальные UTC-даты автора и коммитера. Только свежий readback тех же байтов разрешает записать raw commit object. Следующая CAS-транзакция вместе двигает ref линии и её FIFO и сохраняет состояние пула. В долговечном маршруте родителя и продолжения отдельно сохраняется exact handoff receipt новой схемы `fum.квитанция-commit-handoff-worktree-линии.3`, которая обязательно включает хэш намерения. Прежняя `.2` остаётся читаемой только для recovery и exact replay назначения без соответствующего intent; уже существующие байты не переписываются, а смешение старой версии с новым intent закрывается как downgrade. Поэтому повтор и восстановление остаются однозначными даже после терминала линии и переиспользования физической FIFO слота, а повтор с иным сообщением или staged tree закрывается отказом до движения refs. Продолжение получает `reload_required`, перечитывает доверенный `protocol_oid`, сверяет фактические ref/HEAD/worktree-id и вызывает `подтвердить-вершину-линии --вершина <exact-new-head>`. Лишь `admitted` даёт право записи.

После обрыва любая из этих сессий сначала вызывает read-only `восстановить-сессию --task-id <exact>`. Ответ восстанавливает прежние слот, ref, FIFO, route/continuation hash и следующую команду. Перед допускающим либо терминальным ответом одна verify-only Git-транзакция сверяет exact immutable task-route, pool-ref, queue-ref и вершину worktree `HEAD`; сразу после неё readback подтверждает, что `HEAD` остаётся symbolic-ссылкой exact branch-ref назначения на той же вершине. Исчезнувшая, подменённая или сменившаяся между чтением и ответом связь закрывает восстановление без нового маршрута. Exact-повторы резервации, handoff, ack и терминальной квитанции возвращают прежний исход без дубля, причём handoff и result replay дополнительно требуют прежний хэш сообщения коммита.

Эта проверка даёт устойчивое восстановление среди кооперативных участников одного Git common-dir, но не превращает общий каталог объектов и refs в недоверенную границу безопасности. Процесс с прямым доступом к common-dir, сознательно обходящий протокол, технически может вмешаться; несовпадение будет обнаружено и закрыто, но сам доступ не изолирован.

Текущий документарный и эталонный прототип проверяет exact slot `repo-root` на своих входах, но Codex Desktop пока не предоставляет машинный перенос workspace на уровне host и отдельную ACK-квитанцию этого переноса. Контракт поэтому не является нативной изоляцией host и не доказывает отсутствие чтений первичного checkout: до появления host ACK соблюдение сформированного workdir-маршрута остаётся дополнительной обязанностью агента. Linked worktree также разделяют object database, refs и Git common-dir.

## Пул активных worktree-подузлов

Пул предназначен для локального параллелизма внутри одного физического Git-репозитория. Основной checkout и все слоты обязаны иметь один `git-common-dir`; каждый слот при этом является отдельным linked worktree с собственными `--absolute-git-dir`, `worktree_id`, полным `refs/heads/codex/подузлы/...` и `refs/fum/worktree-subnode-session-queues/...`. Пул не координирует разные клоны, разные common-dir или разные репозитории. Корневой `.gitignore` должен содержать точную отдельную строку, которая Gitignore-якорем от корня исключает каталог `Подузлы`.

Состояние пула хранится каноническим JSON blob под `refs/fum/worktree-subnode-pools/<идентификатор-репозитория>` и меняется только compare-and-swap вместе с затронутыми очередями. Машинно-локальный `primary_root` является частью локального runtime-состояния; переносимым паспортом он не объявляется.

### Безопасный bootstrap пула

Только первая read-only-маршрутизация из чистого первичного checkout может загружать сценарий из точно прочитанного `HEAD`. Незакоммиченный файл рабочего дерева никогда не исполняется:

```text
python3 -I -c 'import os,subprocess,sys;p="Инструменты/fum-ocheredj-zadach-git-vetki/scripts/пул-worktree-подузлов.py";r=sys.argv[1];e={k:v for k,v in os.environ.items() if not (k.upper().startswith("GIT_") or k.upper().startswith("PYTHON") or k.startswith("FUM_TEST_"))};e["GIT_NO_REPLACE_OBJECTS"]="1";e["GIT_OPTIONAL_LOCKS"]="0";b=subprocess.check_output(["git","--no-replace-objects","-C",r,"show","HEAD:"+p],env=e,timeout=30);sys.argv=[p,*sys.argv[2:],"--repo-root",r];exec(compile(b,p,"exec"))' . <команда> <аргументы> --json
```

Далее `<HEAD-bootstrap-пула>` означает всю эту форму до `<команда>` и разрешена только до создания assignment. Как только маршрут вернул `доверенная_ревизия_протокола`, любая команда assignment, включая recovery, handoff, review и integration recovery, обязана исполнять exact байты из этого `protocol_oid`. Непроверенный result/candidate `HEAD` никогда не является источником протокола. `<bootstrap-пула-из-protocol_oid>` использует ту же isolated-форму, но передаёт литеральный `<protocol_oid>` в `git show <protocol_oid>:…`. Прямой вызов файла допустим только в автономной временной фикстуре.

### Выделение слота и восстановление потерянного ответа

Координатор закрепляет полную нагрузку назначения до создания дочерней задачи:

```text
<HEAD-bootstrap-пула> выделить \
  --идентификатор-назначения <assignment-id> \
  --поколение <generation> \
  --идентификатор-попытки <attempt-id> \
  --базовая-вершина <exact-base-OID> \
  --рабочая-ссылка <refs/heads/codex/подузлы/...> \
  --роль <писатель|рецензент|интегратор> \
  --проект <project-id> \
  --шаг <step-id> \
  --разрешённый-путь <путь> \
  --целевая-ссылка <refs/heads/...> \
  --remote <remote-name> \
  --json
```

`--разрешённый-путь` повторяется для каждого непересекающегося пути. Ответ `allocated` либо `allocation_recovered` возвращает идентификаторы слота и worktree, относительный путь `Подузлы/слот-NNNN`, очередь, ref, базу, хэш назначения и готовый `промпт_запуска`. Если процесс потерял ответ после `git worktree add` или переключения ветки, точный повтор с теми же полями восстанавливает тот же слот; новый ref, иной payload или второй assignment с тем же ref закрываются отказом.

Эта полная форма остаётся маршрутом отдельного назначения рецензента, интегратора или терминального писателя. Обычному независимому пишущему чату координатор-родитель не нужен: доверенный маршрут выводит идентичности назначения, frozen base, новый ref и безопасные значения по умолчанию из точного task, актуального плана и состояния пула, затем использует тот же CAS-аллокатор. Exact-продолжение вообще не вызывает выделение, а использует прежние slot, worktree, ref и FIFO своей линии.

Идентичность assignment неизменяема; его карта commit intent только дополняется, а каждая уже закреплённая запись после CAS неизменяема. Рабочий ref, result-ref и выпущенные квитанции меняются только объявленными ограждёнными переходами. Логический ключ намерения не включает дерево, сообщение, время или идентичности: подмена этих входов попадает в прежнюю попытку и даёт `commit_intent_replay_mismatch`, а не вторую дату. Реальное время выбирается только победителем pre-commit CAS и сохраняется в Git raw-форме; author/committer names, emails и dates каждого replay берутся из intent, а эпоха `2000-01-01` для нового intent запрещена. Освобождение не удаляет ref и не сворачивает сохранённый диапазон. Освобождённый физический слот может получить новое поколение и новый ref, но прежние назначения, результаты, ревью, интеграции и публикационные квитанции остаются в истории пула.

### Необратимая миграция прежних дат

До первого merge затронутого пула отдельная миграция обязана исправить весь live-инвентарь legacy-коммитов, а не только результаты выбранного кандидата. Дата каждого seed восстанавливается по единственной записи exact branch reflog и единственному успешному `custom_tool_call_output` того же создающего вызова в `.jsonl`: совпадают task, assignment, call, branch, commit OID и хэш квитанции создающей операции, а секунда reflog равна `floor(timestamp)` ответа. Текущая версия мигратора принимает только доказанные result- и handoff-seed и до lock обязана установить отсутствие legacy merge-seed; появление такого merge закрывает план до отдельного TDD-расширения доказательства на его commit intent и integration receipt. Время начала вызова, поздний detached-HEAD reflog, mtime, тема commit и порядок FIFO не являются заменой. Отсутствие, повтор или расхождение доказательства закрывают сухой план до записи.

Команды `план-миграции-дат`, `заблокировать-миграцию-дат`, `применить-миграцию-дат` и `подтвердить-протокол-после-миграции` работают только из exact закоммиченной ревизии инструмента. Первый lock одной CAS переводит singleton pool `.2 → .3`, связывает exact task, assignment, generation, tool OID и снимки всех branch-, queue-, target- и task-route refs и навсегда закрывает старый `.2`-код. Если legacy final-CAS победила раньше, lock проигрывает и план строится заново с новым commit; если lock победил, старая CAS не двигает ветку. После завершения первой эпохи каждый новый sentinel в любой управляемой ветке блокирует следующий merge и требует открыть и завершить новую ограждённую эпоху `.3 → .3` по свежему полному снимку. Pool к `.2` не понижается.

Под lock мигратор топологически переписывает каждый seed, меняя только author/committer date на `<reflog-epoch> +0000`, а у уже корректно датированных потомков — только mapped parent OID. Tree, сообщение, имена, email и дополнительные raw-заголовки сохраняются. Финальная одна `update-ref`-транзакция создаёт archive refs старых commits и неизменяемую migration receipt, двигает все затронутые branch-, pool- и queue-refs и verify-проверяет все остальные снимки. Старые receipts и assignment identity остаются прежними; migrated handoff/result `.4` являются отдельными supersession-доказательствами. Штатная FIFO не имеет механизма priority bump, и миграция его не вводит: состав и порядок `(task_id, seq, continuation_hash)`, `next_seq`, generation и первый ticket сохраняются без перестановки. Активные владельцы получают `protocol_reload_required`, а reviewer старого immutable result не ретаргетится и требует нового назначения после миграции.

### Создание отдельного назначения, self-registration и host-привязка

Для отдельного назначения координатор передаёт host ровно `промпт_запуска` из ответа `выделить`. Этот путь применяется к рецензенту, интегратору и явно делегированному терминальному писателю, но не требуется обычному независимому чату self-bootstrap. Промпт не содержит абсолютного пути и требует, чтобы новая задача первым инструментальным действием из назначенного worktree выполнила сформированный safe bootstrap. Конкретная команда закрепляет в назначении `protocol_oid`, равный exact вершине целевой ветки при выделении, и загружает сценарий именно из него, а не из непроверенного `HEAD` рецензента:

```text
<bootstrap-пула-из-protocol_oid> войти-и-ждать \
  --идентификатор-назначения <assignment-id> \
  --task-id "${CODEX_THREAD_ID:?CODEX_THREAD_ID is required}" \
  --таймаут-секунды 86400 \
  --json
```

Команда сначала идемпотентно выполняет self-registration единственного неактивного билета, затем ждёт групповой активации. До `state = admitted` ребёнок ничего больше не читает и не меняет. Рецензент не считает свой candidate `HEAD` доверенным источником правил. Отдельная команда `зарегистрироваться` существует для диагностики и фикстур, но штатный дочерний prompt использует составную `войти-и-ждать`.

После наблюдаемой self-registration и точного host-ответа координатор связывает фактическую пару без догадки и повторного создания:

```text
<HEAD-bootstrap-пула> связать-среду \
  --идентификатор-назначения <assignment-id> \
  --task-id <exact-threadId> \
  --host-id <exact-hostId> \
  --json
```

Один `task_id` и один `host_id` не могут принадлежать двум назначениям. Потерянный или неоднозначный host-ответ не разрешает подставить новую задачу либо среду: назначение остаётся неактивным до exact readback и связи.

### Групповая активация и допуск

После exact host-привязки всех совместимых назначений координатор одной транзакцией открывает всю группу:

```text
<HEAD-bootstrap-пула> активировать \
  --идентификатор-назначения <assignment-a> \
  --идентификатор-назначения <assignment-b> \
  --json
```

Группа обязана иметь разные assignment, слот, путь, worktree, queue-ref, branch-ref, task и host. Пересекающиеся области рецензента или интегратора сериализуются; две независимо классифицированные пишущие линии могут работать параллельно даже при пересекающихся областях, потому что их полные refs различаются, а текстовый конфликт обрабатывает отдельный агент-интегратор с повторным ревью. Перед CAS повторно проверяются чистота каждого worktree, exact база, symbolic ref и единственный неактивный билет. Все очереди группы получают один хэш активации атомарно; частичной активации нет.

Ожидающий `войти-и-ждать` сам выполняет переход к владельцу и возвращает `state = admitted`, поколение владения, хэш активации, точные роль, рабочий ref, target-ref и разрешённые пути. Команда `получить-допуск` является отдельным идемпотентным шагом этого же перехода для диагностики и фикстур. Только после допуска задачи группы могут действительно работать параллельно в своих worktree.

### Результат писателя и освобождение слота

Писатель изменяет только разрешённую область и перед терминальным переходом оставляет непустой staged diff без unstaged, untracked или конфликтных путей. Результат фиксируется не обычным `git commit` и не `commit+handoff`, а командой пула:

```text
<bootstrap-пула-из-protocol_oid> зафиксировать-результат \
  --идентификатор-назначения <assignment-id> \
  --task-id <exact-threadId> \
  --message-file <файл-сообщения> \
  --json
```

Команда принимает только роль `писатель`, сверяет каждый staged-путь с закреплённой областью и закрывается, если в FIFO осталось хотя бы одно продолжение. Для односессионного assignment она создаёт один непосредственный commit от базы. Для `self_line` она создаёт финальный commit от текущей вершины и сохраняет в квитанции весь exact линейный диапазон от исходной базы, включая все промежуточные commit+handoff. До raw commit object отдельная CAS закрепляет result-intent с точными входами, идентичностями и датами; та же CAS становится терминальным барьером линии, поэтому более поздний `join` уже не может добавить билет. Падение после intent либо после создания недостижимого объекта восстанавливается по тем же байтам. Одна следующая Git-транзакция двигает рабочий ref, замораживает очередь и записывает новую схему `fum.квитанция-результата-worktree-подузла.3` с обязательными хэшем intent и SHA-256 точных UTF-8-байтов сообщения. Exact повтор возвращает прежний `result_frozen`; иное сообщение, staged tree, владелец, база или нагрузка не переиспользуют намерение и квитанцию. Существующие квитанции `.2` без intent остаются читаемыми для recovery и replay, не дополняются задним числом и не проходят новый изменяющий target merge.

После заморозки координатор освобождает физический слот точным хэшем результата:

```text
<bootstrap-пула-из-protocol_oid> освободить \
  --идентификатор-назначения <assignment-id> \
  --хэш-квитанции-результата <sha256:...> \
  --json
```

Освобождение требует чистый worktree на exact result head, отсутствие владельца и ожидающих FIFO-билетов, восстанавливаемо снимает ветку со слота через detached HEAD и делает слот доступным новому назначению. Result-ref, commit и квитанция не удаляются. После `result_frozen` вся `self_line` терминальна, а её последний владелец больше не меняет слот. Следующая независимая задача, рецензент или интегратор получает свободный физический слот как новое assignment с новым ref.

### Отдельный агент-рецензент

Каждый результат проверяет отдельное назначение с ролью `рецензент`, собственной задачей, host, веткой и worktree. Его `--базовая-вершина` при выделении равна exact head проверяемого объекта. После допуска рецензент выполняет заявленные проверки, сохраняет содержательный отчёт в отдельном обычном файле и фиксирует решение:

```text
<bootstrap-пула-из-protocol_oid> зафиксировать-ревью \
  --идентификатор-назначения-рецензента <reviewer-assignment-id> \
  --task-id <exact-threadId> \
  --хэш-объекта-ревью <result-hash|integration-candidate-hash> \
  --вердикт <принято|на_доработку|отклонено> \
  --отчёт <файл-отчёта> \
  --проверка <проверка> \
  --json
```

`--проверка` повторяется, список не может быть пустым. Рецензент обязан оставить worktree чистым и не создаёт кандидатный commit. Квитанция связывает exact объект, head, ref, task, host, вердикт, проверки и SHA-256 отчёта, после чего слот рецензента освобождается. Проверка `публикационная чистота` одновременно сохраняет durable `publication_pending` intent результата независимо от merge-вердикта. План слияния принимает для каждого result ровно одно отдельное ревью с вердиктом `принято`.

Если exact объект уже вошёл в принятую интеграцию раньше завершения рецензента, поздний ответ не становится новым вердиктом и не меняет `reviews` либо `publications`. Команда проверяет неизменённые object ref, assignment, owner и сохранённый `integration_hash`, отсоединяет чистый reviewer-worktree и одной CAS-транзакцией выдаёт терминальную квитанцию `review_sealed`, освобождая очередь и слот. Потерянный ответ восстанавливается по этой квитанции даже после полного переиспользования физического слота.

### Отдельный агент-интегратор и конфликт слияния

Интегратор также получает отдельное назначение и worktree с ролью `интегратор`, base OID равным ожидаемой вершине цели и точным `target_ref`. После принятых ревью результатов он запускает ограждённый план:

```text
<bootstrap-пула-из-protocol_oid> слить-результаты \
  --идентификатор-назначения-интегратора <integrator-assignment-id> \
  --task-id <exact-threadId> \
  --хэш-результата <result-hash-a> \
  --хэш-результата <result-hash-b> \
  --хэш-ревью <accepted-review-hash-a> \
  --хэш-ревью <accepted-review-hash-b> \
  --json
```

Наборы результатов и ревью закрепляются в плане и не меняются при повторе. До записи плана и заново перед каждым внутренним merge, его recovery и конфликтным commit pool-side-барьер переснимает все канонические live refs пула, требует completed migration epoch `.3`, нулевой достижимый legacy-date остаток и отсутствие stale OID-зависимостей. Обычный result `.3` доказывается intent каждого handoff и terminal result, мигрированный `.4` — полной supersession-цепью от неизменённого old receipt до old/new raw objects. Лишь после этого интегратор последовательно создаёт обычные многородительские merge-коммиты, сохраняя каждый полный result-диапазон в родословной. После подготовки чистого индекса и после ручного разрешения конфликта один логический ключ шага merge закрепляет pre-commit intent с упорядоченными родителями, деревом, сообщением, идентичностями и реальными датами. Raw commit object не вызывает commit hooks и сам не двигает ветку. Следующая единая CAS одновременно сверяет result-, target-, task-route- и рабочую ссылки, двигает рабочий ref, обновляет exact `current_oid` assignment и base владельца очереди и записывает фазу очистки; подтверждённый `MERGE_HEAD` затем очищается идемпотентно до следующего шага. Авария до объекта, после объекта, после CAS либо до очистки восстанавливает тот же OID; иной индекс или промежуточная вершина закрываются mismatch. Если Git обнаруживает конфликт до такого intent, команда возвращает ненулевой код и `state = integration_conflict`, а worktree и владение остаются у того же интегратора. Агент разрешает конфликт в этом worktree, полностью устраняет unmerged и unstaged пути, помещает решение в индекс и продолжает:

```text
<bootstrap-пула-из-protocol_oid> продолжить-слияние \
  --идентификатор-назначения-интегратора <integrator-assignment-id> \
  --task-id <exact-threadId> \
  --json
```

После всего диапазона пул замораживает новую схему `fum.квитанция-интеграционного-кандидата-worktree-подузлов.2`, включая входные результаты и ревью, полный список интеграционных commits, упорядоченные хэши и exact записи использованных commit intent или migration proof. Слот интегратора освобождается, но его ref и кандидат сохраняются. Обновлённый bridge проверяет цепочку merge-intent, достижимость каждого заявленного result head и полный диапазон каждого result. Существующие кандидаты `.1` без новых полей остаются читаемыми для recovery и replay и не переписываются. Единственный кандидат C0 после pool lock не использует старый bridge и не понижает `.3`: независимо проверенный exact новый protocol выполняет одноразовый receipt-bound bootstrap CAS при неизменном первом FIFO-билете. После попадания нового bridge в target все последующие вызовы снова загружаются только из target `HEAD`. Схема `fum.квитанция-CAS-интеграции-worktree-подузлов.1` не меняется.

### Независимое ревью кандидата и exact CAS цели

Интеграционный кандидат независимо проверяет ещё один агент-рецензент. Он выделяется на exact `head_oid` кандидата и вызывает ту же `зафиксировать-ревью`, передавая `integration-candidate-hash`. Ревью отдельных результатов не заменяет это повторное ревью, а интегратор не может одобрить собственный кандидат.

Только отдельная квитанция кандидата с вердиктом `принято` разрешает координатору продвинуть цель:

```text
<bootstrap-пула-из-protocol_oid> продвинуть-цель \
  --хэш-интеграционного-кандидата <sha256:...> \
  --хэш-ревью <accepted-integration-review-hash> \
  --целевая-ссылка <refs/heads/...> \
  --ожидаемая-вершина <exact-base-OID> \
  --task-id <CODEX_THREAD_ID-владельца-основной-FIFO> \
  --generation <generation-владельца-основной-FIFO> \
  --идентификатор-продолжения <exact-threadId-продолжения> \
  --json
```

Команда повторно проверяет candidate ref, exact target/base, отдельное ревью с обязательной проверкой `публикационная чистота`, достижимость всех result heads, exact владельца обычной branch FIFO и заранее созданный ожидающий ticket продолжения. Мост исполняет exact проверенные байты очереди в `python -I`, очищая `GIT_*`, `PYTHON*` и `FUM_TEST_*`; после одноразового C0 источником снова служит только target `HEAD`. Обычная FIFO самостоятельно проверяет закрытый old→new-переход пула: неизменность посторонних полей, exact candidate, принятое независимое ревью, пересчитанный хэш квитанции и exact pending intent. Перед каждым изменяющим target merge мост заново требует pool-wide migration attestation, candidate `.2`, связанные обычные result `.3` либо migrated `.4` и полную exact-цепочку intent/migration proof и raw objects. Барьер не переставляет и не создаёт FIFO-билеты. Checkout сначала готовится к точному дереву кандидата без изменения ref. Затем одна Git-транзакция двигает target, передаёт обычную FIFO ребёнку, создаёт неизменяемую квитанцию принятой интеграции, записывает `fum.квитанция-CAS-интеграции-worktree-подузлов.1`, сохраняет pending intent remote-target и CAS-обновляет пул. Поэтому `master` нельзя сдвинуть под иным FIFO-владельцем, а падение не оставляет очередь на старой базе. Проигранный CAS восстанавливает checkout к фактическому target `HEAD`, а stale base не переписывает конкурирующую вершину; exact повтор восстанавливается из квитанции. Успех является обычным терминальным `commit+handoff`: прежний корень после ответа не выполняет публикацию, а продолжение сначала перечитывает новый HEAD, получает допуск и обрабатывает pending intent.

### Публикация результата и принятой интеграции

Результат можно опубликовать в заранее настроенный именованный remote независимо от merge-вердикта, если хотя бы одно его агентское ревью содержит точную проверку `публикационная чистота`:

```text
<HEAD-bootstrap-пула> опубликовать-результат \
  --хэш-результата <result-hash> \
  --remote <remote-name> \
  --task-id <CODEX_THREAD_ID-владельца-основной-FIFO> \
  --generation <generation-владельца-основной-FIFO> \
  --json
```

Вердикты `на_доработку` и `отклонено` запрещают включать результат в план интеграции, но не уничтожают публикационно чистый кандидат и не запрещают передать его точный ref. Команда никогда не двигает целевой `master`: она публикует неизменный result-ref под тем же полным именем, делает авторитетный `ls-remote` readback и сохраняет отдельную квитанцию.

Принятая локальная интеграция публикуется только по exact CAS-квитанции:

```text
<HEAD-bootstrap-пула> опубликовать-интеграцию \
  --хэш-квитанции-интеграции <integration-hash> \
  --remote <remote-name> \
  --task-id <CODEX_THREAD_ID-владельца-основной-FIFO> \
  --generation <generation-владельца-основной-FIFO> \
  --json
```

Обе команды требуют exact владельца основной FIFO. Политика транспорта принимает ровно один сырой `remote.<name>.url` и не более одного `pushurl`, закрепляет оба значения хэшем intent и передаёт Git буквальный адрес, а не имя remote. Совпадение адреса с remote-псевдонимом и любое применимое `url.*.insteadOf` либо `url.*.pushInsteadOf` закрывают публикацию до транспорта. Push содержит только exact `<OID>:<полный-ref>` и явно отключает follow-tags, рекурсивную публикацию submodule, signed push и push-options, поэтому сопровождающие refs и побочные транспортные действия не добавляются.

Target перед первым push может отсутствовать либо совпадать с локальными base/head, а иная вершина закрывает публикацию. Неоднозначный push, недоступный readback или временный remote-отказ оставляет долговечный `publication_pending`: локальные refs, результаты и интеграция сохраняются. Каждая вновь допущенная корневая задача до выбора следующей карточки автоматически повторяет весь backlog одной командой:

```text
<HEAD-bootstrap-пула> повторить-ожидающие-публикации \
  --task-id <CODEX_THREAD_ID-владельца-основной-FIFO> \
  --generation <generation-владельца-основной-FIFO> \
  --json
```

Retry не создаёт новый слот, результат, ревью или интеграцию и не использует force-push. Подтверждённая публикация требует exact `ls-remote` readback; изменение закреплённого URL или уже опубликованного ref закрывается отказом вместо переписывания.

### Состояние и диагностическая граница

Точное назначение можно читать без изменения:

```text
<bootstrap-пула-из-protocol_oid> состояние --идентификатор-назначения <assignment-id> --json
```

Ответ показывает слот, worktree, очередь, ref, базу, task/host, активацию, результат и ревизию пула. Он не выдаёт полномочие писать, активировать либо переиспользовать чужую задачу. Служебные refs и квитанции пула являются локальным runtime-состоянием и не заменяют переносимые отчёты памяти FUM.

## Безопасный HEAD-bootstrap обычной branch FIFO

Сессия обычной branch FIFO не исполняет сценарий из незакоммиченного рабочего дерева. Все её команды используют одну форму:

```text
python3 -I -c "import os,subprocess,sys;p='Инструменты/fum-ocheredj-zadach-git-vetki/scripts/ocheredj-zadach-git-vetki.py';r=sys.argv[1];e={k:v for k,v in os.environ.items() if not k.upper().startswith('GIT_')};e['GIT_NO_REPLACE_OBJECTS']='1';e['GIT_OPTIONAL_LOCKS']='0';b=subprocess.check_output(['git','--no-replace-objects','-C',r,'show','HEAD:'+p],env=e,timeout=30);sys.argv=[p,*sys.argv[2:],'--repo-root',r];exec(compile(b,p,'exec'))" . <команда> <аргументы>
```

Isolated mode, очистка `GIT_*`, запрет replace-объектов и закреплённый `--repo-root` исключают перенаправление операции через грязный checkout или унаследованную Git-среду. Прямой вызов сценария из рабочего дерева допустим только в автономных временных фикстурах.

## Вход и ожидание

После доверенного маршрута команда `join` применяется только для доказанной обычной branch FIFO, включая `refs/heads/master` в первичном checkout и долговечные непуловые линии. Worktree-линия вместо неё использует `подтвердить-и-войти` для первого владельца либо `присоединиться-к-линии → войти-в-линию-и-ждать` для продолжения. Read-only-задача без писательского допуска ни одну FIFO не занимает.

Задача передаёт свой точный `CODEX_THREAD_ID`:

```text
<HEAD-bootstrap> join --task-id <CODEX_THREAD_ID> --json
```

Замена отсутствующему идентификатору не придумывается. Маршрутизатор до `join` обязан доказать начальную квитанцию входа либо exact-квитанцию продолжения; отсутствие или mismatch не разрешает прямой вход и не создаёт другую линию как резервный маршрут. `admitted` возвращает `generation` и `base_head`, которые владелец сохраняет до терминального перехода. `waiting` не разрешает читать незаконченный diff линии как вход, менять checkout, индекс, refs или внешнее состояние.

Ожидающая задача использует один долгоживущий вызов:

```text
<HEAD-bootstrap> wait-until-actionable --task-id <CODEX_THREAD_ID> --json
```

Запасной ограниченный вызов `wait --timeout-seconds 300` предназначен только для среды, которая не удерживает один процесс. Время не меняет порядок и не снимает билет. Собственный ожидающий билет до допуска можно отменить точной командой `cancel`; чужой билет и владелец этим путём не удаляются.

После коммита предшественника передний билет получает `reload_required`. Задача перечитывает новый закоммиченный `AGENTS.md`, этот навык и затронутые материалы, получает точный `git rev-parse HEAD`, затем выполняет:

```text
<HEAD-bootstrap> ack-head --task-id <CODEX_THREAD_ID> --head <точный-HEAD> --json
<HEAD-bootstrap> wait-until-actionable --task-id <CODEX_THREAD_ID> --json
```

Право записи появляется только после нового `admitted`.

## Переход на активную веточную цепочку

Явно выбранная новая активная карточка цепочки не обходит единый runtime-route. `перейти-на-цепочку` является отдельным bootstrap-профилем ordinary FIFO: первая транзакция одновременно проверяет исходный полный ref на exact исходной вершине, создаёт immutable task-route, отсутствующий `refs/heads/codex/...` на той же вершине и переходную запись пустой очереди; вторая сверяет exact OID текущего `HEAD`, route и объект переходной FIFO, переключает symbolic `HEAD` и допускает того же владельца. Подготовка, допуск и завершённый replay ограждены записанными source HEAD OID, task-route и queue OID; replay дополнительно выполняет единый verify-only снимок symbolic `HEAD`, исходного ref, очереди, route и отсутствия аннулирования. Потерянный ответ восстанавливает только exact переход, а задача с worktree-, delegated- или иным ordinary-маршрутом получает закрытый отказ без движения ветки. Команда принимает точные ID и хэш карточки, исходный полный ref и `HEAD`, требует чистый checkout и пустую очередь; уже допущенный владелец ветку не переключает. Этот специальный branch-bootstrap не является переключением уже выделенного worktree-назначения: обычная новая параллельная линия выбирает свой ref до материализации слота.

## Предактивационный барьер новой fork-ветки

Корневой реестр начального двоичного запуска до host-вызова закрывает первый `join` каждого нового живого клона несвязанным барьером. Для этого в checkout с пустой очередью и точным symbolic `HEAD` он сначала закрепляет веточные ограждения и идентификатор клиентской попытки, ещё не зная будущий `threadId` и не приписывая попытке будущую квитанцию активации:

```text
<HEAD-bootstrap> установить-барьер-предактивации --ветка <refs/heads/...> --базовая-вершина <HEAD> --идентификатор-форка <fork> --поколение-запуска <поколение> --идентификатор-попытки-создания <client-attempt> --идентификатор-назначения <assignment> --хэш-назначения <sha256:...> --идентификатор-ресурсной-попытки <resource-attempt> --хэш-ресурсного-допуска <sha256:...> --json
```

Команда сохраняет неизменяемое ограждение в checkout-scoped Git-реестре схемы `fum.реестр-барьеров-предактивации.2`: exact идентификатор и хэш структурированного назначения, exact идентификатор ресурсной попытки и хэш выданного до host-вызова ресурсного допуска. Реестр `.1` явно fail-closed как устаревший и не мигрируется автоматически. Установка не создаёт FIFO-билет и queue-ref. Повтор с теми же полями является идемпотентным; изменение любого ограждения, ветки или базы закрывает переход. Установка после появления владельца либо ожидающего билета запрещена. Только после её успешного ответа координатор вправе совершить единственный host-вызов создания; неоднозначный исход не разрешает привязку наугад и оставляет все `join` закрытыми состоянием `задача_барьера_не_связана`.

После точного ответа host координатор отдельным CAS связывает барьер с фактическими `threadId`, `hostId`, хэшем полного конверта и канонически пересчитанным хэшем этой привязки; этот переход ещё не открывает FIFO и не записывает будущую квитанцию:

```text
<HEAD-bootstrap> связать-задачу-барьера --task-id <threadId> --host-id <hostId> --хэш-конверта <sha256:...> --хэш-привязки <sha256:...> --ветка <refs/heads/...> --базовая-вершина <HEAD> --идентификатор-форка <fork> --поколение-запуска <поколение> --идентификатор-попытки-создания <client-attempt> --идентификатор-назначения <assignment> --хэш-назначения <sha256:...> --идентификатор-ресурсной-попытки <resource-attempt> --хэш-ресурсного-допуска <sha256:...> --ожидаемый-объект-реестра <OID-несвязанного-реестра> --json
```

Дублирующая, неточная или устаревшая привязка не меняет реестр. Связанная неактивная задача может выполнить своё обязательное первое действие `join`, но получает `предактивация_не_подтверждена`: ни билет, ни queue-ref при этом не возникают. Пока exact-задача не вошла после открытия, любая другая задача этой ветки получает `барьер_предактивации_занят`.

Только после единого CAS корневого реестра координатор открывает барьер точным объектом прежнего Git-реестра:

```text
<HEAD-bootstrap> открыть-барьер-предактивации --task-id <threadId> --ветка <refs/heads/...> --базовая-вершина <HEAD> --идентификатор-форка <fork> --поколение-запуска <поколение> --идентификатор-попытки-создания <client-attempt> --идентификатор-назначения <assignment> --хэш-назначения <sha256:...> --идентификатор-ресурсной-попытки <resource-attempt> --хэш-ресурсного-допуска <sha256:...> --квитанция-активации <sha256:...> --хэш-предактивации <sha256:...> --хэш-привязки-пары <sha256:...> --хэш-привязки-пары <sha256:...> --хэш-активации <sha256:...> --ожидаемый-объект-реестра <OID-связанного-реестра> --json
```

Открытие сравнивает все ограждения, exact CAS-основу и неизменную веточную вершину, требует ровно два разных сортированных хэша host-привязок и само пересчитывает общее корневое доказательство схемы `.2` из поколения, хэша предактивации, общей квитанции и этой пары. Хэш каждой host-привязки схемы `.2` коммитит все четыре exact ресурсных поля своей стороны, поэтому общий хэш активации связывает обе разные ресурсные стороны транзитивно, а не подмешивает branch-local tuple в общий payload. Повтор точного успешно открытого перехода восстанавливает ту же запись; устаревший объект или изменённое поле отклоняются. Первый последующий `join` одной транзакцией проверяет неизменность реестра барьеров, исходного branch-ref и активированной базовой вершины и записывает обычный FIFO-билет. Выделенный `seq` и ожидающий билет не доказывают допуск exact-задачи: до её фактического перехода во владельца чужой билет не создаётся, отмена её ожидающего билета не открывает чужой первый допуск, а повторный exact-вход снова проверяет исходную базу. Атомарный переход exact-задачи во владельца сохраняет в очереди неизменяемое свидетельство, после которого продолжения могут регистрироваться обычным FIFO. Первый и каждый последующий билет сохраняют и перед допуском повторно сверяют все четыре exact поля с открытым checkout-scoped барьером. Checkout навсегда связан с одной начальной веткой: переключение symbolic `HEAD` не открывает обход. После входа exact-задачи ветка использует только прежний унарный протокол продолжений; родительская FIFO не выдаётся за владение ребёнка, а барьер не становится планировщиком, диспетчером или вторым владельцем.

## Работа владельца

Владелец не вызывает обычный `git commit`, не переключает ветку и не позволяет субагентам менять индекс или историю. Корень может параллельно делегировать непересекающиеся файлы, но до staging и терминального перехода дожидается всех процессов и субагентов, способных позднее записать результат.

Если законная работа не требует изменения — например, прямой веточный selector вернул `done` или `not_ready`, — владелец останавливает писателей и выполняет:

```text
<HEAD-bootstrap> finish-clean --task-id <CODEX_THREAD_ID> --generation <generation> --json
```

Команда требует неизменный `HEAD`, чистые индекс и рабочее дерево и одной Git-транзакцией передаёт FIFO без коммита. Узкий `finish-own-clean` восстанавливает такое же чистое завершение только для точного текущего владельца и не обходит проверки. После `finished_clean` прежняя задача ничего не меняет и не создаёт продолжение.

## Предварительное создание продолжения обычной branch FIFO

Этот раздел относится к `master` и другим обычным именованным веткам, но не к FIFO self-line пула, описанной выше. До host-вызова владелец обычной branch FIFO завершает содержательную работу, проверки, журнальный отчёт, recency, публикационный просмотр diff и staging. Затем ограждённый переход закрепляет неизменяемую квитанцию продолжения и формирует prompt:

```text
<HEAD-bootstrap> сформировать-промпт-продолжения --task-id <CODEX_THREAD_ID-владельца> --json
```

Квитанция связывает идентичность именованной линии, полный текущий `refs/heads/...`, физический checkout, его FIFO, родительские task и generation и исходный `HEAD`. Prompt содержит её точный хэш и идентичность родителя, не содержит абсолютного пути, host-идентификатора или заранее выбранной карточки и требует от ребёнка первым инструментальным действием выполнить доверенный read-only-маршрут. Маршрут регистрирует `join` той же branch FIFO; отсутствие, использование или mismatch квитанции закрывает вход без независимого выделения.

Родитель получает exact сохранённый проект через host `list_projects` и ровно один раз вызывает `create_thread` в этом проекте с локальной средой, без явных `model`, `thinking` и второго worktree. Новая host-задача использует тот же физический checkout обычной линии; для `master` он остаётся первичным. Успех доказывают только непустые точные `threadId` и `hostId` одного ответа. Ошибка, тайм-аут, потерянный ответ или один `clientThreadId` запрещают коммит и автоматический повтор: возможное создание нельзя отличить от отсутствия.

Созданная задача до передачи только предъявляет квитанцию маршрутизатору, выполняет `join` со своим фактическим `CODEX_THREAD_ID` и ждёт. Родитель продолжает лишь после read-only `status`, подтверждающего ровно один билет с exact `task_id = threadId`, хэшем квитанции продолжения, теми же worktree/FIFO/полной веткой и `acknowledged_head`, равным `base_head` владельца. Этот билет не обязан быть первым: уже зарегистрированные более ранние задачи сохраняют позиции, а продолжение не получает скрытого приоритета. `hostId` и сохранённый проект проверяет родитель на host-границе; очередь доказывает Git-сторону связи.

## Атомарный commit+handoff

После exact waiting-билета владелец вызывает:

```text
<HEAD-bootstrap> commit --task-id <CODEX_THREAD_ID-владельца> --generation <generation> --идентификатор-продолжения <threadId-ребёнка> --message-file <файл> --json
```

Активированный протокол последовательной именованной линии машинно требует `--идентификатор-продолжения` и связанную с билетом exact-квитанцию продолжения. Единственное bootstrap-исключение — текущая сессия, уже допущенная прежним `HEAD`: миграционная задача один раз закрепляет эквивалентные prompt и квитанцию сама и всё равно заранее создаёт exact ожидающего ребёнка. Наличие канонического маркера в новом `HEAD` активирует требование, а связанный коммит закрепляет необратимый признак в очереди; последующее удаление маркера не возвращает legacy-режим. Терминальные commits result, review и integration candidate пула проходят собственные команды и квитанции и этим требованием не охватываются.

До `write-tree` и `commit-tree`, а затем повторно на свежем объекте очереди внутри CAS команда проверяет:

- точных владельца, `generation`, полный ref и исходный `HEAD`;
- отсутствие unstaged, untracked и конфликтных путей и наличие непустого staged-дерева;
- отличие ребёнка от владельца;
- ровно один exact waiting-билет ребёнка;
- `acknowledged_head` ребёнка, равный `base_head` владельца.

Если билет отменился после первой проверки, Git может получить недостижимые tree/commit/blob-объекты, но branch-ref, queue-ref и квитанция не меняются. Документируемая атомарность относится к ссылкам и наблюдаемому состоянию, а не к отсутствию недостижимых объектов.

Успешная `update-ref --stdin`-транзакция одновременно:

- двигает точный `refs/heads/...` с `base_head` на новый коммит;
- снимает владельца и сохраняет `last_completion` со связью, не переупорядочивая ожидающие билеты;
- создаёт неизменяемую квитанцию продолжения под branch- и checkout-scoped `refs/fum/`.

Квитанция связывает физическую рабочую копию, полный ref, родительские `task_id` и `generation`, старый и новый HEAD и exact идентификатор ребёнка. Она не перезаписывается следующей передачей FIFO. Поэтому повтор той же команды после потерянного Git-ответа возвращает прежний `committed` даже после `finish-clean` или коммита ребёнка; иной либо отсутствующий идентификатор даёт безопасный отказ. Для связанного коммита снятые dispatcher-, reservation-, claim-, ledger- и analytics-переходы не исполняются.

Успех принимается только при нулевом коде и полном единственном JSON с точными `state = committed`, `task_id`, `generation`, `old_head`, `new_head`, `branch_ref`, полным `queue_oid` и `идентификатор_продолжения`. Неизвестный исход разрешает лишь точный повтор этой Git-команды с тем же ребёнком, но не второй `create_thread`.

После `committed` родитель не меняет Git, checkout, очередь или host-состояние и не вызывает `create_thread`, `push` либо публикацию. Разрешены только финальный ответ и интерфейсные директивы.

## Работа продолжения обычной branch FIFO

Когда билет ребёнка обычной branch FIFO после одной или нескольких передач становится первым, он получает `reload_required`, перечитывает фактический текущий `HEAD` из того же checkout, выполняет `ack-head` и дожидается `admitted`. Более ранняя задача могла законно добавить в тот же ref следующий коммит; старый prompt не закрепляет ребёнка на прежней вершине и не разрешает другой checkout. После допуска он сначала вызывает `повторить-ожидающие-публикации` профиля пула со своими exact `task_id` и `generation`, а затем напрямую вызывает:

```text
python3 Инструменты/fum-sleduyusjhij-shag-vetki/scripts/branch-next-step.py show --repo-root . --json
```

Между сессией и selector нет heartbeat, диспетчера, общей резервации или карточочного claim. `ready` разрешает исполнить одну точную карточку; `done` и `not_ready` приводят к `finish-clean`. Каждый собственный коммит ребёнка повторяет предварительное создание следующего продолжения.

## Диагностика и восстановление

Read-only `status --json` показывает текущий полный ref, queue OID, владельца, ожидающие билеты и `next_seq`. Очередь хранится как канонический JSON blob под checkout-scoped `refs/fum/worktree-task-queues/...` и поддерживает SHA-1 и SHA-256 object format.

Периодический heartbeat, постоянная задача диспетчера, автоматическое возобновление, `heartbeat-status`, общий реестр заданий, reservation/claim и починка автозапуска сняты. Оставшиеся CLI и refs прежних схем являются только исторической совместимостью и не дают текущей задаче полномочий. Ни молчаливое падение, ни долгое выполнение не разрешают автоматически удалить билет.

Старый dispatcher-only штатный сброс также не является действующим маршрутом. Открытое требование безопасного host-stop не реализовано текущей поверхностью. Доступный человеку `./sbrositj.sh` — отдельный подтверждаемый break-glass: он строит точный TTY-план, архивирует обслуживаемые runtime-refs, восстанавливает индекс и tracked-дерево к текущему HEAD, удаляет только подтверждённые неигнорируемые обычные файлы и символические ссылки и выпускает свежую пустую очередь. Он не останавливает Codex-задачи, не выясняет исход неоднозначного `create_thread` и не создаёт продолжение.

Обычная branch FIFO не координирует отдельные клоны и отклоняет одну именованную ветку, открытую сразу в нескольких worktree. Detached HEAD в этом профиле не поддерживается. Отдельный пул выше намеренно координирует linked worktree одного common-dir, но только с разными полными branch refs и собственными очередями слотов; это не расширяет полномочия обычной очереди. Процесс, сознательно игнорирующий `AGENTS.md`, технически не перехватывается.

## Публикация

Локальный `commit+handoff` обычной branch FIFO не выполняет push. Ручная публикация пользователя либо отдельно авторизованный низкоуровневый `publish` остаётся самостоятельным транспортным действием с точными commit/ref/URL и не входит в причинную цепочку продолжений. Команды `опубликовать-результат` и `опубликовать-интеграцию` принадлежат только отдельному профилю пула и требуют его квитанции, проверки и авторитетный remote-readback.
