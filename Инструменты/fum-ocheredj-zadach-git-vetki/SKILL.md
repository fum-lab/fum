# Очередь задач Git-ветки

Автоматизация разрешает запускать несколько независимых корневых задач Codex в одной рабочей копии одновременно, но допускает к изменению checkout только одну из них. Порядок строгий: задачи обслуживаются по возрастающему `seq`, который назначен первым успешным compare-and-swap при регистрации. Переупорядочивание, приоритеты и принудительная передача места не поддерживаются.

Это кооперативный контракт `AGENTS.md`, а не project hook. Для штатного запуска не нужны `/hooks`, одобрение определения hook, POSIX `flock`, hard links, сигналы или отдельные действия человека.

## Безопасный вход из HEAD

Все штатные команды очереди используют один HEAD-bootstrap:

```text
python3 -I -c "import os,subprocess,sys;p='Инструменты/fum-ocheredj-zadach-git-vetki/scripts/ocheredj-zadach-git-vetki.py';r=sys.argv[1];e={k:v for k,v in os.environ.items() if not k.upper().startswith('GIT_')};e['GIT_NO_REPLACE_OBJECTS']='1';e['GIT_OPTIONAL_LOCKS']='0';b=subprocess.check_output(['git','--no-replace-objects','-C',r,'show','HEAD:'+p],env=e,timeout=30);sys.argv=[p,*sys.argv[2:],'--repo-root',r];exec(compile(b,p,'exec'))" . <команда> <аргументы>
```

На системе с другим именем запуска Python используй доступное средство запуска Python 3, сохраняя isolated mode `-I`, код и остальные аргументы. Отдельный аргумент `.` задаёт корень текущего checkout. Isolated mode исключает грязный checkout и пользовательские Python-настройки из поиска импортов. Bootstrap удаляет унаследованные `GIT_*` из среды загрузочного `git show`, игнорирует replace-объекты, ограничивает чтение 30 секундами и добавляет доверенный `--repo-root` после пользовательских аргументов. Сценарий для каждого внутреннего Git-вызова отключает replace-объекты и optional locks и удаляет все унаследованные `GIT_*`, включая trace-файлы, перенаправления репозитория, индекса, object database, namespace и Git-конфигурации. CLI не принимает сокращённые имена параметров. Поэтому ожидающая задача не исполняет незавершённую версию автоматизации из общего diff и не может случайно перенаправить очередь в другой каталог или записать trace в checkout.

Прямой вызов `Инструменты/fum-ocheredj-zadach-git-vetki/scripts/ocheredj-zadach-git-vetki.py` из рабочего дерева запрещён в обычной сессии и используется только автономными тестами разработки.

## Регистрация корневой задачи

Первым действием корневая задача получает точный `CODEX_THREAD_ID` из среды и выполняет:

```text
python3 -I -c "import os,subprocess,sys;p='Инструменты/fum-ocheredj-zadach-git-vetki/scripts/ocheredj-zadach-git-vetki.py';r=sys.argv[1];e={k:v for k,v in os.environ.items() if not k.upper().startswith('GIT_')};e['GIT_NO_REPLACE_OBJECTS']='1';e['GIT_OPTIONAL_LOCKS']='0';b=subprocess.check_output(['git','--no-replace-objects','-C',r,'show','HEAD:'+p],env=e,timeout=30);sys.argv=[p,*sys.argv[2:],'--repo-root',r];exec(compile(b,p,'exec'))" . join --task-id <корневой-CODEX_THREAD_ID> --json
```

Не придумывай замену отсутствующему `CODEX_THREAD_ID`.

Результат `admitted` возвращает `ticket_id`, `seq`, `generation` и `base_head`. Сохрани `task_id` и `generation`: только эта пара разрешает итоговую передачу. Результат `waiting` возвращает текущую позицию и не разрешает изменять файлы, индекс, ветки или внешнее состояние.

Повторный `join` того же владельца или ожидающего билета идемпотентен. Билет не имеет TTL и не удаляется по времени.

## Переход на ветку карточки цепочки

Если новая корневая задача явно начинает реализацию единственной активной [карточки цепочки шагов](../../Глоссарий/карточка-цепочки-шагов.md), её первым инструментальным действием вместо отдельного `join` служит HEAD-bootstrap-команда:

```bash
python3 -I -c "import os,subprocess,sys;p='Инструменты/fum-ocheredj-zadach-git-vetki/scripts/ocheredj-zadach-git-vetki.py';r=sys.argv[1];e={k:v for k,v in os.environ.items() if not k.upper().startswith('GIT_')};e['GIT_NO_REPLACE_OBJECTS']='1';e['GIT_OPTIONAL_LOCKS']='0';b=subprocess.check_output(['git','--no-replace-objects','-C',r,'show','HEAD:'+p],env=e,timeout=30);sys.argv=[p,*sys.argv[2:],'--repo-root',r];exec(compile(b,p,'exec'))" . перейти-на-цепочку \
  --task-id "$CODEX_THREAD_ID" \
  --chain-card Планирование/карточки-цепочек-шагов/<карточка>.md \
  --expected-chain-id FUM-ЦЕПОЧКА-NNNN \
  --expected-card-sha256 sha256:<64-hex> \
  --expected-source-branch-ref refs/heads/<исходная-ветка> \
  --expected-source-head <точный-Git-OID> \
  --json
```

Первая версия перехода намеренно узкая. Она требует именованную исходную ветку, точный `HEAD`, полностью чистые index/worktree, канонически пустую очередь и отсутствующий целевой ref `refs/heads/codex/...` из карточки. Одна Git-транзакция проверяет exact symbolic `HEAD`, отсутствие checkout-scoped tombstone и объект очереди, создаёт целевой ref ровно на исходной вершине и заменяет пустую очередь переходной записью. Пока эта запись активна, обычные `join`, ожидание, передача, commit и другие операции закрыты. Поскольку обе ветки указывают на один commit и дерево, следующая Git-транзакция одним атомарным исходом выполняет `symref-update HEAD <целевая-ветка> ref <исходная-ветка>`, повторно проверяет отсутствие tombstone и заменяет переходную запись обычной очередью уже с целевой веткой, `текущая_цепочка` и владельцем той же задачи. Эти symref-команды требуют Git версии не ниже `2.46`; текущий зарегистрированный Git имеет версию `2.54.0`. Реализация выполняет безмутирующий preflight и при отсутствии symref-транзакций отказывает как `unsupported_git_symref_transaction`; старого неатомарного fallback через отдельный `symbolic-ref` нет. Ответ `admitted` возвращает обычные `ticket_id`, `seq`, `generation` и `base_head`; отдельный `join` после него не нужен.

Активная или ожидающая очередь, dirty/staged/untracked-состояние, неверный хэш или идентификатор карточки, target вне `refs/heads/codex/`, уже существующий target либо несовпавшие исходные ref/OID дают отказ до переключения. Повтор точного вызова после потерянного ответа идемпотентно возвращает тот же допуск, если symbolic `HEAD`, владелец и сохранённая идентичность цепочки совпадают. Переход между разошедшимися ветками, reset/force, remote-ref и переключение уже допущенным владельцем эта версия не разрешает.

## Ожидание

Ожидающая корневая задача по умолчанию запускает одно бесшумное ожидание до действенного состояния:

```text
python3 -I -c "import os,subprocess,sys;p='Инструменты/fum-ocheredj-zadach-git-vetki/scripts/ocheredj-zadach-git-vetki.py';r=sys.argv[1];e={k:v for k,v in os.environ.items() if not k.upper().startswith('GIT_')};e['GIT_NO_REPLACE_OBJECTS']='1';e['GIT_OPTIONAL_LOCKS']='0';b=subprocess.check_output(['git','--no-replace-objects','-C',r,'show','HEAD:'+p],env=e,timeout=30);sys.argv=[p,*sys.argv[2:],'--repo-root',r];exec(compile(b,p,'exec'))" . wait-until-actionable --task-id <корневой-CODEX_THREAD_ID> --json
```

`wait-until-actionable` удерживает один локальный процесс, продолжает внутри него пятиминутные окна read-only-наблюдения и не печатает промежуточный `waiting`. Пока более ранний билет остаётся владельцем или ожидающим, команда не меняет checkout, индекс, ветку, историю или Git-ссылку очереди. Она завершается и выдаёт ровно один итоговый JSON только при действенном состоянии, например `reload_required`, `admitted`, `dirty` или ошибке. При освобождении очереди допуск владельца остаётся обычным атомарным CAS-переходом.

В пределах, разрешённых более приоритетной политикой обновлений host, во время неизменного ожидания агент не отправляет пользователю отдельные промежуточные сообщения, отчёты о ходе или пересказы состояния. Если инструмент среды вернул дескриптор ещё работающего процесса, продолжается именно этот процесс: команда очереди не запускается заново, а пустые host-проверки не получают отдельного содержательного комментария. Если среда поддерживает удержание продолжений процесса внутри одного инструментального или оркестрационного вызова, используй эту форму, чтобы промежуточные проверки по возможности не возвращались в контекст модели. Служебные возвраты и обязательные обновления, навязанные host, остаются вне контроля репозиторной команды. Прерывание во время достоверно неизменного `waiting` не снимает билет. При неоднозначном результате та же корневая задача повторяет идемпотентный `join`: он определяет, осталась ли задача ожидающей или уже стала владельцем, и возвращает существующее `generation` без второго допуска.

Ограниченный пятиминутный `wait` остаётся запасным путём для среды, которая не способна безопасно удерживать долгоживущий вызов, а также для явной диагностики и тестов:

```text
python3 -I -c "import os,subprocess,sys;p='Инструменты/fum-ocheredj-zadach-git-vetki/scripts/ocheredj-zadach-git-vetki.py';r=sys.argv[1];e={k:v for k,v in os.environ.items() if not k.upper().startswith('GIT_')};e['GIT_NO_REPLACE_OBJECTS']='1';e['GIT_OPTIONAL_LOCKS']='0';b=subprocess.check_output(['git','--no-replace-objects','-C',r,'show','HEAD:'+p],env=e,timeout=30);sys.argv=[p,*sys.argv[2:],'--repo-root',r];exec(compile(b,p,'exec'))" . wait --task-id <корневой-CODEX_THREAD_ID> --timeout-seconds 300 --json
```

Запасной вызов возвращает неизменное `waiting` не раньше чем через 300 секунд. Такой результат не получает отдельного содержательного сообщения или рассуждения сверх того, что требует host; следующий ограниченный вызов начинается первым доступным инструментальным ходом, но неизбежный служебный возврат может занять модельный контекст. Внутренний опрос Git-ref завершается раньше при действенном переходе и не создаёт heartbeat blob/ref churn. Более поздний билет не обходит более ранний билет, даже если уже подтвердил текущий `HEAD`.

После коммита предшественника передний билет получает `reload_required`: сохранённый `acknowledged_head` больше не совпадает с текущим `HEAD`. Тогда задача:

1. Читает текущие закоммиченные `AGENTS.md` и этот `SKILL.md` заново, а также материалы, которые изменил предшественник.
2. Получает точный текущий object ID командой `git rev-parse HEAD`.
3. Подтверждает именно его:

```text
python3 -I -c "import os,subprocess,sys;p='Инструменты/fum-ocheredj-zadach-git-vetki/scripts/ocheredj-zadach-git-vetki.py';r=sys.argv[1];e={k:v for k,v in os.environ.items() if not k.upper().startswith('GIT_')};e['GIT_NO_REPLACE_OBJECTS']='1';e['GIT_OPTIONAL_LOCKS']='0';b=subprocess.check_output(['git','--no-replace-objects','-C',r,'show','HEAD:'+p],env=e,timeout=30);sys.argv=[p,*sys.argv[2:],'--repo-root',r];exec(compile(b,p,'exec'))" . ack-head --task-id <корневой-CODEX_THREAD_ID> --head <object-id-HEAD> --json
```

4. Снова вызывает `wait-until-actionable` и начинает мутирующую работу только после `admitted`.

Собственный ожидающий билет можно снять без влияния на остальных:

```text
python3 -I -c "import os,subprocess,sys;p='Инструменты/fum-ocheredj-zadach-git-vetki/scripts/ocheredj-zadach-git-vetki.py';r=sys.argv[1];e={k:v for k,v in os.environ.items() if not k.upper().startswith('GIT_')};e['GIT_NO_REPLACE_OBJECTS']='1';e['GIT_OPTIONAL_LOCKS']='0';b=subprocess.check_output(['git','--no-replace-objects','-C',r,'show','HEAD:'+p],env=e,timeout=30);sys.argv=[p,*sys.argv[2:],'--repo-root',r];exec(compile(b,p,'exec'))" . cancel --task-id <корневой-CODEX_THREAD_ID> --ticket-id <собственный-ticket_id> --json
```

Владелец не использует `cancel`: он передаёт очередь через `commit` либо через узкий `finish-clean`, если изменений действительно нет.

## Работа владельца и субагентов

Владелец не переключает ветку и не применяет обычный `git commit`. Веточный переход, если он требовался, уже завершён командой `перейти-на-цепочку` до выдачи этого допуска. Владелец может запускать субагентов параллельно, но они являются частями одной корневой задачи:

- субагенты не регистрируются в очереди и не вызывают её команды;
- корень передаёт им непересекающиеся области файлов и свой корневой `CODEX_THREAD_ID`;
- субагенты не меняют ветки, Git-индекс или историю;
- корень синхронизирует пересечения штатными сообщениями, собирает итоговый diff и сам выполняет проверки;
- до любой передачи корень дожидается каждого процесса и субагента, который способен позднее записать результат.

Так параллельная внутренняя работа остаётся видна в общем diff, но независимые корневые задачи не смешивают незавершённые изменения.

Явно запрошенный родительский запускатель [починки автозапуска](../fum-pochinka-avtozapuska/SKILL.md) создаёт не субагента общего хода, а новую независимую корневую задачу. Поэтому родитель до внешнего вызова должен уже владеть FIFO, после единственного `create_thread` немедленно выполнить `finish-clean` и не ждать ребёнка. Ребёнок первым инструментальным действием вызывает собственный `join`; только его отдельные `task_id` и `generation` могут разрешить ремонт. Последующий управляющий ход, терминализирующий результат ребёнка, снова входит в FIFO и после узкой CAS-записи также завершается через `finish-clean`. Точный ещё не перезаписанный `last_completion` может подтвердить только коммит ребёнка, но не живой уровень приёмки; иначе ремонтная ссылка закрывается лишь исходом «неподтверждён» после доказанного отсутствия ребёнка среди владельца и ожидающих FIFO.

## Штатный внеполосный сброс состояния

Штатный сброс является разрушительным восстановлением всей FIFO-очереди и рабочей копии к точному уже зафиксированному `HEAD`. Его может начать только явный пользовательский ход в существующей постоянной задаче диспетчера автоматизаций FUM. Это единственное внеполосное исключение: такой ход не вызывает `join`, а плановый heartbeat никогда не планирует, не подготавливает и не возобновляет сброс сам. Любой другой пользовательский или автоматический ход остаётся обычной корневой задачей и проходит FIFO.

Постоянная задача использует собственный точный `CODEX_THREAD_ID` как `--идентификатор-диспетчера` и не завершает себя до окончания протокола. Все команды запускаются буквальным безопасным HEAD-bootstrap из начала этого навыка; после аргумента корня `.` ему передаются следующие точные суффиксы CLI:

```text
план-сброса --идентификатор-диспетчера <CODEX_THREAD_ID-диспетчера> --json

подготовить-сброс --идентификатор-диспетчера <CODEX_THREAD_ID-диспетчера> --ожидаемая-вершина <целевая_вершина-из-плана> --ожидаемый-объект-очереди <объект_очереди-из-плана-или-absent> --подтверждение <подтверждение-из-плана> --json

подтвердить-остановку-сессий --идентификатор-диспетчера <CODEX_THREAD_ID-диспетчера> --идентификатор-сброса <идентификатор_сброса> [--неактивная-задача <точный-task-id>]... --json

применить-сброс --идентификатор-диспетчера <CODEX_THREAD_ID-диспетчера> --идентификатор-сброса <идентификатор_сброса> --json

отменить-сброс --идентификатор-диспетчера <CODEX_THREAD_ID-диспетчера> --идентификатор-сброса <идентификатор_сброса> --json

состояние-сброса --json
```

`план-сброса` ничего не меняет. CLI требует, чтобы `--идентификатор-диспетчера` точно совпадал с непустым `CODEX_THREAD_ID` текущего процесса; перед вызовом постоянная задача отдельно доказывает host-снимком, что это именно единственная прикреплённая задача действующего диспетчера. План возвращает схему `fum.план-сброса-состояния-FIFO.1`, точные `целевая_вершина`, `объект_очереди` либо `absent`, идентификатор диспетчера, упорядоченных участников очереди и связанных служебных записей, изменённые пути, для каждого изменённого отслеживаемого пути точные `до` (preimage) и `цель` (target), перечень и пообъектные типы/хэши Git-видимых неигнорируемых неотслеживаемых объектов, полный отпечаток index/worktree-содержимого и снимок branch-scoped management-, claim-, repair-, существующих reservation-ссылок и фиксированной эпохи диспетчерских резерваций с OID либо `absent`. План fail-closed отклоняет `assume-unchanged`/`skip-worktree` как `hidden_index_flags`, изменённые `.gitignore` или `.gitattributes` как `checkout_policy_changed`, пересечение любого игнорируемого пути с target как `ignored_path_collision` и любой effective либо cached внешний checkout-filter как `unsupported_checkout_filter`; filter не запускается. Встроенные checkout-преобразования, включая EOL, хэшируются как фактические целевые worktree-байты. Git-видимый неигнорируемый неотслеживаемый объект иного типа, чем обычный файл, символическая ссылка или отдельно распознаваемая вложенная Git-граница, даёт `unsupported_untracked_type` уже в read-only-плане до `подготовить-сброс`; специальный объект не попадает в подтверждаемое множество и никогда не удаляется. Вычисленное `подтверждение` одновременно является `идентификатор_сброса`. Перед подготовкой пользователь должен явно подтвердить именно этот план с его потерей незакоммиченных изменений, остановкой перечисленных задач и очисткой очереди. Любая смена HEAD, queue OID, состава участников, содержимого изменений, reservation-эпохи или связанного ограждения делает прежнее подтверждение неприемлемым и требует нового плана и нового явного подтверждения.

До `подготовить-сброс` постоянная задача сопоставляет каждый точный `task_id` из плана со штатным host-снимком. На текущей поверхности без отдельного чистого stop любой участник, кроме точного идентификатора самой задачи диспетчера, со статусом `active`, неизвестным, неполным или неоднозначным состоянием закрывает ход до первой мутации. `handoff`, архивирование, отправка сообщения, исчезновение из recent-снимка и остановка автоматизации не заменяют остановку задачи. Если будущая поверхность предоставит штатный stop, его вызывают только после подготовленного ограждения, а каждый участник затем подтверждается повторным точным readback того же `task_id` в состоянии `idle` или `notLoaded`; drift сохраняет reset-record без очистки. Точный идентификатор диспетчера исключается из требуемого множества только сравнением идентификаторов, чтобы задача могла довести сброс до финала.

`подготовить-сброс` одной Git-CAS-транзакцией проверяет exact HEAD, queue OID, фиксированную reservation-эпоху и все закреплённые служебные ссылки и заменяет queue-ref закрытой записью схемы `fum.сброс-состояния-FIFO.1` в фазе `подготовлен`. Запись хранит воспроизводимый исходный queue blob, точный план, общий и пообъектные отпечатки содержимого, участников, уже подтверждённые неактивные задачи, служебные ограждения и идентификаторы диспетчера и сброса. Каждый действительный переход любой общей резервации, включая verify-only run-fence, атомарно сдвигает фиксированную эпоху; поэтому CAS обнаруживает и изменение существующей, и создание ранее отсутствовавшей reservation-ссылки. Общая резервация схемы `3` хранит типизированное свидетельство: exact-пара `threadId`/`hostId` включает `threadId` в host-множество ещё до `bind-run` и запрещает привязку иного `task_id`; `clientThreadId` остаётся предварительным и блокирует план до фактического `bind-run`. Схема `4` с `возобновление.состояние=вызов_мог_состояться` также блокирует уже read-only-план сброса до квитанции `подтверждено_исполнителем`, поскольку исход единственного сообщения той же задаче остаётся неоднозначным. Повтор точного подтверждения способен атомарно мигрировать долговечную резервацию схемы `2` в схему `3`, но конфликт уже связанного `task_id` с exact `threadId` закрывает миграцию. Та же fail-closed-семантика применяется к починке. Пока reset-record находится в queue-ref, обычные мутирующие FIFO-команды возвращают `reset_in_progress`, узкая `heartbeat-status` отображает очередь как `busy`, а общая резервация диспетчера, `начать-вызов-среды`, `начать-управление` и карточочный claim закрываются без изменения служебных ссылок.

`подтвердить-остановку-сессий` принимает повторяемый `--неактивная-задача` ровно для множества участников плана без самой задачи диспетчера. Лишний, отсутствующий или повторный идентификатор даёт `session_set_mismatch` и не меняет queue-ref. Успех переводит запись из `подготовлен` в `сессии_остановлены` и делает сброс необратимым. До этого перехода `отменить-сброс` CAS-восстанавливает точный исходный queue OID и не трогает файлы; после него отмена запрещена. При возобновлении прерванного хода `состояние-сброса` различает `отсутствует`, `подготовлен`, `сессии_остановлены`, `очистка_рабочей_копии` и `завершён`; до терминальной Git-транзакции единственным долговечным источником продолжения остаётся активный reset-record, а квитанции ещё нет. Продолжение допускается только теми же идентификаторами диспетчера и сброса и после нового exact host-readback всех требуемых задач. Терминальная транзакция атомарно создаёт квитанцию, и только после неё повтор применения и последующее dispatcher-recovery используют эту квитанцию как завершённое свидетельство.

`применить-сброс` до необратимого перехода повторно доказывает точное совпадение полного отпечатка index/worktree, обычные флаги индекса и неизменную checkout-политику, не пересекает грязный tracked submodule и отказывает на любой неотслеживаемой границе вложенного обычного или bare Git-репозитория, переходе между gitlink и обычным объектом и коллизии игнорируемого пути с target. Затем CAS переводит фазу в `очистка_рабочей_копии`. Если `read-tree --reset -u` был прерван после частичного изменения рабочего дерева, crash-retry разрешён только при совместимом состоянии: индекс целиком совпадает либо с сохранённым preimage плана, либо с целевым деревом, а каждый изменённый tracked-путь совпадает с собственным сохранённым `до` или `цель`; новый либо третий вариант tracked-пути и любое иное состояние индекса дают `reset_plan_changed`. После этих preflight-проверок команда повторяет `read-tree`, восстанавливая индекс и отслеживаемые файлы к закреплённому `HEAD` без движения branch-ref. До и после `read-tree` она доказывает совместимость полного подтверждённого untracked-набора. Затем перед удалением каждого отдельного объекта заново сверяет его тип и SHA-256; target, уже занявший прежний untracked-путь, считается завершённым восстановлением пути, а не новым объектом для удаления. Любое позднее расхождение tracked-, index- или untracked-состояния блокирует текущий вызов до дальнейшего удаления. Удаляются по одному через literal `git clean -f -x` только подтверждённые Git-видимые неигнорируемые неотслеживаемые обычные файлы и символические ссылки, поэтому плановый объект удаляется даже если после восстановления `.gitignore` стал игнорируемым; игнорируемые во время плана, новые, изменившиеся после подтверждения объекты и пустые каталоги не удаляются. Перед финалом команда доказывает неизменный HEAD, отсутствие блокирующих путей и точное равенство индекса дереву целевого коммита. Последний CAS заменяет reset-record обычной очередью схемы `1`, удаляет только неизменившиеся branch-scoped management- и repair-fence, сохраняет exact next-step-claim схемы `4`/`5`/`6`, аналитический claim, резервации и их эпоху, выпускает `owner = null`, `waiting = []` с прежним возрастающим `next_seq` и атомарно создаёт неизменяемую checkout-, branch- и reset-scoped квитанцию схемы `fum.квитанция-сброса-состояния-FIFO.1`. Квитанция инлайнит канонические reset-record и итоговую очередь, связывает их OID, прежнее завершение, вершину и точные service guards, поэтому переживает Git GC, повторный сброс и последующую смену однослотового `last_completion`. Следующий ход диспетчера сам приоритетно проверяет долговечный успех либо clean-доказательство, а затем exact receipt/host/ledger, текущие queue/branch и прежние reservation/epoch. Для переходного precommit-claim схемы `4` общий безопасный отказ сначала исторически подтверждает exact ready-выбор и затем удаляет тот же OID под квитанцией и всеми общими guards. Terminal-success сохраняет specialized terminal claim для replay; safe failure удаляет clean-claim и записывает `подтверждение_результата = base_head`. Следующая резервация того же адаптера атомарно поглощает сохранённый terminal claim вместе с заменой terminal reservation и guards; crash после reserve видит claim отсутствующим. Внешний `release` после host-границы или reset запрещён. Совпадение только по повторно использованному `task_id` или `clientThreadId` не принимается. Повтор применения с теми же идентификаторами идемпотентно возвращает `сброшено`.

После успешного `применить-сброс` постоянная задача в том же пользовательском ходе больше не выполняет ни одной записи в репозиторий, индекс, ветку, историю или служебные Git-ссылки и не запускает способных позднее записать исполнителей. Она только сообщает уже возвращённый результат. Новый heartbeat или пользовательский запрос начинает отдельный ход и заново проходит свой применимый контракт.

## Корневой человеческий break-glass

Если ограждения сами делают штатный маршрут недоступным, человек может из корня репозитория запустить:

```bash
./sbrositj.sh
```

Запускатель не требует `sudo`, не принимает аргументы и загружает core из exact закоммиченного `HEAD`, а не из грязной рабочей копии. Он работает только при TTY на stdin и stdout, печатает exact именованную ветку, `HEAD`, стираемые tracked/index/untracked-изменения и raw scoped ref/OID-инвентарь, а затем требует ввести напечатанную динамическую фразу. Pipe, перенаправление, аргумент, общий `yes`, флаг force и фраза от прежнего плана не дают права применения.

Действительная переходная запись цепочки закрывает уже read-only-план простого сброса как `chain_transition_in_progress`: сначала тот же исполнитель идемпотентно завершает атомарное согласование symbolic `HEAD` и FIFO. Простой сброс не удаляет уже созданную целевую ветку перехода и не теряет её карточочные метаданные, поэтому не превращает безопасно возобновимый переход в постоянный `target_branch_exists`.

После подтверждения операция сохраняет raw preimage в неисполняемом аварийном снимке, ставит общий fence, восстанавливает индекс и tracked-дерево к `HEAD` и удаляет только подтверждённые Git-видимые неигнорируемые обычные файлы и символические ссылки. Игнорируемые объекты, вложенные Git-границы, чужие worktree и ветки, теги, remote и история не удаляются. Финал аннулирует scoped queue, management, claim, repair, reservation, ledger и analytics, выпускает свежую пустую очередь, новые epoch/boundary и checkout-scoped tombstone прежних задач, которые запрещают повторный старый `join` после смены ветки в том же checkout. Валидные неизменяемые official reset receipts в `refs/fum/квитанции-сброса-состояния-FIFO/` строго парсятся и сохраняются; повреждённые архивируются и удаляются. Квитанция этого ручного сброса хранится отдельно в `refs/fum/квитанции-простого-сброса/`; строгий readback terminal receipt после неоднозначного ответа финальной CAS возвращает точный записанный исход без второго сброса или иной мутации.

Это локальная аннуляция, а не host-stop. Старая задача может физически продолжаться, но её прежние ticket, generation, lease и reservation не дают права записи, а повторный старый `join` отклоняется. Автоматизация не вызывает этот маршрут, а агент не воспроизводит фразу за человека. После успеха только новый обычный heartbeat при `ACTIVE` и host-простое заново вычисляет selector. Проверки маршрута исполняют launcher только во временном Git-репозитории, никогда не в живой рабочей копии.

## Чистое завершение без коммита

Если допущенная задача законно не имеет изменений — например, read-only аудит завершился без замечаний или созданная диспетчером задача до первой записи обнаружила несовпадение ожидаемых `branch_ref`/`step_id`/`selection_id`, — корень после остановки всех возможных писателей выполняет:

```text
python3 -I -c "import os,subprocess,sys;p='Инструменты/fum-ocheredj-zadach-git-vetki/scripts/ocheredj-zadach-git-vetki.py';r=sys.argv[1];e={k:v for k,v in os.environ.items() if not k.upper().startswith('GIT_')};e['GIT_NO_REPLACE_OBJECTS']='1';e['GIT_OPTIONAL_LOCKS']='0';b=subprocess.check_output(['git','--no-replace-objects','-C',r,'show','HEAD:'+p],env=e,timeout=30);sys.argv=[p,*sys.argv[2:],'--repo-root',r];exec(compile(b,p,'exec'))" . finish-clean --task-id <корневой-CODEX_THREAD_ID> --generation <generation-из-admitted> --json
```

Команда требует точного владельца и поколения, неизменного `base_head`, чистоты вне корневой `.obsidian/` и отсутствия любых staged-изменений, включая `.obsidian/`. Одна `update-ref --stdin` transaction одновременно проверяет ref ветки и меняет ref очереди, записывая `last_completion` вида `finished_clean` с точными `task_id`, `generation` и неизменным `head`; исходный `base_head` уже доказан самой clean-транзакцией и в эту форму завершения не дублируется. Для связанного next-step-claim схемы `5` та же транзакция проверяет его exact поля и переводит в схему `6`, сохраняя все поля схемы `5` и добавляя `свидетельство_чистого_завершения = {"base_head": <selection_head>, "task_id": <FIFO-task>, "generation": <FIFO-generation>}`. Для аналитического claim она аналогично фиксирует фазу `очищена`. Это завершение no-op-задачи, а не переупорядочивание или принудительный обход; claim позднее удаляет только общая terminal-CAS. После `finished_clean` прежняя задача больше ничего не записывает и не запускает писателей.

Для узкого восстановления прерванного чистого завершения та же корневая задача может не переносить `generation` через историю диалога, а выполнить:

```text
python3 -I -c "import os,subprocess,sys;p='Инструменты/fum-ocheredj-zadach-git-vetki/scripts/ocheredj-zadach-git-vetki.py';r=sys.argv[1];e={k:v for k,v in os.environ.items() if not k.upper().startswith('GIT_')};e['GIT_NO_REPLACE_OBJECTS']='1';e['GIT_OPTIONAL_LOCKS']='0';b=subprocess.check_output(['git','--no-replace-objects','-C',r,'show','HEAD:'+p],env=e,timeout=30);sys.argv=[p,*sys.argv[2:],'--repo-root',r];exec(compile(b,p,'exec'))" . finish-own-clean --task-id <корневой-CODEX_THREAD_ID> --ограждающая-ссылка <полная-служебная-ссылка> --ожидаемый-объект-ограждения <OID-или-absent> --json
```

Имя `finish-own-clean` фиксирует всю его семантику: `own` разрешает завершить только текущего владельца с точно тем же `task_id`, а `clean` делегирует обычному `finish-clean` все проверки `base_head`, рабочего дерева, индекса и атомарного CAS. Команда в одном процессе читает текущего владельца, захватывает его точное `generation` и повторно проверяет эту пару внутри обычного clean-handoff. Необязательная пара `--ограждающая-ссылка` и `--ожидаемый-объект-ограждения` принимается только целиком; первая обязана быть полной служебной ссылкой `refs/fum/*`, а второе значение — полным Git OID либо точным `absent`. Тогда та же транзакция `update-ref --stdin` вместе с веткой и queue ref проверяет неизменность внешнего ограждения. Встречная смена ссылки даёт `guard_changed` и сохраняет владельца. Отсутствие владельца, чужой `task_id` или смена поколения в гонке также завершаются отказом. Команда не регистрирует и не допускает билет, не отменяет ожидающих, не создаёт коммит и не обходит FIFO.

## Атомарный коммит и передача

Перед завершением владелец формирует полное сообщение коммита по `AGENTS.md`, проверяет `.obsidian/`, явно индексирует весь осмысленный набор и вызывает команду только после просмотра полного `git status --short --untracked-files=all`. Сама очередь индексирование не выполняет: неиндексированные изменения, неигнорируемые новые пути и конфликты должны отсутствовать, а локальный игнорируемый мусор нельзя добавлять принудительно ради чистого статуса.

```text
python3 -I -c "import os,subprocess,sys;p='Инструменты/fum-ocheredj-zadach-git-vetki/scripts/ocheredj-zadach-git-vetki.py';r=sys.argv[1];e={k:v for k,v in os.environ.items() if not k.upper().startswith('GIT_')};e['GIT_NO_REPLACE_OBJECTS']='1';e['GIT_OPTIONAL_LOCKS']='0';b=subprocess.check_output(['git','--no-replace-objects','-C',r,'show','HEAD:'+p],env=e,timeout=30);sys.argv=[p,*sys.argv[2:],'--repo-root',r];exec(compile(b,p,'exec'))" . commit --task-id <корневой-CODEX_THREAD_ID> --generation <generation-из-admitted> --message-file <путь-к-сообщению> --json
```

Вместо файла допустим `--message '<сообщение>'`; значение `--message-file -` читает сообщение из стандартного ввода.

Команда проверяет неизменность ветки и `base_head`, точное поколение владельца, наличие индексированных изменений и отсутствие неиндексированных изменений, неигнорируемых новых путей или конфликтов вне корневой `.obsidian/`. Отказ `dirty` с кодом `13` происходит до `write-tree` и не создаёт объекта коммита. Его однострочный ASCII JSON ограничен `16 384` байтами вместе с переводом строки. Поле `blocking_paths_schema = 1` задаёт схему сводки; `blocking_paths` содержит точный префикс не более чем из 16 путей сортированного полного множества; `blocking_paths_count`, `blocking_paths_sha256` и `blocking_paths_truncated` хранят общее число, SHA-256 всего множества и признак усечения. Полный список сохраняется только когда весь конверт укладывается в байтовую границу; иначе префикс сокращается вплоть до пустого. SHA-256 рассчитывается в области `FUM\0queue-dirty-blocking-paths\0v1\0` по общему числу как беззнаковому 64-битному целому от старшего байта к младшему и затем по каждому пути: его 64-битной байтовой длине в том же порядке и байтам UTF-8 с `surrogateescape`. Латинский префикс новых ключей является аддитивным расширением существующего версионированного JSON-контракта `blocking_paths`, а не образцом для новых независимых форматов.

После успешной предварительной проверки команда строит дерево через `git write-tree`, создаёт объект коммита через `git commit-tree` и одной транзакцией `git update-ref --stdin` сравнивает и обновляет сразу две ссылки:

- текущую `refs/heads/...` с прежнего `base_head` на новый коммит;
- служебную ссылку очереди с текущего JSON blob на состояние без владельца.

При падении до транзакции не меняется ни одна ссылка; после успешной транзакции изменены обе. Конкурирующие `join`, `ack-head` или `cancel` могут изменить только ссылку очереди, поэтому владелец перечитывает её и повторяет транзакцию, не ослабляя проверку старого `HEAD`. `last_completion` вида `committed` хранит точные `task_id`, `generation`, `base_head` и новый `head`, поэтому делает повтор ответа после неоднозначного результата идемпотентным и даёт общему диспетчеру узкое доказательство завершения именно связанного исполнителя. Повторное чтение уже совершённого точного результата выполняется раньше чтения файла сообщения: отсутствующий файл остаётся ошибкой первичного вызова, но не лишает восстановимости коммит с потерянным ответом.

Вызывающий исполнитель принимает успех только при известном нулевом коде и полном разобранном единственном JSON с точным `state = committed`, совпавшими заранее известными `task_id`, `generation`, `old_head` и `branch_ref`; `new_head` и `queue_oid` отдельно проверяются как полные Git OID возвращённого результата. Усечённый, повреждённый или потерянный вывод и неизвестный код завершения не являются ни `committed`, ни разрешением менять состояние. В таком случае исполнитель повторяет ту же точную команду с прежними задачей, поколением и аргументом сообщения. Повторное чтение возвращает записанный результат без второго коммита, пока точное `last_completion` ещё доступно либо адаптер сохранил долговечное свидетельство; только во втором случае сохранённый `new_head` может уже быть предком текущей вершины. Если более поздняя передача уже заменила единственное `last_completion`, а долговечного свидетельства нет, повтор закрывается безопасным отказом, и до авторитетной сверки истории успех не заявляют. Интерфейсная Git-директива и сообщение пользователю допустимы только после этого машинного подтверждения. Сам ответ `committed` не разрешает публикацию.

Нулевой код внутреннего проверочного процесса smoke-check не заменяет эту передачу. Для владельца с `текущая_цепочка` успешное завершение полной smoke-сессии означает только `committed` после закрытия отчёта и атомарного `commit+handoff` в сохранённый `branch_ref` карточки; внутренний smoke не выполняет Git-коммит. Bootstrap-владелец, допущенный на `master` до появления веточного перехода, завершает единственную миграционную сессию прежним протоколом и не переключает ветку.

## Отдельно авторизуемый транспорт точного коммита

Обычная корневая задача и созданная heartbeat-задача ветки `refs/heads/master` после `committed` завершаются и не вызывают `push` или `publish`. Ручной push пользователя выполняется вне корневой задачи и FIFO: его подтверждённый результат означает публикацию точного проверенного коммита и всех его достижимых предков. Remote не является условием готовности карточки, допуска очереди, завершения сессии или запуска следующего автоматического шага. Ручной push не предоставляет полномочий на модельные провайдеры, секреты, платные затраты, новые данные или иные внешние эффекты.

Низкоуровневая команда `publish` сохраняется для отдельного явно разрешённого транспортного действия и не входит в обычный протокол `master` или heartbeat. Ни сам `committed`, ни ручной push пользователя не являются разрешением вызвать её. Отдельная авторизация должна заранее закрепить точные commit object, полный целевой ref, credential-free HTTPS push URL и право внешнего эффекта. Только такой отдельно авторизованный вызов загружает сценарий из точного публикуемого коммита, а не из подвижного `HEAD` или рабочего дерева:

```text
python3 -I -c "import os,subprocess,sys;p='Инструменты/fum-ocheredj-zadach-git-vetki/scripts/ocheredj-zadach-git-vetki.py';r=sys.argv[1];h=sys.argv[2];e={k:v for k,v in os.environ.items() if not k.upper().startswith('GIT_')};e['GIT_NO_REPLACE_OBJECTS']='1';e['GIT_OPTIONAL_LOCKS']='0';b=subprocess.check_output(['git','--no-replace-objects','-C',r,'show',h+':'+p],env=e,timeout=30);sys.argv=[p,*sys.argv[3:],'--repo-root',r];exec(compile(b,p,'exec'))" . <new_head> publish --commit <new_head> --branch-ref <branch_ref> --push-url <сохранённый-push-URL> --json
```

Команда принимает только полный SHA-1 или SHA-256 commit object, полную ссылку `refs/heads/...` и credential-free HTTPS URL GitHub. Она отключает интерактивные запросы терминала и менеджера учётных данных, локальный pre-push hook, очищает унаследованные `GIT_*` и отправляет единственный refspec `<new_head>:<branch_ref>` без wildcard, тегов и force-вариантов. Каждый транспортный Git-процесс запускается в отдельной группе; при тайм-ауте публикатор завершает всю группу и только затем проверяет удалённую вершину. Ни checkout, ни индекс, ни локальные refs, ни очередь при этом не меняются.

`published` означает успешный ответ отправки либо подтверждённое равенство удалённой вершины точному коммиту. Если более поздняя задача успела опубликовать потомка, повтор возвращает `already_published_descendant`: прежний результат уже достижим, а удалённая ветка не откатывается. После неуспешной или неоднозначной отправки публикатор читает точную удалённую вершину; при неизвестном локально объекте проверка достижимости проходит во временном bare-репозитории с явно пустым каталогом hooks и не записывает данные в общий `.git`.

Состояния `diverged`, `rejected` и `unconfirmed` завершаются ошибкой и не устраняются через `pull`, merge, rebase, force-push, откат локального коммита или возврат владения. Отдельно авторизованный исполнитель сообщает такой результат пользователю и после любого результата `publish` больше не выполняет внешних мутаций. `commit`, `finish-clean` и `finish-own-clean` публикацию не запускают.

## Диагностика

Состояние очереди читается без изменения:

```text
python3 -I -c "import os,subprocess,sys;p='Инструменты/fum-ocheredj-zadach-git-vetki/scripts/ocheredj-zadach-git-vetki.py';r=sys.argv[1];e={k:v for k,v in os.environ.items() if not k.upper().startswith('GIT_')};e['GIT_NO_REPLACE_OBJECTS']='1';e['GIT_OPTIONAL_LOCKS']='0';b=subprocess.check_output(['git','--no-replace-objects','-C',r,'show','HEAD:'+p],env=e,timeout=30);sys.argv=[p,*sys.argv[2:],'--repo-root',r];exec(compile(b,p,'exec'))" . status --json
```

Ответ показывает `queue_ref`, `queue_oid`, `branch_ref`, владельца, ожидающие билеты и следующий `seq`. Состояние хранится как канонический JSON blob под `refs/fum/worktree-task-queues/<sha256-идентичности-worktree>`. Запись и передача используют только Git object database и compare-and-swap ссылок, поэтому object ID может быть SHA-1 или SHA-256.

Плановый heartbeat не разбирает полный диагностический payload для решения о свободе очереди. После доказательства собственной host-идентичности он выполняет узкую read-only-команду:

```text
python3 -I -c "import os,subprocess,sys;p='Инструменты/fum-ocheredj-zadach-git-vetki/scripts/ocheredj-zadach-git-vetki.py';r=sys.argv[1];e={k:v for k,v in os.environ.items() if not k.upper().startswith('GIT_')};e['GIT_NO_REPLACE_OBJECTS']='1';e['GIT_OPTIONAL_LOCKS']='0';b=subprocess.check_output(['git','--no-replace-objects','-C',r,'show','HEAD:'+p],env=e,timeout=30);sys.argv=[p,*sys.argv[2:],'--repo-root',r];exec(compile(b,p,'exec'))" . heartbeat-status --task-id <корневой-CODEX_THREAD_ID> --json
```

Каждое валидное наблюдение возвращает код `0` и JSON ровно с одним полем `state`. `idle` означает точное одновременное отсутствие владельца и ожидающих. `own_owner` означает владельца с переданным `task_id`; наличие ожидающих последователей не меняет этот результат и не запрещает отдельный `finish-own-clean`. Любой чужой владелец или любой список ожидания без собственного владения, включая собственный ожидающий билет, дают `busy`. Непрозрачные `task_id`, `ticket_id`, `generation`, записи владельца и билетов в узкий ответ не попадают. Ошибка Git-контекста, повреждённая очередь или неверный аргумент остаются обычным ненулевым fail-closed-отказом. Команда ничего не завершает и не меняет Git-ссылку; восстановление собственного чистого владельца остаётся отдельным `finish-own-clean`.

## Отказы и границы

Ни ожидающий билет, ни владелец не имеют TTL. Молчаливо упавшая и долго работающая задача неразличимы без внешнего достоверного сигнала, а автоматическое удаление любого предшественника нарушило бы строгий FIFO. Узкое автоматическое возобновление не удаляет и не заменяет владельца: после строгого host-доказательства failed-разрыва потока диспетчер может отправить ровно одно ограждённое сообщение той же связанной задаче, а неоднозначный исход запрещает повтор. Возобновлённая задача сохраняет тот же корневой `CODEX_THREAD_ID`, первым инструментальным действием идемпотентно продолжает прежний билет через `join`, после допуска перечитывает правила и `HEAD`, подтверждает сохранённые общий и карточочный fence и отдельной CAS квитирует возобновление; до допуска она может отменить только собственный билет, а после допуска завершает `commit` или `finish-clean`. Автоматического принудительного удаления нет; единственным штатным удалением чужих поколений остаётся описанный выше явно подтверждённый сброс постоянной задачей диспетчера с точным host-доказательством остановки всех участников.

Очередь координирует сотрудничающие задачи одного локального checkout и общего Git-каталога. Она не связывает отдельные клоны и отклоняет одну именованную ветку, принудительно открытую в нескольких worktree. Когда очередь пуста, следующий `join` может привязать тот же worktree к другой именованной ветке. Detached HEAD не поддерживается.

Автоматизация не перехватывает произвольный процесс, который сознательно игнорирует `AGENTS.md`, поэтому корневые задачи обязаны соблюдать протокол. При этом штатный путь полностью машинный и не зависит от hook-поддержки конкретного host или ОС.

## Общий диспетчер и адаптер следующего шага

Плановый heartbeat общего диспетчера не использует очередь как backlog и сам не входит в неё: он не рабочий билет и не меняет checkout, индекс, ветку или историю. После проверки собственной идентичности и management-fence, но до `heartbeat-status`, выхода по занятой FIFO и выбора нового запуска он проверяет уже связанную незавершённую резервацию. Только строгий `read_thread` схемы `1` для тех же `threadId`/`hostId` с состоянием задачи `idle` либо `notLoaded` и ровно одним новейшим `failed`-ходом с точной ошибкой разрыва потока разрешает CAS до единственного сообщения той же задаче. Любой результат отправки завершает тик без resend и `create_thread`; наблюдение не устанавливает физическую причину разрыва. Если возобновляемого запуска нет и доступный recent-снимок показывает любую другую активную задачу, heartbeat не резервирует общее задание или карточочный шаг и не создаёт автоматическую задачу. Только после двух проверок наблюдаемого простоя он выбирает маршрут `master.next-step` и его точную `selection_head`, вызывает специализированные `show`/`claim` и создаёт обычную корневую задачу, которая первым инструментальным действием проходит тот же `join`.

После каждого допуска исполнитель до записи выполняет общий `bind-run`/`verify-run` по `job_id`, поколениям, `run_key`, UUID попытки, собственному `task_id`, `generation` и `base_head`, а затем отдельные карточочные `bind-run`/`verify-run` по `branch_ref`, `step_id`, `selection_id` и совпадающему `lease_id`. Возобновлённый исполнитель использует те же сохранённые значения и после их сверки подтверждает точный ключ возобновления; pending-резервация схемы `4` до этой квитанции блокирует терминализацию и штатный сброс. Mismatch любого уровня вызывает `finish-clean` и прекращение работы. Next-step `finish-clean` атомарно переводит claim схемы `5` в `6` с exact clean-witness; `rearm` для схемы `5` является fenced no-op, а legacy `4 → 5` после миграции завершается тем же `5 → 6`. После атомарного `commit`+handoff исполнитель ничего не записывает; common-terminal приоритетно принимает текущий `last_completion`, долговечный журнал схемы `5` либо clean-свидетельство схемы `6` независимо от позднего handoff, нового владельца или reset. Success оставляет terminal claim для replay, clean-safe-failure его удаляет; следующий reserve того же адаптера атомарно поглощает сохранённый terminal claim. Официальный reset сохраняет claim и не требует внешнего `release`.

Переходный claim схемы `4`, который завершил работу прежней HEAD-версией очереди без журнала, остаётся защищён текущим `last_completion`: пока связанная общая резервация нетерминальна, следующий владелец может войти в FIFO и готовить изменения, но его `commit` и `finish-clean` получают повторяемый отказ `legacy_terminalization_pending` и не заменяют подтверждение. После exact общей терминализации тот же вызов разрешён; официальный reset не блокируется, потому что его квитанция сохраняет прежнее завершение. Новая HEAD-версия очереди при собственном commit схемы `4` вместо этого атомарно мигрирует claim в `5` по исторически воспроизведённому выбору и записывает обычное событие журнала.

## Переход со старого hook

В `.codex/config.toml` нет project hooks. По прежнему пути `Инструменты/fum-branch-task-gate/scripts/branch-task-gate.py` оставлен только минимальный no-op без `SKILL.md`: он позволяет уже открытой сессии с кэшированным старым loader завершить переход и не считается активной автоматизацией. Сама миграционная задача завершает старое владение после обычного коммита; первая следующая корневая задача загружает уже закоммиченную очередь из `HEAD`.

Сбросовые сценарии отдельно закрепляют отказ `unsupported_untracked_type` до подготовки, сохранённые preimage/target изменённых tracked-путей, допустимый повтор частично применённого `read-tree` только из совместимого состояния индекса и путей, блокировку позднего tracked/index/untracked-drift до дальнейшего удаления, reset-record как источник продолжения до финала и квитанцию как самодостаточное свидетельство после финала.

Отдельные break-glass-сценарии закрепляют TTY одновременно на stdin и stdout, exact-план и drift, raw scoped inventory, архив неизвестного runtime, сохранение ignored и вложенных Git-границ, отдельные официальную и человеческую квитанции, terminal receipt replay, свежие FIFO/epoch/boundary, checkout-scoped tombstone, отказ старых полномочий после смены ветки и новый selector/claim из того же `HEAD`.
