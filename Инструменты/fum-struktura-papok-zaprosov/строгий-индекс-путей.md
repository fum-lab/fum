# Строгий индекс путей Журнала

LAB-срез Issue301 сокращает повторное перечисление и нормализацию общих родителей внутри одного полного прохода. Он предназначен для проверки малого открытого корпуса; применение к живому ROOT требует отдельной приёмки.

`ИндексПутей` полностью перечисляет непосредственный корень, поддерево `Журнал` и непосредственных детей `Индексы`. Для каждого родителя сохраняются точные имена и все группы NFC/casefold. Метаданные закрепляются в управляемой области; корневые соседи вроде `.obsidian` остаются только именами, поэтому локальное изменение `graph.json` не блокирует проход. Поиск продолжает проверять физический корень, каждый компонент, символические ссылки и промежуточные типы прежним кодом. Перед каждым обращением сверяется живая идентичность родителя. Перед успешным возвратом независимо перечитываются все имена и закреплённые метаданные, включая ранее пройденные ветви и пустые каталоги. Наблюдённый дрейф закрывает проход отказом.

Каждый `проверить_журнал` и `проверить_смешанный` получает новый одноразовый экземпляр. Объект закрывается и при отказе; перенос между plan/apply/replay отсутствует. Все исходные проверки H/W, байтов, владельца, inode, nlink, режимов, source pins, Git/ref/index/config и поздние барьеры сохраняются. Новый исходник добавлен в закрепляемый исполняемый контур установщика. Прямой вызов прежнего `точный_путь` без индекса сохраняет полный прежний алгоритм без early return.

Это кооперативная проверка наблюдаемых имён и метаданных. Между последним наблюдением и действием остаётся прежняя граница TOCTOU; абсолютная атомарность ФС не заявляется. Кэш не доверяет только прежнему положительному исходу и не заменяет следующие независимые полные проходы.

## Воспроизведение

Нужны Python, Git и два отдельных полных клона точного C573 `bac942c7bf9f0d6f68290ddc1fa12ea632d5bd76`. Первый остаётся неизменным. Во втором заменяются только три предметных исходника из проверяемого LAB-среза. Оба клона имеют собственный Git-admin; остальные зависимости берутся целиком из C573. Скрипт проверок запускается в свежих процессах, а Git-фикстуры создаёт в приватных временных каталогах. Сам кандидат не становится принимающим кодом контрольной точки.

Через штатную отчётную обёртку своей v4-сессии запустите:

```text
python3 -B Инструменты/fum-struktura-papok-zaprosov/tests/test_строгий_индекс_путей.py --основа <полный-C573> --код <отдельный-кандидат>
python3 -B Инструменты/fum-struktura-papok-zaprosov/tests/профиль_строгого_индекса_путей.py --основа <полный-C573> --код <отдельный-кандидат> --выход <новый-профиль.json>
```

Для различающего RED добавьте к первой команде `--только-red` и выберите C573 также как `--код`. Успешный прежний путь должен не пройти ограничение повторного listing. Обычный набор сравнивает положительные и отрицательные исходы, проверяет дрейф, закрытие индекса, четырнадцать apply-проходов, mixed guard и два независимых replay-контекста. Исключение, неизвестная основа или ненулевой код работника требуют просмотра ошибки; результата не следует считать GREEN.

Обычный `unittest discover` без аргументов выполняет две автономные проверки самого индекса и явно пропускает три парных Git-сценария, которым нужны два полных контура. Он не подменяет показанный выше явный запуск без пропусков.

Профиль выполняет три свежие пары одного удержанного корпуса, отдельно сохраняет setup, wall/CPU, память и счётчики listing/normalization/stat/bytes/Git. Измерения включают диагностические накладные расходы. JSON фиксирует SHA корпуса и кода до/после; вложенные времена не суммируются. Вывод относится только к малому корпусу, а отсутствие выигрыша остаётся допустимым результатом.
