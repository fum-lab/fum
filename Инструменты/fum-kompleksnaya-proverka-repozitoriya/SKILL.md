# FUM Smoke Check

Эта локальная [автоматизация FUM](../../Глоссарий/автоматизация-FUM.md) разделяет две разные приёмочные задачи. Стандартный профиль `документационный`, выбранный по умолчанию, быстро подтверждает работоспособность наблюдаемого документационного прототипа перед обычным коммитом. Явный профиль `полный` сохраняет прежний широкий репозиторный контур для целевой регрессии автоматизаций, Git-зависимости и коробочных SwiftPM-прототипов, но никогда не запускается автоматически вместо стандартного.

Оба профиля работают локально, не требуют секретов, сетевых запросов и внешних сервисов и измеряют монотонное wall-clock-время подготовки, каждого объявленного шага и полного процесса. Стандартный профиль строится непосредственно из положительного перечня: восемь live-проверок и двенадцать автономных наборов ядра. Он не выполняет общий автопоиск `Инструменты/*/tests`, не читает SwiftPM-манифесты, не загружает историю риска и не требует файлов, принадлежащих только полному профилю. Новый набор тестов не попадает в стандарт сам собой: изменение перечня требует осмысленной правки и регрессионного теста состава.

Нулевой код внутреннего проверочного процесса означает только, что объявленный проверочный план пройден. Сам `run-smoke-check.py` не выполняет Git-коммит: после его выхода обязательная отчётная обёртка ещё сохраняет терминальную запись запуска, закрывает хэшированный снимок и допускает ограниченные проверки замыкания. Полная ручная сессия с осмысленным diff считается завершённой только после одного итогового локального коммита на `refs/heads/master`; smoke-check не создаёт continuation, FIFO-handoff или публикацию.

## Когда использовать

Используй стандартный профиль, когда нужно:

- выполнить обязательный приёмочный прогон документационной рабочей сессии перед локальным коммитом;
- убедиться, что `.codex/config.toml` сохраняет `skills.include_instructions = false` и не возвращает внешний каталог навыков в агентский контекст;
- проверить, что запросы находятся в `Журнал/<YYYY-MM-DD_HH-MM-SS_MSK[_slug]>/запрос.md`, отчёты лежат рядом, а старого `Запросы/` и верхнеуровневых журнальных отчётов нет;
- пересобрать и сверить плановый реестр;
- проверить действующее содержимое на машинно-локальные пути и раскрытие Swift `#filePath`;
- проверить компактность корневой инструкции и полноту тематического индекса в `Документация/README.md`;
- проверить существование, регистр и обратные ссылки заявленных целей открытых и частично прояснённых вопросов;
- убедиться, что `FUM-MD-RECENCY` и индекс Markdown-файлов свежие;
- проверить связность выбранного файла `Журнал/<YYYY-MM-DD_HH-MM-SS_MSK[_краткое-название-запроса]>/запрос.md`.

Выбирай полный профиль отдельно, когда изменён необязательный инструмент, Git-зависимость, Swift-код или политика пакетов либо когда нужен широкий аудит всех сохранённых регрессий. Он автоматически обнаруживает все Python-наборы, проверяет остаток перевода объявлений и реестр названий автоматизаций, разбирает все SwiftPM-манифесты и выполняет Swift-тесты, сборки продуктов и lint.

## Команда запуска

Стандартный проверочный этап рабочей сессии:

```bash
python3 Инструменты/fum-kompleksnaya-proverka-repozitoriya/scripts/run-smoke-check.py \
  --request Журнал/<YYYY-MM-DD_HH-MM-SS_MSK[_краткое-название-запроса]>/запрос.md \
  --commit-message-file <путь-к-файлу-сообщения> \
  --codex-thread-id <корневой-CODEX_THREAD_ID>
```

Для запросов с именем родительской папки начиная с `2026-07-14_02-31-47_MSK_добавлять-идентификатор-сеанса-Codex` оба новых параметра обязательны; исторические запросы можно проверять без них. Список стандартных проверочных команд без их запуска:

```bash
python3 Инструменты/fum-kompleksnaya-proverka-repozitoriya/scripts/run-smoke-check.py \
  --request Журнал/<YYYY-MM-DD_HH-MM-SS_MSK[_краткое-название-запроса]>/запрос.md \
  --list
```

Стандартный `--list` не вызывает Swift, автопоиск тестов или чтение аналитической истории. Полный профиль и его список выбираются только явно:

```bash
python3 Инструменты/fum-kompleksnaya-proverka-repozitoriya/scripts/run-smoke-check.py \
  --request Журнал/<YYYY-MM-DD_HH-MM-SS_MSK[_краткое-название-запроса]>/запрос.md \
  --commit-message-file <путь-к-файлу-сообщения> \
  --codex-thread-id <корневой-CODEX_THREAD_ID> \
  --профиль полный
```

Для просмотра полного плана добавляется `--list`. Только в этом сочетании `Package.swift` оцениваются локальным `swift package dump-package` с offline-флагами; тесты, сборка и lint при просмотре не запускаются.

Частичный локальный запуск без проверки конкретной рабочей сессии:

```bash
python3 Инструменты/fum-kompleksnaya-proverka-repozitoriya/scripts/run-smoke-check.py \
  --skip-session-coherence
```

## Что запускается

Стандартный профиль выполняет две фазы. Сначала идут восемь live-проверок в точном порядке: структура папок запросов; сборка и проверка планового реестра; машинно-локальные пути; двунаправленность вопросов; тематический индекс README; Markdown-recency; связность сессии. Затем по каноническому POSIX-ключу следуют двенадцать явно разрешённых наборов:

- `fum-indeks-readme`;
- `fum-kompleksnaya-proverka-repozitoriya`;
- `fum-materialyi-zaprosov`;
- `fum-moskovskoye-vremya-rabochej-sessii`;
- `fum-obratnyiye-ssyilki-voprosov`;
- `fum-otchyotyi-o-zapuskakh-proverok`;
- `fum-proverka-mashinno-lokaljnyikh-putej`;
- `fum-proyektnyiye-fajlyi`;
- `fum-reyestr-planirovaniya`;
- `fum-struktura-papok-zaprosov`;
- `fum-svezhestj-markdown`;
- `fum-svyaznostj-rabochej-sessii`.

Каждый каталог обязан существовать внутри checkout как обычный локальный каталог и содержать хотя бы один обычный `test_*.py`. Отсутствие, пустой набор или подмена символической ссылкой останавливают подготовку. Локальный ignored `.obsidian/graph.json` и исторический генератор его тепловой карты не требуются стандартному профилю.

Полный профиль сохраняет четыре прежние фазы: Swift-разбор и загрузка закрытой истории; расширенный ранний префикс; риск-упорядоченные автоматически найденные Python- и Swift-тесты; фиксированный хвост сборок и lint. Статистика полного профиля читается только из `fum.test-run.v2` в проверенных закрытых `снимок.json`. Стандартный профиль историю не читает, поэтому старый повреждённый снимок не превращает быстрый документационный прогон в скрытую широкую проверку.

Ниже команды перечислены по видам проверок для справки. Автопоиск и Swift-команды относятся только к явному полному профилю.

При запуске любого профиля через обязательную обёртку отчётов сначала создаётся канонический конверт `fum.smoke-test-observations.v1` с UUID и `план: null`. До исполнения первого раннего шага smoke-check атомарно добавляет точный упорядоченный план аналитических тестов выбранного профиля. Если ранняя проверка отказывает, терминальная v2-запись сохраняет план и пустые наблюдения. Перед каждым достигнутым тестом сохраняется текущий шаг, а после исхода — фактический префикс. Обёртка проверяет каноничность ключей, полноту успешного плана, единственный последний неуспех при fail-fast и согласованность длительностей. При тайм-ауте достигнутый текущий тест добавляется как `не завершено`, при внешнем сигнале — как `прервано`. Переменные capability удаляются из окружения каждого вложенного шага.

Перед построением списка шагов автоматизация разбирает `.codex/config.toml` стандартным TOML-парсером и требует точное логическое значение `skills.include_instructions = false`. Затем она разрешает символические ссылки каждого `Инструменты/*/SKILL.md` и отклоняет путь, вышедший за корень checkout. Отсутствующий, синтаксически неверный или ослабленный проектный конфиг, сломанная ссылка и внешний путь останавливают как обычный запуск, так и режим `--list` до остальных проверок. Эта статическая проверка защищает сохранность проектного контракта, но не обещает поведение неизвестной будущей версии Codex или запуска с явным переопределением настройки; применимость текущих runtime отдельно проверяется через их модельный вход.

Обычный запуск печатает машиночитаемые строки `smoke-timing <JSON>`. Записи `manifest` появляются только в полном профиле и измеряют каждый вызов `swift package dump-package`; `preparation` охватывает подготовку списка, `step` — объявленный шаг, а `total` — полный интервал. Невозможность запустить вложенный процесс стабильно обозначается `exit_code: 127`, а ошибка подготовки завершает smoke-check с кодом `2`. Вложенные длительности не складываются с `total` как независимые вызовы. Режим `--list` не запускает объявленные шаги; стандартный список не выполняет Swift-подготовку, полный — выполняет только разбор манифестов.

1. Только в полном профиле находит все каталоги `Инструменты/*/tests`, содержащие `test_*.py`, и запускает для каждого:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s <tests-dir> -p 'test_*.py'
```

2. Только в полном профиле находит все `Прототипы/*/Package.swift`, получает фактические продукты и пути целей через:

```bash
swift package \
  --package-path <путь-к-пакету> \
  --disable-dependency-cache \
  --manifest-cache none \
  --disable-prefetching \
  --disable-netrc \
  --disable-keychain \
  --disable-automatic-resolution \
  dump-package
```

Для каждого пакета автоматизация запускает автономные тесты:

```bash
swift test \
  --package-path <путь-к-пакету> \
  --disable-dependency-cache \
  --manifest-cache none \
  --disable-prefetching \
  --disable-netrc \
  --disable-keychain \
  --disable-automatic-resolution
```

Каждый объявленный исполняемый продукт собирается отдельно:

```bash
swift build \
  --package-path <путь-к-пакету> \
  --disable-dependency-cache \
  --manifest-cache none \
  --disable-prefetching \
  --disable-netrc \
  --disable-keychain \
  --disable-automatic-resolution \
  --product <имя-продукта>
```

По умолчанию все пути целей и `Package.swift` проходят строгий lint:

```bash
swift format lint \
  --configuration Инструменты/fum-kompleksnaya-proverka-repozitoriya/swift-format.json \
  --strict \
  --recursive \
  <путь-к-пакету>/Package.swift \
  <пути-целей>
```

Центральная [конфигурация форматтера](swift-format.json) фиксирует набор правил и параметров вместо зависимости от неявного файла среды. Файлы `.swift-format-ignore` запрещены во всей применимой иерархии, потому что они могут молча исключить явно переданный Swift-файл даже из строгого lint.

Правило `IdentifiersMustBeASCII` явно отключено, чтобы строгий lint разрешал кириллические Swift-идентификаторы. Исполнитель по-прежнему передаёт `--strict`; остальные правила центральной конфигурации не ослабляются.

[Политика SwiftPM-пакетов](swift-package-policy.json) схемы `2` хранит ожидаемый инвентарь пакетов, исполняемых продуктов и точный allowlist прямых локальных package- и product-связей. Исчезнувший пакет или продукт, новый незарегистрированный пакет и несовпадение с фактическим `dump-package` останавливают smoke-check. Пакет без зависимостей обязан явно хранить `"localDependencies": []`: прежняя строгая граница для него не ослабляется.

Минимальная разрешённая композиция выглядит так:

```json
{
  "schemaVersion": 2,
  "defaultMode": "strict",
  "packages": [
    {
      "package": "Прототипы/consumer",
      "executableProducts": ["ConsumerCLI"],
      "localDependencies": [
        {
          "package": "Прототипы/provider",
          "identity": "provider",
          "products": [
            {
              "target": "ConsumerCLI",
              "product": "ProviderLibrary"
            }
          ]
        }
      ]
    },
    {
      "package": "Прототипы/provider",
      "executableProducts": ["ProviderCLI"],
      "localDependencies": []
    }
  ],
  "exceptions": []
}
```

`package` всегда является каноническим repo-relative-путём ровно к одному соседнему верхнеуровневому пакету `Прототипы/<имя>`. `identity` совпадает с фактической package identity из `dump-package`. Каждый элемент `products` задаёт точную связь потребляющей цели `target` с библиотечным продуктом `product` провайдера; лишняя, исчезнувшая или переименованная связь считается дрейфом. Зависимость в `Package.swift` записывается единственной переносимой литеральной формой `.package(path: "../provider")`. Именованные, вычисляемые, абсолютные, неканонические и дополнительные аргументы не допускаются.

Чтобы статическая граница не расходилась с итоговым объектом SwiftPM, манифест ограничен декларативной формой: после директивы tools version разрешён только `import PackageDescription`, затем ровно один `let package = Package(...)` и никакого кода после закрывающей скобки. Поле `dependencies:` самого этого инициализатора является литеральным массивом разрешённых вызовов. Вспомогательная фабрика, alias, backtick-вызов, неиспользуемый allowlist-маркер и последующая мутация `package.dependencies` закрываются отказом.

SwiftPM неизбежно возвращает `fileSystem.path` абсолютным. Smoke-check раскрывает символические ссылки, выполняет `realpath`-проверку существования и нахождения внутри корня репозитория и `Прототипы/`, после чего нормализует путь обратно в точный repo-relative-вид и сопоставляет его с политикой и исходным литералом. Выход за любую границу, self-dependency, повтор package path или identity, повтор product-связи и цикл закрываются отказом. Так же до тестов и сборки отклоняются source-control-, registry-, неизвестные и binary-зависимости, неоднозначная внешняя `byName`-связь, условная product-связь и product, который провайдер фактически не экспортирует как библиотеку.

Чтобы добавить зависимость:

1. Зарегистрируй потребителя и провайдера в `packages`; для остальных пакетов сохрани пустые allowlist.
2. Добавь потребителю канонический `.package(path: "../<сосед>")` и явную `.product(name: ..., package: ...)` в конкретную цель.
3. В `localDependencies` зафиксируй repo-relative-путь провайдера, identity из свежего локального `dump-package` и все точные пары `target`/`product`.
4. Запусти тесты автоматизации, затем явный профиль `--профиль полный`. Не добавляй разрешение ради уже наблюдаемого дрейфа: сначала проверь происхождение изменившейся identity или связи.

Offline-флаги одинаково применяются к `dump-package`, `swift test` и `swift build`. Контур не загружает зависимости и не использует пользовательские credential- и dependency-кэши; локальный путь является единственным разрешённым транспортом между пакетами.

Если временное lint-исключение необходимо, оно обязано содержать причину, критерий снятия, существующий источник и SHA-256 центральной конфигурации, `Package.swift` и Swift-файлов целей. Исключение печатается в полном запуске и его `--list`; любое изменение защищённого снимка останавливает полный профиль как устаревшая политика. Текущая политика не содержит исключений.

3. Проверяет структуру папок запросов и контракт их канонических шаблонов:

```bash
python3 Инструменты/fum-struktura-papok-zaprosov/scripts/struktura-papok-zaprosov.py \
  validate \
  --repo-root .
```

Проверка требует обязательный временной префикс имени родительской папки и `запрос.md`, допускает `материалы/`, запрещает прежний `Запросы/` и разрешает непосредственно в `Журнал/` только `README.md` среди Markdown-файлов. Для новой рабочей сессии обязателен соседний `отчёт.md`; историческая папка может оставаться без него только при отсутствии отчёта до миграции. Тем же вызовом закрыто проверяются точные поля, активный каркас, обязательные разделы, порядок заголовков и выравнивание таблиц хранимых шаблонов `запрос.md.шаблон` и `отчёт.md.шаблон`; автопоиск тестов отдельно подтверждает генерацию по этим файлам, отказ при незаполненном маркере и независимую валидацию результата.

4. Пересобирает машинно читаемый плановый реестр:

```bash
python3 Инструменты/fum-reyestr-planirovaniya/scripts/build-planning-registry.py build \
  --output Планирование/реестр-требований-вариантов-и-кандидатов.json
```

5. Проверяет свежесть планового реестра:

```bash
python3 Инструменты/fum-reyestr-planirovaniya/scripts/build-planning-registry.py validate \
  --registry Планирование/реестр-требований-вариантов-и-кандидатов.json
```

6. Только в полном профиле проверяет реестр названий автоматизаций:

```bash
python3 Инструменты/fum-proverka-nazvanij-avtomatizacij/scripts/proveritj-nazvaniya-avtomatizacij.py \
  --repo-root . \
  --registry Инструменты/реестр-названий-автоматизаций.json
```

Канонический реестр находится в состоянии `ready`, поэтому полный профиль требует материализованный пакет и живой вызов LinguisticKit. После свежего клонирования сначала нужно [инициализировать submodule и локальный `upstream`](../../Зависимости/README.md); перевод реестра в `blocked` не является допустимым обходом этой операции.

## Проверки автоматизации

Локальные тесты самой автоматизации запускаются без сети и секретов:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s Инструменты/fum-kompleksnaya-proverka-repozitoriya/tests -p 'test_*.py'
```

Тесты сначала фиксируют профильную границу: по умолчанию выбирается `документационный`, его состав и порядок равны точному положительному перечню, лишний каталог тестов игнорируется, а отсутствующий, пустой или вынесенный символической ссылкой разрешённый набор закрывает подготовку отказом. Стандартный `--list` не вызывает автопоиск, Swift-контур и историю; `--профиль полный --list` сохраняет прежний разбор манифестов и показывает все тяжёлые команды без их исполнения. Полный профиль сохраняет прежний автопоиск, риск-сортировку и фиксированный Swift-хвост.

Остальной набор фиксирует базовый контракт: smoke-check требует отключённую передачу общего каталога навыков в проектной конфигурации, отклоняет выход локального `SKILL.md` за корень через символическую ссылку, считает аварийный сигнал и незавершившийся достигнутый тест ошибкой, не считает внешнее прерывание ошибкой, сохраняет только достигнутый fail-fast-префикс и не передаёт capability-переменные дочерним шагам. Полнопрофильные тесты сверяют инвентарь SwiftPM-пакетов и продуктов, `dump-package`, `swift test`, сборку каждого исполняемого продукта, строгий lint и политику локальных зависимостей. Общие тесты закрепляют структуру запросов, плановый реестр, машинно-локальные пути, корневую инструкцию, индекс документации, вопросы, recency и связность сессии.

Регрессия схемы `2` создаёт настоящую локальную SwiftPM-композицию и проверяет allowlist прямых зависимостей, нормализацию путей, совпадение identity и product-связей, циклы и запрещённые внешние зависимости. Внедряемый монотонный таймер закрепляет стабильные записи длительности каждого шага и полного интервала при успехе и ошибке. Отдельный сквозной тест создаёт отслеживаемую first-party-регрессию и подтверждает остановку исполнителя на сканере машинно-локальных путей.

## Граница автоматизации

Smoke-check не заменяет смысловую проверку изменений, публикационную чистоту diff и решение агента о том, какие файлы нужно коммитить. Он объединяет локальные структурные проверки и останавливается на первом упавшем шаге, чтобы ошибка оставалась наблюдаемой и не маскировалась следующими командами.

Прямой нулевой выход этой команды нельзя сообщать как завершённый успех smoke-сессии. Корневая задача сначала замыкает журнальные доказательства без повторного полного прогона, индексирует только проверенное состояние и создаёт один итоговый локальный коммит на `refs/heads/master`. Переходная сессия, впервые вводящая `manual-sequential-v1`, завершает этот единственный коммит прежним атомарным протоколом к чисто завершающему мосту; последующие сессии очередь и selector не вызывают.

Если во время выполняющегося smoke-check обнаружен уже подтверждённый дефект, делающий проверяемый снимок заведомо непринимаемым, корневой агент немедленно прерывает дочерний процесс штатным сигналом. Обязательная обёртка отчётов сохраняет исход `прервано`; после исправления заново запускается тот же выбранный профиль, и именно новый успешный прогон становится приёмочным.

Если в репозитории появляется новый проверяемый реестр, его добавляют в стандарт только при доказанной необходимости документационному прототипу и закрепляют ожидание тестом. Новый `Инструменты/<имя>/tests` автоматически входит лишь в полный профиль; для стандартного требуется отдельное обоснованное изменение положительного перечня.

Обнаружение SwiftPM намеренно ограничено устойчивыми прототипами вида `Прототипы/<имя>/Package.swift`, поэтому кэши `.build`, `.swiftpm` и пакеты транзитивных зависимостей не становятся самостоятельными входами smoke-check. Разрешаются только прямые локальные связи между зарегистрированными соседними пакетами; транзитивная достижимость не заменяет allowlist прямой связи. Локальная служебная обёртка использует LinguisticKit только через отдельно проверяемый Git submodule. Результат `dump-package` зависит от локального Swift toolchain и платформы, поэтому неизвестная структура манифеста или отсутствие исполняемого продукта считается ошибкой, а не основанием тихо пропустить сборку.

Текущий Swift-контур предназначен для macOS: все пакеты требуют macOS 14 или новее, Swift 6.0 или новее и Xcode с командами `swift` и `swift format`, а сборки smoke-check являются отладочными сборками SwiftPM по умолчанию. Центральная конфигурация не содержит имён правил, отсутствующих в Swift 6.0, но более старый форматтер может игнорировать неизвестные ему дополнительные параметры, поэтому идентичная семантика lint между разными версиями toolchain не обещается. Принятый снимок полностью проверен на Swift 6.4 и Xcode 27.0; это наблюдаемая текущая среда, а не обещание бинарной совместимости со всеми будущими toolchain.
