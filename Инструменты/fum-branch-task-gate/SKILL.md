# Барьер задач Git-ветки

Барьер допускает к общему checkout одну корневую задачу Codex и сохраняет за ней именованную Git-ветку до явного завершения. В проектной конфигурации для него существует только один обработчик — `UserPromptSubmit`; отдельные `SubagentStart`, `PreToolUse` и `Stop` hooks не используются.

## Контракт допуска

Корневой `UserPromptSubmit` без `agent_id` и `agent_type` атомарно захватывает ветку за внутренним `session_id`. Первый ход ждёт, пока нет другого владельца и рабочее дерево вне корневой `.obsidian/` чисто. Повторный корневой ход того же `session_id` подтверждает уже существующее владение независимо от текущей чистоты дерева: `lease_id` и сохранённый первый `turn_id` не меняются.

Успешный корневой допуск возвращает в `hookSpecificOutput.additionalContext` две строки:

```text
FUM-BRANCH-TASK-GATE: admitted-v1
FUM-BRANCH-TASK-GATE-OWNER: <внутренний-session_id>
```

Первая строка является точным сигналом допуска для правил `AGENTS.md`, вторая даёт корневому ходу адрес штатного освобождения. Внутренние `session_id` и `turn_id` не являются `Codex-Thread-ID` и не публикуются под его именем.

`UserPromptSubmit`, содержащий хотя бы `agent_id` или `agent_type`, считается дочерним событием и завершается без вывода и изменения состояния. Субагенты являются исполнителями уже допущенной корневой задачи: они не регистрируются в барьере, не получают собственного маркера или lease, не захватывают и не освобождают ветку. Корневой ход координирует их записи и отвечает за остановку всех дочерних исполнителей до освобождения.

Файл владения хранится вне рабочей копии, в `fum-branch-task-gate/` общего Git-каталога. Ключом служит SHA-256 полного имени `refs/heads/<ветка>`. JSON-запись схемы 6 хранит корневые `task_id`, `turn_id`, `branch_ref`, `acquired_at`, уникальный `lease_id` и идентичность worktree. Реализация читает прежние схемы 4 и 5 для диагностики и восстановления, а новое владение записывает в схеме 6. Короткие переходы общего Git-каталога сериализуются POSIX-блокировкой, а начальный lease публикуется атомарным hard link только после полной записи.

## Диагностика

Показать состояние текущей ветки:

```bash
python3 Инструменты/fum-branch-task-gate/scripts/branch-task-gate.py \
  status \
  --repo-root . \
  --json
```

Код `0` и состояние `ready` означают готовность. Код `1` с состоянием `locked`, `dirty` или `locked_and_dirty` означает, что другая корневая задача пока не должна начинать работу. JSON занятого барьера показывает `schema_version`, `task_id`, `turn_id`, `lease_id` и при смене ветки владельцем исходный `owner_branch_ref`.

Видимые в `git status` staged-, unstaged-, untracked-, конфликтные и submodule-изменения вне корневой `.obsidian/` блокируют только первый захват и штатное освобождение. Игнорируемые Git-файлы и изменения внутри корневой `.obsidian/` не блокируют очередь. Это исключение не отменяет обязанность классифицировать состояние `.obsidian/` по `AGENTS.md`.

## Смысловое завершение

Корневой ход освобождает ветку только после завершения всей пользовательской задачи, а не в конце каждого ответа. Перед освобождением он:

1. Дожидается всех процессов и субагентов, которые способны позднее записать в репозиторий.
2. Завершает проверки и коммит.
3. Подтверждает чистоту рабочего дерева вне корневой `.obsidian/`.
4. Подставляет значение из строки `FUM-BRANCH-TASK-GATE-OWNER` текущего допуска и синхронно выполняет:

```bash
python3 Инструменты/fum-branch-task-gate/scripts/branch-task-gate.py \
  release \
  --repo-root . \
  --task-id '<внутренний-session_id>' \
  --json
```

Обычный `release` отклоняет чужого владельца, грязное дерево и смену ветки. После успешного освобождения текущий ход не изменяет репозиторий и не запускает отложенных писателей. Следующий пользовательский запрос в той же задаче при необходимости создаст новый lease через корневой `UserPromptSubmit`.

## Аварийное восстановление

Автоматического TTL нет: срок жизни без надёжного heartbeat мог бы допустить две живые задачи одновременно. Если прежняя задача прервана и не выполнила штатный `release`:

1. Выполни `status --json` и сохрани точный `lease_id`.
2. Отдельно подтверди, что прежняя задача, её процессы и субагенты больше не исполняются и не могут возобновить запись.
3. Только после этого сними именно наблюдённое поколение:

```bash
python3 Инструменты/fum-branch-task-gate/scripts/branch-task-gate.py \
  release \
  --repo-root . \
  --task-id recovery \
  --force \
  --expected-lease-id <lease_id-из-status> \
  --json
```

Принудительное снятие не делает грязное дерево чистым. Уже отсутствующее ожидаемое поколение возвращает mismatch с состоянием `missing`, а несовпавший `lease_id` не удаляет нового владельца.

Если владелец переключил или переименовал ветку и диагностика сохранила исходный полный ref, после той же внешней проверки укажи его явно:

```bash
python3 Инструменты/fum-branch-task-gate/scripts/branch-task-gate.py \
  release \
  --repo-root . \
  --task-id recovery \
  --force \
  --expected-lease-id <lease_id-из-status> \
  --branch-ref refs/heads/<исходная-ветка> \
  --json
```

`--branch-ref` и `--expected-lease-id` запрещены без `--force`; `--force` без предварительно наблюдённого поколения также отклоняется. Повреждённая запись, из которой нельзя надёжно получить поколение, требует ручной локальной диагностики после подтверждения остановки прежнего исполнителя.

## Активация hook

Проектный hook исполняется только для доверенного репозитория. После добавления или изменения определения пользователь открывает `/hooks`, просматривает полный список project-, user-, plugin- и managed-hooks и одобряет точное единственное определение `UserPromptSubmit` веточного барьера. Наличие записи в `.codex/config.toml` и включённой функции hooks само по себе не доказывает фактический вызов.

Загрузчик берёт helper через `git show HEAD:Инструменты/fum-branch-task-gate/scripts/branch-task-gate.py`, буферизует его stdout и публикует ответ только после штатного `SystemExit(0)`. Ошибка загрузки или исполнения даёт корневому событию `decision: block`; частичный вывод отбрасывается. Если host пропустил недоверенный или отключённый hook, helper не получает управления и маркер допуска не появляется.

`UserPromptSubmit` ждёт не дольше 85 800 секунд внутри сценария, оставляя запас до host-timeout 86 400 секунд. Достижение внутреннего дедлайна возвращает `decision: block`, после чего запрос можно повторить, когда прежний владелец освободит ветку.


Набор закрепляет единственный проектный hook, точный корневой маркер и идентификатор владельца, один неизменяемый lease между корневыми ходами, дочерний no-op без регистрации, явное освобождение, ожидание handoff, исключение только корневой `.obsidian/`, основные виды Git-изменений, одновременный захват, атомарную публикацию, чтение прежних схем, fenced-восстановление, исполнение helper из `HEAD`, смену ветки и worktree, безопасную обработку ошибок и отказ в detached HEAD.

## Граница автоматизации

Барьер рассчитан на POSIX-среду с `flock` и атомарными hard links, один зарегистрированный worktree на именованную ветку и сотрудничающие задачи одного общего Git-каталога. Он не координирует отдельные клоны и не поддерживает Windows. Именованная локальная ветка обязательна; одну ветку, принудительно открытую сразу в нескольких worktree, автоматизация отклоняет.

Во время владения нельзя переключать ветку: lease остаётся привязан к исходному полному ref и идентичности worktree. Возврат на исходную ветку сохраняет владение; адресное аварийное освобождение допускается только по предварительно наблюдённому поколению.

Единственный корневой hook — кооперативная граница допуска задач, а не полная enforcement-граница. Он не перехватывает действия уже запущенных процессов, hosted-инструментов и специализированных путей и не проверяет каждый вызов инструмента. Надёжность handoff поэтому зависит от дисциплины корневого хода: не освобождать lease до остановки всех возможных писателей и не писать после освобождения.
