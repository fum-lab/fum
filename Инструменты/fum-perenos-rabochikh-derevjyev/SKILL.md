# Перенос рабочих деревьев

Инструмент перемещает один linked worktree целиком и восстанавливает только его Git-привязки. Отслеживаемые изменения, отдельное состояние индекса, неотслеживаемые и игнорируемые файлы сохраняются. После прерывания та же команда продолжает сохранённую операцию; завершённый повтор возвращает прежнюю квитанцию. Реальный перенос пользовательских деревьев требует отдельной приёмки фактического дерева и внешних привязок.

## Подготовка

Нужны Python 3.11+ и Git, поддерживающий `--path-format=absolute` и `--show-object-format`. Собственные модули берутся из того же клона FUM: канонический JSON и читатель объектов из `fum-snimki-indeksa`, атомарный перенос из `fum-bratislavskaya-proyekciya-pamyati`. Обычный запуск переноса и автономные тесты не требуют Swift, LinguisticKit, сети или секретов.

Исходный каталог должен быть штатным linked worktree с Git-dir в `common-dir/worktrees/<имя>`. Его submodule должны быть уже инициализированы, а их Git-dir должны находиться в `modules/<имя секции>` непосредственно под Git-dir родителя. Имя секции `.gitmodules` может отличаться от рабочего пути. Все административные каталоги остаются вне перемещаемого дерева.

До работы владелец исключает других писателей исходного дерева и вложенных репозиториев и резервирует дерево штатным `git worktree lock --reason fum-перенос:<UUID-владельца> <исходный-каталог>`. Инструмент требует точный текст этой резервации и сохраняет её после переноса. UUID и lock-файл подтверждают согласованное владение; они не останавливают процесс, который обходит этот протокол и продолжает менять файлы.

Назначение должно отсутствовать. Его родитель, common-dir и отдельный приватный каталог состояния должны существовать на том же томе. Каталог состояния принадлежит текущему пользователю, имеет режим `0700` и находится вне обоих рабочих деревьев и common-dir. Один такой каталог обслуживает ровно одну операцию и сохраняется после её завершения.

## Приватные привязки и открытый план

Подготовьте вне публикуемого checkout JSON с шестью полями:

| Поле         | Значение                                               |
| ------------ | ------------------------------------------------------ |
| `схема`      | `fum.привязки-переноса.1`                              |
| `владелец`   | Канонический UUID, совпадающий с причиной Git-lock     |
| `источник`   | Точный абсолютный физический корень linked worktree    |
| `назначение` | Точный абсолютный новый корень                         |
| `общий`      | Точный абсолютный Git common-dir                       |
| `состояние`  | Отдельный существующий приватный каталог этой операции |

Файл имеет каноническое кодирование `канон.кодировать`: UTF-8, сортировка ключей, отсутствие необязательных пробелов и один завершающий LF. Для подготовки из отредактированного JSON можно вызвать из корня FUM следующую команду, передав приватный файл:

```text
python3 -B -c 'import json,sys; from pathlib import Path; sys.path.insert(0,"Инструменты/fum-snimki-indeksa/scripts"); import канон; путь=Path(sys.argv[1]); путь.write_bytes(канон.кодировать(json.loads(путь.read_text())))' '<приватный файл привязок>'
```

План выводится в stdout. Сам процесс не создаёт файлов, замков или bytecode и не меняет индекс. Перенаправление stdout в выбранный файл выполняет вызывающий:

```text
python3 -B Инструменты/fum-perenos-rabochikh-derevjyev/scripts/перенос.py план --привязки '<приватный файл привязок>' > '<файл плана>'
```

План `fum.план-переноса.1` содержит владельца, идентичность операции, хэш приватных привязок, хэши идентичностей каталогов, исходные HEAD, полные refs и индексы каждого репозитория, относительные маршруты Git-dir/common-dir, снимки данных и разрешённый перечень ремонта с хэшами старых и будущих байтов. Он не раскрывает физических абсолютных корней. При просмотре сопоставляйте его с приватным файлом привязок: одни хэши не объясняют человеку назначение каталога.

## Применение и возобновление

После просмотра запустите:

```text
python3 -B Инструменты/fum-perenos-rabochikh-derevjyev/scripts/перенос.py применить --привязки '<приватный файл привязок>' --план '<сохранённый файл плана>' --владелец '<UUID-владельца>'
```

Первый вызов заново выводит план из фактического состояния. Под отдельным постоянным `flock` сохраняется намерение с точными приватными байтами ремонта; затем выполняются фазы `перемещение`, `ремонт`, `сверка`, `завершён`. Переименование не заменяет существующее назначение. После него сначала синхронизируется родитель назначения, затем родитель источника.

Ремонт ограничен `.git` переносимых рабочих каталогов, обратным `gitdir` linked worktree и строками `core.worktree` штатных submodule. Остальные байты конфигурации сохраняются. Перед каждым изменением проверяются данные, индексы, HEAD, refs и допустимые старые/новые байты привязок. Замена каждого файла и продвижение курсора долговечны. Соседние worktree, refs, индексы и содержимое primary checkout инструмент не изменяет.

При прерывании повторите **ту же команду с теми же файлами и UUID** новым процессом. В окне после rename инструмент узнаёт тот же каталог по идентичности, читает Git через сохранённый административный путь и явно заданное рабочее дерево, повторно закрепляет каталоги и продолжает ремонт. Повторное перемещение не выполняется. То же относится к потерянному ответу после завершения.

Код `0` сопровождается JSON-квитанцией `fum.результат-переноса.1`. Код `2` означает явный отказ. Профиль в stderr отделён от результата. При отказе сохраните план, привязки и весь приватный каталог состояния; не исправляйте его поля вручную и не пытайтесь восстановиться через `clean`, `prune`, `remove`, пересоздание worktree или инициализацию submodule. Изменившиеся данные, третьи байты конфигурации, занятая цель и повреждённый журнал требуют отдельной сверки. Если до установки `операция.json` остался `подготовка.tmp`, новый процесс явно отказывает и сохраняет его побайтово, даже когда файл пуст, полностью записан или содержит неизвестные байты. Дерево в этом окне ещё не перемещено. Автоматическое возобновление гарантируется только после долговечной установки первичного намерения; очистка раннего остатка требует отдельной сверки владельцем.

## Явный пересмотр данных прерванной операции

Если после перемещения внешний писатель изменил данные, обычное возобновление строго отказывает. После отдельной сверки владельцем текущего содержимого можно принять новый снимок уже перемещённой операции в фазе `ремонт` либо `сверка`. Сначала сохраните старый план и выполните команду без записи состояния:

```text
python3 -B Инструменты/fum-perenos-rabochikh-derevjyev/scripts/перенос.py пересмотреть --привязки '<приватный файл привязок>' --план '<прежний план>' --владелец '<UUID-владельца>' > '<приватный кандидат>'
```

Кандидат `fum.пересмотр-переноса.1` связывает точные исходные байты состояния, прежний план, актуальные байты Git-привязок и полный инвентарь данных с индивидуальными хэшами. Инвентарь содержит имена локальных и игнорируемых файлов; кандидат хранится приватно. Новый план отличается только хэшем данных и вычисленной идентичностью операции. HEAD, refs, индексы, административные идентичности, конфигурация и перечень ремонта сохраняются; выполненная часть ремонта должна иметь ожидаемые конечные байты. Два полных обхода проверяют устойчивость текущего снимка.

После проверки кандидата примите именно его:

```text
python3 -B Инструменты/fum-perenos-rabochikh-derevjyev/scripts/перенос.py принять-пересмотр --привязки '<приватный файл привязок>' --кандидат '<приватный кандидат>' --владелец '<UUID-владельца>' > '<новый план>'
```

Под прежним постоянным замком заново проверяются кандидат и фактическое состояние. До замены `операция.json` долговечно сохраняется `пересмотр.json` с точными исходными и целевыми байтами состояния и их хэшами. Меняется только план; фаза, курсор и приватные байты ремонта остаются прежними. Эта команда не выполняет очередной ремонт. Затем продолжите обычной командой `применить` с новым планом; в партии контейнера также используйте новый план. Прежний план и оба состояния сохраняются как происхождение, прежний хэш данных больше не является подтверждением актуальных байтов.

Авария после намерения либо замены состояния возобновляется повторным принятием того же кандидата. Любое третье состояние, включая уже продвинутый обычным исполнением курсор, отклоняется без отката. Неизвестные или неполные `пересмотр-намерение.tmp` и `пересмотр-состояние.tmp` сохраняются с отказом; хвосты обычного ремонта не очищаются. До завершения перехода обычное исполнение отказывает при временных файлах пересмотра. Новый пересмотр после первого, завершённые операции и операции с отметками финализации контейнера не поддержаны. Это отдельное принятие конкретного текущего снимка, а не автоматическое игнорирование дрейфа.

## Завершение общего контейнера

Если несколько завершённых переносов освобождают один старый каталог, используйте ту же автоматизацию. Все деревья должны сохранять свои имена и иметь одного владельца, общий старый родитель и общий новый родитель. Приватная партия `fum.партия-переноса.1` содержит поля `схема` и `операции`; каждый элемент списка `операции` содержит ровно `план` и `привязки` с исходными JSON-объектами отдельного переноса.

```text
python3 -B Инструменты/fum-perenos-rabochikh-derevjyev/scripts/перенос.py завершить-контейнер --партия '<приватный файл партии>' --владелец '<UUID-владельца>'
```

Команда принимает только уже завершённые операции и заново проверяет каждую квитанцию. Новый контейнер должен содержать точно перечисленные деревья. В старом допустим только обычный `.DS_Store` без hardlink: он переносится без замены, с сохранением байтов, режима и идентичности. Неизвестный объект останавливает завершение и сохраняется.

До переноса файла и удаления пустого старого контейнера во всех приватных состояниях долговечно устанавливается одинаковое намерение партии, связанное с конкретной операцией. Авария после части отметок, переноса файла или удаления каталога возобновляется той же командой новым процессом. Повтор проверяет идентичности сохранившихся родителей и закрепляет результат синхронизацией каталогов. Квитанция `fum.результат-завершения-контейнера.1` сохраняет идентичность партии. Обычный повтор каждого переноса после удаления старого родителя возвращает прежнюю квитанцию только при завершённом состоянии и соответствующей отметке партии.

Сохраните все прежние состояния, планы, привязки и файл партии. Неизвестные или неполные байты `контейнер.tmp` дают явный отказ и сохраняются; до долговечной отметки автоматического восстановления такого раннего остатка нет. Постоянный `контейнер.lock` не удаляется. Команда не меняет внешние приложения и не создаёт ссылку совместимости.

## Проверки и профиль

Из чистого клона FUM, без инициализации внешних зависимостей:

```text
python3 -B -m unittest discover -s Инструменты/fum-perenos-rabochikh-derevjyev/tests -p 'test_*.py'
python3 -B Инструменты/fum-perenos-rabochikh-derevjyev/tests/профиль.py --выход '<файл измерений.json>' --повторы 3
python3 -B Инструменты/fum-perenos-rabochikh-derevjyev/tests/профиль.py --выход '<файл измерений detached.json>' --повторы 3 --отсоединённый
```

В агентской сессии команды выполняются через отчётную обёртку своего Журнала. Фикстура строит три собственных локальных Git-репозитория, linked worktree, два уровня submodule, разные индексные/рабочие байты и игнорируемые данные. Драйвер аварий — отдельный тестовый процесс; у рабочего CLI нет команды аварийного завершения.

Первый RED прервал процесс после реального перемещения каталога и до ремонта; новый процесс обнаружил отсутствие реализации восстановления. GREEN подтверждает восстановление того же каталога, сохранение данных, OID, refs и индексов и точный повтор. Дополнительные сценарии проверяют обе формы привязок, отказы, конкурирующий повтор, каждую существенную фазу и отказ синхронизации после rename.

Профиль различает сбор плана, повторную проверку, переименование, ремонт, сверку, возобновление и точный повтор. Он сохраняет версии среды, SHA-256 исходников и исходные интервалы. Время родителя включает детей; интервалы не складываются повторно. Исходный профиль и итог проверки находятся в [отчёте реализации](../../Журнал/2026-09-11_07-17-34_MSK_реализовать-перенос-рабочих-деревьев/отчёт.md).

## Границы поддержки

Проверено на macOS arm64, Git 2.54.0 и Python 3.14.7. Linux использует существующий `renameat2`-примитив, однако собственного запуска этого переноса на Linux ещё нет; поддержка платформы не принята. Windows и перенос между томами не поддержаны. Фикстура другого тома проверяет отказ подменой наблюдаемого `st_dev`; испытание реального второго тома не заявляется.

Поддержаны относительные и абсолютные `.git` и `core.worktree`, attached/detached linked корень и штатные submodule, обычный индекс, локальные изменения и UTF-8-имена. Отсоединённый HEAD содержит точный исходный OID; его изменение, присоединение к ветке или сдвиг индекса после прерывания останавливают повтор. У submodule допустимо отсутствие `core.worktree`, если Git через рабочую `.git` доказывает точный корень; тогда конфигурация сохраняется побайтово и новая строка не добавляется. Содержимое payload symlink сохраняется без перехода по нему; абсолютные внутренние и относительные внешние ссылки требуют отдельной проверки переносимости.

До переноса отклоняются неинициализированные и нестандартные вложенные репозитории, bare-корень, конфликтный индекс, split/sparse index, явно заданные `core.sparseCheckout` или `core.splitIndex` (включая `false`), включения `include/includeIf`, неоднозначный `core.worktree`, Git-lock-файлы операций в административном поддереве выбранного worktree, symlink и коллизии регистра в управляющих путях, управляющие символы, кавычка и обратная косая черта в путях, специальные файловые объекты и вложенные тома. `extensions.worktreeConfig` допускается только как единственное точное `true` общей конфигурации linked корня при отсутствии выбранного `config.worktree`; его позднее появление отклоняется. Общий config не изменяется. Другие варианты этого флага, sharedindex и нештатные внешние Git-dir не ремонтируются.

Модель предполагает добросовестного единственного писателя и доверенный приватный каталог состояния. Наблюдения и хэши обнаруживают дрейф, но не дают защиты от намеренной согласованной подделки всех свидетельств тем же пользователем или подмены предков между проверкой и системным вызовом. Успешные процессные аварии и `fsync`-фикстуры не являются испытанием отключения питания либо гарантией конкретного файлового устройства.

Результат не меняет проекты Codex и внешние приложения. Перед первым живым переносом отдельно принимаются свежие владелец, резервирование и полная топология выбранного дерева, фактический том, новый маршрут, внешние пути Codex/Obsidian/сборок и состояние фоновых процессов. Исторический пул и автоматическое продолжение не подключаются.
