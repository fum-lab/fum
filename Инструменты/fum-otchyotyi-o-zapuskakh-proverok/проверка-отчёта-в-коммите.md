# Проверка закрытого отчёта в коммите

[Читатель](scripts/закрытый_отчёт_из_гита.py) проверяет приёмочные свидетельства, сохранённые в конкретном коммите: полный каталог запусков, закрытый снимок, управляемый блок отчёта, готовность плана и [связь Git-отпечатка с кодом](связь-с-коммитом.md). Для v4 он дополнительно строит узкого кандидата содержательного отпечатка из объектов выбранного одиночного коммита. Совпадение обоих отпечатков подтверждает связь отчёта с этим коммитом, но не завершение обязательства.

```bash
python3 -B Инструменты/fum-otchyotyi-o-zapuskakh-proverok/scripts/закрытый_отчёт_из_гита.py \
  --корень-репозитория . \
  --коммит <полный-OID> \
  --запрос Журнал/<stem>/запрос.md
```

Передаётся полный OID доступного коммита и точный относительный путь запроса. Корень совпадает с реальным checkout. Без явного режима слияния допускается коммит с одним родителем; merge и начальный коммит отклоняются. Тег и сокращённый OID не принимаются в любом режиме. Отсутствующие объекты не загружаются из сети.

Для точного C с родителями `[L, M]` параметр `--слияние` проверяет закрытый отчёт и связь отпечатков, а `--допуск-слияния` дополнительно требует сохранённое происхождение проверок из M. Режимы взаимоисключающие; оба требуют полные `--база L`, `--присоединяемый M` и `--дерево T`. Подготовка и команды описаны в [проверке слияния из master](проверка-слияния-из-master.md).

| Код | Состояние | Значение |
| --- | --- | --- |
| 0 | `подтверждён` | Закрытый отчёт готов; исторический Git-отпечаток совпал, а для v4 совпал и содержательный кандидат из Git. |
| 2 | `не подтверждён` | Отчёт целостен, но один из отпечатков не совпал либо кандидат v4 недоступен. Это не доказательство подмены. |
| 1 | Ошибка | Вход, состав, тип объекта, формат, целостность либо готовность не подтверждены. |

Вывод имеет схему `fum.проверенный-отчёт.1`, содержит полный коммит, путь запроса, число запусков, UUID финального запуска, хэш снимка, Git-отпечатки и результат их связи. Для v4 добавлены `отпечаток_содержимого_закрытия` и `связь_содержимого` со значением `подтверждён`, `не совпадает` либо `не восстановлен`. Общий итог подтверждается только при обеих подтверждённых связях. Поле `завершение_обязательства_доказано` всегда равно `false`: успешная приёмка кода сама по себе не закрывает пользовательское обязательство.

## Что проверяется

Режим допуска добавляет `происхождение_проверок`: путь и blob OID свидетельства, M и его дерево, L, обёртку, зависимость, хэш политики, запрос и UUID, равный `финальный_запуск`. Метка исполнения в поле `ожидаемое_свидетельство` финальной записи должна точно связывать канонические байты этого свидетельства. Обычная полная запись с `null` не подтверждает источник M. Свидетельство читается из C; политика и её описание — из M. Проверяются одинаковые деревья архивируемого пакета M/L/C и gitlink M/C. Отсутствие свидетельства, иной режим файла, неканонические байты, другой UUID или источник означают отказ. Этот режим не меняет refs и не доказывает завершение обязательства.

Инвентарь берётся из дерева Git, включая вложенные деревья. Список внутри снимка не служит единственным источником состава. В каталоге запусков недопустимы неизвестные файлы, вложенные каталоги, даже пустые, и переходный журнал возобновления. Запрос, отчёт и свидетельства должны быть обычными blobs с режимом `100644` или `100755`; символические ссылки и gitlink отклоняются. Фактический тип каждого объекта проверяется отдельно от режима записи дерева: tag на корректный blob не подменяет сам blob.

Все JSON-объекты отклоняют повторные ключи и нечисловые константы. Проверяются схемы запусков, UUID, уникальность порядка, совместимость истории, точные хэши и состав снимка. Для самого снимка дополнительно обязательны канонические байты. Форматирование JSON записей может отличаться, если их точные байты связаны согласованными хэшами; это сохраняет контракт прежней обёртки.

Маркер и управляемый Markdown-блок совпадают с результатом существующего генератора. Затем отдельно проверяется план: закрытый, но неготовый отчёт не принимается. Для v3 последняя запись должна быть единственной успешной полной приёмкой на отпечатке закрытия; прежний порядок истории сохраняется. Для v4 проверяется полный план раундов с обоими отпечатками, включая границу перехода и запрет повторной полной попытки на том же содержимом. Режимы слияния по-прежнему принимают только v3: подтверждение v4 для одиночного коммита не расширяет допуск слияния.

## Чтение без побочных изменений

Исторические свидетельства читаются из Git, даже если живые запрос, отчёт или снимок в checkout удалены либо испорчены. Исправленный checkout также не исправляет плохой архив в выбранном коммите. Читатель не создаёт временный checkout, журнальные lock-файлы или новые записи проверки и не меняет индекс, refs либо конфигурацию. При запуске Python используется `-B`, чтобы импорт не создавал `__pycache__`.

Git получает только полные OID объектов из выбранного дерева. Свидетельства читаются одним пакетом уникальных объектов, сохраняя соответствие каждому исходному пути; кандидат v4 читает включённые в отпечаток blobs потоком ограниченными порциями. Чтение проверяет точный OID, тип, десятичный размер, байты заданной длины, разделительный LF и конец ответа. Ненулевой код Git, отсутствующий объект, пропуск и лишний ответ означают отказ без частичного результата. Пакет свидетельств целиком хранится в памяти, содержимое остальных файлов — нет.

## Границы доказательства

Читатель использует доверенный локальный Git; независимый пересчёт Git OID и полный аудит повреждения объектной базы не входят в контракт. Историческая реконструкция наследует ограничения адаптера по конфигурации и буквальному diff. Проверяется управляемое свидетельство, а не истинность свободного текста отчёта.

Кандидат v4 интерпретирует режимы Git `100644` и `100755` как фактические права `644` и `755`. Git не сохраняет полный режим файлов и не содержит файлы, оставшиеся вне индекса. Поэтому другой фактический режим или неотслеживаемый вход при закрытии обычно не даст совпадения; это отсутствие подтверждения. Для gitlink нужны доступные локальные объекты подмодуля и его каталог; текущие файлы и HEAD подмодуля не используются как исторические байты. Исключённая область `Proyekcii/**` не читается для содержательного кандидата.

Содержимое пользовательских команд, `Codex-Thread-ID`, полнота реестра, смысловая приёмка результата и актуальность обязательства требуют следующего слоя. Наличие обычного файла запроса ещё не доказывает происхождение команды. Читатель не выполняет merge и не подключён к завершению Codex. Сохранённые v4-поставки не становятся автоматически принятыми: совпадение отпечатков доказывает лишь оговорённую связь с объектами выбранного коммита.

## Измерение

[Профиль сравнения](../../Журнал/2026-09-10_02-01-28_MSK_проверять-закрытые-отчёты-из-коммитов/материалы/профиль-сравнения.json) воспроизводится [сценарием](../../Журнал/2026-09-10_02-01-28_MSK_проверять-закрытые-отчёты-из-коммитов/материалы/измерить-чтение-отчёта.py) на принятом коммите `6fc2c7a76dd7d23a703418b4072f0fdc561a4f53`. Импорты и отдельный замер памяти не входят во временную серию; это не холодный дисковый кеш и не время CLI. Пиковая учтённая память Python составила 679198 и 679360 байт; память дочерних Git-процессов не измерялась. Ускорение относится к этому входу и окружению.

[Профиль содержательного кандидата v4](../../Журнал/2026-10-02_20-35-30_MSK_связать-содержательный-отпечаток-раундов/материалы/профиль-связи-содержимого.json) выполнен на реальном коммите `474bdeb12a4e6d508c335fe8468671c67ccb9101`: медиана трёх повторов — 2,827 с, пик учтённой памяти Python — 35,7 МБ. В дереве 470,0 МБ blob-данных, из них 228,0 МБ в исключённой проекции; для кандидата эти объекты не читаются. Память Git-процесса, холодный дисковый кеш и полный CLI-цикл не измерялись; сравнения скорости с прежним пакетным вариантом этот профиль не заявляет.

Дочерний smoke в фикстуре синтетический: эти тесты не заявляют выполнение реального полного набора.
