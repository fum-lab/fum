# Отчёты о запусках проверок

Эта локальная автоматизация заменяет ручное переписывание результатов прямых проверочных вызовов в журнальный отчёт. Она запускает ровно один переданный процесс без оболочки, сразу создаёт принадлежащую рабочей сессии машинную запись, сохраняет наблюдённую длительность и исход, а после завершения всех параллельных исполнителей детерминированно строит раздел `### Прямые запуски проверок` соседнего `отчёт.md`.

Автоматизация учитывает только верхнеуровневые вызовы, прямо запущенные корневым агентом или субагентом: тест, валидатор, сборку, lint, benchmark, полный smoke-check либо иной проверочный процесс. Внутренние шаги составного исполнителя остаются его детализацией и второй раз в машинный журнал не добавляются. Одинаковые команды и повторные попытки никогда не сворачиваются: каждый фактический запуск получает собственную запись.

Начиная с рабочей сессии `2026-08-04_20-45-26_MSK_формировать-отчёты-о-запусках-тестов`, закрытый машинный снимок и соответствующий ему закрытый Markdown-блок являются обязательной границей нового отчёта, если в охваченном профилем интервале были прямые проверки. Более ранние отчёты сохраняют исторический формат.

## Командный интерфейс

Точка входа автоматизации принимает одну из шести команд: `запустить`, `предпросмотр`, `проверить-план`, `закрыть`, `возобновить` или `проверить`. Для каждой команды обязательны общие параметры `--корень-репозитория` и `--запрос`. Путь запроса канонически разрешается внутри указанного корня и обязан вести к обычному файлу `Журнал/<stem>/запрос.md`; соседний `отчёт.md` выводится только из него.

Прямой запуск оформляется так:

```bash
python3 Инструменты/fum-otchyotyi-o-zapuskakh-proverok/scripts/отчёты_о_запусках_проверок.py \
  запустить \
  --корень-репозитория . \
  --запрос Журнал/<stem>/запрос.md \
  --название '<человекочитаемое название вызова>' \
  --исполнитель '<устойчивая метка исполнителя>' \
  --класс-проверки адресная \
  --тайм-аут-секунды <положительное число> \
  -- <программа> <аргументы...>
```

Параметр `--идентификатор-запуска <UUID>` можно передать после `--исполнитель` для автономной фикстуры или заранее связанного вызова. В обычном запуске автоматизация создаёт новый канонический lowercase UUID. Повтор уже существующего идентификатора, пустое название, пустой исполнитель, управляющий символ в этих публикуемых метках, неизвестный параметр, отсутствующая команда после `--`, NUL в аргументе дочерней команды и недопустимый тайм-аут отклоняются до запуска процесса. Другие аргументы дочерней команды передаются буквально и не публикуются. `--тайм-аут-секунды` необязателен; если он отсутствует, автоматизация не придумывает неявный предел.

Обязательный параметр `--класс-проверки` выбирает ровно один закрытый класс: `адресная`, `диагностическая` или `полная`. Адресная запись не объявляет полных наборов. Диагностическая запись повторяет `--полный-набор <ключ>` для каждой затронутой границы, сохраняет `--основание` и `--ожидаемое-свидетельство`; основание `локализация_наблюдаемого_отказа` дополнительно требует `--идентификатор-отказа <UUID>` ранее завершённой неуспешной записи на том же снимке. Класс `полная` разрешён только для точно распознанного `run-smoke-check.py`; его ключи наборов выводятся из фактически сформированного плана, а исходы — из достигнутых наблюдений, поэтому `--полный-набор` для него не передаётся. Каждый новый запуск с первой записи сессии создаётся как v3; v1/v2 разрешены только при чтении исторического журнала, а сессия с v2 не переводится в смешанный v3-контур.

Собственные человекочитаемые значения `--название` и `--исполнитель` задаются по-русски кириллицей; точные технические токены сохраняются только там, где без них теряется идентичность проверяемого контракта. После создания эти метки становятся частью хэшированного свидетельства фактического запуска и не переписываются ради перевода или косметического исправления: ошибочную метку явно признают в отчёте, а последующие запуски называют правильно.

Остальные команды используют тот же точный запрос:

```bash
python3 Инструменты/fum-otchyotyi-o-zapuskakh-proverok/scripts/отчёты_о_запусках_проверок.py предпросмотр --корень-репозитория . --запрос Журнал/<stem>/запрос.md
python3 Инструменты/fum-otchyotyi-o-zapuskakh-proverok/scripts/отчёты_о_запусках_проверок.py проверить-план --корень-репозитория . --запрос Журнал/<stem>/запрос.md
python3 Инструменты/fum-otchyotyi-o-zapuskakh-proverok/scripts/отчёты_о_запусках_проверок.py закрыть --корень-репозитория . --запрос Журнал/<stem>/запрос.md
python3 Инструменты/fum-otchyotyi-o-zapuskakh-proverok/scripts/отчёты_о_запусках_проверок.py возобновить --корень-репозитория . --запрос Журнал/<stem>/запрос.md
python3 Инструменты/fum-otchyotyi-o-zapuskakh-proverok/scripts/отчёты_о_запусках_проверок.py проверить --корень-репозитория . --запрос Журнал/<stem>/запрос.md
```

`предпросмотр` читает записи, проверяет их и атомарно обновляет открытый управляемый Markdown-блок без создания снимка. `проверить-план` ничего не меняет, допускается только в открытой сессии без снимка и журнала возобновления и требует ровно один успешный полный прогон, его терминальность, отсутствие неразрешённого перекрытия и равенство текущего отпечатка снимку финальной проверки. `закрыть` допускается только после завершения всех исполнителей: сначала оно долговечно устанавливает канонический снимок, затем атомарно заменяет управляемый Markdown-блок. Закрытие сохраняет фактическое состояние `не готов`, если порядок был нарушен: это делает отказ закрываемым и проверяемым, но не проходящим терминальный допуск. `возобновить` открывает только неготовый профилированный или чисто v1 исторический сбор после строгого подтверждения всех хэшей и байтов и проводит переход через отдельный журнал восстановления. Готовый v3-снимок и исторический снимок с v2 не возобновляются; уже установленный журнал `.1` или `.2` всегда лишь детерминированно доводится. `проверить` ничего не меняет: открытый сбор оно допускает только при наличии выполняющейся записи, а закрытый — как точное равенство записей, снимка, marker-хэша и Markdown; любая незавершённая переходная фаза отклоняется.

## Размещение и схема записи запуска

Все машинные данные принадлежат одному запросу и размещаются только в каталоге:

```text
Журнал/<stem>/материалы/запуски-проверок/
  <порядок>_<uuid>.json
  снимок.json
  возобновление.json
```

`снимок.json` существует в подготовленном или закрытом состоянии. `возобновление.json` существует только во время незавершённой команды `возобновить` и удаляется последним; в готовом открытом или закрытом состоянии его нет.

Каждый запуск получает один файл `<порядок>_<uuid>.json`. `порядок` — уникальное положительное десятичное число, назначенное под межпроцессным замком; UUID в имени точно совпадает с полем `идентификатор`. Числовой порядок, а не лексикографический обход файловой системы, является порядком строк отчёта. Повтор номера и несоответствие имени содержимому запрещены.

Историческая запись v1 имеет схему `fum.test-run.v1` и закрытый набор полей:

- `схема` — точная строка `fum.test-run.v1`;
- `сессия` — канонический repo-relative путь `Журнал/<stem>/запрос.md` с `/` как разделителем;
- `порядок` — положительное целое число, совпадающее с именем файла;
- `идентификатор` — канонический lowercase UUID, совпадающий с именем файла;
- `состояние` — `выполняется` или `завершён`;
- `исполнитель` — непустая однострочная метка, полученная из `--исполнитель`;
- `вызов` — непустое однострочное название, полученное из `--название`;
- `длительность_наносекунды` — `null` во время выполнения либо неотрицательное целое число после завершения;
- `статус` — `null` во время выполнения либо одна из строк `успешно`, `неуспешно`, `прервано`, `не завершено`;
- `код_завершения` — `null` либо наблюдённый целый код завершения;
- `пояснение` — `null` либо однострочное диагностическое пояснение без сырого вывода процесса.

Исторический точно распознанный полный `run-smoke-check.py`, запущенный непосредственно либо поддержанной командой Python без `--list`, мог получить схему `fum.test-run.v2`. Она сохраняет все поля v1 и добавляет `план` и `наблюдения`. План равен `null`, если подготовка не успела его сформировать, либо хранит упорядоченные пары канонического repo-relative POSIX-ключа `ключ_проверки` и `название`. Каждое наблюдение повторяет эту пару и добавляет терминальный `статус` и целую неотрицательную `длительность_наносекунды`. Активная v2-запись всегда содержит `план: null` и пустые наблюдения. Новые v2-файлы командный интерфейс не создаёт.

Каждая новая профилированная запись имеет схему `fum.test-run.v3`, сохраняет все поля v2 и добавляет закрытый объект `профиль_проверки`. Его точные поля — `класс`, `отпечаток_снимка`, `полные_наборы`, `основание`, `идентификатор_отказа` и `ожидаемое_свидетельство`. Отпечаток SHA-256 автоматически связывает `HEAD`, индекс, рабочую tracked-разницу и байты неигнорируемых untracked-файлов; индекс и рабочая разница хэшируются раздельно. Зафиксированное изменение gitlink входит в эту разницу, а внутренне грязный инициализированный подмодуль запрещает вычисление отпечатка. Из отпечатка исключены только текущие `отчёт.md` и `материалы/запуски-проверок/`: атомарные записи самой обёртки не меняют снимок, а любое иное содержательное изменение его меняет. Схемы v1/v2 остаются читаемыми историческими свидетельствами; v1 перед первой v3-записью допустима как загрузочная история миграции, v2 с v3 и любая историческая запись после первой v3 отклоняются аналитическим планом и до запуска дочернего процесса.

Для передачи детализации обёртка создаёт вне репозитория одноразовый capability-путь, UUID и канонический начальный конверт `fum.smoke-test-observations.v1` с `план: null`, пустыми `наблюдения` и пустой `текущая_проверка`. Smoke-check атомарно заменяет его после формирования плана, до первого раннего фиксированного шага, перед стартом и после исхода каждого теста; capability-переменные удаляются из окружения вложенных тестов. Обёртка принимает конверт только при совпадении UUID, закрытых наборах полей, уникальных канонических ключах без регистронезависимых коллизий, точном соответствии наблюдений префиксу плана, не более чем одном последнем неуспешном исходе и сумме вложенных длительностей не больше внешней. При тайм-ауте она завершает текущий тест как `не завершено`, при сигнале — как `прервано`; сигнал имеет приоритет над ошибкой конверта. Успешный внешний smoke обязан подтвердить весь сформированный план только успешными наблюдениями. Внешний отказ до первого теста допустимо сохраняет непустой план и пустые наблюдения, а отказ после полностью успешной тестовой фазы — полный успешный префикс, поскольку ошибиться может фиксированная проверка вне аналитического плана. Без более сильной причины нарушение протокола получает `не завершено` и код `125`, а временный каталог удаляется.

До запуска дочернего процесса автоматизация под замком атомарно устанавливает полную запись с состоянием `выполняется` и `null` во всех терминальных полях. После наблюдаемого завершения она атомарно заменяет этот же файл состоянием `завершён`. Файл никогда не дописывается частями. Невозможность установить начальную запись запрещает запуск процесса; невозможность установить терминальное состояние делает сам вызов неуспешным и оставляет активную запись, которая закрывает формирование отчёта до явного устранения причины.

Собственные записи автоматизация сериализует в UTF-8 с `ensure_ascii=False`, `sort_keys=True`, `indent=2` и ровно одним завершающим переводом строки LF. Проверка принимает только точную схему и допустимые значения; пары терминального статуса и кода завершения проверяются совместно. Публикуемые метки отклоняют управляющие символы Unicode категорий `Cc` и разделители строк и абзацев `Zl`/`Zp`. Хэш снимка связывает фактические байты каждой принятой записи, поэтому их последующая перезапись обнаруживается независимо от форматирования JSON. Символические ссылки в лексически наблюдаемых компонентах управляемого пути, неизвестные поля и выход за каталог сессии закрываются отказом. Общая публикационная проверка репозитория отдельно отклоняет машинно-локальные пути в публикуемых файлах.

## Закрытый снимок

Для сессии только с историческими v1/v2-записями `снимок.json` сохраняет схему `fum.test-run-report.v1` и ровно три верхнеуровневых поля:

- `схема` — точная строка `fum.test-run-report.v1`;
- `сессия` — тот же repo-relative путь к `запрос.md`;
- `файлы` — массив объектов `{ "имя": "<порядок>_<uuid>.json", "sha256": "<64hex>" }` в точном числовом порядке запусков.

Хэш `файлы[].sha256` вычисляется по фактическим проверенным байтам соответствующего JSON-файла и записывается без префикса. Сам `снимок.json` сериализуется каноническим способом. SHA-256 его полных байтов в Markdown-marker записывается уже с обязательным префиксом `sha256:`. `снимок.json` не включает сам себя в `файлы`.

Сессия с v3 получает снимок `fum.test-run-report.v2`: к тем же полям добавляется `отпечаток_закрытия`. Он вычисляется в момент закрытия по той же Git-границе и хэшированно фиксирует фактический вердикт плана. Поэтому drift после финального full честно рендерится как `не готов`, а последующая структурная проверка и возобновление заново строят те же байты из сохранённого отпечатка, не завися от будущего состояния worktree.

Закрытая проверка требует точного равенства отсортированного инвентаря фактическим обычным JSON-файлам запусков. Перестановка элементов, повтор, лишняя или исчезнувшая запись, изменение байта, подмена состояния, неизвестный файл, временный остаток, символическая ссылка, неканонические байты снимка и несовпадающий хэш являются ошибкой. Снимок с хотя бы одной записью `выполняется` не создаётся. После долговечной установки снимка и до замены Markdown может наблюдаться подготовленная фаза `снимок.json` вместе с открытым marker: она блокирует новые запуски и предпросмотр, не принимается строгой проверкой и завершается только повтором `закрыть`.

## Журнал возобновления

Перед первой мутацией закрытого состояния команда `возобновить` долговечно создаёт канонический `возобновление.json`. Исторический снимок v1 получает схему `возобновление-отчёта-проверок.1` с закрытым набором полей `схема`, `сессия`, `хэш_закрытого_отчёта`, `хэш_открытого_отчёта` и `хэш_снимка`; для профилированного снимка схема `возобновление-отчёта-проверок.2` дополнительно сохраняет `отпечаток_закрытия`. Каждый хэш является lowercase SHA-256 без префикса. Журнал не входит в снимок запусков и блокирует `запустить`, `предпросмотр`, `проверить-план`, `проверить` и `закрыть`.

Повтор `возобновить` строго сверяет канонические байты журнала, текущие записи и допустимую закрытую либо открытую проекцию, затем детерминированно продолжает переход из фаз `закрытый отчёт + снимок`, `открытый отчёт + снимок` или `открытый отчёт без снимка`. Журнал удаляется и каталог синхронизируется только после долговечного открытого отчёта и подтверждённого отсутствия снимка. Повреждённый журнал не является разрешением на восстановление.

## Открытый и закрытый Markdown-блок

В новом `отчёт.md` существует ровно одна активная пара marker-строк. Пока сбор открыт, начало и конец имеют точный вид:

```markdown
<!-- FUM-CHECK-RUNS:BEGIN состояние=открыт; каталог=материалы/запуски-проверок -->
...
<!-- FUM-CHECK-RUNS:END -->
```

После закрытия первая строка заменяется на:

```markdown
<!-- FUM-CHECK-RUNS:BEGIN состояние=закрыт; снимок=материалы/запуски-проверок/снимок.json; sha256=sha256:<64hex> -->
```

Конечная строка остаётся `<!-- FUM-CHECK-RUNS:END -->`. Во всём отчёте допускается ровно одна точная пара: отсутствующая, повторная, вложенная, переставленная или синтаксически расширенная пара отклоняется без записи. Поэтому дословный текст, fenced-блок и другой раздел отчёта не должны дублировать управляющие marker-строки.

Готовое открытое состояние означает отсутствие `снимок.json` и `возобновление.json`. Оно допустимо во время выполнения точной активной рабочей сессии, в том числе когда полный smoke-check видит собственную ещё выполняющуюся верхнеуровневую запись. Оно не является готовым отчётом для коммита. Подготовленные фазы закрытия и возобновления также не являются готовыми состояниями. Закрытое состояние требует существующий снимок, отсутствие журнала возобновления, точный marker-хэш канонических байтов снимка и побайтовое совпадение содержимого между marker-строками с заново построенным представлением.

Рабочий предпросмотр может оставаться открытым между вызовами. Такое промежуточное состояние не принимается командой `проверить` без активной записи и не может быть зафиксировано как готовый отчёт. Во время активного вызова предпросмотр показывает технические `0,000 с` и `не завершено — нет итоговой записи`; это значение не входит в сумму и заменяется наблюдённой длительностью до закрытия.

## Детерминированное Markdown-представление

Управляемый блок содержит таблицу с точными колонками `Вызов | Длительность | Результат` и строку `Общее время прямых запусков проверок: <N> с.`. Строки следуют числовому `порядок`; повторяющиеся значения сохраняются как отдельные строки.

Первая ячейка строится как `[<исполнитель>] <вызов>`. Вторая получается только из `длительность_наносекунды`: значение округляется до целых миллисекунд по правилу round-half-up, затем отображается в секундах с запятой как десятичным разделителем и не более чем тремя знаками без бессмысленных конечных нулей. Например, `1 499 999` нс дают `0,001 с`, а `1 500 000` нс — `0,002 с`.

Третья ячейка начинается с точного `статус`; непустое безопасное пояснение добавляется через тире как `<статус> — <пояснение>`. Наблюдённый `код_завершения` остаётся машинным полем и не дублируется в человекочитаемой ячейке. Разделители Markdown в пользовательских ячейках экранируются, переводы строк не допускаются, а ширина колонок и строки разделителя выравнивается пробелами в стиле Obsidian.

Если сессия содержит v3-записи, после итоговой строки блок показывает состояние экономного порядка. Каждое перекрытие раннего полного или диагностического охвата с наборами финального smoke-check на том же отпечатке рендерится отдельно: в одной строке видны разрешённость, длительность, исход, ключи наборов и основание. Диагностика с основанием `не_покрывается_финальной_комплексной_проверкой` и действительно непересекающимся набором получает отдельную строку с теми же свидетельствами, но не называется дублем. Так неразрешённое дублирование остаётся закрываемым и проверяемым историческим свидетельством, но не проходит строгий терминальный допуск.

`нормативный_контур` в машинном плане — декларативный список обязательных стадий протокола, а не извлечённое из свободной метки `вызов` свидетельство. Отдельные профильные регрессии и протокол сессии доказывают фактические RED/GREEN, плановые контракты, recency, связность, закрытие и атомарную передачу. `доказанные_условия` содержат только вычисленные из записей и текущего отпечатка булевы инварианты; состояние `готов` достигается ровно при истинности всех этих условий.

Общее время вычисляется как сумма уже округлённых до миллисекунд отображаемых значений строк, а не как отдельное округление суммы исходных наносекунд. Поэтому число в итоговой строке всегда арифметически равно видимой таблице и независимо проверяется `fum-svyaznostj-rabochej-sessii`. Рендер не использует текущее время, порядок обхода каталогов, locale или скрытую среду: одинаковые канонические записи дают одинаковые байты блока и снимка.

## Параллельные процессы и файловая граница

Короткий межпроцессный файловый замок сериализует согласованные чтения каталога, назначение следующего порядка, атомарную установку начальной записи, терминальную замену, предпросмотр, проверку, `закрыть` и `возобновить`. Сам проверочный процесс не удерживает глобальный замок, поэтому независимые исполнители работают параллельно и обновляют только собственные JSON-файлы. Операционная система освобождает замок при завершении владельца; таймер, TTL и эвристическое снятие не используются.

`закрыть` сначала получает замок, запрещает новые старты, перечитывает весь каталог, отклоняет активные или неканонические записи и строит будущие байты в памяти. Затем оно долговечно устанавливает `снимок.json` и только после этого атомарно заменяет управляемый блок `отчёт.md`. Сбой второго шага оставляет обнаружимую закрытую отказом подготовленную фазу; повтор `закрыть` сверяет снимок с неизменными записями и завершает Markdown. Повтор успешного `закрыть` с неизменными входами является побайтовым no-op.

`возобновить` не является способом обойти ошибку. Первый вызов допускается только при полностью корректном закрытом снимке, совпадающем marker-хэше, точном Markdown и отсутствии активных записей. Готовый v3-снимок не открывается, чтобы исторический успешный full не делал новую сессию заведомо неготовой; исторический снимок с v2 тоже не открывается, поскольку новая v3-запись создала бы запрещённую смесь. Команда под замком сначала ставит журнал восстановления, переводит marker в `состояние=открыт`, затем удаляет и синхронизирует снимок, а журнал восстановления удаляет последним. Прежние записи не удаляются; следующий порядок продолжает существующую последовательность. После наблюдаемого сбоя повтор разрешён только через строго проверенный журнал, а остальные действия остаются закрытыми.

## Запуск процесса, неуспехи и сигналы

Переданная команда запускается как точный массив аргументов с `shell=False`. Стандартные потоки вывода и ошибок наследуются, поэтому человек и вызывающий инструмент видят исходный вывод без задержки. Автоматизация не сохраняет stdout, stderr, полную среду, секреты, hostname или PID в публикуемом машинном журнале и не пытается извлекать статус из недоверенного текста тестового фреймворка.

Дочерний процесс получает отдельную группу процессов, идентификатор которой сохраняется независимо от жизненного цикла лидера. Нулевой код даёт статус `успешно`, ненулевой — `неуспешно`; невозможность запуска получает `не завершено`, безопасное пояснение и наблюдаемый совместимый код. Естественное завершение сигналом или сигнал, полученный обёрткой и переданный всей группе, фиксируется как `прервано`. При достижении тайм-аута автоматизация посылает сохранённой группе `SIGTERM`, ждёт фиксированный короткий период, при необходимости посылает `SIGKILL` и в ограниченный срок требует подтверждения исчезновения PGID. Процесс, намеренно покинувший эту группу, такой очисткой не охватывается.

Длительность измеряется монотонным таймером от непосредственной попытки запуска до наблюдённого завершения и уборки группы. Абсолютное значение монотонных часов в JSON не сохраняется. `SIGINT` и `SIGTERM` блокируются вокруг установки начальной и терминальной записи; исходная маска восстанавливается в дочернем процессе перед `exec`. Терминальная атомарная запись является точкой линеаризации: только уже учтённые ожидающие сигналы поглощаются, а новый сигнал после неё передаётся прежнему обработчику. Необрабатываемый `SIGKILL`, авария среды выполнения, машины или файловой системы могут оставить состояние `выполняется`; такое состояние является наблюдаемым отказом и блокирует закрытие. В терминальную запись автоматизация не подставляет `0 с`, время обнаружения или оценку задним числом.

## Интеграция с smoke-check и завершением сессии

Каталог `tests` этой автоматизации автоматически входит в общий smoke-check. Дополнительный шаг только для чтения `проверить` строго сверяет снимок переданного запроса, а этот запрос допускает в открытом состоянии только при наличии активной записи, чтобы обёрнутый предфинальный smoke-check не потребовал собственного результата до завершения. Открытая проверка не выдаётся за готовность к коммиту: перед финальной связностью текущий запрос обязан пройти `закрыть`. Только после такого полного закрытия наблюдения исторической v2- или текущей v3-записи могут стать входом аналитического порядка следующего smoke-check; текущая открытая сессия, подготовленный снимок и журнал возобновления не используются как история.

Корневой исполнитель перед закрытием дожидается всех субагентов и других способных позднее писать процессов, завершает весь текст, генераторы, recency, граф и связность, затем переводит в индекс все содержательные пути. Предфинальный полный smoke-check является последней записываемой строкой охваченной границы и получает класс `полная`. Сразу после его успеха корень вызывает `проверить-план` только для чтения до любых содержательных изменений кроме собственных исключённых файлов отчёта. Затем корень закрывает снимок и выполняет только необходимые проверки замыкания изменившегося отчёта: строгую проверку снимка, связность рабочей сессии, recency в режиме без записи и `git diff --check`. Канонический журнальный `отчёт.md` хэшируется для recency без единственного канонического блока `FUM-CHECK-RUNS`, поэтому его переход open→closed не меняет recency-индекс. Эти вызовы явно называются в тексте отчёта, находятся вне закрытой границы профиля и не порождают рекурсивный новый полный smoke-check или бесконечное самоизменение таблицы.

## Граница автоматизации

Машинный журнал доказывает полноту только тех прямых вызовов, которые действительно проведены через команду `запустить`. Правило рабочей сессии должно требовать эту обёртку от корня и субагентов в охваченной границе; автоматизация не может обнаружить процесс, намеренно запущенный в обход неё. Она также не оценивает смысл теста, не разбирает фреймворк-зависимые счётчики, не сохраняет сырой вывод, не заменяет публикационную проверку точной команды и не складывает внутренние шаги составного процесса как независимые запуски.

Лексическая проверка символических ссылок не устраняет враждебную TOCTOU-подмену предка между проверкой пути и файловой операцией; полная защита потребовала бы привязанных к `dirfd` операций с `O_NOFOLLOW`. Числовой PGID теоретически может быть переиспользован, а процесс может намеренно покинуть группу. Постоянный одновременный отказ всех восстановительных файловых операций не позволяет обещать автоматическое завершение перехода; стандартные одинаковые POSIX-сигналы могут объединяться ядром. Хэши обнаруживают несогласованную подмену, но не защищают от субъекта, способного согласованно переписать все локальные файлы.
