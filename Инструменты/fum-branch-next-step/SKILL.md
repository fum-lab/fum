# Следующий шаг Git-ветки

Используй сценарий `scripts/branch-next-step.py` как fail-closed контракт между планированием ветки и внешним диспетчером Codex. Список активных задач Codex проверяется только штатным host-инструментом и не выводится из Git, процессов или приватных файлов среды.

## Проверить активную ветку

Проверить все записи и наличие ровно одного совпадения для активной ветки:

```bash
python3 Инструменты/fum-branch-next-step/scripts/branch-next-step.py \
  validate --repo-root . --json
```

Получить готовый шаг:

```bash
python3 Инструменты/fum-branch-next-step/scripts/branch-next-step.py \
  show --repo-root . --json
```

Код `0` означает `ready`, код `3` — корректную запись в состоянии `paused`, `blocked` или `done`, код `2` — недоказанный контракт. Detached HEAD, отсутствие записи, дубликат, неверный ref, пустая задача, отсутствие критериев, проекта или ожидаемого паспорта ветки закрывают запуск.

## Зарезервировать запуск

После первой проверки штатного списка задач Codex зарезервировать только уже прочитанную пару:

```bash
python3 Инструменты/fum-branch-next-step/scripts/branch-next-step.py \
  claim \
  --repo-root . \
  --expected-branch-ref refs/heads/<ветка> \
  --expected-step-id <step_id> \
  --json
```

Код `0` и `state=claimed` разрешают один запуск. Код `4` и `state=already_claimed` запрещают повтор того же шага. Новый `step_id` атомарно заменяет прежний claim ветки.

Claim хранится вне рабочей копии в общем Git-каталоге, сериализуется POSIX `flock` и не имеет TTL. Ожидание самого lock ограничено пятью секундами и при занятости закрывает запуск; публикация, замена и удаление claim закрепляются синхронизацией каталога. Повреждённый или расширенный неизвестными полями claim автоматически не заменяется. Этот слой не заменяет `fum-branch-task-gate`, штатный список задач или проверку идентичности внутри созданной задачи.

## Выполнить созданную задачу

Перед любыми изменениями повторить `show` с обоими ожиданиями:

```bash
python3 Инструменты/fum-branch-next-step/scripts/branch-next-step.py \
  show \
  --repo-root . \
  --expected-branch-ref refs/heads/<ветка> \
  --expected-step-id <step_id> \
  --json
```

После успешной сверки полностью прочитать возвращённые `record_path` и `project_path`. Запись шага и паспорт проекта являются обязательными входами: соблюдать их источники, границы действий, доступа, публикации и проверки. Выполнить задачу и критерии из записи. До коммита заменить запись новым выбранным шагом и новым `step_id` либо явно поставить `paused`, `blocked` или `done`. Не оставлять прежний готовый шаг после его выполнения.

## Восстановить claim

Сначала показать наблюдаемое поколение:

```bash
python3 Инструменты/fum-branch-next-step/scripts/branch-next-step.py \
  claim-status --repo-root . --json
```

Только после внешнего подтверждения, что созданная задача больше не исполняется и не может возобновить запись, выполнить compare-and-delete:

```bash
python3 Инструменты/fum-branch-next-step/scripts/branch-next-step.py \
  release \
  --repo-root . \
  --expected-lease-id <наблюдённый-lease_id> \
  --json
```

Код `5` означает отсутствующее или уже сменившееся поколение. Повреждённый claim автоматически не удалять.

## Проверка

Запустить автономные тесты без сети и секретов:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover \
  -s Инструменты/fum-branch-next-step/tests \
  -p 'test_*.py'
```

## Граница автоматизации

Локальный сценарий требует POSIX `flock`, именованную Git-ветку и один общий Git-каталог. Он не координирует отдельные клоны и не доказывает глобальный простой Codex.

Внешний heartbeat должен дважды запрашивать recent-снимок `codex_app.list_threads` с максимальным поддерживаемым `limit = 50`, исключать только собственный точный `CODEX_THREAD_ID`, считать любой другой наблюдаемый `active` занятостью и закрываться при недоступном host, неизвестном состоянии или ошибке. `idle` и `notLoaded` являются известными неактивными состояниями. Контракт не возвращает общее число или признак полноты, поэтому снимок не доказывает отсутствие более старой активной задачи за его пределами. После claim heartbeat повторяет инвентаризацию. До вызова `create_thread` собственный claim освобождается при провале повторных проверок; после вызова — только если штатный ответ явно подтверждает, что задача не создана. Ошибка, тайм-аут или неоднозначный ответ сохраняют claim для обычного fenced-восстановления после внешней проверки. Между последней инвентаризацией и созданием задачи остаётся неатомарное окно; проектные hooks и повторная проверка `branch_ref`/`step_id` уменьшают риск, но не превращают host-интерфейсы в транзакцию.

При регистрации диспетчера в новом форке или клоне используй [шаблон heartbeat](references/heartbeat-prompt.md), подставляя точный абсолютный корень сохранённого локального проекта. Создавай его в паузе и активируй только после чистого коммита установки.
