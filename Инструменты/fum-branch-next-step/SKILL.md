# Следующий шаг Git-ветки

Используй сценарий `scripts/branch-next-step.py` как fail-closed контракт между планированием ветки и внешним диспетчером Codex. Список активных задач Codex проверяется только штатным host-инструментом и не выводится из Git, процессов или приватных файлов среды.

## Проверить активную ветку

Проверить все записи и наличие ровно одного совпадения для активной ветки:

```bash
python3 Инструменты/fum-branch-next-step/scripts/branch-next-step.py \
  validate --repo-root . --json
```

Получить готовый шаг:

```bash
python3 Инструменты/fum-branch-next-step/scripts/branch-next-step.py \
  show --repo-root . --json
```

Код `0` означает `ready`, код `3` — корректную запись в состоянии `paused`, `blocked` или `done`, код `2` — недоказанный контракт. Detached HEAD, отсутствие записи, дубликат, неверный ref, пустая задача, отсутствие критериев, проекта или ожидаемого паспорта ветки закрывают запуск.

## Зарезервировать запуск

После первой проверки штатного списка задач Codex зарезервировать только уже прочитанную пару:

```bash
python3 Инструменты/fum-branch-next-step/scripts/branch-next-step.py \
  claim \
  --repo-root . \
  --expected-branch-ref refs/heads/<ветка> \
  --expected-step-id <step_id> \
  --json
```

Код `0` и `state=claimed` разрешают один запуск. Код `4` и `state=already_claimed` запрещают повтор того же шага. Новый `step_id` атомарно заменяет прежний claim ветки.

Claim хранится вне рабочей копии как канонический JSON blob под служебной ссылкой `refs/fum/worktree-next-step-claims/<sha256-physical-checkout>/<sha256-branch-ref>`. Публикация, замена и удаление выполняются только compare-and-swap `git update-ref`; символическая служебная ссылка отклоняется, а запись дополнительно использует `--no-deref`. После проигранного CAS тот же вызов не заменяет другой `step_id`: для такой замены нужны новая проверка и свежий вызов. Git-вызовы игнорируют replace-объекты, optional locks и все унаследованные `GIT_*`, включая trace-файлы и перенаправления. Claim не имеет TTL, а повреждённый или расширенный неизвестными полями blob автоматически не заменяется. Файлы прежней POSIX-реализации под `.git/fum-branch-next-step/` больше не авторитетны, не импортируются и не требуют ручной миграции. Этот слой не заменяет [fum-ocheredj-zadach-git-vetki](../fum-ocheredj-zadach-git-vetki/SKILL.md), штатный список задач или проверку идентичности внутри созданной задачи.

## Выполнить созданную задачу

Созданная корневая задача первым действием проходит общую FIFO-очередь checkout и дожидается состояния `admitted`. Затем перед любыми изменениями она повторяет `show` с обоими ожиданиями:

```bash
python3 Инструменты/fum-branch-next-step/scripts/branch-next-step.py \
  show \
  --repo-root . \
  --expected-branch-ref refs/heads/<ветка> \
  --expected-step-id <step_id> \
  --json
```

После успешной сверки полностью прочитать возвращённые `record_path` и `project_path`. Запись шага и паспорт проекта являются обязательными входами: соблюдать их источники, границы действий, доступа, публикации и проверки. Выполнить задачу и критерии из записи. До атомарного `commit` общей очереди заменить запись новым выбранным шагом и новым `step_id` либо явно поставить `paused`, `blocked` или `done`. Не оставлять прежний готовый шаг после его выполнения.

Если fenced `show` после допуска возвращает mismatch до первой записи, созданная задача не меняет запись шага и не оставляет владельца очереди: она дожидается отсутствия всех возможных писателей, выполняет документированный `finish-clean` очереди с точными `task_id` и `generation`, после успеха прекращает любые записи и завершает работу.

## Восстановить claim

Сначала показать наблюдаемое поколение:

```bash
python3 Инструменты/fum-branch-next-step/scripts/branch-next-step.py \
  claim-status --repo-root . --json
```

Только после внешнего подтверждения, что созданная задача больше не исполняется и не может возобновить запись, выполнить compare-and-delete:

```bash
python3 Инструменты/fum-branch-next-step/scripts/branch-next-step.py \
  release \
  --repo-root . \
  --expected-lease-id <наблюдённый-lease_id> \
  --json
```

Код `5` означает отсутствующее или уже сменившееся поколение. Повреждённый claim автоматически не удалять.

## Проверка

Запустить автономные тесты без сети и секретов:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover \
  -s Инструменты/fum-branch-next-step/tests \
  -p 'test_*.py'
```

Набор из 28 тестов проверяет в том числе одновременный и межшаговый claim, exact-lease release, замену шага, повреждённые и символические refs, dirty checkout/index, Unicode-ветку, SHA-256, очистку Git-среды и trace-файлов, а также отсутствие POSIX-примитивов.

## Граница автоматизации

Постоянная диспетчерская задача не является рабочим билетом FIFO-очереди и не вызывает `join`. Она не меняет checkout, индекс, ветку или Git-историю; её единственные локальные мутации — fenced claim/release этой автоматизации. Созданная ею обычная задача сама входит в очередь до работы.

Локальный сценарий требует Python 3, Git и именованную Git-ветку, но не зависит от POSIX-блокировок, сигналов или hooks. Служебная ссылка ограничена идентичностью физического checkout; сценарий не координирует отдельные клоны и не доказывает глобальный простой Codex.

Внешний heartbeat должен дважды запрашивать recent-снимок `codex_app.list_threads` с максимальным поддерживаемым `limit = 50`, исключать только собственный точный `CODEX_THREAD_ID` и считать любой другой наблюдаемый `active` занятостью. При занятости он не публикует claim, не ставит плановую работу в FIFO-очередь и вообще не создаёт задачу. Недоступный host, неизвестное состояние или ошибка также закрывают запуск; `idle` и `notLoaded` являются известными неактивными состояниями. Контракт не возвращает общее число или признак полноты, поэтому снимок не доказывает отсутствие более старой активной задачи за его пределами. После claim heartbeat повторяет инвентаризацию. До вызова `create_thread` собственный claim освобождается при провале повторных проверок; после вызова — только если штатный ответ явно подтверждает, что задача не создана. Ошибка, тайм-аут или неоднозначный ответ сохраняют claim для обычного fenced-восстановления после внешней проверки. Между последней инвентаризацией и созданием задачи остаётся неатомарное окно; FIFO-очередь созданной задачи и повторная проверка `branch_ref`/`step_id` уменьшают риск, но не превращают host-интерфейсы в транзакцию.

При регистрации диспетчера в новом форке или клоне используй [шаблон heartbeat](references/heartbeat-prompt.md), подставляя точный абсолютный корень сохранённого локального проекта. Создавай его в паузе и активируй только после чистого коммита установки.
