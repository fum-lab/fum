# Переименование файла с обновлением ссылок

Каноническое русское имя этой локальной [автоматизации FUM](../../Глоссарий/автоматизация-FUM.md) — `переименование файла с обновлением ссылок`. Один запуск переносит один отслеживаемый файл внутри текущего checkout и согласованно обновляет поддержанные живые ссылки, не подменяя операцию простой заменой имени файла во всём тексте.

## Команды

Активный вход — Swift-команда существующего компонента актуализации путей. Собственный бинарник `fum-puti` собирается по конечному рецепту ниже. Значения `mode` в JSON остаются `plan` и `apply` ради совместимости. Python-скрипт и его тесты сохранены как закреплённый источник происхождения; этот Swift-вход их не запускает.

Сначала построить детерминированный план без изменений рабочего дерева, индекса и истории:

```bash
'<собственный-каталог-сборки>/fum-puti' \
  план-файла \
  --source '<прежний-путь-от-корня>' \
  --destination '<новый-путь-от-корня>' \
  --repo-root . \
  --время-свежести '<yyyy-MM-dd HH:mm:ss MSK>'
```

Применить тот же контракт после полного preflight:

```bash
'<собственный-каталог-сборки>/fum-puti' \
  применить-файл \
  --source '<прежний-путь-от-корня>' \
  --destination '<новый-путь-от-корня>' \
  --repo-root . \
  --время-свежести '<то же точное время MSK>'
```

Оба пути задаются как относительные POSIX-пути от точного корня Git-worktree. Источник должен быть отслеживаемым обычным файлом внутри checkout и не иметь staged- или unstaged-изменений: чистота источника сохраняет точный предшествующий Git-index при возможном откате. Назначение должно быть отсутствующим безопасным путём с существующим реальным родительским каталогом, без символических ссылок, выхода из репозитория, структурно исключённых каталогов и коллизии имени. Автоматизация работает с файлами, а не с каталогами; уже изменённый источник сначала нужно вернуть в доказуемое Git-состояние или переименовать до его содержательной правки.

## Контракт ссылок

Автоматизация распознаёт локальные Markdown-ссылки по разрешённой цели, а не по совпадению basename. Поддерживаются:

- обычные inline-ссылки и изображения, включая допустимый перенос адреса на следующую физическую строку;
- цели в угловых скобках и необязательные заголовки ссылок;
- percent-encoded сегменты пути с сохранением query и fragment;
- одно- и двухстрочные определения reference-style-ссылок и их использования;
- входящие ссылки из других проектных Markdown-файлов;
- исходящие ссылки из перемещаемого Markdown-файла, включая ссылки на себя.

При переносе между каталогами каждая поддержанная локальная цель заново вычисляется относительно итогового расположения содержащего её файла. Внешние URL, чистые fragment-ссылки, похожий basename, обычная проза, несвязанные пути, inline-code, отступные блоки кода и fenced-блоки, в том числе внутри Markdown-контейнеров, не изменяются. Если синтаксис, кодировка, регистр или полнота ссылок не позволяют доказать однозначное преобразование, команда останавливается до записи; нераспознанная wiki-ссылка на переносимый файл не пропускается молча, но явная wiki-ссылка на другой путь с тем же basename не создаёт ложного запрета.

## Защищённые зоны

Сырые материалы в `Источники/` и дословный раздел `## Текст запроса` точных файлов `Журнал/<имя-с-обязательным-временным-префиксом>/запрос.md` не редактируются. Если такая зона содержит ссылку на переносимый файл, которую потребовалось бы изменить для сохранения живой связности, и `plan`, и `apply` завершаются fail-closed с диагностикой защищённой цели.

Карточки шагов в `Планирование/карточки-шагов/` не переименовываются общей командой. Для них обязательно используется `Инструменты/fum-reyestr-planirovaniya/scripts/rename-step-card.py`, потому что доменная операция дополнительно синхронизирует статус, полный индекс и веточный рабочий набор. Другой доменный формат также должен получить отдельный явный адаптер, если простого переноса файла и Markdown-ссылок недостаточно для сохранения его инвариантов.

## Границы однофайлового Swift-входа

Версия `one-file.2` закрыто отклоняет вложенные Markdown-ссылки/изображения внутри подписи, включая `[![badge](target.md)](https://example.invalid)`: внешняя цель не доказывает несвязанность вложенной ссылки. Простая встроенная ссылка с кодом в подписи сохраняется только при доказанно неизменяемом адресе относительно прежнего и будущего документа. Если адрес требуется изменить либо доказательство неоднозначно, команда отказывает до записи. Для локальной исходящей цели перемещаемого документа дополнительно обязательны существование и прежние проверки регистра, NFC и алиасов, как для обычной ссылки.

После прежнего строгого разбора однофайловый вход допускает узкую историческую форму `[text](directory with spaces/file.md)`: внутренние ASCII-пробелы именно в пути, одна физическая строка, точная существующая локальная цель без регистровых, NFC- и символических алиасов. Пробелы в query/fragment, ведущие или замыкающие пробелы, title, кавычки, обратные косые, внутренние скобки, табуляция и перенос строки в этой дополнительной форме закрыто отклоняются. Неизменяемая несвязанная ссылка сохраняет исходные байты; изменяемый путь получает percent-encoding, непрозрачный суффикс сохраняется. Угловые адреса, percent-encoding и корректные title идут прежним строгим путём. Нераспознанное видимое reference-определение `[label]:` даёт явный отказ; определения с голыми пробелами этим срезом не поддерживаются и молча не пропускаются. Общий парсер и `batch9` не получают нового режима.

Полной эквивалентности всем случаям Python-реализации не заявлено; её молчаливый пропуск неподдержанной формы не переносится в этот контракт. Несвязанная wiki-ссылка допускается, значимая wiki-ссылка на переносимый файл блокирует перенос.

Локальные цели, извлечённые тем же лексером, получают отдельную проверку каждого физического компонента пути без следования символическим ссылкам. Gitignore не доказывает отсутствия алиаса: проверка действует также для игнорируемых целей и повторяется на независимых границах применения и отката. Отсутствующая несвязанная цель другого документа может остаться неизменной, но сломанная исходящая цель самого перемещаемого документа блокирует операцию.

Предел одного входного и итогового файла — 8 MiB, суммарных документов — 256 MiB; размер и остаток проверяются до чтения следующего файла. Проверки входных имён и ссылок различают точные UTF-8 байты, регистр и NFC-алиасы. Автоматизация не выбирает новое имя: CamelCase → lowercase-kebab задаёт существующий Names/LinguisticKit, а перенос получает одну явную пару.

Однофайловый разбор префикса контейнера проходит UTF-8 байты строки монотонно, сохраняя прежнюю ASCII-грамматику списков и цитат. Просмотренные начальные пробелы не поглощаются при неудачном следующем префиксе. Маркеры списка требуют пробельного хвоста или конца строки. Особая семантика ICU `$` и граница совпадения перед первым не-ASCII байтом сохраняются прежним выражением на одном завершающем суффиксе, после чего проход возвращает результат. Это учитывает отказ `String.range` при конце совпадения внутри графемы. Повторного декодирования остатка после каждого маркера нет. Эта локальная граница линейна по длине строки; она не задаёт линейной границы всего планировщика и не объясняет прежний корпусный тайм-аут.

## Свежесть изменённых документов

Необязательный `--время-свежести` задаёт одно точное время `yyyy-MM-dd HH:mm:ss MSK` для плана и применения. Проверяются формат и календарная действительность. Внутреннее текущее время не подставляется. Если действительно изменяемый Markdown содержит метки recency, отсутствие времени закрывает операцию до записи. Фикстуры без меток и без этого параметра сохраняют прежний контракт.

При заданном времени существующий `РешательСсылокПакета.обновитьСвежесть` входит в построение будущих байтов изменённых ссылками документов. Footer с временем и контрольной суммой составляет тот же атомарный payload, резервную копию и readback; отдельной последующей записи нет. Один перенос с неизменными байтами файла не обновляет его footer. Поле JSON `время_свежести` появляется только при явном параметре.

В изменяемом документе с метками требуется ровно один корректный завершающий footer. Дополнительные буквальные метки, неполная структура, скрытый footer, смешанные LF/CRLF и одиночный CR закрывают этот профиль. Чистые LF и CRLF сохраняются; контрольная сумма тела использует прежнюю нормализацию существующего обновителя. После добавления footer повторно проверяются предел файла и общий объём будущих байтов. Проверки этого расширения и их границы сохраняются в [отдельном отчёте совместимости](../../iskhodniki/aktualizaciya-putej/kontraktyi/otchyot-sovmestimosti-ssyilok.json).

## План, применение и откат

Режим `plan` выполняет тот же read-only preflight, что и `apply`, и возвращает устойчивый JSON-отчёт. Поля `source`, `destination` и `renamed_file` описывают перенос, `rewritten_files` перечисляет файлы с изменёнными байтами, `updated_files` — все итоговые пути затронутых файлов, а `updated_links` — число реально изменённых адресов. Preflight проверяет Git-идентичность и чистоту источника, безопасность назначения, отсутствие коллизии, разбор всех поддержанных входящих и исходящих ссылок, отсутствие сломанных исходящих целей и конфликтов в защищённых или доменных зонах. Read-only Git-вызовы отключают optional locks, все пути передаются как буквальные pathspec, а унаследованные `GIT_*` не могут перенаправить репозиторий, рабочее дерево или индекс.

Режим `apply` повторно строит план на текущих байтах, готовит новые версии затронутых файлов и резервные копии до первой установки, выполняет перенос через `git mv` и устанавливает подготовленные версии атомарной заменой. Перед подготовкой и непосредственно перед переносом повторяются lstat-, symlink-, portable-name-, Markdown-inventory-, HEAD- и exact-index-fences; переводы строк и файловый режим сохраняются. При перехватываемой ошибке процесса после начала применения автоматизация пытается вернуть прежние пути, байты, режимы и исходное Git-состояние, а затем отдельно сверяет восстановленные байты, режимы, `HEAD`, индекс, status и Markdown-инвентарь. Успешный откат подтверждается тестом, включая заранее существовавшие staged- и unstaged-изменения несвязанных файлов. Сбой питания, принудительное завершение процесса, ошибка очистки или самого отката не выдаются за атомарный успех: сохранённая резервная копия и точная диагностика требуют ручного восстановления.

Обязательный path-based-вызов `git mv` оставляет короткое неустранимое окно для враждебной одновременной подмены каталога между последним lstat-fence и системным обращением Git. Контракт рассчитан на сотрудничающие процессы одного checkout: любое наблюдаемое изменение закрывается повторными снимками, но автоматизация не является защитой от процесса, который намеренно выигрывает системную гонку имён файлов.

## Ограниченное наблюдение за читающим планом

Необязательный флаг `--наблюдение` разрешён только для `план-файла`. Обычный результат плана остаётся в stdout; stderr получает компактные JSONL-кадры схемы `fum.наблюдение-однофайлового-плана.1`. Для `применить-файл` флаг отвергается до построения плана. Без него наблюдатель отсутствует; это сохраняет контракт результата, но не является обещанием нулевых накладных расходов.

Девять обязательных фаз: вход, источник, инвентарь, чтение, разбор, префиксы, свежесть, сверка, готово. Фаза источника и первые документы чтения, разбора и сверки попадают в тот же обязательный кадр до работы с ними. Текущий документ и курсор обновляются внутри процесса, а промежуточные кадры выдаются не чаще раза в шесть секунд; частые счётчики проверяют возможность выдачи раз в 4096 обращений. Кадр содержит порядковый номер документа, относительный путь до 128 UTF-8 байтов либо только его SHA-256 и длину, известные хэш/размер документа, участок и UTF-8 курсор. Тела документов не выводятся. Курсор может двигаться назад при повторном поиске и не доказывает полноты обхода.

Счётчики отдельно показывают прочитанные файлы/байты, число полных инвентарей, работу общих масок, объём декодирования, проверки экранирования, шаги поиска и обращения к разбору контейнера. Это выбранные точки существующей программы, а не полный профиль всех операций. Git, перечисление путей, stat, блокирующее чтение и неинструментированные участки не имеют внутреннего heartbeat; между редкими кадрами фактическая позиция может оставаться неизвестной. Независимое повторное чтение и проверки индекса, инвентаря, путей и Git сохраняются.

Внутренний предел — 128 кадров, 1536 байтов на кадр с LF и 64 KiB суммарно. CLI оставляет 4 KiB под итоговую ошибку, ограничивая кадры 60 KiB. Превышение, переполнение счётчика, обратный ход часов и ошибка вывода закрывают план предметным отказом; кадры не отбрасываются с выдачей успеха. Внешний наблюдатель ресурсов и отдельный конечный бюджет остаются необходимыми: этот флаг не разрешает повторять остановленный корпусный запуск или применять перенос.

Для выбранных тестов наблюдения используется compile-time define `ФУМ_ПРОВЕРКИ_НАБЛЮДЕНИЯ_ПЕРЕИМЕНОВАНИЯ`. Он исключает прежние тесты однофайлового входа и свежести, оставляя семь функций и 21 инстанцирование на открытых малых фикстурах. Одновременное включение профилей свежести и наблюдения является ошибкой компиляции. Без define остаётся общий набор. Прохождение выбранных тестов не означает повторного прохождения всего набора или реального корпуса.

Отдельный define `ФУМ_ПРОВЕРКИ_ПРЕФИКСОВ_ПЕРЕИМЕНОВАНИЯ` выбирает три функции и 70 случаев: 49 сравнений с прежним `String.range`-алгоритмом, 18 проверок масок и точных будущих байтов, три проверки линейного объёма декодирования на прежних глубинах 32/64/128. Все три выбранных профиля взаимоисключающие. Oracle сохраняет EOF, одиночный CR, Unicode-разделители строки, комбинируемые знаки и диапазон с ненулевым UTF-8 началом. Общие маски inline-кода, экранирование скобок, независимые проверки и прочие входы этим исправлением не меняются.

## Нативное наблюдение за группой процессов

Этот наблюдатель сохраняется как наработка. Текущий выбранный набор **не пройден**: исправленный zombie-case проходит, но сценарий `orphan` дал `UNKNOWN` и неподтверждённое отсутствие группы в момент квитанции. Старый CLI получил `UNKNOWN` при отдельной привязке; CLI из нынешнего исправленного исходника не собирался. Готовность к реальному чтению корпуса и общая приёмка не заявлены.

Отдельный Swift-вход запускает одну заданную программу в новой process group и сохраняет ограниченные stdout, stderr и квитанцию. Он проверяет SHA программы и объявленных исходников до запуска и после завершения. Это конечный локальный исполнитель: состав наблюдается только внутри PGID, RSS суммируется по сэмплам. Пик RSS, все потомки, kernel containment и exactly-once не гарантируются.

Вход CLI — `nablyudatelj-gruppyi-processov --запрос <абсолютный-путь-JSON>`. JSON схемы `fum.запрос-наблюдения-группы.1` содержит UUID `поколение`, абсолютные `программа`, `рабочийКаталог`, `каталогИсходов`, `программаSHA256`, массив `аргументы`, массив `исходники` с `путь`/`sha256` и объект `пределы`. Каталог исходов заранее существует, принадлежит пользователю, закрыт для остальных и пуст. Пути проверяются по компонентам без следования символическим ссылкам.

Пределы: `миллисекунды` 500–180000; `очисткаМиллисекунд` 400–1000 и меньше общего времени; `памятьБайт` 1–536870912; `выводБайт` 1–65536 совместно на stdout/stderr; `членов` 1–32. Монотонный срок включает резерв очистки: работа останавливается до его начала, затем TERM и при необходимости KILL. Блокирующие системные обращения и сохранение квитанции не имеют kernel deadline. Превышение состава, неполный сэмпл, потеря якоря лидера или непроверенная очистка сохраняют UNKNOWN.

Перед spawn создаётся и синхронизируется `attempt.json` с generation/request/executable SHA. После spawn добавляется `spawn.json` с PID/PGID. Метка остаётся при ошибке и UNKNOWN; повтор в том же каталоге запрещён и при неполном намерении. Это защита одной локальной попытки, а не гарантия отсутствия повторов между разными каталогами. После очистки сохраняются `stdout.bin`, `stderr.bin`, `result.json` (не более 16 KiB). Коды CLI: 0 для completed, 2 для stopped/failed, 3 для UNKNOWN или раннего отказа. Отсутствие result.json не разрешает повторять неизвестный эффект.

Пять сериализованных тестовых функций дают восемь случаев: обычный вывод и отсутствие группы; TERM-непослушный ребёнок, завершившийся лидер с оставшимся ребёнком и подтверждённое наблюдение nonleader SZOMB; отдельные остановки по RSS и выводу; UNKNOWN при недостаточном пределе состава; запрет повторной и незавершённой попытки. Самозапускаемые фикстуры дополнительно имеют alarm 5 с. Прохождение набора не заменяет привязку CLI и отдельный разрешённый запуск реального читающего плана.

Квитанция сохраняет максимум один подробный отказ сэмпла: время, номер, PID/PGID, имеющиеся return/errno вызовов списка, TASKALL, BSD, WNOWAIT и signal 0. Успешный BSD-ответ проверяется по точным PID/PGID; живой процесс без полного TASKALL остаётся `member-rss`/UNKNOWN. Ненулевой аргумент BSD-запроса предназначен для zombie identity. Максимальный состав проверенных nonleader SZOMB нужен отдельному регрессионному утверждению; он не доказывает отсутствие других процессов. Для TERM/KILL сохраняются максимум две записи попыток с исходами системных вызовов; попытка не означает доставки.

В прежнем снимке helper при `deinit` пытался удалить свой временный каталог. Полный UNKNOWN receipt случая `orphan` и его locator не попали во внешний журнал; первичная причина остаётся неизвестной. Новый исходник удерживает фикстуры и каждый вызов наблюдателя отдельно. Это изменение не восстанавливает утраченную квитанцию и не доказывает причину прежнего UNKNOWN.

Профиль `ФУМ_ДИАГНОСТИКА_ПОТОМКОВ_НАБЛЮДАТЕЛЯ` вместе с `ФУМ_ЗАПУСК_ПРОВЕРОК_НАБЛЮДАТЕЛЯ` оставляет ровно одну функцию `диагностикаСохранённогоИсходаСироты()` и один случай `orphan`. Остальные `@Test` исключены при компиляции; точные аргументы запуска — `--no-parallel`, фильтр не требуется. Диагностика без тестовой точки входа и совместное включение тестов с CLI дают ошибку компиляции. Вариант без диагностического define сохраняет прежние восемь случаев, но требует того же явного контекста хранения; без тестового define проверочный helper отказывает до запуска.

До запуска объявляются физическая новая база 0700 вне checkout и JSON-контекст схемы `fum.контекст-сохранения-наблюдателя.4`: `поколение` (UUID), `корень`, `программа`, два `исходники`, `компилятор`, `комплектРазработчика`, `пределПакетаБайт`. Пины имеют поля `путь`/`sha256`; SDK-пин относится к `SDKSettings.json`. Контекст сохраняется вне базы, его SHA передаётся отдельно. Helper проверяет SHA контекста, программы и двух исходников; пины компилятора и SDK дополнительно сверяет внешний исполнитель до и после запуска. Необъявленный временный каталог не используется.

В базе создаются `фикстура-UUID/исходы/` для исходных артефактов и `фикстура-UUID/захваты/вызов-UUID/` для каждого отдельного вызова. Даже отклонённый повтор одинакового запроса получает новый invocation UUID. До вызова сохраняются точные исходные байты запроса, длина и SHA, контекст, физические locator/dev/inode/UID/mode и снимок прежних файлов. `готовность.json` записывается последним. Используются существующий native writer, EXCL/NOFOLLOW, полная запись, fsync файла и каталога, readback; ошибка до ready запрещает эффект. После return или throw до прежних assertions сохраняются отдельные raw-снимки attempt/spawn/result/stdout/stderr, производная возвращённая квитанция и независимые исходы наблюдателя и захвата. Прежняя квитанция при отклонённом повторе помечается существовавшей до вызова. Частичный захват или отсутствие квитанции остаются UNKNOWN; ошибка сохранения не скрывает исходный throw и даёт NOTGREEN после return. Автоудаления нет.

Индивидуальные пределы: request 128 KiB; context, каждый индекс, native result, производный return и outcome — по 16 KiB; attempt/spawn/failure — по 4 KiB; locator/ready/существующая post-return kill0-проверка — по 1536 байтов; stdout/stderr — совместно 64 KiB на снимок. Перед эффектом резервируется 512 KiB на вызов, включая два снимка и native run-файлы; сумма применимых caps — 492032 байта. Диагностический профиль ограничен одной фикстурой/вызовом/лидером/внуком и пакетом 1 MiB. Прежний полный профиль ограничен девятью фикстурами, десятью вызовами, восемью лидерами, четырьмя внуками и пакетом 8 MiB. Исходники, executable и scratch учитываются отдельно в манифесте сборки. Один диагностический случай не проверяет ветви throw, повторного запроса, отказа захвата или аварийного завершения.

Новые поля квитанции описывают только уже существующие обращения: `времяСбораЛидераНс` — время наблюдения успешного waitpid своего PID; `числоПроверокПослеСбора` и до двух записей `перваяИПоследняяПроверкиПослеСбора` — фактические post-reap kill0 с кодом/ошибкой/наносекундами. `наблюдениеПослеСбора` принимает `не-проверялось`, `наблюдалось-наличие`, `наблюдалось-отсутствие`, `ошибка-проверки`. Нулевое число проверок означает отсутствие наблюдения. `наблюдалось-наличие` описывает исторический rc 0, отсутствие подтверждает только ESRCH. Новые process probes, сигналы, reap или sleep не добавлены; прежние deadline, очистка и UNKNOWN сохранены.

Первый тест проверяет CLI на заданной fixture без изменений; остальные создают собственные временные Git-репозитории. При неизвестном исходе Git сохраняются синхронизированное намерение, прежний индекс и резервные копии; новый автоматический повтор или неподтверждённый откат не выполняется. При известном отказе второй установки независимые резервы удерживаются до успешной сверки отката. Дрейф при этой сверке даёт явный неполный откат с адресами сохранённых резервов.
