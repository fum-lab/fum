# FUM Planning Registry

Этот навык описывает локальную [автоматизацию FUM](../../Глоссарий/автоматизация-FUM.md), которая собирает машинно читаемый JSON-реестр планового слоя проекта из текущих Markdown-источников:

- [канонических карточек требований FUM](../../Требования/README.md);
- [сводной таблицы требований и реализаций](../../Планирование/сводная-таблица-требований-и-реализаций.md);
- [дорожной карты](../../Планирование/дорожная-карта.md);
- [стадий планирования](../../Планирование/стадии/README.md);
- [направлений проектирования и развития](../../Планирование/направления-проектирования-и-развития/README.md);
- [MVP-кандидатов](../../Планирование/MVP-кандидаты/README.md);
- [предложений о следующих шагах](../../Планирование/предложения-о-следующих-шагах.md);
- [открытых вопросов](../../Вопросы/README.md).

Результат хранится в [реестре требований, стадий реализации и кандидатов](../../Планирование/реестр-требований-вариантов-и-кандидатов.json). Массив `requirements` строится только из атомарных карточек `Требования/` с устойчивыми `FUM-REQ-*`; широкие строки сводной таблицы входят отдельно как `planning_views`. JSON не заменяет исходные Markdown-материалы, а даёт проверяемый слой для программной сверки и будущей пересборки навигации.

## Когда использовать

Используй эту автоматизацию, когда меняются плановые материалы, сводная таблица, направления, MVP-кандидаты, предложения или вопросы и нужно убедиться, что машинно читаемый слой соответствует текущему состоянию памяти.

Автоматизация также полезна перед разработкой новых плановых проверок: JSON уже содержит формулировки, статусы, критерии и типизированный граф атомарных требований, широкие плановые представления, предполагаемую реализацию на документационной стадии и в коробочной FUM, кандидатов, стадийную карту MVP, стадийную очередь продуктовых кандидатов, дорожные горизонты, активные предложения, историю предложений и вопросы по статусам.

## Команды

Собрать реестр:

```bash
python3 Инструменты/fum-planning-registry/scripts/build-planning-registry.py build \
  --output Планирование/реестр-требований-вариантов-и-кандидатов.json
```

Проверить, что сохранённый реестр не устарел относительно источников:

```bash
python3 Инструменты/fum-planning-registry/scripts/build-planning-registry.py validate \
  --registry Планирование/реестр-требований-вариантов-и-кандидатов.json
```

## Что проверяется

Валидатор:

- проверяет JSON-схему `fum.planning.requirements-registry.v5`;
- пересобирает ожидаемый реестр из текущих источников и сравнивает его с сохранённым файлом;
- фиксирует хэши исходных Markdown-файлов без служебного блока `FUM-MD-RECENCY`;
- требует ровно один уникальный маркер `FUM-REQUIREMENT-ID` в каждой карточке и не выводит ID из имени, статуса или позиции;
- сверяет полный набор карточек с `Требования/README.md`, допустимый статус в имени, индексе и теле, четыре обязательных раздела и непустые формулировку с критериями;
- проверяет допустимые типы семантических связей, индексированные цели и ровно одну согласованную обратную запись для каждого направленного отношения;
- требует, чтобы каждая широкая строка имела явный `PLAN-LAYER-*` и была либо связана с карточками, либо помечена как `Производный слой`;
- отклоняет любой нетабличный текст внутри раздела `Актуальные предложения`, чтобы плановый реестр не пропускал актуальный пункт;
- проверяет, что в источниковом инвентаре есть дорожные горизонты, стадии, направления, MVP-кандидаты, стадийная карта MVP, предложения и вопросы по статусам;
- проверяет, что MVP-кандидаты покрыты широкими плановыми представлениями, стадийной картой или очередью продуктовых кандидатов.

## Проверки автоматизации

Локальные тесты запускаются без сети и секретов:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s Инструменты/fum-planning-registry/tests -p 'test_*.py'
```

Тесты фиксируют базовый контракт: сборка нормализует карточки и обратные пары связей, различает карточечно-связанные и производные широкие строки, отклоняет дефекты структуры, статуса, индекса, идентичности, графа и актуальных предложений, принимает свежесобранный JSON и сообщает об устаревании после изменения источника.

## Граница автоматизации

Скрипт не выводит новые требования из смысла документов, не назначает `FUM-REQ-*` и не решает, какой MVP выбирать в работу. Он нормализует уже записанные карточки и плановый слой и помогает обнаружить структурное расхождение между машинно читаемым реестром и Markdown-источниками. Смысловая ответственность за формулировки требований, связи широких слоёв, статусы предложений и открытые вопросы остаётся у рабочей сессии.
