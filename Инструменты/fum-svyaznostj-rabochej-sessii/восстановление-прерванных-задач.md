# Выбрать одно действие между этапами

Для восстановления ожидаемого перечня из Git и сохранения реальных адресных наблюдений используйте [состояние задач узла](состояние-задач-узла.md). Новый модуль передаёт проверенную проекцию и её контейнерное основание в то же ядро выбора через `предпросмотр_наблюдений()`. Прежний файловый вход, формат compact и CLI сохраняются. Наблюдение не даёт допуска эффекта.

Первый срез [STEP0228](../../Планирование/карточки-шагов/🟡-FUM-STEP-0228-контролировать-доставку-в-постоянную-ветку.md) — читающая библиотека [предпросмотр()](scripts/восстановление_прерванной_задачи.py) и единственная одноимённая CLI-команда. Результат предлагает координатору одно действие, показывает каждого ожидаемого исполнителя, точные источники и неизвестности. `допуск_эффекта` и `завершение_всей_работы_доказано` всегда ложны. Даже полный переданный перечень не доказывает полноты всех обязательств FUM.

```sh
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/восстановление_прерванной_задачи.py предпросмотр --корень КОРЕНЬ --каталог-снимков КАТАЛОГ_СНИМКОВ --вход ВХОД_JSON
```

Вход — сохранённый JSON, снимки — обычные JSON-файлы внутри явно выбранного физического каталога. Относительные пути не содержат переходов вверх, скрытого `.git`, символических ссылок или несовпадения регистра. Живой JSONL не читается. Сеть, API, расписания, отправка, создание коммитов и изменение Git из предпросмотра отсутствуют. Ошибка входа возвращает код 2 без JSON-решения; рекомендация адресной сверки — корректный результат с кодом 0.

## Вход первого среза

Все схемы закрыты: лишние поля, повторные JSON-ключи на любой глубине, неизвестные версии, неверные UUID/SHA и булево число вместо целого отклоняются. Корень библиотеки и каталог снимков передаются отдельно от данных. Поле `координатор` — канонический UUID ROOT.

Схема `fum.вход-предпросмотра-продолжения.2` содержит ровно `схема`, `координатор`, `постановка_выбора`, `полнота_перечня`, `исполнители`. `постановка_выбора` — точный Git-источник `{коммит, путь, sha256}` согласованного объёма выбора и приоритетов. Полный commit OID первого среза имеет 40 знаков, SHA-256 — 64. Источник читается из обычного blob закреплённого коммита каноническим `сверить_источник()`, независимо от текущих байтов checkout.

Предметная постановка каждого исполнителя берётся из его независимо выбранного ACT и проверяется принятым `прочитать_акт()`. Она может отличаться от постановок других ACT и от общей постановки выбора; совпадение также допустимо. UUID координатора и исполнителя сверяются с входом, отдельное решение ROOT закрепляет конкретный ACT. Принадлежность конечному согласованному объёму заявляет доверенный ROOT своим выбором перечня и источников; равенство Git-источников её не заменяет. Новый алгоритм проверки или дополнительная копия постановки во входе исполнителя не нужны.

Вход v1 закрыто отклоняется с кодом 2 и объяснением перехода на v2. Для перехода координатор переименовывает общее поле `постановка` в `постановка_выбора` и явно выбирает схему v2; источники ACT и их собственные постановки сохраняются. V2 со старым полем или смесью обоих полей также отклоняется. Успешный выход имеет схему `fum.предпросмотр-продолжения.2`: каждый исполнитель содержит свою рекомендацию и причину, а его основания отдельно показывают `постановка_выбора` и `постановка_ACT`. Исторический выход v1 не переинтерпретируется.

Каждый элемент упорядоченного массива `исполнители` содержит ровно:

| Поле | Значение |
| --- | --- |
| `задача`, `хост`, `владелец` | Ожидаемый UUID чата, hostId и актуально заявленный UUID владельца |
| `поручение` | Независимый выбор обычного ACT: координатор, исполнитель, коммит, путь, sha256 |
| `решение_координатора` | Git-источник отдельного сохранённого решения ROOT |
| `снимок` | `{путь, sha256, наблюдение, курсор_запроса}` либо `null` при недоступности |
| `доставка` | `{план, владельцы}` либо `null`; допускается только план доставки v2 |
| `необязательная_инфраструктура` | Явный bool из согласованного объёма |

`наблюдение` — ISO-время с зоной, `курсор_запроса` — исходный запросный курсор либо `null` для первой страницы. Это утверждение сохраняющей стороны: ответ API сам курсор запроса не доказывает. Снимок имеет полную сохранённую MCP-оболочку `content[0].text` с JSON `read_thread` версии 1. Он приводится штатным [представить_ответ()](scripts/компактный_ответ_задачи.py); hostId отдельно сверяется с ожидаемым. Текст ответа остаётся данными, в полном файле по SHA и JSON-указателям адаптера. Он не объявляет приёмку, паузу или полномочия. Активный текущий ход имеет приоритет перед final из старого хода.

## Решение ROOT и граница доверия

Схема `fum.сохранённое-решение-root.1` содержит ровно `схема`, `координатор`, `задача`, `хост`, `этап`, `событие`, `поручение`, `владелец`, `ход`, `состояние`, `остаток`, `ожидание`, `результат`, `план_доставки`, `эффекты`.

- `этап` и `событие` — непустые стабильные идентификаторы; `ход` — ID последнего рассмотренного хода либо `null`.
- `состояние`: `открыт`, `закрыт`, `пауза`, `отменён` или `unknown`. `остаток` — отдельно согласованный bool, а не вывод из текста ответа.
- `ожидание` — непустая причина либо `null`.
- `результат` — `null` либо `{состояние: готов|принят, источник: {коммит, путь, sha256}}`. Точный файл свидетельства читается из Git; смысл готовности/приёмки заявляет ROOT.
- `план_доставки` — точный SHA идентификатора плана либо `null`. Он связывает разрешённый срез с переданным планом v2; назначение плана обязано принадлежать ROOT и включать ожидаемого исполнителя.
- `эффекты` содержит ровно `отправка` и `репозиторий`; каждое значение — `не было`, `подтверждён` или `unknown`. Они относятся к данному сохранённому событию/этапу. При неизвестном исходе повтор не предлагается; подтверждённый эффект также исключается из повторения. Новый эффект требует нового события и собственной проверки ROOT.

Git SHA/OID подтверждает целостность выбранного источника, но не авторство и смысл текста. Вход и последнее решение выбирает доверенный координатор из своей сохранённой истории; библиотека не ищет «последнюю» запись по всему репозиторию и не удостоверяет человеческое разрешение автоматически. Поздняя действительная пауза или отмена должна входить в выбранное решение. До любого эффекта ROOT снова проверяет поздние команды, текущий ход, владельца, ACT и отдельный нативный допуск. Смена этой привязки делает решение устаревшим. Preview не заменяет такой допуск.

## Выбор и доставка

Доступные предметные действия следуют согласованному порядку исполнителей. Они выбираются раньше необязательной инфраструктуры; адресные неизвестности и ожидания одного исполнителя не скрывают доступное действие другого. Среди сверок и ожиданий также сохраняется исходный порядок. Закрытый этап не возобновляется: лишь отдельный согласованный остаток позволяет предложить новый ACT. Принятый результат не реализуется и не принимается повторно.

Отдельно разрешённая доставка уже принятого среза остаётся доступной после закрытия предметного этапа и выбирается перед новым ACT на остаток. Узнаваемый краткий снимок без ID, статуса или completedAt последнего хода требует адресного чтения; неизвестные схемы, поля и неверные типы остаются ошибками входа. Недостающие значения не выдаются как наблюдённые.

Доставка использует ровно [наблюдать_назначение()](../fum-reyestr-planirovaniya/scripts/доставка_план.py). Новый алгоритм Git-истории не вводится. Устаревший план, грязное дерево или эквивалентные патчи требуют адресной сверки. Равное дерево и наличие среза в предках не доказывают получения. Поля `получатель: unknown`, `квитанция: не наблюдалась`, `ожидание_секунд: unknown` сохраняются из канонического сигнала. Его реальное `время_наблюдения` также сохраняется: повторный Git-вызов может иметь новое время при том же решении.

Устойчивый ключ действия содержит хост, задачу, последний ход, событие ROOT, `completedAt` и этап. SHA снимка находится отдельно в основаниях. При одинаковых сохранённых условиях ключ и действие совпадают; сам результат нового наблюдения доставки может отличаться временем. Снимок `completed`, `notLoaded`, пустая страница или неизменный HEAD по отдельности не доказывают прерывания. Предложение «проверить продолжение открытого ACT» означает только следующую проверку возможности, а не send или доказательство сбоя.

## Первый тестовый эффект одного писателя

[Восстановление писателя](scripts/восстановление_писателя.py) — отдельная библиотека `восстановить()`. Она принимает только конкретный `ТестовыйАдаптер`; подклассы, имена драйверов из JSON и живой транспорт не поддержаны. Адаптер последовательно возвращает управляемые наблюдения и сохраняет тестовые конверты в памяти. Он имитирует свежий сбор, не удостоверяет состояние настоящего чата. CLI предпросмотра остаётся читающим. Библиотека не создаёт чаты или checkout, не сливает, не коммитит, не публикует и не запускает расписания.

Ожидание `fum.ожидание-восстановления-писателя.1` содержит ровно `схема`, `координатор`, `задача`, `хост`, `владелец`, `корень`, `ref`, `HEAD`, `поручение`, `решение_координатора`, `поздняя_постановка`, `этап`, `событие`, `ход`, `completedAt`, `модель`, `усилие`, `текст`. UUID владельца равен исполнителю, полный ref принадлежит его ACT, HEAD закреплён отдельно. `текст` — конечное поручение до 65536 байтов. Bootstrap-постановка проверяется внутри ACT; поздняя постановка — самостоятельный Git-источник. Наличие двух целых источников не доказывает машинную связь позднего расширения с первоначальным native-поручением.

Наблюдение `fum.тестовое-наблюдение-писателя.1` содержит ровно `схема`, `координатор`, `задача`, `хост`, `владелец`, `корень`, `ref`, `HEAD`, `поручение`, `решение_координатора`, `модель`, `усилие`, `снимок`. Физический checkout, единственное закрепление ветки и фактический HEAD повторно проверяет канонический `доставка_план.снимок()`. Git не удостоверяет владельца чата; владелец, модель и усилие поступают от доверенной тестовой стороны. Compact-снимок этих сведений не содержит. Исходный последний ход должен точно совпасть по ID, `interrupted` и `completedAt`; нужны первая страница, `idle` и отсутствие activeFlags. Старый final, `completed`, `notLoaded`, краткий ответ и отсутствие чата в перечне не разрешают эффект.

Порядок одного вызова: проверить источники и первое наблюдение; сохранить намерение с полным конвертом; повторно проверить наблюдение; выполнить максимум одну тестовую отправку; отдельно сохранить ответ отправки. Между двумя наблюдениями поздняя пауза/отмена, смена ROOT-решения, ACT, владельца, модели/усилия, ref/HEAD или отсутствие дерева закрывают отправку. Готовый результат переводится к приёмке, принятый — к проверке его доставки. Они не запускают реализацию заново и не очищают прежнее неопределённое намерение.

Хранилище выбирает доверенная вызывающая сторона один раз для данного исполнителя. Это существующий приватный физический каталог вне checkout и общих Git-данных обоих корней, с правами без группового/общего доступа. Смена каталога или ручное удаление записей не являются допустимым повтором. На UUID исполнителя приходится один файл; хост, ход, событие, completedAt и этап входят в устойчивый ключ внутри него. Полный конверт и его SHA связывают также текст, модель, ACT, ROOT-решение, корень/ref/HEAD и область. Новый хост или событие не обходят существующую запись. Широкие корневые области вроде `Инструменты/` исключены по ограничению обычного поручения; конечный предметный каталог допустим.

Файл `fum.намерение-тестовой-отправки.1` содержит ровно `схема`, `ключ`, `связь`, `конверт`, `состояние`, `ответ`. Создание — `O_EXCL|O_NOFOLLOW`, права 0600, затем flush/fsync файла и каталога. Ответ устанавливается отдельной атомарной заменой с fsync. Эксклюзивный замок исключает параллельную отправку; замок после настоящего падения автоматически не удаляется по времени. Пустая, усечённая, неполная, повреждённая запись или ошибка сохранения требуют адресной сверки. Они не превращаются в отсутствие намерения. Любая существующая запись, включая состояние без сохранённого ответа, допускает только наблюдение и сверку исхода. Автоматического второго send нет.

Результат `fum.тестовое-восстановление-писателя.1` отдельно сохраняет `ожидалось`, `наблюдалось`, `ответ_отправки`, `новый_ход`, `завершение_нового_хода`, `запуск_этим_намерением` и `приёмка`. Положительный ответ транспорта не доказывает появления хода; новый ID не доказывает причинной связи с отправкой. Даже новый `completed` не доказывает смысловой приёмки. Причинность и приёмка остаются `unknown`; `live_send`, перепроверка живого источника и завершение всей работы ложны. Управляемое `Прерывание` проверяет границы процесса; испытание настоящего отключения питания и живого API не выполнялось.

## Проверки и профиль

Адресные [тесты](tests/test_восстановление_прерванной_задачи.py) используют настоящие временные Git-репозитории, закреплённые ACT/решения и реальные фикстуры принятого сигнала доставки. Запускайте штатной отчётной обёрткой своей пары Журнала:

```sh
python3 -B -m unittest discover -s Инструменты/fum-svyaznostj-rabochej-sessii/tests -p test_восстановление_прерванной_задачи.py
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/tests/профиль_восстановления_прерванной_задачи.py --выход НОВЫЙ_ФАЙЛ_JSON --повторы 3
```

Профиль v3 исключает установку фикстур, сохраняет сырые монотонные длительности, пик Python-памяти, байты явных источников и stdout Git, число обращений и отдельное вложенное время канонического сигнала. Помимо прежних трёх случаев он измеряет первый тестовый эффект и сверку повтора: наблюдение, чтение/запись намерения и тестовая отправка показаны отдельно. В каждом повторе первый вызов отправляет один раз, второй — ноль; checkout и источники не меняются. SHA исходников сверяются до и после серии. Это конечная локальная фикстура, не весь файловый ввод ОС и не ускорение FUM. Без измеренного основания для нового кэша сохраняются канонические читатели и повторная сверка.

Полный STEP0228 остаётся открытым. Живая приёмка требует настоящего адресного наблюдения ROOT и отдельного допуска эффекта. Тестовый первый эффект не разрешает live-send, пробуждение выключенного приложения или слияние. Исторический испытательный срез начинался от H2; новый адаптер ниже поставляется от отдельно выбранного C553. Свежесть всей ветки fuma этим не доказывается.

## Один живой получатель

[Контроллер](scripts/живое_восстановление_писателя.py) и [фиксированный мост](scripts/мост_живого_восстановления_писателя.cjs) реализуют отдельный живой вход. Предпросмотр и точный `ТестовыйАдаптер` не меняются. Поставка кода не разрешает вызов send настоящему адресату: ROOT отдельно выбирает уже существующий UUID, host, полный ref/HEAD, текст, модель/усилие, прерванный ход и `completedAt`.

Библиотека `восстановить()` получает прежнее `fum.ожидание-восстановления-писателя.1`, физический корень канона, существующий `КонтейнерПроцессов`, конкретный `ПотокМоста` и независимые путь/SHA выбора ROOT. Выбор `fum.выбор-живого-восстановления.1` содержит ровно `схема`, `ожидание_sha256`, `хранилище`, `нативный`, `контроль_координатора`, `начало`, `конец`. SHA ожидания вычисляется прежней `восстановление_писателя.байты()` с LF. Интервал допуска — целые Unix-секунды, не более 600 секунд; он проверяется после каждого из двух чтений перед отправкой и повторно непосредственно перед send. Отдельный readback сохраняет наблюдение после эффекта без нового разрешения отправки. Неизвестные поля и повторные JSON-ключи отклоняются.

`нативный` содержит `путь`, `размер`, `sha256` полного текущего JSONL адресата. Приватный обычный файл читается без symlink/hardlink, ограничен 256 МиБ; изменение, неполная строка и неподтверждённая модель блокируют отправку. Байты и FD identity закрепляются совместно: метка снимается до bounded-чтения, сверяется после него и с повторно открытым адресом. Новая метка после чтения не принимается. Канонический читатель проверяет первоначальные UUID/cwd/C и literal первого `create_thread`; последний фактический `turn_context` отдельно подтверждает модель/усилие. Поздняя постановка из ожидания читается как отдельный Git-источник и не подменяет нативное начало. Этот первый вход поддерживает локально доступный native; неизвестное удалённое происхождение не заполняется ожиданием.

`контроль_координатора` содержит физический `корень`, полный `ref` и `HEAD` текущего канона. Корень совпадает с аргументом библиотеки; ref/HEAD проверяются заново. Любое продвижение этого основания, даже независимым коммитом, консервативно закрывает текущий допуск. Отдельно проверяются обычный ACT, сохранённое решение `fum.сохранённое-решение-root.1`, физическое дерево адресата и единственное закрепление ref. Пауза, отмена, закрытый этап, готовый/принятый результат, ожидание, неизвестный прежний эффект либо дрейф основания запрещают send. Статус API должен подтвердить именно последний `interrupted` с точными ID/`completedAt`, `idle` и без activeFlags. `notLoaded` и `completed` этого не доказывают.

`хранилище` — выбранный ROOT общий приватный ledger получателей вне checkout и общих Git-данных. Он общий с испытательным каналом и всеми операциями/хостами, а не подкаталог текущего запуска. Имя пары `.json/.lock` получается из SHA прежних байтов `{"задача": UUID}` с LF; имя операции, host, этап и новый процесс его не меняют. Любая прежняя, испытательная, неизвестная или повреждённая запись и stale lock блокируют новую попытку. Автоматического удаления по времени нет. Процесс не обнаруживает произвольные другие приватные каталоги: выбор единственного общего ledger и запрет его замены ради обхода неизвестного исхода — обязательное независимое основание ROOT. Новый descriptor или UUID не считаются доказательством отсутствия прежнего эффекта.

Порядок: полное `read1` → контейнер/извлечение/проекция → gate → долговечное намерение → новое `read2` → контейнер/проекция/gate → долговечный захват → максимум один вызов `send_message_to_thread` → сохранение и извлечение полного ответа → отдельное `readback`. Запись намерения и захвата использует прежние `O_EXCL|O_NOFOLLOW`, права 0600, fsync файла и каталога; замены атомарны. Файл `fum.намерение-живой-отправки.1` хранит точный цикл, ключ, связанный конверт, состояние, ответ, ссылки чтений и отдельные проверенные свидетельства. Ответ send имеет собственную схему `fum.ответ-отправки-живого-восстановления.1`; тестовый ACK и формат read_thread не интерпретируются как его успех.

Полные доступные JSON-объекты API сохраняются прежним контейнером до предметного разбора; HTTP-байты остаются `unknown`. Живые чтения имеют отдельный тип `fum-живое-чтение-задачи`, чтобы не загрязнять принятый каталог наблюдений типа `codex-read_thread`. Спецификация `fum.полный-ответ-живого-восстановления.1` связывает цикл, фазу, запрос, длину и SHA. После квитанции проверяются описание, длина, SHA и повторное извлечение. Ссылки трёх чтений и ответа находятся в ledger. Исходное поле проекции `неподтверждённые` сохраняет owner/ACT/model/effort как `unknown`; нативные свидетельства показываются отдельно.

Исторический RAW сверяется с сохранённым циклом и полными точными параметрами фазы, включая prompt/model/thinking для send и пределы latest для чтения; замена другим корректным ответом тому же UUID/host отказывает. Повтор с существующим намерением не вызывает API и не меняет ledger, включая inode/mtime. Даже намерение без захвата не разрешает send. Неизвестный исход требует отдельной читающей сверки и решения ROOT. Ответ API, наблюдение нового хода, его завершение, причинная связь с данной попыткой и смысловая приёмка различаются; причинность и приёмка остаются `unknown`. Официальный API не даёт используемого здесь idempotency key или атомарного CAS: окно между последним gate и внешним вызовом сохраняется. Гарантия ограничена одной клиентской попыткой в выбранном общем ledger; ровно один внешний эффект не заявляется.

## Запуск фиксированного моста

Единственный экспорт CJS — `выполнить_живое_восстановление(среда, параметры)`. Среда закрепляет абсолютный путь `интерпретатор` к выбранному Python 3.14 и предоставляет `хэш(строка) → {байты, sha256}` и фиксированные `инструменты.exec_command`, `write_stdin`, `mcp__codex_app__read_thread`, `mcp__codex_app__send_message_to_thread`. Передача функций из JSON не поддержана. Параметры — абсолютные физические `корень`, `вход`, `выбор`, `контейнер`, `писатель`, `читатель`; для входа, выбора и двух существующих исполняемых файлов контейнера передаются отдельные поля с суффиксом `_sha256`. Их выбирает доверенная вызывающая среда; наблюдение или текст задачи не выбирают программу. Проверенные исполняемые файлы должны оставаться неизменными в течение цикла.

Мост запускает только фиксированный контроллер выбранным абсолютным Python 3.14 с `-B`. Контроллер выдаёт `fum.запрос-живого-восстановления.1` в порядке `read1/read2/send/readback`. Закрытые кадры `fum.передача-ответа-живого-восстановления.1` и `fum.конец-ответа-живого-восстановления.1` связывают цикл/фазу/UUID/длину/SHA. Кадр передаётся через stdin порциями; необязательный `лимит_аргумента` находится в пределах 512–262144 байт и учитывает сериализованный аргумент инструмента. Unicode-пара не разрывается. Следующий запрос не исполняется без точного `fum.ACK-ответа-живого-восстановления.1` после контейнерного подтверждения; завершившийся контроллер, лишний запрос, чужой ACK и неизвестный исход останавливают мост без повторной отправки. Процессная память CJS не заменяет ledger.

Адресные проверки запускаются через отчётную обёртку своего этапа:

```text
ПОЛНЫЙ_ПУТЬ_PYTHON_3_14 -B -m unittest discover -s Инструменты/fum-svyaznostj-rabochej-sessii/tests -p test_живое_восстановление_писателя.py
ПОЛНЫЙ_ПУТЬ_PYTHON_3_14 -B Инструменты/fum-svyaznostj-rabochej-sessii/tests/профиль_живого_восстановления_писателя.py --выход НОВЫЙ_ПРИВАТНЫЙ_JSON
```

Профиль выполняет три новых интерпретатора, измеряет первый цикл и повтор, сохраняет сырые монотонные стадии, вызовы/байты, пик Python и `ru_maxrss` в единицах ОС. Установка Git-фикстур и запуск интерпретатора исключены; вложенные стадии повторно не складываются. Сеть заменена управляемым транспортом, кэш ОС не очищается. Это не измерение настоящего узла или задержки API. Без такого наблюдения дополнительный кэш native/полномочий не вводится; свежие проверки сохраняются.
