# Восстановить перечень и наблюдения задач узла

[Модуль состояния](scripts/состояние_задач_узла.py) загружает конечный ожидаемый перечень из Git и сохраняет адресные ответы отдельно. Он переиспользует [предпросмотр продолжения](восстановление-прерванных-задач.md), читателей ACT, решений ROOT и поставок. Все результаты имеют `допуск_эффекта=false`. Модуль не отправляет команды, не создаёт чаты, не вызывает тестового восстановления и не включает расписания. Производственная ветка состояния и её писатель назначаются отдельным решением ROOT.

## Доверенный вход и Git

Внешний доверенный вход `fum.доверие-ожиданиям-узла.1` имеет ровно поля:

| Поле | Смысл |
| --- | --- |
| `схема` | Точное имя схемы |
| `узел`, `репозиторий` | Устойчивые ID, назначенные координатором; путь и URL их не заменяют |
| `координатор`, `владелец` | Канонические UUID, назначенные внешним основанием полномочий |
| `поколение_полномочий` | Непустое внешнее обозначение полномочий |
| `ref` | Полный `refs/heads/...`, который должен указывать на точный commit источника |
| `источник` | Объект с `коммит` (OID40), `путь` (относительный путь), `sha256` (hex64) |

Git-объект источника содержит закрытый `fum.ожидаемое-состояние-узла.1`: `схема`, те же пять полей идентичности, `основание` (Git-источник смысловой постановки) и `предпросмотр`. Последнее поле — прежний `fum.вход-предпросмотра-продолжения.2`; все `снимок` у исполнителей равны `null`. Сохраняются порядок, ACT, решения ROOT и отдельный признак полноты перечня. Нового реестра обязательств нет.

Читатель проверяет физический корень, commit/tree/blob, SHA, идентичности, конечные поля, дубликаты UUID и прежние контракты. Он читает Git-объект офлайн; грязный checkout не подменяет expected. Совпадение SHA устанавливает целостность, а доверенность источника задаётся внешним входом. После наблюдений и после повторного предпросмотра все привязки читаются заново. Дрейф ref, ACT или решения закрывает рекомендацию (`предпросмотр=null`, `поколение_актуально=false`), сохраняя прежнее expected и raw. Новое поколение самопроизвольно не выбирается. Получение remote не выполняется; публикация — отдельное свидетельство.

## Цикл и наблюдение

Каждый экземпляр `ЦиклНаблюдения` сам создаёт новый UUID. Он отличается от Git OID/SHA и поколения полномочий. Повторный `наблюдать()` того же экземпляра запрещён. На каждый ожидаемый UUID делается один вызов переданного читающего адаптера с явными `threadId`, `hostId`, `turnLimit`, `includeOutputs`, `maxOutputCharsPerItem`. По умолчанию это последний ход, outputs включены, предел текста 16000. Внутренний курсор `null` означает отсутствие необязательного поля `cursor` во внешнем запросе; заданная строка передаётся без изменения. Описание сохраняет фактически переданные поля. Пределы метаданных проверяются до вызовов. Ошибка одного чата не удаляет задачу и не скрывает следующие.

Адаптер возвращает целый доступный объект либо полные байты его сериализации. Объект кодируется `json.dumps`, UTF-8, с отсортированными ключами, компактными разделителями, `ensure_ascii=False`, `allow_nan=False`. Внешние байты сохраняются как переданы; UTF-8 проверяется после хранения. Предел payload — 64 МиБ включительно; превышение даёт явный отказ без усечения и нового обращения. Несериализуемый объект даёт отдельный отказ. Исключение адаптера сохраняется как локальная диагностика, не как полученный MCP-ответ.

Полные доступные байты передаются существующему [контейнеру наблюдений](../../Приложения/FUMA/Packages/КонтейнерНаблюдений/README.md) **до компактного разбора**, включая неизвестную/ошибочную оболочку. Описание хранит источник, время, отдельный цикл, expected, UUID/host, параметры, начало/конец, метод сериализации, длину и SHA. Квитанция проверяется целиком; затем отдельный reader извлекает точные байты и SHA. Только после этого допускается проекция. Ссылка `объект` в observed связывает проекцию с описанием и содержимым контейнера. SHA не доказывает аутентичность.

«Полный объект» означает всё, что доступный инструмент вернул вызывающей среде. Оригинальные HTTP-байты и полнота истории остаются `unknown`; текст может быть ограничен самим `read_thread`. Проекция различает первый текущий ход и старый final, статус/времена хода и решение ROOT о приёмке. Owner, ACT, модель и effort из API остаются `unknown`. `sleep`, `functionCallOutput`, `subAgentActivity`, `contextCompaction`, `fileChange` принимаются только новым адаптером состояния. Служебные элементы учитываются по точному типу и счётчику; ссылка `объект` наблюдения ведёт к полным исходным байтам. Внутренние `status`, `changes`, пути и тексты этих элементов непрозрачны и не дают фактов приёмки, полномочий, отправки, создания либо продолжения. Неизвестный будущий тип сохраняется в raw и явно отклоняется проекцией. Старые compact CLI и порождённые модели сохраняют прежние байты и отказы.

Общее ядро сохраняет различие паузы, отмены, неизвестного прежнего эффекта, готовой поставки, открытого/закрытого этапа и принятого результата. Отсутствующий локальный `cwd` требует сверки; наличие каталога не доказывает владение. Remote cwd локально не проверяется. Ни рекомендация, ни completed, ни новый ход не разрешают эффекта.

Только новый адаптер принимает точную строковую фазу `agentMessage.phase=final_answer` наряду с `commentary` и `final`, сохраняя исходную строку в RAW. Фаза не заменяет статус хода, `completedAt` или решение ROOT и не доказывает приёмку, свежесть либо право продолжения. Строки с добавленными пробелами, будущие фазы, нестроковые значения и лишние поля остаются отказом после сохранения полных байтов. Прежний компактный CLI не расширяется.

При потерянной квитанции `повторить_доставку(UUID)` использует **те же ID, описание, время и payload** в памяти процесса. MCP не вызывается повторно. Это локальный повтор контейнера, а не повтор наблюдения. После потери самого процесса неизвестный ответ не восстанавливается догадкой: новый экземпляр получает новый цикл. Явно переданная история проверяется по извлечению и SHA; она всегда получает `свежее_в_этом_цикле=false` и не используется для текущей рекомендации. Новый экземпляр автоматически обнаруживает историю подтверждённых групп того же приватного контейнера. Ручной перечень не требуется. Дополнительный `--история` остаётся совместимым входом: объект проверяется по байтам, повтор обнаруженного объекта не дублируется, несовпадение отклоняется.

## Каталог циклов в том же контейнере

[Каталог](scripts/каталог_наблюдений_узла.py) использует прежние `сохранить`/`извлечь`, не создавая другого склада RAW или реестра задач. Команда читателя `перечень ПРИВАТНЫЙ_КАТАЛОГ` возвращает `fum.перечень-контейнера.1`: проверенные библиотекой `записи` в порядке commit-групп и `неполный_хвост`. Вывод ограничен 64 МиБ, число объектов — прежними4096. Читатель ничего не исправляет. Отсутствующий сегмент, блокировка или повреждённый кадр дают отказ, а не успешную пустую историю; подготовка сегмента остаётся отдельной операцией существующего контейнера.

Тип `fum-каталог-цикла` содержит закрытые служебные события `fum.событие-каталога-цикла.1`. Каждое связывает пять идентичностей, UUID цикла, точный expected и ref, вид/ключ/время. Детерминированный ID и SHA спецификации проверяются вместе с точным извлечением. Служебный payload ограничен64 КиБ. Изменение ID, описания, байтов, SHA, узла, цикла, expected, адресата или запроса отвергается.

| Событие | Смысл |
| --- | --- |
| `начало` | Упорядоченный конечный перечень UUID/host/запросов, параметры и `полнота_перечня=false`. Подтверждается писателем и точным извлечением до первого внешнего чтения; неизвестный ACK блокирует чтение. |
| `проверка` | Ссылка на прежний RAW, номер попытки, отдельный исход ACK и состояние разбора. ACK подтверждается только после проверенных квитанции RAW и извлечения. Сохранённый RAW при потерянной квитанции остаётся доступным с `ACK=unknown`. |
| `итог` | Упорядоченные ссылки на последние проверки всех адресатов и результат повторной сверки expected. Недостающая проверка, в том числе отказ сериализации, оставляет цикл без итога. |
| `ACK-итога` | Свидетельство, записанное после проверки квитанции и извлечения конкретного предшествующего итога. Сам итог не доказывает получение своей квитанции. ACK этого свидетельства рекурсивно не требуется и не утверждается. |

При неизвестном исходе служебной записи процесс хранит замороженный вход. Локальный retry повторяет прежние ID/время/описание/байты; сначала подтверждает ожидающий итог, затем допускает следующую попытку RAW. Неизвестные прежние события не переписываются. Порядок задаётся commit-группами; настенные часы не заменяют причинную связь. ACK себя, ACK отсутствующей/будущей/чужой цели и RAW до начала того же цикла отклоняются.

Новый процесс перечисляет группы и независимо извлекает SHA-связанные объекты. Исторические наблюдения всегда несвежие и не участвуют в текущей рекомендации. Старые RAW без lifecycle остаются явно обозначенной legacy-историей с неизвестным ACK; они не прикрепляются к позднему началу того же цикла. Отсутствующий итог, отсутствие ACK итога или неполный хвост оставляют цикл `unknown`. Подтверждённый итог означает сохранённое свидетельство учёта попытки, включая её неизвестные адресные исходы; он не доказывает полноту активных задач, свежесть, получение ACK свидетельства или право возобновления. `полнота_перечня=false`, `допуск_эффекта=false` сохраняются.

## CLI и внешний MCP

Сначала соберите процессы контейнера и подготовьте существующий сегмент в приватном физическом каталоге вне checkout и common Git. Передавайте физические пути двоичных файлов. Из корня FUM:

```text
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/состояние_задач_узла.py --корень-репозитория КОРЕНЬ --доверие ДОВЕРИЕ_JSON --корень-контейнера ПРИВАТНЫЙ_КАТАЛОГ --писатель ПИСАТЕЛЬ --читатель ЧИТАТЕЛЬ
```

CLI создаёт цикл сам. Он выводит одну JSON-строку `fum.запрос-внешнего-чтения.1` с циклом и параметрами. Внешняя среда делает ровно указанный реальный MCP-вызов, сериализует **весь фактически возвращённый объект**, записывает его обычным приватным файлом внутри каталога контейнера и передаёт строку stdin:

```json
{"цикл":"UUID из запроса","задача":"threadId из запроса","файл":"абсолютный путь полного ответа"}
```

Повторите обмен для следующей выданной строки. После конечного перечня CLI выводит `fum.состояние-задач-узла.1`. EOF завершает процесс. Пока процесс открыт, неизвестную квитанцию можно повторить строкой `{"повторить_доставку":"UUID"}`; новый read_thread не выдаётся. Сам bridge не доказывает реальности внешнего MCP: это проверяется отдельной живой читающей приёмкой.

Новый процесс без `--история` обнаруживает прежние циклы и RAW автоматически. С `--только-восстановить` он загрузит expected и каталог без MCP-запросов и записей в сегмент и завершится. Без флага он выдаст новые адресные запросы собственного цикла. Ошибки верхнего входа идут в stderr с кодом 2; диагностика отдельного чата остаётся в итоговом JSON. Входы читаются ограниченно через `openat`, `O_NOFOLLOW`, `O_NONBLOCK`, `fstat`; FIFO, ссылки, hardlink и изменение файла при чтении отклоняются. Это не защита от произвольного враждебного процесса того же пользователя.

## Назначенный писатель expected

[Писатель](scripts/обновление_ожиданий_узла.py) обновляет один назначенный файл в собственном `refs/heads/codex/…`. Общий валидатор выделен из читателя с сохранением его контракта. Писатель дополнительно требует `полнота_перечня=false`. Пять идентичностей сохраняются, все `снимок=null`; членство, порядок, причины и точные ACT/ROOT-источники выбирает координатор. Пауза, отмена, закрытый этап, приёмка и unknown не превращаются в разрешение возобновления.

Закрытый приватный вход `fum.обновление-ожиданий-узла.1` содержит `операция` (UUID), физический `корень`, полный `ветка`, настоящий `исполнитель`, точный относительный `путь`, прежнее `доверие`, `первое_создание`, независимые `акт`, `назначение`, `решение`, `контроль`, `кандидат`, `параметры`, `каталог_операции`. Последний — собственный каталог0700 вне Git. `кандидат` и `параметры` имеют форму `{путь,хэш}`: физические приватные файлы0600 и SHA-256 их сырых байтов; параметры — обычный maker `.7`. ACT выбирается независимо прежним контрактом; назначение и разрешающее решение читаются из точных Git-источников. `контроль={ветка,коммит}` закрепляет поколение ROOT. SHA не доказывает отсутствия поздней команды: актуальность подтверждает ROOT перед допуском.

Назначение `fum.назначение-писателя-ожиданий.1` содержит пять идентичностей и ровно `операция`, `корень`, `ветка`, `путь`, `исполнитель`, `акт`, `решение`, `контроль`, `доверие`, `первое_создание`, `хэш_кандидата`. Оно связывает конкретный файл, байты и владельца с ACT. `решение` — прежняя `fum.сохранённое-решение-root.1`: нужен открытый этап этого исполнителя с тем же ACT, без ожидания, результата и неизвестного/подтверждённого прежнего эффекта. Смена владельца не выполняется этим переходом.

Публикуемая версия `fum.назначение-писателя-ожиданий.2` заменяет только `корень` полем `хэш_корня`; остальные поля и пять идентичностей прежние. Это ровно 64 строчные шестнадцатеричные цифры SHA-256 от `str(проверенный_физический_корень).encode('utf-8')`. BOM, конечные LF/NUL, trim, нормализация Unicode, регистра либо разделителей не добавляются. Приватный runtime-корень должен буквально совпадать с этой физической строкой; эквивалентные записи с `./` или лишним `/` не принимаются. Сам адрес остаётся только в приватном входе.

Историческая `.1` сохраняет точное прежнее поле `корень` и его буквальное равенство runtime-входу. Она не принимает `хэш_корня`, его отсутствие не восполняется и переход по неизвестной схеме не угадывается. `.2` не принимает публичный `корень`, лишние поля, иной формат или неверный digest. Хэш устанавливает связь байтов, а полномочия по-прежнему проверяются через отдельный ACT, native UUID/cwd, владельца, полный ref, решение ROOT, контрольный OID, `.7`, кандидат и индекс. Действующий публикационный сканер не меняется: открытые байты `.1` с локальным адресом отклоняются, `.2` проходят прежнюю проверку.

При обновлении `первое_создание=null`; прежний trust должен указывать на текущий HEAD/ref и тот же файл. Первое создание требует `доверие=null`, явное `первое_создание={коммит,узел,репозиторий,координатор,поколение_полномочий,владелец}`, совпадающие HEAD/параметры `.7` и отсутствие конкретного пути в Git и checkout. Повреждённый прежний expected не включает этот режим автоматически.

```text
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/обновление_ожиданий_узла.py план --вход ВХОД_JSON
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/обновление_ожиданий_узла.py установить --вход ВХОД_JSON --план СОХРАНЁННЫЙ_ПЛАН_JSON
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/обновление_ожиданий_узла.py зафиксировать --вход ВХОД_JSON --проверка UUID_ПРОВЕРКИ
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/обновление_ожиданий_узла.py повтор --вход ВХОД_JSON
```

План только читает и показывает точную разницу, raw SHA, прежний blob OID и исходное дерево. До установки повторно проверяются назначения, native UUID/cwd, HEAD/ref, единственная регистрация worktree, контроль ROOT, кандидат, пути, служебные Git-записи, поддерживаемое дерево и пустой индекс. До эффекта сохраняется намерение с точными прежними и новыми байтами, входом и приватными адресами. Устойчивая привязка по полному ref и пути находится в собственном административном Git-каталоге под замком; файл и каталоги синхронизируются. Внешняя копия намерения сверяется или восстанавливается до каждой установки. Для base64 и разницы действует отдельный предел намерения512 МиБ; отдельный expected ограничен64 МиБ. Смена UUID/каталога не обходит неизвестную попытку. Защита кооперативная; произвольный процесс того же пользователя не изолируется.

Установка меняет только expected, без staging или собственного update-ref. Вызывающий слой штатно готовит `.7/.9`, точный индекс, отчётные v4-проверки и готовность. `зафиксировать` связывает точную `.9` с намерением до вызова прежнего creator. Дополнительная читающая пересверка выполняется после fsync и непосредственно у его `write-tree`/`commit`, затем штатный Git-вызов выполняет прежний creator. Без успешной завершённой канонической квитанции начатая попытка автоматически не повторяется, даже при нужных байтах checkout или похожем HEAD.

Разрешённый состав `.7` ограничен expected, собственными `запрос.md`, `отчёт.md`, объявленной историей модели, номерными JSON-записями проверок своей сессии и двумя служебными индексами: `Журнал/README.md` и `Индексы/markdown-файлы-по-времени-редактирования.md`. Дополнительный предметный файл запрещён даже при расширенном ACT и явном включении в `.7`. Поздний чужой staged-файл отклоняется до creator и у его Git-границ. Подтверждение результата отдельно сверяет конечный diff с тем же составом.

Читающий повтор проверяет настоящую квитанцию раньше допуска прежнего base-HEAD, связывает её ожидание с `.9`, независимо сверяет сырой коммит, родителей, дерево, blob OID, байты/SHA и читает явное новое доверие. Он не вызывает creator или write-tree. Старый trust после продвижения ref отклоняется. Новый процесс использует прежние вход, подготовку и квитанцию. Следующая операция требует подтверждённое предыдущее поколение, точный новый trust как прежний, другой UUID, новое назначение и другое контрольное поколение ROOT; старое намерение архивируется без перезаписи. Неизвестный исход закрывает этот переход.

На пути подтверждения и повтора дополнительно читается то же неизменяемое Git-назначение: обе версии сверяют runtime-корень и статические полномочия, `.2` также вычисляет digest заново. Приватная `.7` снова связывается с физическим корнем, ref и исполнителем runtime-входа. Этот узкий шаг не требует прежнего HEAD или прежней вершины живого контрольного ref после уже совершённого коммита; допуск нового эффекта остаётся отдельным строгим путём.

Локальный результат сохраняет `доставка=unknown`. Публикация остаётся отдельным штатным exact push; неизвестный push требует точного remote readback. Production-путь, владелец, дерево и каталог операции назначаются отдельно после приёмки разработки. `доверие.ref` связано с точным OID: production-ref ожидаемого состояния должен позволять обычному продвижению `fuma` не инвалидировать expected. Его точное назначение выдаёт ROOT отдельно. Отправки сообщений, создание чатов, второй реестр, RAW-хранилище, расписание и массовое возобновление отсутствуют.

Установленная операция до первой попытки поддерживает отдельную [переподготовку](переподготовка-установленной-операции-ожиданий.md). Она сохраняет прежний runtime и expected, связывает прежние RAW с подлинной `.9` до архива и активирует одну новую обычную `.7/.9` через намерение `.2`. Email автора, имя/email коммиттера и буквальный набор явных дат сверяются с прежней `.9`, в том числе после последнего наблюдения модели перед активацией. Неполный вызов остаётся `pending/unknown`; новое поколение после попытки или квитанции запрещено. Отдельные адресные проверки покрывают восемь внутренних окон и двадцать внешних границ; остановка процесса не доказывает сохранность при потере питания. Доставка принятого исполняемого контура в неизменный production-checkout требует отдельной проверенной привязки кода; живая W7964 остаётся на паузе до её отдельной приёмки ROOT.

## Проверка и профиль

Запускайте через штатную отчётную обёртку своей пары Журнала:

```text
python3 -B -m unittest discover -s Инструменты/fum-svyaznostj-rabochej-sessii/tests -p test_состояние_задач_узла.py
python3 -B -m unittest discover -s Инструменты/fum-svyaznostj-rabochej-sessii/tests -p test_каталог_наблюдений_узла.py
python3 -B -m unittest discover -s Инструменты/fum-svyaznostj-rabochej-sessii/tests -p test_обновление_ожиданий_узла.py
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/tests/профиль_обновления_ожиданий_узла.py --выход НОВЫЙ_JSON
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/tests/профиль_каталога_наблюдений_узла.py --выход НОВЫЙ_JSON --повторы 3
```

`FUM_TEST_BIN_DIR` указывает на физический каталог собранных процессов контейнера; без него процессный Python-тест явно пропускается. Профиль требует эту переменную и не менее трёх повторов. Новый профиль запускает независимые Python-процессы на одном неизменном настоящем Swift-контейнере. Он отдельно измеряет перечень, извлечение, разбор метаданных, выходную сериализацию, Python peak/RSS и сохраняет SHA исходников/двоичных файлов. Общее обнаружение включает первые три стадии: вложенные интервалы не складываются. Git-фикстура, запись RAW и импорт находятся вне таймеров. Память Swift и холодный диск неизвестны. Профиль H4 воспроизводится на его историческом коммите; текущая команда относится к каталогу H6. Реальная MCP-задержка измеряется отдельно; холодный I/O, падение ОС, приложения или питания не заявляются.

Состояние узла не завершает STEP0228 и не развёртывает production-писателя. Нативное первоначальное поручение/ACT и поздняя смысловая постановка имеют отдельное происхождение: прежний ACT не доказывает машинную связь позднего prompt с новой постановкой.
