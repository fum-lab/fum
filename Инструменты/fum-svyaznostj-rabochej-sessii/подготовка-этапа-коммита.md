# Подготовка этапа коммита

[Фасад](scripts/подготовка_этапа_коммита.py) составляет читающий план и последовательно вызывает прежние инструменты подготовки обычной дочерней контрольной точки `.7` либо корневой `.5`. Обычная `.7` сохраняет независимый выбор ACT и собственную нативную привязку; её готовность объявляется отдельно. Корневая `.5` доводится до настоящей готовности через [прежний API](создание-коммита.md). Создание коммита остаётся отдельным действием. Формат приёмки и допуски сохраняются.

Для обычной `.7` новую пару предварительно создаёт штатный `start`; корневой `.5` включает start в собственное исполнение. Действие берётся из имени этапа, заголовок — из его канонического преобразования: календарная метка не является `--label`. План сверяет фактические заголовки пары до первой записи. Закрытая история не возобновляется.

Нестейджированное удаление отслеживаемой разрешённой цели получает явный отказ до первого эффекта: последовательность рассчитана на добавление и обновление файлов. Будущие отсутствующие записи проверок разрешаются отдельно.

Вход фасада — приватный JSON с полями `вход_коммита`, `поручение`, `наполнение`, `план_наполнения`, `время`, `повтор`, `проверки`, `связность`. Первые три поля адресуют прежние приватные входы. `время` — точная метка recency вида `2026-10-04 19:59:55 MSK`; новое время начала фасад не получает. `повтор` выбирает прежний `подготовить-повтор`, сохраняя модельную историю и курсор с новыми выходами подготовки.

Каждая проверка содержит `идентификатор`, `порядок`, `название` и один элемент `наборы` с точными `каталог` и `шаблон`. Адресный каталог тестов должен быть плоским, найденные тестовые файлы входят в ACT. Команда `unittest discover` строится алгоритмически; произвольные команды вход не принимает. `связность` содержит собственные UUID и следующий номер. Будущие отсутствующие `N_UUID.json` должны точно совпадать с ожидаемыми целями прежнего наполнителя. Номер перечитывается перед каждым настоящим процессом; план его не резервирует.

```text
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/подготовка_этапа_коммита.py план --вход <новый приватный вход>
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/подготовка_этапа_коммита.py выполнить --вход <тот же вход> --план <сохранённый план> --sha256 <SHA его точных байтов>
```

`план` печатает канонический JSON в stdout и не устанавливает файлов. Вызывающий слой сохраняет его в новый собственный файл0400, затем передаёт независимый raw SHA. Каталог приватных файлов имеет0700, изменяемые входы и курсоры —0600; разные роли требуют разных путей. Фасад не исправляет режимы чужих файлов. Родители всех приватных файлов должны уже существовать. Для обычной `.7` также существует родитель истории модели; корневая `.5` создаёт его после start.

Исполнение сначала повторяет план и сверку снимка. Далее следуют прежние maker.prepare, `наполнение-план` и `наполнение-применить`. SHA наполнения берётся из stdout `план_sha256` и независимо сравнивается с байтами immutable planfile0400; в самом JSON плана такого поля нет. Любой отказ сохраняет наблюдённые stdout, stderr и код, прекращая зависимые стадии. Разрешённые предыдущие эффекты сохраняются; общей транзакции и автоматического отката нет.

Recency выполняет штатный полный читающий обход. Допускаются только ожидаемые missing/stale-диагностики точных изменяемых целей. Malformed-вход, дрейф или `changed_paths` вне ACT прекращают применение. Повторная сверка полного Markdown-инвентаря, HEAD/ref и сырого индекса предшествует прежнему apply. Общий индекс должен быть явно разрешён; эта процедура не CAS и не защита от враждебной гонки между сверкой и записью.

Необязательное поле фасада `обновления` содержит известные неповторяющиеся имена `журнал` и `recency`. План связывает исходные SHA/режимы зависимых входов, stock-аргументы и конечные допустимые выходы с точным разрешением. После fill, до staging выполняется штатный reindex Журнала, затем прежний guarded recency. Окончательные SHA фиксируются результатом каждой стадии; промежуточный README может далее получить recency. Входы вне разрешённых целей остаются неизменными. Неизвестные имена, зависимый индекс вне области и дрейф закрыто отказывают. Отсутствующее поле сохраняет прежнюю последовательность; пустой список не отменяет исторический guarded recency.

Каждый `снимок_обновления` создаёт собственный кэш каталогов и передаёт его прежнему `точный_путь`. В неизменном каталоге его состав перечисляется один раз за снимок; перед повторным использованием по-прежнему сверяются device, inode, mtime и ctime. Изменение метаданных вызывает прежнее перечитывание, ошибки закрывают подтверждение пути. Кэш не переживает вызов и не хранит содержимое файлов: каждый существующий вход заново читается целиком, хэшируется и получает режим через `lstat`. Отсутствующий Markdown-индекс сохраняет ключ с `null`. Три отдельные сверки Журнала, полные обходы recency, проверки регистра и символических ссылок остаются обязательными.

[Регрессия кэша](tests/test_кэш_снимков_обновления.py) сравнивает результат с исходной функцией из точного C `a271b4af8c2600bfa6eb0476d98aba01a7cc6db9` и проверяет свежесть, режимы, дрейф, замену каталога и прежние отказы на настоящей Git/ФС-фикстуре. [Парный профиль](tests/профиль_кэша_снимков_обновления.py) принимает заранее сохранённый вне checkout обычный файл фасада с режимом `0400` и SHA256 всех его байтов. Выход должен отсутствовать в собственном физическом каталоге `0700` вне checkout:

```text
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/tests/профиль_кэша_снимков_обновления.py --корень <физический-checkout> --кандидат <фасад0400> --sha256-кандидата <raw-SHA256> --выход <новый-JSON-в-каталоге0700>
```

Профиль извлекает Python-исходники A из C, B отличается только сохранёнными байтами фасада; общие импортированные исходники сверяются по SHA. Двенадцать свежих процессов в порядке ABBA×3 снимают каждый по три снимка Журнала и два recency с одного закреплённого Git-входа из 300 сессий. До и после каждого замера проверяются файлы, режимы, метаданные ФС, HEAD, ref и сырой индекс. Наблюдаются общее время снимка, вложенные интервалы путей, чтения и SHA, вызовы, файлы, байты и перечисления каталогов. Сравнение с manifest, импорт, подготовка, сохранение и агрегация находятся вне таймеров. Кэш ОС не сбрасывается; предсверки прогревают вход. Измерение относится к снимкам, ускорение всего фасада остаётся неизвестным. Отказ сохраняет полученные наблюдения с `готов: false`; публикационный результат содержит SHA и относительные имена, приватные планы и сырые каналы остаются вне Git. Будущий OID B неизвестен до коммита; совпадение его blob с кандидатом подтверждается отдельным поздним свидетельством.

Модельный курсор проверяется до эффекта: существующая оболочка должна иметь точный хэш и назначение текущей истории. Простое копирование чужого курсора не переносит его привязку. Штатный перенос истории выполняется отдельно; новый генератор требует отсутствующий курсор.

Полный staging предшествует настоящим адресным v4-процессам. Терминальный предпросмотр выполняется перед обёрнутой связностью с её собственным `FUM_CHECK_RUN_ID`; после терминализации следуют повторный предпросмотр, staging только исключённых текущих свидетельств и прежнее читающее замыкание000188. Чужая active-запись блокирует план. Между стадиями повторяются прежний дешёвый адресный допуск и сверки приватных входов/индекса. В обычной `.7` фасад не создаёт готовность, квитанцию или коммит.

Поздние `готово` и `создать` прежнего типизированного CLI вызываются отдельно. `--предел-секунд` принадлежит только `готово`; независимый выбор там передаётся как `--выбранное-поручение`. У maker.prepare этот параметр называется `--доверенное-поручение`. Фасад не переносит флаги между разными parser contracts.

Настоящие малые сценарии находятся в [TDD-наборе](tests/test_подготовки_этапа_коммита.py), парное измерение способов композиции — в [профиле](tests/профиль_подготовки_этапа_коммита.py). Логические байты именованных читателей не доказывают физический I/O или отсутствие чтения во всём API. Кэш ОС не сбрасывается. Ограниченная подготовка не означает полной приёмки FUM-STEP-0235 или обработки полного диалога ROOT.

Корневой режим выбирается полем `начало`. Его точный вход содержит `вход_коммита`, `наполнение`, `план_наполнения`, `время`, `повтор`, `начало`, `проверки`, `связность`, `готовность`. Maker-вход остаётся прежней `.5`, без независимого ACT и полей обычного исполнителя. `повтор` равен false: этот режим создаёт новую отсутствующую папку, не возобновляя заполненный или закрытый этап. Повторные подготовки прежними API используют отдельные новые приватные выходы; существующие файлы не перезаписываются.

`начало` содержит метку действия и канонический заголовок. Без нового поля контура владелец заранее выполняет слияние: план сверяет обоих родителей и фактический MERGE_HEAD. Явное `контур: "обычный"` выбирает обычную ROOT `.5` с единственным родителем, равным исходному HEAD. Любая запись MERGE_HEAD, включая пустую или висячую ссылку, запрещена; исторический merge-коммит в HEAD допускается. Неизвестный контур, unmerged index, dirty-путь вне разрешения и сдвиг HEAD/ref запрещают start. Фасад не выполняет merge; общий создатель `.5` сохраняет прежнюю схему. Штатный план start заранее объявляет пару, реальных соседей и общий индекс; назначение модели ограничено `материалы/история-модели.json` новой папки. Перед установкой callback повторно сверяет состав, SHA, режимы и компоненты каждого пути, затем вызывает прежнюю установку start. Родитель новой модели создаётся только после пары. Контур, индекс и приватные входы повторно сверяются на границах стадий, включая prepare, fill, staging и ready.

Команды выбирает прежний читатель из подтверждённого полного LF-префикса с SHA и точным списком неоднозначных ID. Выбор сохраняет порядок и повторы A–B–A с разными ID; повтор одного ID запрещён. Глобальные raw-позиции сравниваются по подтверждённой идентичности native, включая копии источника. Для хронологии между источниками читаются только точные выбранные raw spans и исходные метки времени с временной зоной. Неизвестное или равное время разных native не восполняется предположением. Один и тот же массив текстов передаётся start и проверяется по настоящей выдаче maker; смысл и достаточность выбора определяет ROOT.

ROOT выбирает явные argv проверок, название, класс, UUID и следующий номер. Класс «полная» сверяется со штатным распознавателем exact smoke; наборы получает сама обёртка из фактического конверта. `связность` объявляет ещё один собственный UUID. `готовность` содержит весь выбранный упорядоченный массив UUID, включая связность, и положительный предел секунд. Перестановка или будущие UUID без настоящего успешного current v4 не объявляют готовность. Прежние терминальные записи остаются в разрешении, но не входят в массив будущих отсутствующих целей.

После prepare/fill, guarded recency и literal staging выполняются настоящие v4, предпросмотры, связность, staging исключённых свидетельств и читающее замыкание. Затем прежний типизированный API проверяет текущие stage0, модель, команды, v4 и связность и объявляет готовность. Его вложенные Python-проверки наследуют `PYTHONDONTWRITEBYTECODE`; прежнее значение среды восстанавливается даже при отказе. Фасад не создаёт квитанцию или коммит, не вызывает push, PR либо завершение чата. Законные эффекты до первого отказа сохраняются.

ROOT-наполнение требует хотя бы двух различимых стадий: фактическое наблюдение либо null с непустой причиной. Фасад не придумывает метрики. Парный ROOT профиль выбирается `--контур root5` либо `--контур корневой-обычный`, с `--раунды 3`. Календарный интервал включает setup, слияние при старом контуре и проверки до прочитанной готовности; внутренняя длительность отдельно исключает setup. Запись диагностических свидетельств обеих сторон включена, последующая агрегация, cleanup и сериализация общего результата исключены. Ручной baseline независимо вызывает прежние API; execute фасада там не используется. Стадии и вложенные времена не складываются повторно с общим интервалом. Именованные читатели наблюдаются в parent и maker CLI; физический I/O, кэш ОС и ненаблюдаемые дочерние читатели остаются unknown. Raw SHA ready независимо сверяется с результатом прежнего API. Сырые каналы сохраняются в новых приватных файлах0600; разные физические привязки сравниваются по семантике. Этот профиль не утверждает ускорение полезной работы FUM. Обычный профиль fresh/repeat/tail остаётся доступен по умолчанию `ordinary7`. Отдельный [генератор и его календарный профиль](подготовка-дочернего-поручения.md) включают композицию постановки и объявленные зависимые индексы.

## Перенос модели обычного ROOT этапа

Необязательный приватный вход `перенос_модели` принимает ровно два адреса: `прежняя_история={путь,sha256}` и `прежний_кэш={путь,sha256}`. Пути абсолютные, SHA относится к сырым байтам файла. Новый UUID, нативный источник, курсор и история выводятся из обычного maker `.5`. Без поля действует прежний путь. Поле запрещено для `.7` и контура слияния.

[Композиция переноса](scripts/перенос_модели_этапа.py) до start проверяет полную старую пару, отсутствующие новые назначения, несовпадение данных и замков, SHA/stat и замыкание предметного кода. План закрепляет весь maker вход. После штатных start/mkdir выполняются сухой штатный перенос, пересверка, пишущий штатный перенос и обычный prepare. Обе операции переноса обязательно хэшируют полный прежний LF-префикс. JSON этого префикса повторно не разбирается: отдельно сверяется сохранённая строка наблюдения, новый хвост разбирает прежний читатель. Полнота и безопасные известные model/effort проверяются до записи. Дописывание между планом и dry допустимо; дрейф между dry и write закрывает следующую стадию.

Если установка прервалась, новую пару сохраняют. Повтор всего фасада и второй transfer запрещены. Для адресного восстановления сохраняют поле переноса и вложенный `перенос_модели` из ROOT плана в отдельных приватных JSON-файлах; SHA последнего выбирают независимо. Команда принимает тот же maker:

```text
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/перенос_модели_этапа.py восстановить --вход <maker.json> --перенос <поле-переноса.json> --план <план-переноса.json> --sha256 <сырой-SHA-плана>
```

Восстановление повторяет адресный допуск ordinary ROOT, затем выполняет только обычный dry/write импорт той же новой пары. Обе исходные partial-точки и повтор после прерывания самого recovery поддержаны; nullable ожидаемый SHA проверяет штатный importer. Неполный хвост, неизвестная модель, подмена истории или утрата курсора закрывают восстановление. Ограниченный временный profile hook останавливает вход обычного importer в полный приём без курсора даже при его утрате в окне check→use; состояние восстанавливается при любом исходе. Уже занятый Python либо C profile hook отклоняется до установки и до записи пары. Исходники и API обычного читателя сохранены. Общей транзакции с Git, источником и ФС нет: поздний дрейф обнаруживается завершающими сверками, состоявшийся частичный эффект остаётся, prepare не выполняется. Recovery не объявляет готовность и не продолжает весь фасад автоматически.

[Адресные тесты](tests/test_переноса_модели_этапа.py) проверяют побайтное совпадение с независимым полным импортом, неизменность старой пары и границы отказов. [Парный профиль](tests/профиль_переноса_модели_этапа.py) запускает свежие процессы AB/BA на нескольких открытых входах, включая preflight, start/mkdir, dry, write, пересверки и настоящий prepare. Полное время не складывается с вложенными интервалами. Порог выгоды выводится из измерений; маленький вход может стать медленнее. Физический I/O, влияние кэша ОС, создание коммита, связность и весь ROOT цикл этим профилем не доказаны.

## Первая подготовка открытой независимой ROOT-карточки

Вход `fum.фасад-открытой-независимой-контрольной-точки.1` использует закрытые поля независимого фасада, Maker `.9` и внешний `--выбранный-состав`. Выбирается только обычный ROOT-контур: каноническая пара P.1 уже существует целиком, история модели согласована с её приватным курсором, а история проверок содержит собственные завершённые v4. Первая подготовка, READY и квитанция отсутствуют. Создание пары и перенос модели этим режимом не выполняются.

Читающий план сохраняет путь, UUID, номер, SHA и режим всех прежних RAW, включая неуспешные. Они остаются в точном разрешении T; будущие номера начинаются с фактического `max+1`, повтор прежнего UUID запрещён. `ожидаемые_цели` содержит только новые отсутствующие RAW; READY выбирает именно новые проверки. После плана смена старых байтов, режима, курсора, модели, выбора состава или появление постороннего RAW закрывают исполнение. SHA-сверки последовательны и не обещают атомарности с внешним писателем.

Общий исполнитель сначала применяет наполнение, recency и staging, затем обновляет терминальный предпросмотр по прежним RAW и ставит отчёт в индекс. Только после этого вызывается штатное `подготовить-повтор`, сохраняющее уже наблюдённую модель. Далее выполняется прежняя последовательность новых проверок, предпросмотров, связности и READY. Create, push и приёмка полного объёма остаются отдельными действиями; наличие прежнего RED не заменяет новый успешный допуск.

До первого эффекта резервируется канонический приватный результат эпизода. Его ключ выводится из адреса штатной готовности: физический checkout, полный ref, HEAD, UUID задачи и адрес пары. Смена имён входов, выходов, будущих UUID и обёртки не открывает повторный эффект через API или CLI. При обрыве сохраняется `начато` и уже созданные выходы; при известном завершении сохраняется полный исход. Автоматического восстановления частичного исполнения и успешного replay этот первый режим не предоставляет. [Адресные проверки](tests/test_первой_подготовки_открытого_этапа.py) используют настоящую P.1, модель, RED/GREEN v4 и подготовку `.11` до READY без Create.

## Защита технических входов ROOT

[Читающие предикаты композиции](scripts/защита_технических_входов.py) закрывают два наблюдённых сбоя. `снять_открытую_пару` уже возвращает полный объект с полями `план` и `файлы`; результат передаётся через `проверить_снимок_открытой_пары` прямо в поле `открытая` выбора, без повторной обёртки. Предикат проверяет форму до дорогого запуска установщика. Содержимое плана, происхождение, полномочия и свежесть по-прежнему проверяет сам установщик; этот предикат их не заменяет.

`команда_продолжения` составляет штатный читающий ROOT guard с обязательными явными `исходник` и `кэш`. Пустой, относительный, недоступный или символический файл отказывает до процесса; отсутствие аргумента `кэш` не допускается сигнатурой. Команда всегда содержит `--перед-завершением`, а профиль включается явно. Принадлежность и содержимое источника и кэша проверяет прежний guard. Построитель не запускает процесс, не изменяет кэш, не переводит код 3 в успех и не создаёт автоматическое продолжение.

[Регрессии](tests/test_защиты_технических_входов.py) воспроизводят двойную обёртку и пропуск кэша, проверяют настоящий снимок открытой Git-пары и запуск составленного argv с сохранением исходных кода 3 и каналов. Это ограниченные предикаты, а не весь общий построитель технических входов по задаче 327. Сбой считается закрытым только в проверенной границе применённой меры; намеренный RED не является отдельной ошибкой исполнения. Общий процент покрытия ошибок этим модулем не вычисляется.

## Полная область на границе независимого фасада

Каждая граница заново читает Maker, внешний выбор S и контракт, сверяет их pins, а в открытом ROOT-режиме также сохранённую модель, курсор и терминальную историю RAW. Затем выполняется один полный `проверить_область_записей`. Прежние вызовы границы до и после каждой операции сохраняются; результат полного прохода не кэшируется между операциями. Планировщик продолжает использовать прежний полный контекст.

Ранняя полная сверка внутри загрузки контекста раньше дублировала заключительную сверку той же границы. Её удаление меняет приоритет одновременных ошибок: после проверки формы и полномочий сначала обнаруживается дрейф pins, модели или RAW, затем нарушение полной области. Нарушение, исчезнувшее до единственного полного прохода, не обещается обнаружить; защита от враждебной гонки писателей ранее также не заявлялась. Это не утверждение побайтной эквивалентности всех промежуточных наблюдений. Проверитель области, его Git/FS-проверки и заключительная пересверка не изменены.

[Адресные тесты границы](tests/test_сверки_границы_фасада.py) фиксируют один настоящий полный вызов, отсутствие записей, повторное чтение входов на следующей границе, отказ при записи вне T, приоритет ошибки модели и сохранение прежних двух проходов планировщика. Число вызовов само по себе не доказывает ускорение полного ROOT-цикла; длительности измеряются отдельно.

[Компонентный профиль](tests/профиль_границы_фасада.py) получает `--базис <полный-принятый-OID>` и необязательное `--число-пар 3`. Он отклоняет различия кода вне выбранных функций, исполняет старую и новую границы по очереди на одной открытой временной Git-фикстуре и возвращает JSON в stdout для штатной отчётной обёртки. Общие зависимости берутся из текущего checkout. Setup, построение плана и проверочные снимки находятся вне измеряемого окна; полные проходы исполняются без подмены результата. Чередование порядка не превращает один процесс и малую фикстуру в независимые производственные измерения.

Профиль очищает `GIT_*` для изолированной фикстуры, читает базис штатным Git-reader без replace objects, связывает загруженные функции с ожидаемыми исходниками и пересверяет пины загруженных зависимостей. Запись bytecode отключена до проектных импортов. [Регрессии проверки кода](tests/test_профиля_границы_фасада.py) сохраняют допуск штатной повторной компиляции и отказы при подмене кода либо пути модуля: различие деталей `marshal`-сериализации не подменяет сравнение объектов кода.

## Компактное наблюдение и полный результат

Необязательный режим `выполнить --компактно --результат <новый приватный файл>` возвращает код и события с ровно пятью полями: `идентификатор`, `порядок`, `состояние`, `код`, `длительность_наносекунды`. Идентификатор стадии выбирает исполнитель; пользовательское название проверки его не меняет. Длительность монотонная. Аргументы, исходные каналы, base64 и снимки остаются в полном результате. Обычная выдача фасада сохраняется.

Родитель результата существует с правами0700. Новый файл0600 резервируется до эффекта, после завершения атомарно заменяется полным результатом с исходными каналами и их контрольными суммами. Занятый путь, включая пересечение с курсором или другой ролью, отказывает до подготовки. При ошибке сохранения, прерывании или неизвестном исходе резерв сохраняется; он запрещает слепой повтор подготовки и готовности. Наличие файла не означает успешного завершения.

## Повтор ROOT после явного отзыва

[Повторный генератор](scripts/повторная_подготовка_этапа.py) принимает вход `fum.повторная-подготовка-ROOT.1`: четыре выбранных адреса `прежняя_подготовка`, `прежний_вход`, `прежний_план`, `отзыв_готовности`, перечень `новые_выходы` и один раз выбранные `новые_проверки`. Адрес содержит путь и независимо выбранный SHA-256 сырых байтов. Старый план имеет0400, остальные выбранные приватные входы —0600. Восемь новых выходных ролей: `вход_коммита`, `вход_фасада`, `наполнение`, `разрешение`, `план_наполнения`, `сообщение`, `подготовка`, `квитанция`; все пути различны, свободны и имеют существующих приватных родителей.

```text
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/повторная_подготовка_этапа.py план --вход <выбранный вход>
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/повторная_подготовка_этапа.py выполнить --вход <тот же вход> --план <сохранённый план0400> --sha256 <сырой SHA плана>
```

План ничего не записывает. Он связывает обычную ROOT .5 с одним родителем и отсутствующим MERGE_HEAD либо настоящее слияние с прежними двумя родителями; противоречивый контур отказывает. Проверяются настоящий отзыв последнего поколения, упорядоченный перечень всех старых v4 с SHA и режимами, фактический следующий номер, подписанный курсор, история и прежняя модель, выбранное время и карта замен UUID. Из ожидаемых отсутствующих исключаются только точные существующие RAW, проверенные штатным читателем истории своей сессии. Они остаются в разрешённом составе, включая терминальные неуспешные записи; старый исход и отпечаток не становятся текущим допуском. Наличие файла или похожее имя RAW не заменяют проверку схемы, UUID, порядка, сессии и обычного типа файла. Неиспользованные прежние будущие цели исключаются; новые отсутствующие цели перечисляются отдельно.

При исполнении после повторного расчёта всего плана и зависимых обновлений непосредственно перед резервированием результата повторяется штатная сверка фактических корня, полного ref, HEAD, родителей, MERGE_HEAD и конфликтного индекса. Поздняя смена ref при той же вершине либо смена HEAD отказывает до маркера и четырёх новых входов. Поля HEAD/ref/родители снимка плана обозначают ожидаемые привязки; равенство планов не заменяет эту живую сверку. Чтения последовательны: атомарность и защиту от изменения во время сверки либо после неё до записи этот допуск не обеспечивает.

Выбранные старые вход и план задают рецепт нового повтора. Старые байты и состояние проверяются; исторические аргументы и время фактически выполненного прошлого вызова остаются неизвестными. UUID, заголовок и класс записи не доказывают исторический argv. Новый полный приватный результат сохраняет фактически наблюдённые текущие аргументы и каналы.

Цикл использует прежние подготовку модели, наполнение, индексы, staging, отчётные v4, предпросмотры, связность, замыкание и готовность. Он сохраняет UUID задачи и исходную эпоху/предел готовности, создавая поколение после явного отзыва. До и после каждой стадии сверяются неизменные выбранные входы, старые v4, курсор и история; для курсора и истории проверяются обычный тип файла, режим и SHA сырых байтов, закреплённые планом. Изменение только прав после успешной подготовки отказывает на ближайшей границе до наполнения, сохраняя уже созданные входы и результат подготовки. Та же сверка действует в независимой ручной композиции профиля. Штатный переход готовности в конце проверяется отдельно. Закрытая карточка и потерянный курсор отказывают. `start`, создание каталогов и создание коммита в этот цикл не входят.

После повторного наполнения выполняются recency и staging всего существующего разрешённого предварительного состава, включая запрос и отчёт. Затем штатный предпросмотр по старым терминальным RAW обновляет открытый отчёт; этот отчёт снова ставится в индекс до первой новой читающей проверки. Далее сохраняется прежний порядок: новые проверки, предпросмотр, связность в новой RAW, повторный предпросмотр, staging терминальных свидетельств и читающее замыкание. Такой же предварительный предпросмотр и staging отчёта применяются общим фасадом при непустой истории. Старые RAW на всём пути остаются побайтно неизменными. Независимая ручная композиция выполняет тот же порядок собственными вызовами прежних API.

Полный результат привязан к адресу штатной готовности и номеру отозванного поколения. Смена выбранных новых путей или UUID не открывает второй эффект после отрицательного, незавершённого либо неизвестного процесса. Для следующего поколения требуется новый действительный явный отзыв. Частичные эффекты и файл резерва сохраняются для разбора.

[Парный профиль](tests/профиль_подготовки_этапа_коммита.py) с `--контур повтор-ROOT --раунды 3 --выход <новый приватный JSON>` сравнивает независимую ручную композицию прежних API с генератором на свежем снимке, точном повторе и изменившемся хвосте. Ручная композиция рассчитывает свой план и сама повторяет штатную сверку живого ROOT после зависимых чтений до reserve, не вызывая функции нового генератора. Оба варианта проходят матрицу поздней смены ref при той же вершине и HEAD для обычного и merge-контуров; время включает эту обязательную сверку у каждого исполнителя. Порядок чередуется; проверяется равенство корпуса, модели, разрешений, проверок, готовности и исхода. Генерация, допуск, выполнение и сериализация измеряются раздельно; вложенные интервалы не складываются с календарным временем. Диагностические процессы отдельно считают наблюдаемые проходы и логические байты и сверяются с чистым результатом. Физический ввод-вывод и ненаблюдаемые чтения остаются неизвестными. Исторические 53,07с и 0,54с не образуют парного измерения; ускорение всего цикла этим профилем не обещается.

До первого setup профиль закрепляет конечный набор всех канонических файлов `Инструменты/**`, правил, конфигурации и селекторных политик, включая новые неотслеживаемые продукты: точные относительные пути, raw SHA, тип, режим и отсутствие обязательных селекторов. Вложенные `.gitignore` и `.gitattributes` собираются отдельным обходом независимо от ignore, также внутри фикстуры. Состав и метки файлов сверяются до и после каждого процесса, setup и чистых фаз; все варианты и диагностические дочерние исходники должны соответствовать одному набору. Сгенерированный тест и локальные политики Git фикстуры проверяются отдельно. Эти сверки, импорт, setup и диагностика находятся вне чистых таймеров. Они подтверждают кооперативную стабильность одного замороженного писателя; общей атомарности нет. Исполняемые файлы Python/Git и их версии указаны отдельно; их стандартные и динамические библиотеки не замкнуты этим профилем.

Публикационный рецепт заменяет только точный исполняемый файл текущего Python ролью `@Python` и объявленные корни ролями `@checkout`/`@private`; исходный argv остаётся в приватных результатах. Перед сохранением сводки рекурсивно отклоняются оставшиеся абсолютные пути в значениях и ключах. Неизвестные пути не маскируются общей заменой.
