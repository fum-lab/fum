# Создать проверенный коммит контрольной точки

Команда подготавливает сообщение из реальных пользовательских команд и наблюдаемой истории модели, затем создаёт один локальный коммит после проверки индекса и обязательных проверок. Она сохраняет email автора и данные committer, меняя только `GIT_AUTHOR_NAME`: к явно назначенной роли добавляет подтверждённые модель и усилие, например `FUM Писатель [gpt-6-astra; effort=max]`. Поддержаны обычный коммит и настоящее слияние с двумя упорядоченными родителями.

Это полный путь создания **контрольной точки разрешённой постоянной задачи**. Итоговый режим пока закрыто отказывает: ещё требуется отдельное проверенное включение однократного замыкания проекции по правилу 000188. Проверенная контрольная точка не означает итоговую приёмку, завершение задачи, интеграцию в `master` или публикацию. Команда не создаёт задач, расписаний или hooks.

Для конечного дочернего назначения существует отдельный [вход v3 и подготовка v5](../fum-konvejyer-proizvodnyikh-vetok/передача-слоя.md) по допуску `НОВОЕ-000019`. Проверены открытые фикстуры; реальный пилот ещё не выполнен. Описанный ниже режим контрольной точки сохраняется.

Для обратного приёма подготовлен отдельный [вход v4 и подготовка v6](../fum-konvejyer-proizvodnyikh-vetok/коммит-получателя.md). Его фикстуры не разрешают запуск настоящего получателя до отдельного допуска правил.

## Типизированный адресный вход

[Фасад](scripts/типизированная_контрольная_точка.py) поддерживает существующие контрольные точки `.2/.4`, `.5/.7`, `.6/.8` и `.7/.9`. В библиотеке `ВходКонтрольнойТочки.из_значений(подготовка, список_UUID)` создаёт неизменный вход, а `готово(предел)` и `создать()` вызывают прежний полный создатель. Старые CLI и схемы сохраняются; конечные режимы дочерней передачи и приёма сохраняют собственный допуск.

Новый эффект требует точных путей и непустого упорядоченного списка канонических UUID. Путь к JSON, повтор, сокращение или перестановка закреплённого списка отказывают перед большим читателем первичных команд. HEAD, полный ref, merge-родители, охват, stage-0 байты и режимы, успешные терминальные v4 и оба отпечатка проверяются до чтения команд и модели. Независимая привязка обычного поручения `.7` остаётся обязательной; её ограниченный нативный префикс проверяется прежним читателем. Поздние полные проверки повторяются перед Git.

Успешная сохранённая квитанция читается до нового gate индекса и v4: HEAD после первого коммита уже изменился. Повтор требует того же полного ref и HEAD, равного точному сохранённому OID, затем возвращает прежний проверенный объект. Подбор эквивалентного объекта запрещён. Порог возраста разрешает фиксацию задержавшейся готовности и не становится TTL; повтор не меняет первоначальную эпоху. Замены проверок после явного отзыва остаются доступны прежнему CLI `готово --замена-проверки`; ограниченный CLI фасада не добавляет отдельную политику замен.

```bash
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/типизированная_контрольная_точка.py готово --подготовка /абсолютный/приватный/подготовка.json --проверка <UUID> --предел-секунд 600
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/типизированная_контрольная_точка.py создать --подготовка /абсолютный/приватный/подготовка.json --проверка <UUID>
```

Для `.7/.9` обе команды дополнительно принимают `--выбранное-поручение /абсолютный/приватный/выбор.json`. Оно передаёт независимый выбор того же опубликованного акта, который нужен старому создателю; вход не назначает себе полномочия.

## Первая открытая история v4

После установки пары Журнала подготовьте конечный приватный вход контрольной точки. Включите точную будущую цель от корня checkout `Журнал/<этап>/материалы/запуски-проверок/1_<UUID>.json` в разрешённые цели. Запустите адресную сверку только внутри отчётной обёртки:

```bash
python3 -B Инструменты/fum-otchyotyi-o-zapuskakh-proverok/scripts/отчёты_о_запусках_проверок.py запустить --корень-репозитория . --запрос Журнал/<этап>/запрос.md --название 'Первичная адресная сверка' --исполнитель корень --класс-проверки адресная --приёмочные-раунды --идентификатор-запуска <UUID> -- python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/типизированная_контрольная_точка.py первичная-сверка --вход /абсолютный/приватный/вход.json --проверка <UUID>
python3 -B Инструменты/fum-otchyotyi-o-zapuskakh-proverok/scripts/отчёты_о_запусках_проверок.py предпросмотр --корень-репозитория . --запрос Журнал/<этап>/запрос.md
```

Подкоманда принимает единственный собственный активный адресный v4 с UUID из `FUM_CHECK_RUN_ID`, проверяет адрес и конечный охват существующим инструментом и выдаёт только предварительную сверку. Она не объявляет готовность, не вызывает полную связность и не создаёт коммит. Обёртка сама сохраняет настоящий терминальный исход. Отказ остаётся отказом; после исправления нужен новый UUID и следующий фактический порядок. Для готовности по-прежнему нужны индекс, успешные актуальные терминальные проверки и полный допуск. Первичная запись не переносится на изменённый снимок как GREEN.

Адресные тесты: `python3 -B -m unittest discover -s Инструменты/fum-svyaznostj-rabochej-sessii/tests -p test_типизированной_контрольной_точки.py`. Измеримый профиль: `python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/tests/профиль_типизированной_контрольной_точки.py --выход <новый-файл.json>`. Оба процесса запускайте отчётной обёрткой своего Журнала. Профиль исключает установку фикстур, разделяет ранний gate и полный путь, сохраняет реальные счётчики читателей и манифест выполненного Python. Вложенные интервалы не суммируются; общий коэффициент ускорения FUM не вычисляется.

## Подготовить вход

Работайте из собственного физического корня. Переменная среды `CODEX_THREAD_ID` обязательна и должна совпадать с корневой задачей; отсутствие не заменяется значением входного JSON. Поле `имя_автора` поддерживает `FUM Codex` для имени среды исполнения; конкретная задача описывается в сообщении коммита и Журнале. Исторические кириллические роли остаются допустимыми. Поддерживается только точное продуктовое имя `Codex`, а не произвольная латинская роль; обычный пробел после `FUM` обязателен. Допустимы собственная `refs/heads/codex/…` и явно разрешённые постоянные ветки `refs/heads/fuma` и `refs/heads/planirovaniye`. `master`, detached HEAD, незавершённые rebase/cherry-pick/revert и более двух родителей не поддержаны.

Сохраните JSON вне Git. Все поля обязательны; значения в угловых скобках заменяются фактическими данными:

```json
{
  "схема": "fum.создание-коммита.2",
  "корень": "<абсолютный физический корень>",
  "ветка": "refs/heads/codex/<своя ветка>",
  "исходный_коммит": "<полный HEAD>",
  "родители": ["<полный HEAD>"],
  "задача": "<корневой UUID>",
  "имя_автора": "FUM Codex",
  "запрос": "Журнал/<папка текущего этапа>/запрос.md",
  "источник_модели": "<абсолютный native JSONL корневой задачи>",
  "кэш_модели": "<новый приватный курсор вне Git>",
  "история_модели": "Журнал/<папка текущего этапа>/материалы/история-модели.json",
  "источники": [
    {
      "путь": "<абсолютный первичный JSONL>",
      "задача": "<UUID задачи источника>",
      "экземпляры": ["<идентичность выбранного экземпляра>"]
    }
  ],
  "заголовок": "Сохранить проверенный результат",
  "описание": "Конкретное описание сделанного и оставшейся работы.",
  "сообщение": "<новый приватный файл сообщения вне Git>",
  "подготовка": "<новый приватный файл подготовки вне Git>",
  "квитанция": "<новый приватный файл результата вне Git>",
  "режим": "контрольная-точка",
  "разрешённые_цели": ["<точный относительный путь каждого разрешённого файла>"]
}
```

`разрешённые_цели` — независимый конечный список точных относительных путей. Перечислите исходники, документы, навигацию, индексы, историю модели и все записи проверок своего этапа. Каталоги, повторения, абсолютные пути, выход за корень, symlink и неверный регистр не допускаются. Ещё не созданный файл допустим как будущая цель. Не копируйте весь Git-status как разрешение: состав задаётся принятым объёмом работы.

Будущим проверкам заранее назначьте UUID через `--идентификатор-запуска` отчётной обёртки. Имя записи имеет вид `<следующий-порядок>_<UUID>.json`; при одном последовательном писателе оно известно до подготовки. Это не резервирование. Непредвиденный дополнительный запуск меняет порядок и требует сверенного нового входа и новых приватных файлов подготовки. Прежняя подготовка не переписывается.

Для слияния сначала разрешите его в своём дереве обычным согласованным способом. В `родители` укажите ровно `[L, M]`: текущий HEAD и точный второй OID из `MERGE_HEAD`. Команда сама слияние не начинает и конфликты не разрешает.

В каждом элементе `источники` можно дополнительно указать `кэш` — точный путь существующего приватного индекса `fum.индекс-сообщений.1`, созданного штатным читателем. Это не `кэш_модели`. Без поля сохраняется полный разбор. Кэш проверяется читателем, не обновляется подготовкой и не заменяет первичный JSONL: при росте весь прежний префикс хэшируется, разбирается хвост; поздние байты, повреждение и несовпадение выбранных команд по-прежнему дают отказ. Неизменность метаданных ФС остаётся прежней границей доверия читателя.

До дорогого чтения источника подготовка проверяет непустую историю запусков: требуется v4. Отсутствующий каталог означает новую сессию; существующий каталог читается строго, включая отказ при повреждении или ссылке. Пустая история допускает подготовку сообщения, но её первый запуск необходимо явно начать с `--приёмочные-раунды`; создание без v4 всё равно запрещено. Автоматической миграции v3 нет.

Идентичности `экземпляры` берутся из [штатного читателя сообщений](обработка-сообщений.md), а не из текста или позиции в списке. Сохраняются порядок и реальные повторы; один экземпляр нельзя выбрать дважды. Каждый источник должен иметь подтверждённый завершённый снимок. При изменяющемся живом JSONL согласуйте тихое окно либо независимо проверенный неизменяемый завершённый префикс; автоматического повторения до случайного успеха нет. Область, актуальность поздних указаний и достаточность выбранных команд проверяет корень.

Раздел `Текст запроса` содержит отдельные ограждённые блоки `text` с выбранными командами в том же порядке. Перед блоком допускается единственная точная служебная метка `<!-- FUM-INTAKE: <идентичность экземпляра> -->` штатного сохраняемого приёма: её идентичность обязана совпадать с соответствующим первичным экземпляром. Чужая, повреждённая или повторённая метка отклоняется. После точного исходного текста перед закрывающей оградой добавляется один структурный LF; собственный конечный LF оригинала сохраняется отдельно. В прежних входах v2/v5 неоднозначный ввод, вложение или неподдержанный каркас дают отказ. В сообщение коммита включается сам текст каждой команды, затем наблюдаемые `model` и `effort` и единственный последний корневой `Codex-Thread-ID`.

Запуск из корня:

```text
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/создание_коммита.py подготовить --вход <приватный-вход.json>
```

Выход подтверждает только подготовку. Приватные файлы создаются с режимом `0600`; существующие сообщение, подготовка или квитанция не перезаписываются. История модели может сохраниться до последующего отказа формирования сообщения: отсутствие коммита не означает отсутствие подготовительных записей. При неизвестных обязательных метаданных команда отказывает и не заполняет их догадкой.

## Ограниченная контрольная точка подтверждённых команд

Если завершённый первичный снимок содержит отдельный неоднозначный ввод, для сохранения выбранных подтверждённых человеческих команд доступен явный вход `fum.создание-коммита.5`. Режим остаётся `контрольная-точка`; остальные поля прежнего v2 сохраняются. В каждом источнике обязательно дополнительное поле `граница_снимка` с точными `граница`, `sha256` и упорядоченным массивом `неоднозначные_экземпляры` из штатного читателя. Пустой массив допустим только при отсутствии таких экземпляров.

Подготовка требует целого LF-префикса, совпадения размера и границы, отсутствия роста во время чтения, точного SHA256 и полного списка неоднозначностей. Выбранные экземпляры отдельно проходят прежние проверки человеческого происхождения, порядка, повторов и дословного текста. Старый вход v2 не принимает новое поле и сохраняет прежний отказ. Вложенный сырой исходник не фильтруется и не переписывается.

Результат — `fum.подготовленный-коммит.7`. Готовность хранится в отдельной обёртке `fum.готовность-выбранных-команд.1`, привязанной к физическим путям источников, UUID и всем границам снимков. Изменение позднего контекста или списка неизвестных событий не наследует прежнюю готовность; её исходный возраст сохраняется при точном повторе. Старую готовность без этой привязки новый режим отвергает.

Этот допуск сохраняет ограниченный этап, но не доказывает разбор всего диалога, актуальность относительно более позднего живого JSONL или выполнение поручений. Неоднозначный ввод остаётся в исходнике и остатке; прежние флаги полноты, обработка сообщений и Stop/final-допуск не меняются. Смысловую достаточность выбранных команд и поздние уточнения проверяет корень.

Адресная регрессия: `tests/test_выбранные_команды.py`. Парный профиль `tests/профиль_выбранных_команд.py --выход <новый JSON>` сравнивает прежний допуск и новый выбор на одном открытом полностью человеческом корпусе с одинаковым результатом. Он использует проверенный кэш, сохраняет прогрев, три чередующиеся пары и хэши; ускорение полного рабочего цикла им не измеряется. Оба запуска выполняются через отчётную обёртку своей пары Журнала.

## Текстовая команда с изображением

Вход `fum.создание-коммита.6` сохраняет все поля, режим контрольной точки и точную границу источника v5. Дополнительно он принимает подтверждённый человеческий каркас: основной `input_text`, затем одна или несколько троек из текстового открытия `<image name=[Image #N] path="…">`, `input_image` и текстового `</image>`. Каждая текстовая часть сохраняется дословно; в Журнал и сообщение коммита попадает их соединение одним LF между частями, без trim. Обычный однокомпонентный текст остаётся побайтно прежним.

Изображение остаётся непрозрачным: проверяются только известные поля, форма data URL PNG/JPEG/GIF/WebP с base64 и допустимый `detail`. Сеть, декодирование и проверка пикселей не выполняются. Неизвестные части, поля, внешние адреса и другие каркасы дают отказ. Исходный экземпляр и SHA всей нативной строки, включая изображение, сохраняются в подготовке и повторно сверяются перед первым Git-эффектом. Сам data URL в сообщение коммита не переносится; полный исходник и вложение сохраняются приватно по обычному протоколу источников.

Результат — `fum.подготовленный-коммит.8`; готовность имеет отдельную обёртку `fum.готовность-команд-с-изображением.1` с точными источниками и границами. Готовность v5 нельзя перенести в v6. Прежние схемы не расширяются молча. Текстовая проекция не означает полного сохранения или обработки многочастного сообщения: учёт обработки по-прежнему требует свидетельства `части-json`.

Регрессия: `tests/test_команды_с_изображением.py`; профиль: `tests/профиль_команды_с_изображением.py --выход <новый JSON>`. Они проверяют настоящий Git-коммит, повтор, подмену вложения, неизвестный каркас, дословность и прежний текстовый контракт. Парный профиль сравнивает сохранённую ветвь v5 и v6 в текущем коде; большой синтетический data URL измеряется отдельно. Все запуски выполняются отчётной обёрткой.

## Обычная дочерняя контрольная точка

Вход `fum.создание-коммита.7` сохраняет все поля контрольной точки и добавляет `исполнитель` и `выбранное_поручение`. Его режим — `контрольная-точка`. В `задача` хранится UUID координатора, в `исполнитель` — действительный UUID отдельного видимого чата. Нативный JSONL модели принадлежит исполнителю; выбранные пользовательские команды и последний `Codex-Thread-ID` сохраняют корневое происхождение. Текст запуска ребёнка сам по себе не является новой командой человека.

Каждая подкоманда требует второй независимый вход `--доверенное-поручение <приватный-выбор.json>`. Он содержит ровно координатора, исполнителя, полный коммит акта, путь его обычного blob и SHA-256. Копия внутри параметров или подготовки не заменяет этот вход. [Читатель поручения](обычное-дочернее-поручение.md) проверяет закреплённую постановку, первое нативное поручение, физический корень, полный ref и конечную область до записи истории модели.

~~~text
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/создание_коммита.py подготовить --вход <приватный-вход.json> --доверенное-поручение <приватный-выбор.json>
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/создание_коммита.py готово --подготовка <подготовка.json> --проверка <UUID> --предел-секунд 600 --доверенное-поручение <приватный-выбор.json>
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/создание_коммита.py создать --подготовка <подготовка.json> --проверка <UUID> --доверенное-поручение <приватный-выбор.json>
~~~

Подготовка имеет схему `.9`, готовность — `fum.готовность-дочерней-контрольной-точки.1`. Строгий JSON отвергает дубли и лишние поля. До `write-tree` повторяются поручение, собственная модель и число её наблюдений, история, индекс, проверки и подготовленные байты. Смена модели после проверки готовности даёт отказ. Повтор с сохранённой квитанцией снова требует независимый выбор, но возвращает прежний проверенный OID без второго `git commit`.

Подкоманды `подготовить-повтор` и `отозвать-готовность` также передают независимый аргумент. Ключ этапа и правила возраста не меняются. Прежние схемы не принимают новый вход и не становятся дочерней точкой; конечные `дочерняя-передача` и `дочерний-приём` сохраняют свои контракты. Производный автообзор пока не поддерживает подготовку `.9`: его предупреждение после успешного создания не отменяет подтверждённый коммит. Контрольная точка не разрешает final, слияние или продвижение чужого ref.

## Повторить подготовку без изменения истории модели

Если нужно уточнить конечный состав разрешённых файлов или подготовить новое сообщение, а новые наблюдения модели не появились, доступен явный режим:

```text
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/создание_коммита.py подготовить-повтор --вход <новый-приватный-вход.json>
```

Вход остаётся v2; сообщение, подготовка и квитанция должны иметь новые приватные пути. История и её прежний курсор должны существовать и совпадать; их автоматического восстановления нет. Свежий JSONL читается штатным импортёром без записи. Обычный корректный хвост без новых turn_context допустим. Новое наблюдение даже с прежними model/effort, пропуск, неполный хвост, изменение старого префикса или рассогласованный курсор дают отказ. Тогда отдельно сверяют источник и выполняют обычную подготовку до staging и проверок.

Подготовка сохраняет SHA неизменных канонических байтов истории. Дополнительное поле результата CLI `сверка_истории` содержит свежую читающую сверку: её `история_sha256` относится к рассчитанному объекту истории, а не к сохранённому файлу и не к самому JSONL. Сохраните этот результат приватно как свидетельство проверки хвоста. Старые подготовка, сообщение, история и курсор не перезаписываются; обычный импорт сохраняет прежнюю семантику.

Режим предотвращает инвалидирование проверок только из-за переписывания истории при росте служебного JSONL. Он не разрешает использовать проверки другого canonical diff или индекса, не создаёт коммит и не повторяет отказ автоматически. [Парный профиль](tests/профиль_повторной_подготовки.py) с `--выход <новый JSON>` сравнивает обе подготовки на хвосте 1 МиБ через штатную отчётную обёртку.

## Совместимость подготовки

Новая команда подготавливает `fum.подготовленный-коммит.4`. Вход `fum.создание-коммита.2` сохраняет поле `имя_автора` для роли без суффикса, например `FUM Писатель`. Верхнее поле `имя_автора` содержит вычисленное полное имя; поле `готовность` — устойчивый приватный адрес состояния этапа. Они вместе со списком разрешённых целей входят в неизменяемые байты подготовки и связываются с квитанцией их SHA. Перед Git имя заново вычисляется из подтверждённого наблюдения и сравнивается целиком; неполная модель, неизвестное усилие, пробелы и разделители внутри машинных токенов отклоняются без исправления входа.

Прежние представления v1/v2/v3 допускаются только для чтения уже существующей успешной квитанции, после проверки её связи с сырыми байтами исходной подготовки. Для такого повтора готовность не требуется. Полный сохранённый результат должен совпадать с точным Git-объектом; автор, committer и их даты читаются буквально, без назначения сегодняшней модели. Без квитанции создание по прежней подготовке закрыто отказывает: требуется новая подготовка v4. Неполные старые файлы не дополняются на месте. Схема квитанции остаётся v1; эта совместимость не разрешает повтор неизвестного Git-вызова. Имя содержит последнее подтверждённое наблюдение, полная история переключений сохраняется в Журнале и не заменяется суффиксом.

## Проверить и создать

Завершите содержательные файлы и recency, просмотрите точный diff, затем индексируйте канонический вход. После этого запустите применимые проверки через [отчётную обёртку](../fum-otchyotyi-o-zapuskakh-proverok/SKILL.md) в истории v4. Обновите предпросмотр и индексируйте только исключённые из отпечатка текущие отчёт и записи запусков. Это сохраняет связь проверок с тем же Git-отпечатком и фактическим содержимым.

Команда `готово` проверяет SHA подготовленного сообщения и связность текущего
Журнала тем же допуском, который повторяется в `создать`. Перед записью готовности
повторно сверяются индекс, v4 и сообщение. Неполный раздел инструментов поэтому
отклоняется до объявления готовности. Это не заменяет модель, авторство и остальные
окончательные проверки непосредственно перед Git.

Объявите готовность по фактическому индексу и UUID каждого обязательного успешного запуска, затем передайте те же UUID созданию:

```text
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/создание_коммита.py готово --подготовка <приватная-подготовка.json> --проверка <UUID-запуска> --проверка <UUID-другого-запуска> --предел-секунд 600
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/создание_коммита.py создать --подготовка <приватная-подготовка.json> --проверка <UUID-запуска> --проверка <UUID-другого-запуска>
```

600 секунд — явно выбранный пример порога, а не общая норма. Отсутствующая, повреждённая или отозванная готовность останавливает новый вызов до дорогих проверок. Перед записью намерения коммита повторно сверяются снимок и точные SHA сырых записей проверок. Прошедший порог отмечает задержку, но не отменяет необходимость фиксации уже готового этапа.

Если допуск обнаружил ошибку, явно отзовите последнее поколение, исправьте прежний объём и повторите применимые проверки:

```text
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/создание_коммита.py отозвать-готовность --подготовка <приватная-подготовка.json> --поколение 0 --основание <наблюдаемая-причина>
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/создание_коммита.py готово --подготовка <новая-приватная-подготовка.json> --проверка <UUID-нового-запуска> --замена-проверки <UUID-прежнего-запуска>=<UUID-нового-запуска> --предел-секунд 600
```

Поколения сохраняют первоначальное время, максимальный возраст, прежние снимки и SHA свидетельств. Корень, ref, исходный OID, запрос, исходные экземпляры сообщений и состав содержательных целей не расширяются. Разрешены новые записи проверок текущего этапа; замена обязательных UUID задаётся явно без сокращения списка. Это структурная проверка соответствия, а не доказательство смысловой эквивалентности двух тестовых команд. Новый независимый объём получает следующий этап. Подробнее — [контроль фиксации](контроль-фиксации.md).

Перед чтением первичных JSONL выполняется готовая ранняя сверка материалов: она сопоставляет раздел «Повлиял на файлы», полный Git-status и независимый разрешённый список. После чтения источников и метаданных снимок сверяется повторно до дорогой проверки индекса. Неполный состав, лишний файл или дрейф останавливают создание до записи намерения Git. Полная связность, обязательные проверки и заключительная сверка индекса сохраняются.

Список не может быть пустым; все выбранные записи должны относиться к текущим двум отпечаткам. Исторические RED-запуски остаются в журнале, но не заменяют обязательные успешные результаты. Определение применимых проверок и оценка их достаточности остаются обязанностью корня; один UUID не доказывает полноты выбранного контура. Открытый журнал требует точного предпросмотра, без активных, переходных и закрытых состояний.

Команда использует настоящую проверку связности без отключения Git-состояния. Дополнительно она проверяет каждый stage-0 файл, его сырые байты и исполняемый режим, ссылки, точные gitlink OID и отсутствие неиндексированного хвоста. `assume-unchanged`, `skip-worktree`, конфликты и преобразующие фильтры, при которых сырые рабочие байты отличаются от blob, не обходят этот допуск. Изменённая проекция тоже включается в полный индексный снимок, но её итоговая правильность этим не доказана.

После повторной сверки входа команда получает дерево через `git write-tree`, сохраняет приватное намерение и вызывает `git commit` с тем же файлом сообщения и `--cleanup=verbatim`. `write-tree` может создать Git-объекты и обновить cache-tree даже без успешного коммита. Проверяются сырой OID, дерево, порядок родителей, author/committer, фактическое сообщение и последний trailer.

## Прочитать результат или отказ

Успех возвращает полный OID, дерево, родителей и фактические поля. Квитанция хранит входную границу и монотонные длительности стадий. Публикация выполняется отдельно по действующему правилу 000064, после проверки точного назначения и удалённого OID; нового неявного push нет.

После проверенного результата и освобождения замка автоматически применяется [доказательный обзор](../fum-ocenki/доказательный-обзор.md). Он сохраняет приватную пару JSON/Markdown рядом с квитанцией, читая точный созданный коммит и выбранный допуск. Повтор с существующей квитанцией проверяет тот же обзор без нового коммита. Шесть полей публичного результата не меняются. Ошибка обзора, неподдерживаемая старая подготовка или перехватываемое прерывание после создания дают предупреждение в stderr, сохраняя успешный проверенный коммит.

Повтор `создать` с той же подготовкой требует успешную квитанцию `fum.квитанция-создания-коммита.1` в состоянии `проверен`, без дублированных JSON-полей. Полный четырёхполевой процесс должен подтверждать код 0, завершение, отсутствие таймаута и прерывания. Полный шестиполевой результат закрепляет OID, дерево, порядок родителей, буквальные author/committer с датами и SHA сообщения; наблюдённый OID обязан совпадать с ним. Полное ожидание сверяется с подготовкой: ref, исходный коммит, родители, сообщение, явные даты и сохранённая identity/роль. Естественные даты наблюдались позже подготовки и не приравниваются к её времени. Сырой Git-объект проверяется по собственному OID и ожиданию; затем все шесть полей сравниваются с сохранёнными. Тот же ref и HEAD проверяются до и после чтения. Отсутствующее, противоречивое или неуспешное свидетельство вызывает отказ без дополнения из текущего HEAD.

Этот путь не вызывает новый `git commit`, `write-tree`, установщик квитанции, большой читатель команд или модели и новый живой gate. Исходная квитанция сохраняет байты при успехе и отказе, включая допустимую нестандартную разметку JSON. Первичная фиксация после собственного нового Git-вызова выделена отдельно: только она записывает наблюдённый объект и диагностическое состояние процесса. Кооперативный замок и последующий автообзор остаются отдельными действиями; отсутствие записи исходной квитанции не означает отсутствия всех файловых эффектов публичного API.

Если Git отказал до передвижения HEAD, либо исход неизвестен, сохранённая попытка запрещает автоматический повтор. Если коммит появился, но поля, сообщение, дерево или родители расходятся, первичная фиксация сохраняет наблюдённый OID и отказ после создания. Явные даты автора и committer сохраняются при подготовке и проверяются в созданном объекте; естественное время наблюдается при создании и закрепляется полным результатом для последующего повтора. Завершённый отказ Git и таймаут сохраняются с кодом процесса и профилем. При таймауте, `SIGINT`, `SIGTERM` и `KeyboardInterrupt` собственная группа Git и hooks завершается до чтения результата. Локальный обработчик только запоминает сигналы во время запуска, ожидания и очистки; основной поток проверяет их между ожиданиями до 0,1 с и после завершения процесса. Общий монотонный предел Git остаётся 120 с. Повторные сигналы не прерывают остановку группы; неизвестное завершение запрещает успех. Даже при правильном созданном объекте отказ процесса требует разбирательства и не возвращает успешное создание. Команда не делает reset, amend, force push и не скрывает уже созданный объект.

Первичная фиксация без подтверждённого завершения процесса записывает `исход-процесса-неизвестен`; повтор существующего неполного свидетельства сохраняет его байты и отказывает. Один наблюдённый HEAD не доказывает остановку поздних писателей. Не удаляйте квитанцию для обхода отказа. Сначала установите фактическое состояние и сохраните основание новой попытки. Приватный замок сериализует только вызовы с одной квитанцией; это кооперативный контракт единственного назначенного писателя, а не защита от произвольной конкурентной записи на машине.

[Профиль точного повтора](tests/профиль_точного_повтора_квитанции.py) запускается отчётной обёрткой: `python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/tests/профиль_точного_повтора_квитанции.py --выход <новый-файл.json>`. Три настоящие пары `.4` отделяют подготовку от таймеров, сохраняют счётчики установок исходной квитанции и читателей, снимки байтов и SHA исполненного кода. Автообзор не отключается и измеряется отдельно. Вложенные интервалы не суммируются; малые фикстуры и измерительные перехватчики ограничивают выводы о скорости.

Отказы подготовки и допуска до Git также содержат наблюдаемую длительность и профиль: в атрибутах исключения API и JSON ошибки CLI, включая отсутствующий или повреждённый вход. Вызывающая сторона сохраняет этот вывод вне Git штатным захватом; это не квитанция созданного коммита. Неперехватываемое завершение, например `SIGKILL`, может оставить неполное намерение и требует отдельной сверки. Автоматическое удаление Git-lock файлов не выполняется.

## Проверка контракта

Адресные тесты используют реальный временный Git, синтетический первичный JSONL и реальную отчётную обёртку. Они не подменяют положительный допуск заглушкой:

```text
python3 -B -m unittest discover -s Инструменты/fum-svyaznostj-rabochej-sessii/tests -p test_создание_коммита.py
python3 -B -m unittest discover -s Инструменты/fum-svyaznostj-rabochej-sessii/tests -p test_допуск_автора.py
python3 -B -m unittest discover -s Инструменты/fum-svyaznostj-rabochej-sessii/tests -p test_ранний_состав_коммита.py
python3 -B -m unittest discover -s Инструменты/fum-svyaznostj-rabochej-sessii/tests -p test_ранний_охват.py
```

Эти прямые тестовые процессы в рабочей сессии также запускаются через отчётную обёртку. Фикстуры не доказывают полного smoke-check FUM или готовности итогового режима.

Воспроизводимый профиль двух положительных сценариев и двух ранних отказов: без native UUID и при неполном составе до чтения первичного JSONL, также через отчётную обёртку:

```text
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/tests/профиль_создания_коммита.py --выход <профиль.json> --подробный-профиль <приватный-файл-cProfile>
```

Публичный JSON содержит стадии и хэш инструмента. Подробный профиль с локальными путями остаётся вне Git. Подготовка временного репозитория исключена; подготовка сообщения, проверки, создание и чтение результата включены.

## Профиль кэша первичных команд

[Открытый измеритель](tests/профиль_кэша_команд.py) создаёт одинаковый синтетический JSONL и сравнивает три чтения. Параметр `--с-кэшем` включает индекс, `--с-хвостом` дописывает строку после его подготовки. Выход `--выход <профиль.json>` содержит SHA входа, результата и исходников. Все варианты вызываются через отчётную обёртку. Подготовка индекса исключена; время полного создания коммита и расход токенов этим не измеряются.
