# Мост полного ответа узла

Мост заменяет ручную передачу крупного ответа читающего API в приватный файл. Он сам вызывает один текущий `read_thread`, сохраняет целиком сериализованный возвращённый объект и передаёт штатному входу контейнера небольшое описание `{цикл, задача, файл}`. Доставка описания и актуальность состояния узла проверяются отдельно. Мост не отправляет поручения, не возобновляет задачи и не разрешает эффекты.

## Вход и компоненты

[Сценарий моста](scripts/мост_полного_ответа_узла.cjs) исполняется в среде JavaScript с инструментами `exec_command`, `write_stdin` и `mcp__codex_app__read_thread`. Среда предоставляет сохранение и чтение локального состояния, [вычисление отпечатка](scripts/хэш_полного_ответа_узла.cjs) и callback передачи описания контейнеру. Производственные компоненты не требуют Node, `Buffer`, `TextEncoder` или доступа JavaScript к файловой системе.

Конечные параметры: физический корень собственного checkout, отдельный приватный каталог, выданный текущему циклу запрос схемы `fum.запрос-внешнего-чтения.1` и предел сериализованного аргумента инструмента. Канонические UUID цикла и задачи обязательны. Читающий запрос содержит точные `threadId`, `hostId`, `turnLimit=1`, `includeOutputs=true`, `maxOutputCharsPerItem` от 1 до 16000 и необязательный строковый `cursor`. Полный исторический ответ не принимается параметром моста и не выдаётся за новое наблюдение.

Объект результата API сериализуется ровно через `JSON.stringify` целиком. Это представление возвращённого объектного ответа, а не доказательство получения исходных HTTP-байтов или полноты истории задачи. На чтение более ранних страниц ограничение `turnLimit=1` не даёт разрешения.

## Намерение до API и точная передача

[Приёмник](scripts/приём_полного_ответа_узла.py) открывает абсолютный каталог через дескрипторы без следования symlink. Любая Git-область, чужой владелец или доступ группы/прочих закрывает допуск. Файлы `чтение-<цикл>.claim.json`, `чтение-<цикл>.json` и `чтение-<цикл>.ack.json` создаются только с `O_EXCL`, без замены существующих байтов, в режиме 0600.

До READY приёмник долговечно сохраняет намерение: цикл, задачу, точный запрос и путь результата; синхронизирует файл и каталог. Поэтому потеря памяти JavaScript после запроса, но до первой порции, не позволяет повторить API этого цикла. Даже неполное намерение или сохранённый частичный ответ блокируют повтор. Они не удаляются автоматически. Новый цикл требует самостоятельного основания, а не служит скрытым повтором неизвестного исхода.

Среда запускает приёмник с `tty=true`; приёмник переводит терминал в raw до READY. Это отключает echo и ожидание строкового буфера. Через обычный pipe приёмник также работает; реальный `exec_command` без TTY может закрыть stdin до передачи, поэтому такой путь не используется мостом. Ни payload, ни его фрагменты не попадают в исполняемый код, аргументы запуска Python или вывод модели.

Канал содержит JSON-заголовок, точное число UTF-8-байтов ответа, LF и JSON-конец с теми же циклом, задачей, размером и SHA-256. Размер ответа ограничен 64 МиБ. Порции инструмента содержат не более 100000 UTF-16 code units; пары суррогатов не разрываются. Их целиком сериализованные аргументы проверяются против заданного предела от 512 до 262144 байтов. Все записи ожидаются последовательно; неизвестная запись не повторяется.

После проверки контекста, размера, конца и SHA приёмник синхронизирует ответ, проверяет неизменность физического каталога, долговечно записывает ACK и только затем выводит ACK. Конец кадра завершает процесс без ожидания EOF. Короткие `os.write` обрабатываются циклом; нулевая запись и ошибка `fsync` не дают успешного ACK.

## Повтор и границы подтверждения

Память среды сверяет полный канонический контекст: корень, каталог, предел аргумента, схему, цикл и все параметры запроса. Точный подтверждённый повтор возвращает прежний результат без нового API и без повторной передачи описания. Другой контекст и прежний неизвестный исход отклоняются. Независимый приёмник дополнительно блокирует повтор долговечным намерением, когда память среды потеряна.

Состояние `полный ответ сохранён` подтверждает только RAW-файл и ACK приёмника. `доставка_описания` остаётся `не подтверждена`: завершение callback само по себе не доказывает сохранение наблюдения штатным CLI. Нужен полный привязанный итог CLI с точным объектом, циклом и подтверждённым каталогом. Неизвестный исход callback сохраняет ACK; повтор моста не делает новый API или новую отправку. Историческое читающее восстановление имеет отдельную границу свежести и не возобновляет задачи.

## Проверка и профиль

~~~text
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/tests/профиль_моста_полного_ответа_узла.py --корень-репозитория . --проверить
~~~

На другом размещении Node передаётся `--узел <путь-к-Node>`. [Адресные тесты](tests/test_моста_полного_ответа_узла.py) проверяют большой поток без EOF, PTY без echo, короткую запись, отказ синхронизации, повреждение, чужой контекст, закрытый путь, прерывание после READY и блокировку повторного запроса.

[Профиль](tests/профиль_моста_полного_ответа_узла.py) запускает три свежих Node и три настоящих Python-приёмника. Объект ровно 2381548 UTF-8-байтов создаётся до таймера; читающий callback синтетический, реальных API нет. Проверяются байты, SHA, режим, ACK, намерение и предел каждой порции. Отдельно измеряются общее время до ACK, хэш, готовность приёмника и ожидания pipe; вложенные интервалы не складываются повторно. Ожидания включают работу приёмника и не являются чистой стоимостью IPC. Пик памяти относится только к Node. Проверка поведения через Node не доказывает выполнение в V8; фактический тракт инструментов среды сохраняется отдельным свидетельством. Новый профиль не измеряет Swift-контейнер, реальный API, скорость восстановления всех задач или выигрыш относительно прежних ручных порций.
