# Читать известную служебную оболочку инструментов

Читатель пропускает проверенную служебную запись `response_item/additional_tools` и продолжает читать последующие команды. Объявления инструментов не становятся человеческим вводом, транспортными дублями команд или разрешением выполнить действие. Исходный JSONL остаётся неизменным; его граница и SHA включают служебные строки.

## Поддержанная форма

Payload содержит ровно `type`, `id`, `role`, `tools`: тип `additional_tools`, непустой строковый `id`, роль `developer` и непустой список объявлений. В этом списке допустимы пространства имён и объявления поиска инструментов в любом сочетании и порядке.

Пространство содержит ровно `type=namespace`, непустое строковое `name`, строковое `description` и непустой список `tools`. Объявление поиска содержит ровно `type=tool_search`, `execution=client`, строковое `description` и JSON-объект `parameters`. Поиск допустим только на верхнем уровне списка; его параметры остаются данными, а не разрешением выполнить запрос.

Внутри пространства поддержаны две конечные формы:

- `function`: ровно `type`, `name`, `description`, `parameters`, `strict`; имя непустое строковое, описание строковое, параметры — JSON-объект, `strict` — булево значение.
- `custom`: ровно `type`, `name`, `description`, `format`; имя непустое строковое, описание строковое; формат содержит ровно `type=grammar`, `syntax=lark` и непустое строковое `definition`.

Параметры и грамматика не исполняются и не интерпретируются читателем. JSON-объект параметров сохраняет свободу внешней схемы; проверка её пригодности для вызова инструмента сюда не входит. Количество пространств и инструментов, их имена и описания не закреплены за одной поставкой runtime.

Отсутствие роли, другая роль, лишнее поле, неизвестный вложенный тип и неправильный тип значения дают отказ. Неизвестная оболочка с `role` также отвергается. Остальные существующие формы сохраняют прежнее поведение; этот ремонт не расширяет их перечень.

## Запуск и результат

Обычная команда остаётся прежней:

```text
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/обработать-сообщения-задачи.py --корень-репозитория . --codex-thread-id <UUID> --исходник <приватный-JSONL> остаток --без-записи
```

Полный вывод содержит приватный ввод: сохраняйте его вне Git штатным [захватом вывода](полный-захват-вывода.md). Код 0 означает завершённый учёт сообщений, 3 — остаток или неполную границу, 2 — отказ чтения. Ни один из них сам по себе не доказывает выполнения поручений. При неверной служебной оболочке обработчик сообщает статическую причину «неподдержанная или повреждённая служебная оболочка response_item», без значений native-полей. Сохраните оригинал приватно и проверьте совместимость формы; вручную переписывать JSONL для обхода отказа нельзя.

Кэш уже связан с SHA реализации reader и классификатора; кэш границ дополнительно учитывает обработчик. После смены исходников индекс перечитывается полностью, а прежний префикс продолжает проверяться. Ручная смена привязок не нужна. Режим `--без-записи` не создаёт и не переписывает кэш.

## Воспроизвести проверку

Открытая [фикстура](tests/фикстуры-служебной-оболочки-событий/сценарии.json) синтетическая и не содержит native-данных. [Тесты](tests/test_служебной_оболочки_событий.py) проверяют неверные формы, команды и повторы, LF-границы, диагностику, оба кэша и действительную смену байтов reader между свежими процессами.

```text
python3 -B -m unittest discover -s Инструменты/fum-svyaznostj-rabochej-sessii/tests -p test_служебной_оболочки_событий.py
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/tests/test_служебной_оболочки_событий.py --профиль <файл-профиля-вне-Git> --повторов 3
```

В рабочей сессии эти прямые процессы выполняются через [отчётную обёртку](../fum-otchyotyi-o-zapuskakh-proverok/SKILL.md). Профиль создаёт один синтетический вход, измеряет холодное, повторное и полное чтение; подготовка исключена, кэш ОС не очищается. Точный размер и SHA входа сохраняются в профиле вместе с монотонными стадиями, исходом, версией Python и SHA исходников. Сравнивать следует одинаковые вход и исходники; изменение алгоритма ради формальной оптимизации не требуется.

Ремонт перенесён на принятую основу `432d5e07f4ce1ea8effcb14a5d1f3f3cc5fe3691`. В читателе добавлена проверка служебной оболочки, а в обработчике — две адресные ветки статической диагностики. Пакетная обработка, общий сеанс чтения, кэш свидетельств и заключительная сверка сохранены. Замена обработчика целиком его ранней версией потеряла бы эти принятые изменения.

Проверка полной основы вызывает её собственный `первичная_управляющая_рамка`: точное поручение должно остаться `адресное-получение` с исходным хэшем текста и `разрешение_эффекта=false`. Проверка выполняется без пропуска. Совместимость дополнительно проверяют существующие `test_сообщения_задачи.py`, `test_обработка_сообщений.py` и `test_кэш_сверки_остатка.py`. Успех этих проверок не активирует читатель в другой сессии и не означает интеграции.

## Совместимость исправлений

В первой поставке синтетическая фикстура не включала `tool_search`, хотя полная исходная запись уже содержала его вместе с пространствами имён. Повторный отказ того же входа показал неполноту ремонта, а не доказанную взаимную регрессию двух исправлений. Исходная запись и полный закрытый префикс сохранены приватно и проверены без подмены байтов; открытая фикстура воспроизводит сочетание форм без раскрытия native-данных.

Совместный набор сохраняет прежнюю форму отдельно, новую отдельно и оба порядка их сочетания. Допустимый поиск не завершает проверку списка досрочно: повреждённое следующее объявление также даёт отказ. Проверки сравнивают полный разбор с чтением добавленного хвоста и подтверждают сохранность кэша после отказа. В этом срезе прошли 14 адресных тестов и полное чтение исходного префикса из 61 208 строк с совпадением SHA и неизменностью источника.

Такой набор удерживает оба условия совместимости одновременно. Сам по себе он не доказывает отсутствия циклов «исправление A ломает B, исправление B возвращает A» во всём проекте: для такого вывода нужны результаты одних и тех же случаев на последовательных версиях, включая ранее успешный случай.
