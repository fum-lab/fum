# Подготовка кандидата базиса узла

Подготовка материализует уже выбранное дерево T в собственном чистом рабочем дереве. Результат содержит полный stage0 и рабочие файлы T, HEAD и собственную ветку на K, единственный `MERGE_HEAD` с R. Коммит B, доказательства D, предметный RAW и state2 создаются отдельными операциями. Успех этой команды не является приёмкой R→B или разрешением Creator.

## Необходимые входы

ROOT заранее выбирает физический собственный W, его единственного писателя, уже созданную собственную ветку `refs/heads/codex/...` на K, ACT_B и контрольное поколение. Подготовка проверяет владение через настоящий список worktree; занятую другим деревом ветку не переключает. Начальный W и индекс должны быть чистыми, без скрывающих флагов, конфликтных стадий и незавершённых операций. Игнорируемые и неучтённые файлы тоже входят в проверку коллизий.

Исполняемые зависимости — цельный неизменный экспорт C572 `3ed222ce81f3985d66186b8e9ec78d1ddfc203eb`. Карта всех 904 Python-файлов под `Инструменты/` имеет SHA-256 `7192441dee1cd79f43aebb97a8d22f88081e36af3bc8d96ecc4e12cb6ee110a0`. Карта связывает относительный путь и SHA-256 сырых байтов; её каноническое представление — UTF-8 JSON с упорядоченными ключами, разделителями `,` и `:`, сохранённой кириллицей и конечным LF. Изменённый, неполный или смешанный экспорт отказывает. Кэши, байткод, двоичные альтернативы и символические ссылки в контуре не допускаются. Загружаются удержанные проверенные исходные байты.

Python и Git независимо закрепляются путями и SHA-256 в существующем выборе базиса. Наблюдаемые native начала, actor, ROOT-поручение и birth K должны соответствовать ACT_B. Начальный читающий bootstrap использует системный `/usr/bin/git` с отключёнными hooks, trace, replace, lazy fetch и внешними конфигурациями; он подтверждает независимое ROOT-поручение **до** загрузки экспортированного кода.

Подготовьте приватный JSON `fum.вход-подготовки-кандидата.1` с ровно шестью содержательными полями и схемой:

- `параметры_базиса` — точные параметры существующей схемы `fum.создание-коммита.12`; подготовка использует их как описание будущего B, не вызывает его создание;
- `выбор_базиса` — тот же независимый предварительный выбор, что записан в параметрах: отчётный корень, selector ACT_B, Python/Git, точный частный вход построителя;
- `код` — `коммит`, физический `корень` полного экспорта и карта `файлы`;
- `код_подготовки_sha256` — SHA-256 исполняемого `подготовка_кандидата_базиса.py`;
- `нативный` — `путь`, `sha256`, `байты` точного выбранного native-файла;
- `состояние` — существующий пустой собственный каталог с режимом 0700 вне Git, W, административных областей и частной ODB построителя.

Поле `схема` имеет точное значение `fum.вход-подготовки-кандидата.1`. Набор закрыт. Схемы подготовки, Creator, D и приёмки не взаимозаменяемы.

ROOT сохраняет в обычном Git-blob отдельное поручение `fum.поручение-подготовки-кандидата.1` с полями `вход_sha256`, `координатор`, `исполнитель`, `ACT_B`, `контроль`. Хэш входа относится к его каноническому JSON; `ACT_B` и `контроль` должны точно совпадать с действующим назначением будущего B. Файл `--назначение` содержит независимый selector этого blob: ровно `коммит`, `путь`, `sha256`. Последний хэш относится к сырым байтам Git-blob. Собственная копия назначения внутри candidate полномочий не даёт.

## План, независимый выбор и применение

Все внешние JSON — обычные физические файлы без ссылок. Сохраните stdout плана в новый приватный файл:

```sh
python3 -I -S -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/подготовка_кандидата_базиса.py \
  план --вход '<вход.json>' --назначение '<selector-назначения.json>'
```

План ничего не записывает. Он связывает исходные HEAD/ref/index, конфигурацию, административные адреса и указатели linked worktree, идентичности областей, частные объекты, K/R/T, шесть исторических защищённых целей и конечный перечень отсутствующих tree-объектов. Сырые private tree-объекты полностью сверяются с независимо пересчитанной сериализацией построителя. Все необходимые blob уже должны находиться в обычной ODB.

Каждый новый контекст читает обычные blob свежим принятым пакетным Git-читателем C572: проверяет тип, OID и полные сырые байты, сохраняя только размеры. Между защитными фазами данные объектов не кэшируются. Число процессов чтения не растёт с числом blob; прежние проверки назначения, защищённых целей и атрибутов сохраняются.

После чтения плана ROOT отдельно сохраняет в Git документ с точными полями:

```json
{
  "схема": "fum.выбор-применения-кандидата.1",
  "назначение": {"коммит": "<OID>", "путь": "<путь-ROOT-blob>", "sha256": "<SHA-256>"},
  "план_sha256": "<SHA-256 канонического плана>"
}
```

`--выбор` содержит selector этого второго blob, а не сам документ. Материализация не принимает собственный план за такое решение.

```sh
python3 -I -S -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/подготовка_кандидата_базиса.py \
  применить --вход '<вход.json>' --назначение '<selector-назначения.json>' \
  --план '<план.json>' --выбор '<selector-выбора.json>'
```

Под собственным неблокирующим замком до каждого эффекта долговечно сохраняется фаза намерения. Только отсутствующие проверенные tree-объекты импортируются штатным Git в обычную ODB; существующие объекты, включая packed, перечитываются и не переписываются. Частная ODB сохраняется. Собственный ref уже равен K и повторного изменения не требует. Индекс и файлы устанавливаются двухдеревным `git read-tree -m -u K T`; затем устанавливается единственный `MERGE_HEAD`. Обычные файлы, индекс, административные и рабочие каталоги синхронизируются перед квитанцией.

Исторические symlink/gitlink остаются непрозрачными и не меняются. Отсутствующий commit объекта gitlink не загружается. Фильтры, активные `.gitattributes`, перенаправления ODB/config, общедоступные Git-области и неоднозначные пути закрывают подготовку отказом. Submodule не инициализируются и не обновляются. `GIT_OBJECT_DIRECTORY`, alternates и `reset --hard` не используются.

## Проверка и свежий повтор

```sh
python3 -I -S -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/подготовка_кандидата_базиса.py \
  проверить --вход '<вход.json>' --назначение '<selector-назначения.json>' \
  --план '<план.json>' --выбор '<selector-выбора.json>'
```

Проверка повторно вызывает неизменённую production-проверку stage0/W/T и шести защищённых целей. Квитанция выдаётся только после полной сверки; та же сверка повторяется после её долговечной публикации, перед терминальным намерением.

Для проверки replay запустите прежнюю команду `применить` новым процессом. Только точное завершённое намерение, каноническая квитанция и всё ещё точный результат допускают `без_повторных_эффектов: true`. Повтор читает данные и не вызывает импорт, checkout, изменение ref или коммит.

Код 2 означает отказ. После возможного эффекта сохраняются намерение, достигнутая фаза и фактическое состояние. Живой замок, незавершённое намерение, неизвестный остаток, утраченная либо подменённая квитанция запрещают слепой повтор. Не удаляйте эти свидетельства и не выполняйте автоматический reset: ROOT сначала разбирает их без записи и отдельно выбирает восстановление.

## Адресные проверки и профиль

Тесты требуют `FUM_C572_ROOT`, указывающий на цельный экспорт указанного commit. Это ASCII-имя переменной среды сохраняется для совместимого запуска из POSIX shell. Отсутствие подготовленной зависимости — ошибка setup, а не RED функции. Запускайте команды через штатную отчётную обёртку текущего Журнала v4:

```sh
python3 -B -m unittest discover -s Инструменты/fum-svyaznostj-rabochej-sessii/tests \
  -p test_подготовки_кандидата_базиса.py
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/tests/профиль_подготовки_кандидата_базиса.py \
  --каталог-raw '<новый-приватный-каталог>' --выход '<новый-профиль.json>'
```

Матрица использует настоящие независимые и linked Git-деревья, исходное отсутствие T в обычной ODB, независимый выбор, public consumer, production-проверку и свежий повтор. Отдельно проверяются подмены источников, коллизии, held lock, пять фаз отказа и поздний дрейф при квитанции. Старые схемы `.12/.14` не изменяются.

Профиль выполняет три повтора на одном K/R/T; в каждом используются свежие процессы плана, применения, проверки и replay. Setup и запись независимого ROOT-выбора измеряются отдельно и исключаются из фаз. `--профиль` направляет в stderr длительности, CPU процесса и детей, число subprocess, tree/blob и логические байты предмета по фазам. Вложенные интервалы не суммируются как независимые затраты; логические байты не являются измерением физического дискового I/O. Результаты малой фикстуры не обещают ускорения production и не измеряют Creator или реальный B.

Для сравнения новой реализации с прежним измерением передайте `--история '<первая-приватная-фикстура-прежнего-профиля>'`. Профилировщик использует сохранённые исходную историю и решения, создаёт новые независимые candidate-клоны и проверяет прежний K/R/T. Старые RAW и профили не переписываются. Собственные тяжёлые проверки во время измерения не запускаются; файловый кэш ОС не сбрасывается.
