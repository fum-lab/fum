# Продолжить открытую подготовку ROOT

Автоматизация восстанавливает существующую подготовку контрольной точки ROOT после отказа до объявления готовности. Она принимает исправленный рецепт проверок, обновляет выбранные управляемые составы карточек штатным обновителем и выполняет новый набор проверок. Успех означает первую строгую готовность. Создание коммита выполняется отдельной штатной командой.

Контракт `fum.продолжение-открытой-подготовки-ROOT.1` доступен через [CLI повторной подготовки](scripts/повторная_подготовка_этапа.py). Контракт повтора после действительного отзыва `fum.повторная-подготовка-ROOT.1` сохраняет своё поведение. [Отдельный планировщик](scripts/продолжение_открытой_подготовки.py) сверяет живые HEAD, ref и родителей до первого чтения terminal history и проверяет открытое состояние до первого эффекта.

## Подготовить вход

Приватные входы — обычные файлы вне любого Git checkout с точными абсолютными физическими путями. Выбранные JSON имеют режим `0600`, сохранённый исходный план — `0400`. Родительские каталоги новых выходов, включая штатное назначение готовности, заранее существуют. Автоматизация сохраняет один результат эпизода рядом с этим назначением и не создаёт каталоги Журнала.

| Поле | Значение |
| --- | --- |
| `схема` | `fum.продолжение-открытой-подготовки-ROOT.1` |
| `прежняя_подготовка` | Выбранные `путь` и сырой `sha256` stock `.7`, созданной из ROOT `.5` |
| `прежний_вход` | Выбранные `путь` и `sha256` первоначального входа ROOT-фасада |
| `прежний_план` | Выбранные `путь` и `sha256` первоначального плана `0400` |
| `новые_выходы` | Восемь различных новых приватных назначений из таблицы ниже |
| `новые_проверки` | Конечный список: `идентификатор`, `порядок`, `название`, `класс`, `аргументы`; число первоначальных предметных проверок сохраняется |
| `новая_связность` | Новые `идентификатор` и `порядок` штатной связности |
| `новый_состав` | Точный конечный T: прежние фактические цели и v4, выбранные запросы и отчёты, новые будущие v4 |
| `наполнение` | Выбранные `путь` и `sha256` stock `fum.наполнение-карточки.1`; разрешение связывает новый файл T и SHA его канонических JSON-байтов |
| `составы` | Объекты `запрос`, сырой `sha256`, `режим`, выбранное `разрешение` и новый приватный `план` для stock updater |
| `закрепления` | Независимые `HEAD`, `ref`, `родители`, полный `v4`, `история_модели`, `курсор_модели`, `источник_модели` |

История и курсор закрепляются объектами `sha256` и `режим`. Источник модели дополнительно содержит точный `путь`. У каждой фактической v4 закрепляются `путь`, `идентификатор`, `порядок`, `sha256`, `режим`. UUID новых запусков различны, ранее не использованы; номера начинаются с фактического max+1 без пропусков. Наполнение перечисляет в `ожидаемых_целях` только новые v4 в том же порядке.

| Роль нового выхода | Назначение |
| --- | --- |
| `вход_коммита` | Новая ROOT `.5` с исправленным T |
| `вход_фасада` | Новый рецепт стадий |
| `наполнение` | Технические байты наполнения |
| `разрешение` | Канонический JSON-массив T |
| `план_наполнения` | Новый immutable stock fill-plan `0400` |
| `сообщение` | Сообщение будущего коммита |
| `подготовка` | Результат stock `подготовить-повтор` |
| `квитанция` | Назначение отдельного создания коммита |

Разрешение состава — выбранный файл `fum.разрешение-состава-карточки.1` с точными задачей, запросом, корнем, веткой и исходным коммитом. Он включает свой запрос и отчёт и покрывает фактический dirty-состав в пределах T. Для предыдущего запроса используйте фактические цели: отсутствующие v4 другого запроса туда не включаются. Текущий fill позднее добавит конечные будущие ссылки. Дословные сообщения, навигация и байты за пределами управляемого блока сохраняет stock updater; обычное recency обновляет разрешённые метаданные. Исторические отчёты исключены из разрешения recency-записи.

## Построить и исполнить план

Из физического корня своего дерева выполните `план --вход <приватный-вход>`. Сохраните stdout как канонический JSON во внешний обычный файл, установите `0400` и независимо вычислите SHA-256 точных байтов. Проверьте T, argv, UUID, составы и назначения. Затем вызовите:

```text
python3 -B Инструменты/fum-svyaznostj-rabochej-sessii/scripts/повторная_подготовка_этапа.py выполнить --вход <приватный-вход> --план <приватный-план> --sha256 <сырой-SHA256-плана>
```

До резерва повторно проверяются план, живые Git-адреса и индекс, выбранные байты и отсутствие обеих квитанций и готовности. Общая проверка ссылок выполняется после создания свежих свидетельств. Стадии: stock повторный prepare, выбранные составы, fill, Журнал, recency, точное staging, терминальные предпросмотры, реальные проверки и связность, read-only замыкание, первый ready. Каждый переход сверяет старые v4, модель, источник, курсор и исторические отчёты. Тип исторического отчёта проверяется до чтения: именованный канал или иной необычный файл вызывает отказ. Полный результат сохраняется приватно; stdout содержит компактные события и код.

Код `0` подтверждает готовность данного снимка. Перед последующим созданием коммита проверьте ready штатным читателем. Код `1` означает отказ; некорректный CLI даёт `2`. При отказе после начала эффекта полученные результаты сохраняются. Состояние `начато` означает неизвестный исход. Существующий результат эпизода запрещает повторный эффект, включая смену UUID, выходов и упаковки старой подготовки. Не удаляйте этот файл ради повторного запуска; передайте исход владельцу задачи.

## Воспроизвести проверки и профиль

[Смысловые тесты](tests/test_продолжения_открытой_подготовки.py) запускаются отчётной обёрткой через `python3 -B -m unittest discover -s Инструменты/fum-svyaznostj-rabochej-sessii/tests -p test_продолжения_открытой_подготовки.py`. Регрессия старого пути выбирает `test_реальный_отзыв_запуски_поколение1_и_неизменная_модель` через unittest `-k`.

[Парный профиль](tests/профиль_продолжения_открытой_подготовки.py) вызывается через ту же обёртку с `--выход <новый-файл-профиля> --повторы 3`. Для каждого образца отдельный процесс сначала прогревает тот же путь. Измеряются полный интервал от генерации плана до сохранения результата, время процесса, подготовки фикстуры и стадий. Самостоятельная ручная композиция не вызывает новые planner/execute/стадии. Равенство планов проверяется на одном seed; результаты сравниваются по явной нормализации путей и выбранных UUID, сырые SHA готовности и v4 сохраняются отдельно. Максимумы памяти процесса и дочерних процессов не складываются и не представляют RSS всего дерева. Версии, источники, политики и runtime закрепляются до и после серии; вложенные медианы не суммируются.

Даты всех настоящих bootstrap Git-команд фикстуры одинаковы; HEAD и оба родителя сравниваются буквально. Полные результаты сохраняются приватно до очистки фикстуры. stdout и stderr процессов пишутся сразу в приватные файлы `0600`, до разбора JSON выполняются fsync и чтение обратно. При SIGINT родителя worker получает мягкое прерывание собственной группы; ограниченное ожидание сменяется TERM/KILL при необходимости. Наблюдённая длительность и текущие каналы сохраняются, частичный образец не становится принятой парой. Ошибка сохранения отражается отдельно от исходного прерывания с фактическим состоянием fsync; исходный обработчик SIGINT восстанавливается после попытки записи отчёта. Публичный артефакт содержит SHA, размеры, стадии и частичные образцы. Неполная или несопоставимая пара вызывает отказ; при любом отказе серия сохраняется без итогов сравнения.

Профиль охватывает открытые обычную и merge-фикстуры. Время человека, живой ROOT, полный Q и завершение постоянной задачи не измеряются. Решение об ускорении принимается по сопоставимому результату; малая локальная серия не доказывает ускорения полного конвейера.
