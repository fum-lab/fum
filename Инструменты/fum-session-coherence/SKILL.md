# FUM Session Coherence

Этот навык описывает локальную [автоматизацию FUM](../../Глоссарий/автоматизация-FUM.md), которая проверяет, что [рабочая сессия](../../Глоссарий/рабочая-сессия.md) связана с [памятью FUM](../../Глоссарий/память-FUM.md) как воспроизводимая цепочка:

исходный запрос -> затронутые файлы -> журнал -> проверки -> коммит.

## Когда использовать

Используй эту автоматизацию перед коммитом рабочей сессии, влияющей на проект, после запуска `fum-md-recency` и после того как файл запроса уже содержит разделы `## Использованные инструменты`, `## Повлиял на файлы` и `## Проверки`.

Автоматизация особенно полезна, когда сессия меняет несколько областей памяти: `Документация/`, `Глоссарий/`, `Инструменты/`, `Планирование/`, `Запросы/` и `Журнал/`.

## Команда запуска

```bash
python3 Инструменты/fum-session-coherence/scripts/check-session-coherence.py \
  --request Запросы/<YYYY-MM-DD_HH-MM-SS_MSK>_<краткое-название-запроса>.md
```

По умолчанию проверка читает `git status --short --untracked-files=all` через `git -c core.quotepath=false`, чтобы пути на кириллице сравнивались с разделом `## Повлиял на файлы`, а новые каталоги раскрывались до конкретных файлов.

Для изолированной проверки файлов и ссылок без Git-состояния можно использовать:

```bash
python3 Инструменты/fum-session-coherence/scripts/check-session-coherence.py \
  --request Запросы/<YYYY-MM-DD_HH-MM-SS_MSK>_<краткое-название-запроса>.md \
  --skip-git-status
```

## Что проверяется

- Имя и заголовок файла запроса соответствуют формату `YYYY-MM-DD_HH-MM-SS_MSK_<краткое-название-запроса>`; начиная с запроса `2026-07-02_23-01-25_MSK_обновить-правило-именования-запросов.md` короткое название должно начинаться с глагола в инфинитиве, а исторические файлы до этого правила остаются допустимыми для обратной совместимости.
- Раздел `## Навигация по запросам` текущего запроса указывает на правильные предыдущий и следующий запросы, а соседний запрос ссылается обратно.
- Для запроса существует файл `Журнал/<YYYY-MM-DD_HH-MM-SS_MSK>_<краткое-название-запроса>.md` с ссылкой на исходный запрос.
- Раздел `## Использованные инструменты` присутствует, содержит список и ссылку на [реестр системных приложений и инструментов](../реестр-системных-приложений-и-инструментов.md). Начиная с запроса `2026-07-10_05-59-58_MSK_уточнить-учёт-версий-ChatGPT-и-Codex.md` общая запись `Codex - версия не раскрывается средой` отклоняется: приложение, runtime, CLI, модель и контракты агентской сессии должны быть квалифицированы раздельно.
- Раздел `## Повлиял на файлы` содержит локальные Markdown-ссылки на затронутые существующие файлы, включая текущий запрос и журнал. Для отсутствующей после текущей сессии цели используется строка с префиксом `- Удалённый файл:` и путём в обратных кавычках; она учитывается при сопоставлении с Git-состоянием без создания битой Markdown-ссылки.
- Локальные Markdown-ссылки во всём репозитории указывают на существующие цели, а регистр каждого компонента пути совпадает с реальным именем файла или каталога; внешние ссылки не проверяются.
- Каждый файл `Вопросы и ответы/*.md`, кроме README, содержит непустой раздел `## Вопрос`, последний содержательный символ которого равен `?`. Это формальная защита наблюдаемого признака, а не лингвистическое доказательство вопросительной семантики.
- Затронутые Markdown-файлы вне `Запросы/` не содержат похожий на пользовательский мета-запрос о правилах [памяти FUM](../../Глоссарий/память-FUM.md), порядке [рабочей сессии](../../Глоссарий/рабочая-сессия.md), `AGENTS.md` или `Запросы/` без ссылки на конкретный файл исходного запроса.
- Затронутые Markdown-файлы вне `Запросы/` не начинаются со справочного блока происхождения: `Источники требований`, `Источники`, `Опорные документы`, `Опорные материалы`, `Внешний материал`, `Затронутая документация` и похожие блоки должны идти после основного содержания перед `FUM-MD-RECENCY`.
- Затронутые Markdown-файлы не содержат Mermaid-подписей узлов, которые начинаются с Markdown-маркера списка вроде `1. `, `1) `, `- `, `* ` или `+ `, потому что Obsidian может отображать такие узлы как `Unsupported markdown: list`.
- Автоматизация `fum-md-recency` подтверждает свежесть служебных recency-меток и индекса `Индексы/markdown-файлы-по-времени-редактирования.md`, если этот локальный инструмент есть в репозитории.
- Все пути из текущего `git status --short` перечислены в разделе `## Повлиял на файлы`; лишние временные файлы, кэши и отладочные артефакты вызывают ошибку.

## Проверки автоматизации

Локальные тесты запускаются без сети и секретов:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s Инструменты/fum-session-coherence/tests -p 'test_*.py'
```

Тесты фиксируют базовый контракт: успешная сессия проходит при перечисленных изменённых файлах, новые заголовочные имена запросов начинаются с инфинитива, историческая общая запись версии Codex сохраняет обратную совместимость, буквальный вопрос с `?` допустим, а README раздела вопросов и ответов не считается карточкой. Для новых запросов неквалифицированная запись версии, отсутствие журнала, битая Markdown-ссылка, Markdown-ссылка с неверным регистром пути, вопросно-ответный файл без вопроса или без конечного `?`, возможный незаведённый мета-запрос без ссылки на `Запросы/`, верхний справочный блок происхождения, Mermaid-подпись узла с Markdown-маркером списка, устаревшая recency-проверка и неожиданный путь в Git-состоянии дают ошибку. Отдельные тесты подтверждают, что маркер действительно удалённого файла участвует в проверке Git-состояния без фиктивной ссылки, а для существующей цели отклоняется.

## Граница автоматизации

Скрипт проверяет структурную связность рабочей сессии, но не подменяет смысловую проверку документации. Агент по-прежнему отвечает за корректность требований, публикационную чистоту содержания, полноту списка инструментов, уместность затронутых файлов и качество коммита.

Проверка локальных Markdown-ссылок и регистра их путей выполняется по всем Markdown-файлам репозитория, чтобы ошибка, скрытая на нечувствительной к регистру файловой системе, не оставалась в памяти до случайной правки конкретного файла.

Проверка каталога `Вопросы и ответы/` также выполняется глобально, а не только по списку файлов текущей сессии. Она проверяет формальный буквальный признак вопроса и не оценивает качество или полноту содержательного ответа.

Проверка мета-запросов является эвристикой. Она ищет формулировки о вопросе, уточнении, ответе или проверке пользователя в контексте правил памяти, порядка рабочей сессии, `AGENTS.md` или `Запросы/`; это ранний сигнал, а не доказательство, что запрос действительно пропущен.

Проверка Git-состояния сравнивает только пути. Она не решает, нужно ли включать конкретное содержимое в коммит; перед staging агент всё равно должен просмотреть diff и исключить секреты, локальное состояние и машинный мусор.
