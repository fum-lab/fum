# Конечный запуск двух производных слоёв

Адаптер подготавливает ровно две отдельные задачи одного `FUM-STEP-0233`. Он сохраняет попытку **до** обращения к Codex Desktop и после перезапуска запрещает второй внешний вызов той же попытки. Python выполняет локальные стадии; официальный инструмент Desktop вызывает внешний адаптер возможностей. Расписание, dispatcher и автоматическое продолжение не создаются.

Это отдельный контракт `fum.запуск-двух-слоёв.1`. Паспорт `fum.конвейер-производных-веток.v1` сохраняет прежний смысл: его относительное `worktree` и строка `writer` не становятся наблюдёнными физическим путём и UUID. Существующий координатор учитывается буквально, например на `codex/derived-pipeline-v1`; переименовывать его в `codex/root` не требуется.

## Что сохраняется

Коммит постановки C содержит JSON-план и два непустых файла поручений. Его полный манифест связывает имена файлов с SHA-256 исходных байтов. Удерживаемая ветка запуска должна по-прежнему указывать на C. Она сохраняется до подтверждения первоначальной базы обеих задач: запоздавшая подготовка Desktop не должна получить уже сдвинутую вершину.

План имеет поля `схема`, `конвейер`, `шаг`, `слои`. Схема — `fum.план-запуска-двух-слоёв.1`; шаг — `FUM-STEP-0233`. Каждый из двух слоёв имеет:

| Поле | Значение |
| --- | --- |
| `слой` | Устойчивая уникальная идентичность |
| `каталог` | Непустой относительный путь с завершающим `/` |
| `роль` | Содержательное название отдельной задачи |
| `ветка` | Полный `codex`-ref, выведенный из каталога |
| `зависит_от` | Идентичности других слоёв, без цикла |
| `поручение` | Относительный путь файла внутри манифеста C |

Первый контракт отклоняет пересекающиеся каталоги, в том числе с учётом регистра и Unicode-нормализации. Git проверяет допустимость ref; перед первой внешней попыткой проверяется его занятость и конфликт префиксов. После сохранения попытки появление её собственной ветки не разрешает повторное создание.

Приватный вход имеет поля `схема`, `задача`, `постановка`, `план`, `проект`, `источник`, `решение`. `постановка` содержит точные `коммит`, `ветка`, `файлы`; `план` указывает на JSON-план из манифеста. `проект` должен совпадать с `projectId` подтверждаемого [решения приёма](../fum-reyestr-planirovaniya/приём-направлений.md). Исходный JSONL, состав сообщений, поздние уточнения и полномочие создать задачи проверяются существующим читателем. Смысловое решение принимает корень; совпадение ключевых слов не является разрешением.

Ключ запуска зависит от корневого UUID, идентичности конвейера и шага. Ключ попытки добавляет `слой`. C, путь входного JSON, хэш манифеста и новый процесс не создают новую идентичность. Изменение закреплённого содержания закрывает прежний запуск; незавершённая попытка не удаляется. Другой запуск с теми же ветками отклоняется.

Входной манифест может включать принятые файлы `Память/`: [его читатель](../fum-reyestr-planirovaniya/входной-манифест.md) проверяет точные обычные Git-объекты, сохраняя отдельные ограничения записи результатов.

## Локальные команды

CLI находится в `scripts/запустить-слои.py`. Нативный `CODEX_THREAD_ID` должен совпадать с `--задача`. Входные JSON и полные ответы хранятся вне Git; stdout с приватными сведениями также сохраняется туда.

Все команды получают общий префикс:

```text
python3 -B Инструменты/fum-konvejyer-proizvodnyikh-vetok/scripts/запустить-слои.py --корень-репозитория . --задача <корневой-UUID>
```

| Команда | Дополнительные аргументы | Результат |
| --- | --- | --- |
| `предпросмотр` | `--вход <JSON>` | Проверенный план и его SHA; без создания состояния |
| `подготовить` | `--вход <JSON> --sha256 <SHA>` | Неизменяемый план в прежнем долговечном хранилище |
| `допустить` | `--вход <JSON> --слой <ID>`; для второго слоя `.7` также `--источник-первого-ребёнка <JSONL>` | Сохранённая попытка и точные аргументы `create_thread` |
| `сохранить` | `--запуск <ключ> --слой <ID> --попытка <UUID> --ответ <JSON>` | Полный ответ, включая неоднозначные идентификаторы |
| `наблюдать` | `--запуск <ключ> --слой <ID> --корень-ребёнка <путь> --задача-ребёнка <UUID> --источник <JSONL>` | Проверенное раннее подтверждение ребёнка |
| `состояние` | `--запуск <ключ>` | Читающий снимок попыток и наблюдений |
| `область` | `--запуск <ключ> --слой <ID> --назначение <путь-в-C> --источник <JSONL-ребёнка>` | [Наблюдённая область](область-писателя.md) без разрешения записи |
| `завершение-предпросмотр` | `--вход <JSON>` | [Конечный переход неудачного пилота](завершение-неудачного-запуска.md), без записи |
| `завершить` | `--вход <JSON> --sha256 <SHA>` | Отдельная квитанция; прежние попытки неизменны |

Внешняя сторона использует существующий [адаптер возможностей](../fum-reyestr-planirovaniya/scripts/адаптер-codex.js): локальный допуск → официальный вызов → локальное сохранение. Вызов выполняется только при `разрешён_вызов=true`; повтор возвращает прежнюю попытку с `false`, даже если ответ потерян. Сбой транспорта требует наблюдения существующей задачи, а не удаления попытки.

Перед запуском исполняемый набор должен находиться в самом C: применён прежний допуск происхождения кода и дополнительная проверка модулей, загруженных после его снимка. Незакоммиченный исполнитель не получает право внешнего вызова. Версии `.1`–`.4` сохраняют узкую совместимость раннего подтверждения `gpt-6-astra/low`.

Версия запуска `.5` закрепляет `gpt-6-luna` с `thinking=low`, версия `.6` — `gpt-6-sol` с `thinking=ultra`. Оба вызова получают выбранную пару. Она фиксируется в пакете и блоке первоначального назначения: `.2` для Luna/Low, `.3` для Sol/Ultra. Координатор, собственный читатель ребёнка и проверка остановки сверяют фактические `model` и `effort` с сохранённым профилем. Версии `.1`–`.4` продолжают назначать `gpt-6-astra/low`; сохранённые попытки не переписываются. Другие сочетания модели и усилия не разрешены. Общий ранний допуск поддержанной пары сам по себе не подтверждает, что эта пара была назначена конкретному ребёнку.

## План и наблюдение

Версия `.7` сохраняет Sol/Ultra и точное назначение `.3`, но требует
последовательность `события → сообщения` и [проверку первоначальных прав](права-запуска.md).
Сам ребёнок выполняет `проверить-права --источник <JSONL>` до ref и ранней квитанции;
команда использует его собственный `--задача`, не UUID корня. Координатор перед
вторым допуском повторяет сверку первого ответа, раннего наблюдения и того же
префикса Native policy. Неизвестные права не становятся разрешающими из текста
ответа. Прежние `.1–.6` сохраняют точные поручения и условия запуска.

До фактического подтверждения `наблюдения[слой]` равно `null`. `clientThreadId` остаётся свидетельством подготовки. Подтверждение требует настоящих UUID, физического корня, ожидаемого ref, начального C, первой модели и точного нативного поручения корневой задачи. Одна задача или дерево не могут подтверждать два слоя.

Полный MCP-ответ и наблюдение проверяются в обоих порядках. Поздний ответ с чужим `threadId` не может противоречить уже сохранённому наблюдению; проверка выполняется под тем же замком до записи ответа. Точный повтор сохраняет прежние байты.

## Проверки и граница результата

Адресные тесты — `tests/test_запуска_слоёв.py`. Они используют настоящий временный Git, linked worktree, первичные JSONL и прежнее хранилище; только допуск совпадения checkout исполняемых инструментов подменён фикстурой, поскольку тестовый Git не содержит весь FUM. Тесты не доказывают работу внешнего Desktop. Этот допуск должен отдельно пройти на реальном C.

`tests/профиль_запуска_слоёв.py --выход <новый JSON>` измеряет предпросмотр, сохранение плана, первую попытку и повтор. Подготовка Git исключена. Измеритель сохраняет размер источника и SHA исходников; маленькая фикстура не доказывает скорость на многогигабайтной истории.

Перед реальным пилотом ещё требуются сверка имён с закреплённым LinguisticKit, конкретные поручения от принятого C и согласованный способ ведения общих индексов. Запуск не разрешает детям писать общие индексы. Приёмка результатов, merge-доставка и обратная квитанция остаются отдельными последующими границами; данный адаптер их не объявляет выполненными.
