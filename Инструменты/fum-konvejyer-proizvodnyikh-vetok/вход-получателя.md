# Единый вход получателя интеграции

Получатель читает адресное нативное поручение и получает собственную пару Журнала вместе с входом для уже существующего создателя коммита. Прежние слияние, установка Журнала и восстановление квитанции используются через один CLI:

```bash
python3 -B Инструменты/fum-konvejyer-proizvodnyikh-vetok/scripts/приём_получателя.py --вход <приватный-файл.json>
```

Технический вход проверен на открытых фикстурах. Разрешение реальным дочерним задачам применять его требует отдельного включения правил приёма в базу C. Старые остановленные задачи этим изменением не возобновляются.

## Вход

Файл находится вне Git. Схема `fum.вход-дочернего-приёма.1` принимает ровно следующие поля:

| Поле | Значение |
| --- | --- |
| `схема` | Точное имя версии выше |
| `источник` | Абсолютный путь первичного JSONL самого получателя |
| `текст` | Полное каноническое поручение адресного приёма |
| `план` | Существующий план обратной доставки |
| `свидетельство` | Первичные свидетельства остановки, ожидания, отправки и получения поручения |
| `реестр` | Приватный реестр владельцев, связанный с планом |
| `коммит` | Ровно `имя_автора`, `заголовок`, `описание`; роль автора проверяется до начала эпизода |

Корень берётся из физического рабочего каталога, исполнитель — из `CODEX_THREAD_ID`. OID, ref, UUID проверки и четыре пути J вычисляются по проверенному поручению. Передать готовое основание, вызываемую функцию, путь модуля или дополнительную область записи нельзя. Дубли ключей и неизвестные поля отклоняются.

## Первый вызов и повтор

Первый вызов проверяет нативный источник и происхождение исполняемого кода из C, сохраняет точные параметры будущего коммита, применяет существующий механизм слияния и устанавливает новую пару Журнала. Ответ содержит `вход_коммита` схемы `.4`, будущий адрес `подготовка` и состояние `журнал-установлен`. HEAD остаётся H, MERGE_HEAD равен S. Собственная добавка ограничена четырьмя назначенными файлами; импортированный S не становится областью редактирования.

Далее получатель заполняет собственные запрос и отчёт, готовит историю модели существующим `создание_коммита.py подготовить --вход`, выполняет единственную назначенную адресную проверку и создаёт R через прежние `готово` и `создать`. Этот CLI сам не выполняет первую попытку создания R, push или финальную приёмку задачи.

Повтор с тем же входом находит прежний эпизод. Уже заполненный J проверяется своим механизмом и не заменяется шаблоном. Другой текст, срез, план, свидетельство или метаданные коммита того же эпизода отвергаются. Потерянный вход начатого эпизода закрывает допуск.

Если квитанция создания R уже существует, сначала проверяются сохранённые параметры и точная подготовка, затем используется штатное восстановление результата. Новое требование HEAD=H и повторное слияние не выполняются. Отсутствие квитанции, неподтверждённый исход процесса или несовпадающий объект не дают права повторить эффект.

## Проверка и профиль

Холодный процесс проверяет полный путь до R, сохранность заполненного отчёта, запрет лишних полей, неверной роли и неподтверждённой отправки, подмены параметров, пятого файла J и импортированных байтов. Повтор после R проверяется с запрещённым свежим читателем H и запрещённым новым merge. Отдельные проверки сохраняют прежний контракт эпизодов.

Профиль внутри `test_входа_приёма.py` печатает `FUM-PROFILE`: хэши кода, стадии первого входа, повторного чтения J и создания R. Первый вход выполняет эффект, повтор читает готовое состояние; их длительности нельзя выдавать за ускорение одной операции. Ранний отказ по неверной роли исключает ненужный запуск всего приёма. Дальнейшие сокращения проверок требуют отдельного доказательства сохранности допуска.
