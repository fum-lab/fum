# Получить своё назначение и подготовить Журнал

Писатель читает первоначальное поручение из собственного JSONL и проверяет его
по коммиту постановки C. Живой checkout координатора и его приватное состояние
для этого не нужны. Команда возвращает область и её снимок. Отдельный
[прототип записи и конечной передачи](передача-слоя.md) проверяется на фикстурах;
согласование действующих правил и реальный пилот ещё не выполнены.

## Подготовка координатора

Вход `fum.запуск-двух-слоёв.2` отличается от [v1](запуск-двух-слоёв.md) обязательным
полем `назначение`: это путь [назначения областей](область-писателя.md) в полном
манифесте C. План, назначение и поручения обоих слоёв входят в манифест. Проверка
каталогов выполняется до внешней попытки. Имя новой папки Журнала должно подходить
каноническому генератору: временной префикс и метка с русского инфинитива.

Сформированный prompt содержит канонический завершающий блок с корневым UUID,
C, полным манифестом, путём плана, слоем и назначением. Этот блок входит в
сохраняемый хэш аргументов запуска. Версия не меняет стабильный ключ запуска:
смена версии, C или назначения не создаёт вторую попытку для прежнего ключа.
Вход v1 и байты его prompt сохраняют прежнее поведение.

## Раннее подтверждение ребёнка

После проверки собственных UUID, дерева, начального HEAD и ref ребёнок выполняет
указанный в v2 поручении `подтвердить-начало --с-поручением`. Новая квитанция
`fum.начальная-база-задачи.2` закрепляет также отправителя, хэш всего prompt и
префикс первичного JSONL до первого `create_thread`. Она создаётся до содержательной
записи на чистом C; старую квитанцию v1 нельзя дополнить задним числом.

Чтение выполняется из собственного checkout, с настоящим UUID ребёнка в среде:

```text
python3 -B Инструменты/fum-konvejyer-proizvodnyikh-vetok/scripts/получить-назначение.py --корень-репозитория . --задача <свой-UUID> --источник <свой-первичный-JSONL>
```

Код 0 возвращает `fum.дочернее-назначение-слоя.1`; код 2 означает отказ. Вывод
с локальными путями сохраняется приватно. `разрешение_записи=false`: это результат
проверки назначения, а не новый режим допуска записи. Произвольного JSON-файла
с разрешёнными каталогами команда не принимает.

Проверяются полный OID до использования в Git, отправитель, собственные UUID/cwd,
начальный C, ранняя квитанция, ожидаемый ref, полный текст поручения из C и снимок
изменений. Повторные JSON-ключи, неканонический блок, позднее поручение и подмена
первоначального назначения дают отказ. Перед возвратом повторяются чтения.

## Подготовить собственную пару

Программный API `журнал_слоя.подготовить(корень, UUID_ребёнка, JSONL, сообщения)`
возвращает план только `запрос.md` и `отчёт.md` в назначенной папке. Он повторно
проверяет назначение, использует общий корневой `Codex-Thread-ID` и
`request_folder_layout.подготовить_собственную_пару`. Общая навигация не сканируется
и не меняется; оба её направления явно помечаются отложенными до передачи
координатору. Нельзя считать их отсутствующими.

План ничего не устанавливает: `разрешение_установки=false`. Проверка происхождения
переданных сообщений пока относится к отдельному допуску, что отражено полем
`происхождение_сообщений_проверено=false`. Нативное поручение координатора не
выдаётся за сообщение человека. Свободно переданный список сообщений не даёт
разрешения его сохранить.

После будущей передачи координатор должен заново вычислить навигацию по уже
объединённому Журналу. Прежний `reindex` меняет только индекс и этого не заменяет.
Установка пары, собственные recency-метки и дочерний коммит реализованы отдельным
программным API. До применения к реальным писателям остаются согласование правил
и настоящий пилот Desktop.

## Граница проверки

Это кооперативная проверка одного писателя, а не защита от произвольного кода,
переписывающего одновременно JSONL, Git и приватные квитанции. Две сверки не
доказывают отсутствие промежуточного изменения. Остальные ограничения снимка
перечислены в [контракте области](область-писателя.md).
