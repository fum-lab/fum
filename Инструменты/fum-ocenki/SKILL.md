# FUM Estimates

Этот навык описывает локальную [автоматизацию FUM](../../Глоссарий/автоматизация-FUM.md), которая создаёт и проверяет оценочные материалы в `Оценки/`. Оценка здесь понимается как воспроизводимый аналитический снимок: она не заменяет фактический тайм-трекинг, финансовую смету или требования, но фиксирует вопрос оценки, состояние репозитория, методику, диапазоны, допущения, ограничения точности и оформление результата.

## Когда использовать

Используй эту автоматизацию, когда нужно создать, обновить или проверить типовой файл в `Оценки/`: трудоёмкость, масштаб работ, ориентировочную стоимость, сложность сопровождения или другую оценку, где важны повторяемая методика и сравнимость результатов.

Не используй её как замену смысловой ответственности агента. Скрипт проверяет структуру, происхождение и наличие заявленных элементов, но численные диапазоны, допущения и выводы всё равно должны быть объяснимы по источникам и контексту задачи.

## Входы

Автоматизация принимает JSON-конфигурацию:

```json
{
  "title": "Оценка трудоёмкости текущей памяти FUM",
  "request_file": "Запросы/2026-06-29_17-50-10_MSK.md",
  "automation_file": "Инструменты/fum-ocenki/SKILL.md",
  "question": "Сколько человеко-часов потребовалось бы для сопоставимой работы?",
  "unit": "человеко-часов",
  "point_estimate": 160,
  "range": {"low": 120, "high": 220},
  "summary": "Краткий вывод оценки.",
  "scope": "Граница оцениваемого результата.",
  "snapshot": {
    "date": "2026-06-29",
    "metrics": [
      {"name": "Отслеживаемые файлы", "value": "332"}
    ],
    "notes": [
      "Снимок зафиксирован при создании оценки."
    ]
  },
  "methodology": [
    {
      "name": "Разложение по видам работы",
      "description": "Итоговая оценка собирается из диапазонов по компонентам."
    }
  ],
  "breakdown": [
    {
      "name": "Написание и связывание документации",
      "low": 40,
      "high": 75,
      "comment": "Документация, глоссарий и планирование."
    }
  ],
  "assumptions": [
    "Оценивается сопоставимое создание результата, а не фактическое время сессий."
  ],
  "precision_limits": [
    "Оценка не является фактическим тайм-трекингом."
  ],
  "result_format": [
    "Ключевой вывод стоит в первых абзацах."
  ],
  "interpretation": [
    "Краткая человекочитаемая интерпретация результата."
  ]
}
```

`request_file` и `automation_file` указываются нормализованными POSIX-путями от корня репозитория. Абсолютные, выходящие из репозитория, URI-, home-, Windows/UNC- и символические формы отклоняются до записи документа. Для воспроизводимых оценок предпочтительно хранить конфигурацию в `Оценки/Автоматизации/`.

## Процедура

1. Сохрани исходный пользовательский запрос в `Запросы/` по правилам `AGENTS.md`.
2. Если нужен новый снимок текущего состояния репозитория, выполни:

```bash
python3 Инструменты/fum-ocenki/scripts/build-estimate.py snapshot \
  --output Оценки/Автоматизации/<имя-снимка>.json
```

3. Подготовь JSON-конфигурацию оценки: вопрос, единицы измерения, точечную оценку, диапазон, снимок репозитория, методику, разложение, допущения, ограничения и правила оформления результата.
4. Собери Markdown-файл:

```bash
python3 Инструменты/fum-ocenki/scripts/build-estimate.py build \
  --config Оценки/Автоматизации/<имя-конфигурации>.json \
  --output Оценки/<имя-оценки>.md
```

5. Проверь готовый файл:

```bash
python3 Инструменты/fum-ocenki/scripts/build-estimate.py validate \
  --config Оценки/Автоматизации/<имя-конфигурации>.json \
  --document Оценки/<имя-оценки>.md \
  --complete
```

6. Зафиксируй вызов автоматизации, конфигурацию, результат проверки и ограничения точности в файле исходного запроса рабочей сессии.

## Что проверяется

Валидатор проверяет:

- заголовок оценки;
- ссылку на исходный запрос;
- ссылку на автоматизацию;
- обязательные разделы `Снимок репозитория`, `Методика расчёта`, `Диапазоны`, `Допущения`, `Ограничения точности` и `Оформление результата`;
- наличие итогового диапазона и точечной оценки;
- наличие заявленных в конфигурации метрик снимка, методических шагов, компонент разложения, допущений, ограничений и правил оформления;
- отсутствие маркеров `ESTIMATE_TODO` при проверке с `--complete`.

## Проверки автоматизации

Локальные тесты запускаются без сети и секретов:

```bash
PYTHONDONTWRITEBYTECODE=1 python3 -m unittest discover -s Инструменты/fum-ocenki/tests -p 'test_*.py'
```

Тесты фиксируют базовый контракт: автоматизация создаёт оценочный Markdown-файл с обязательными разделами, принимает полный результат, сообщает об отсутствующем обязательном разделе и замечает потерянный итоговый диапазон.

## Граница автоматизации

Скрипт поддерживает проверяемую форму оценки, но не вычисляет смысловые коэффициенты автоматически и не гарантирует истинность чисел. Агент отвечает за выбор методики, корректность диапазонов, честность допущений, публикационную чистоту снимка, связь с источниками требований и фиксацию открытых вопросов, если оценка выявляет неоднозначность или противоречие.

Команда `snapshot` собирает только локально наблюдаемую статистику Git-репозитория: коммит, ветку, состояние рабочего дерева, число отслеживаемых файлов, Markdown-файлов, строк и слов. Если оценке нужны внешние данные, стоимость сервисов, трудозатраты людей или приватная история работы, они должны фиксироваться отдельным публикационно чистым источником или явно обозначаться как недоступная часть.
