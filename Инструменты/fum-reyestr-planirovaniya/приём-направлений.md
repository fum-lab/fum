# Приём направлений FUMA

Приём связывает подтверждённое сообщение, смысловое решение, собственный Журнал, уникальные номера и карточки с одной внешней попыткой Codex. Первый реальный приём математического направления подтверждён: сохранены официальный ответ, точное начальное поручение и раннее наблюдение базы новой задачи. Итоговая приёмка общего объёма FUM-STEP-0201 связывается с [закрытым допуском и сохранённым обязательством](../../Журнал/2026-09-11_10-00-32_MSK_завершить-приём-направлений-FUMA/отчёт.md); предметный результат каждой созданной задачи принимается отдельно.

## Обычный запуск

Работайте в своём worktree, в собственной ветке `codex/…` и открытой рабочей сессии Журнала. Для начала следующей сессии используется обычный `start` автоматизации структуры папок запросов. Закрытый отчёт не возобновляется.

Подготовьте приватный JSON входа вне публикуемого checkout. Он содержит путь первичного JSONL, UUID исходной задачи, решение, относительный путь собственного запроса, список создаваемых или обновляемых карточек и ранее согласованные номера либо `null`. Решение схемы `fum.решение-приёма.1` ссылается на конкретный экземпляр сообщения и полный рассмотренный контекст 0177. Агент отдельно определяет актуальность, поздние уточнения, смысл ответа, предметный объём и явное разрешение новой задачи. Автоматизация не выводит эти решения из ключевых слов.

Команда `Инструменты/fum-reyestr-planirovaniya/scripts/принять-направление.py` принимает общие параметры `--корень-репозитория` и `--задача`, затем одну операцию:

| Операция | Дополнительные параметры | Результат |
| --- | --- | --- |
| `подготовить` | `--вход` | Точная пара в Журнале, карточки, индексы и машинный реестр; сохранённое событие и свидетельства |
| `закрепить` | `--событие`, `--коммит`, `--ветка` | Проверенный манифест полного коммита постановки |
| `допустить` | `--вход` | Одна сохраняемая попытка и точные аргументы внешнего инструмента либо запрет повторного вызова |
| `сохранить` | `--событие`, `--попытка`, `--ответ` | Неизменяемая квитанция полного сырого MCP-ответа из приватного JSON |
| `подтвердить-начало` | `--источник`, `--коммит` | Раннее подтверждение собственной новой задачи до первой записи checkout |
| `наблюдать` | `--событие`, `--корень-задачи`, `--идентификатор-задачи`, `--источник` | Сверка фактического дерева, начальной базы и первой модели новой задачи |

Каждая команда исполняется отдельным процессом Python 3. Успех выводит один JSON в stdout; отказ возвращает код 2 с пояснением в stderr. Сам CLI не отправляет запросов Desktop и не запускает фоновую службу.

После `подготовить` проверьте точный результат, заполните отчёт, обновите recency и сохраните проверенный коммит своей ветки обычным порядком. В этот коммит должны входить исполняемые инструменты, пара Журнала, карточки, индексы и машинный реестр. Передайте полный OID и полный существующий ref в `закрепить`; перед вызовом они проверяются повторно. Сохранение карточки только в prompt или выбор default-ветки не дают допуска. До наблюдения новой начальной базы не двигайте ref постановки.

Подготовка сохраняет полные байты общих индексов и точные позиции пары в Журнале. Поэтому завершайте закрепление и внешнюю попытку одного направления до подготовки следующего в том же дереве. После подготовки сохраняйте текст перед вставленной парой неизменным; дополнения отчёта помещайте после неё. Новый этап получает новую папку Журнала. Предварительное выделение номеров само по себе не изменяет индексы.

## Исправление неготового местного приёма

Если первая файловая стадия полностью установлена, но настоящий сборщик реестра отклонил карточки, один раз можно явно исправить их содержание. Приём должен оставаться неготовым, без закреплённой постановки, наблюдения и любой внешней попытки. Первоначальные решение, поручение, номера, пути, карточки, индексы и пара Журнала сохраняются. Коррекция не меняет ID, заголовки и статусы и не создаёт новых карточек.

В приватном JSON подготовьте точный контракт:

```json
{
  "схема": "fum.исправление-плана-приёма.1",
  "событие": "<SHA-256 события исходного приёма>",
  "ожидаемый_план_sha256": "<канонический SHA-256 исходного объекта файлы>",
  "база": "<полный OID текущего этапа>",
  "ветка": "refs/heads/codex/…",
  "причина": "Исправить обратное отношение по действующему словарю.",
  "файлы": [{
    "путь": "Требования/🟡-существующая-карточка.md",
    "ожидаемый_sha256": "<SHA-256 точных исходных after-байтов>",
    "содержимое": "<полный исправленный UTF-8 текст карточки>"
  }]
}
```

Это форма контракта; значения в угловых скобках необходимо заменить проверенными значениями. Хэш плана вычисляется функцией `хэш` модуля `приём_направления` от первоначального объекта `файлы` сохранённого приёма. Полный OID текущего этапа передаётся явно и должен происходить от исходной базы приёма. Пока исправление не завершено, его база и ветка не меняются.

Вызовите из своего checkout:

```text
python3 -B Инструменты/fum-reyestr-planirovaniya/scripts/принять-направление.py --корень-репозитория . --задача <UUID своего корня> исправить-план --исправление <приватный JSON>
```

До карточечных эффектов команда сверяет весь первоначальный набор файлов, повторно получает настоящий отказ сборщика на исходном снимке и сохраняет его вместе с неизменяемым намерением исправления. Это новое диагностическое наблюдение, а не восстановленный текст прежнего отказа. Затем отдельными стадиями устанавливаются исправленные карточки и проверенный полный реестр. Только после долговечной записи реестра приём становится готовым. Закрепление и допуск используют исправленные карточки, сохраняя оригиналы как происхождение.

После прерывания повторите **ту же команду с тем же JSON** новым процессом. Допускаются только исходные и уже установленные исправленные байты; чужие изменения, сдвиг базы и появившаяся попытка закрывают продолжение. Обычная `подготовить` при незавершённом исправлении указывает на `исправить-план`. Точный повтор завершённого исправления при неизменном состоянии возвращает квитанцию без новой записи карточек. Новое исправление готового приёма запрещено.

Поддержана ровно одна коррекция. Если её собственные смысловые данные ошибочны и реестр снова отказывает, другое исправление автоматически не принимается: намерение и эффекты остаются доступными для отдельной сверки. Не редактируйте приватное состояние вручную и не вызывайте native при неготовом результате.

Адресная открытая проверка: `python3 -B -m unittest discover -s Инструменты/fum-reyestr-planirovaniya/tests -p test_исправления_приёма.py`. Небольшой профиль: `python3 -B Инструменты/fum-reyestr-planirovaniya/tests/профиль_исправления_приёма.py --выход <профиль.json>`. Оба запуска выполняются через отчётную обёртку своей сессии; сеть и внешняя задача не нужны.

## Внешняя граница Codex

Сохранённый `адаптер-codex.js` исполняется средой, имеющей три явно предоставленные возможности. `подготовить` вызывает одноразовую команду `допустить`; `исполнить` передаёт её аргументы официальному `create_thread` либо `send_message_to_thread` согласно сохранённой операции; `сохранить` сохраняет полный ответ через одноимённую CLI-команду. До создания проект проверяется официальным `list_projects`, включая `isGitRepository`. Это интерфейс возможностей среды, не отдельный Node-сервис с доступом к внутренней базе Codex.

Модель и рассуждение передаются явно: `gpt-6-astra`, `ultra`. Новая задача использует worktree и `startingState` с закреплённым ref. Первое поручение содержит путь постановки, полный коммит и команду раннего подтверждения. Начальный коммит берётся одновременно из нативной метаинформации JSONL и текущего чистого дерева; после начала работы он не восстанавливается по позднему HEAD. Позднее чтение требует уже сохранённого раннего подтверждения.

При прерывании между сохранением попытки и ответом повтор возвращает прежнюю попытку с `разрешён_вызов: false`. Не вызывайте инструмент снова по отсутствию задачи в кратком списке. Сохранённый `clientThreadId` означает незавершённое создание. Связывание результата требует точного первоначального нативного поручения от своего корня и раннего подтверждения базы, а не одного похожего названия. Если эти свидетельства недоступны, исход остаётся неизвестным.

Файлы приватного состояния и полные JSONL не публикуются. Допустимый итог наблюдения записывается в следующий открытый отчёт своей задачи; ни создание задачи, ни приём её постановки не означает исполнения всего предметного обязательства 0201.

## Локальная проверка

Из корня FUM запустите адресный набор через отчётную обёртку своей рабочей сессии:

```text
python3 -B -m unittest discover -s Инструменты/fum-reyestr-planirovaniya/tests -p test_приём_направления.py
```

Профиль на открытом входе запускается командой:

```text
python3 -B Инструменты/fum-reyestr-planirovaniya/scripts/измерить-приём.py --выход <профиль.json>
```

Он создаёт временный Git-репозиторий с 40 коммитами и измеряет 12 разных выдач пары STEP/REQ и 12 повторов. Подготовка не включена. Сам JSON содержит исходные интервалы, версию Python и SHA реализации; фикстура не требует сети и секретов.

## Сохраняемые границы

Состояние находится в отдельном приватном каталоге внутри фактического Git common-dir. Все связанные worktree получают один файл состояния и постоянный отдельный файл `flock`. Сканируются доступные ветки и их достижимая история, включая карточки, впервые добавленные слиянием. Сдвиг списка refs требует нового чтения. Проверенный снимок истории повторно используется только при совпадении всех refs/OID и SHA реализации. Исчезновение карточки или ветки не освобождает уже учтённый номер.

Ручной резерв импортируется с происхождением и остаётся занятым. Выделение группы номеров возвращается только после записи, синхронизации файла, атомарной замены и синхронизации каталога. Повреждённый или исчезнувший журнал не сбрасывается. Защита не обещает обнаружить согласованную замену всех приватных свидетельств владельцем машины и не координирует независимые клоны или ручных писателей, обходящих протокол.

Внешняя попытка сохраняется до вызова. При неизвестном исходе новое создание запрещено; сохранение того же полученного ответа можно повторить. Проверки источника и коммита выполняются под тем же замком до первой попытки. Независимый писатель JSONL не участвует в этой транзакции: атомарность интервала от последнего чтения до внешнего API не заявляется.

Файловая стадия сначала сохраняет точный план исходных и будущих байтов. После прерывания она допускает только эти два состояния каждого файла; неожиданные изменения требуют сверки. Проверка коммита читает все ожидаемые файлы из его дерева: частичный коммит не является полной поставкой. Автоматизация не коммитит и не публикует Git сама.
