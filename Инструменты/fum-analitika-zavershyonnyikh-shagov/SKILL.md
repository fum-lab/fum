# Аналитика завершённых шагов

Навык превращает каждые настроенные `N` подтверждённых завершений в одну обычную аналитическую задачу. Счётчик является только операционным поводом для ревизии: ни число шагов, ни число коммитов или документов само по себе не доказывает улучшение FUM. Управляющая плоскость выбирает и ограждает диапазон, но не пишет аналитический отчёт.

## Источник событий и состояние

Команда читает уже созданный очередью канонический журнал из Git-ссылки:

```text
refs/fum/worktree-task-completion-ledgers/<sha256-физического-Git-каталога>/<sha256-branch_ref>
```

Blob имеет схему `fum.журнал-завершённых-запусков.1` и точные верхнеуровневые поля `схема`, `branch_ref`, `число_событий`, `события`. Одно событие имеет только поля `номер`, `идентификатор`, `branch_ref`, `step_id`, `card_id`, `selection_head`, `завершивший_commit`, `результат`, `job_id`, `spec_generation`. Счётным является только `результат = commit+handoff` в области задания: адаптер не создаёт и не дописывает событие.

Одинаковая устойчивая идентичность события учитывается один раз. Различающиеся записи с одним идентификатором, неканонические JSON-байты, символическая служебная ссылка, разрыв номеров, неизвестный commit или несчётный результат дают закрытый отказ.

Специализированная претензия живёт под:

```text
refs/fum/аналитика-завершённых-запусков/<sha256-физического-Git-каталога>/<sha256-branch_ref>
```

Она замораживает один порог, конечные источники, назначение, относительные пути реестра и отчёта, детерминированный идентификатор анализа, общую identity запуска и фактические `task_id`/`generation`. Основные фазы идут только вперёд: `зарезервирована` → `привязана` → `подтверждена` → `передана` → `завершена`. До host-границы `зарезервирована` может быть атомарно удалена командой освобождения. Альтернативный безопасный выход до коммита переводит любую связанную предшествующую фазу в долговечную `очищена`, которую общий диспетчер затем подтверждает как отказ до эффекта. Для `передана` и `завершена` поле `свидетельство_передачи` содержит только `{base_head, commit, task_id, generation}`; для `очищена` — `{base_head, task_id, generation}` фактического чистого FIFO-завершения.

## Наблюдение и выбор

Read-only-наблюдение выполняется так:

```bash
python3 Инструменты/fum-analitika-zavershyonnyikh-shagov/scripts/аналитика-завершённых-шагов.py \
  наблюдать \
  --корень-рабочей-копии . \
  --expected-branch-ref refs/heads/<ветка> \
  --json
```

Ответ сообщает число уникальных подтверждённых событий и последний идентификатор. Он не создаёт претензию и не меняет журнал.

Выбор старейшего незакрытого порога читает реестр и его схему из точного `HEAD`:

```bash
python3 Инструменты/fum-analitika-zavershyonnyikh-shagov/scripts/аналитика-завершённых-шагов.py \
  показать \
  --корень-рабочей-копии . \
  --реестр Планирование/реестры-заданий-автоматизаций/<ветка>.json \
  --схема Инструменты/fum-dispetcher-avtomatizacij-fum/схемы/реестр-заданий-v1.schema.json \
  --expected-job-id <job_id-аналитики> \
  --json
```

Даже если накопилось несколько порогов, один вызов возвращает только старейший диапазон. `paused`, `blocked` и `retired` дают `not_ready`; состояние другого задания, в том числе заблокированной публикации, не влияет на аналитику.

## Общая резервация и специализированная претензия

До `претендовать` общий диспетчер уже должен создать каноническую резервацию точного запуска под job-scoped-ссылкой:

```text
refs/fum/резервации-запусков-автоматизаций/<sha256-физического-Git-каталога>/<sha256-branch_ref>/<sha256-job_id>
```

Адаптер требует фазу `зарезервирован` и точное совпадение ветки, вершины, identity реестра, поколений, наступления, `run_key`, UUID попытки и курсора до запуска. Перед созданием претензии он также снимает точное неактивное состояние branch-scoped-ссылки `refs/fum/управление-диспетчером/<рабочая-копия>/<ветка>`. Создание либо замена претензии одной Git-транзакцией проверяет неизменные OID общей резервации и управления, включая отсутствие ссылки; исчезновение резервации, начало управления или CAS-гонка не оставляют orphan-претензию.

```bash
python3 Инструменты/fum-analitika-zavershyonnyikh-shagov/scripts/аналитика-завершённых-шагов.py \
  претендовать \
  --корень-рабочей-копии . \
  --реестр Планирование/реестры-заданий-автоматизаций/<ветка>.json \
  --схема Инструменты/fum-dispetcher-avtomatizacij-fum/схемы/реестр-заданий-v1.schema.json \
  --expected-job-id <job_id> \
  --expected-branch-ref refs/heads/<ветка> \
  --expected-selection-head <точный-OID> \
  --expected-spec-generation <поколение-задания> \
  --expected-registry-generation <поколение-реестра> \
  --expected-run-key <run_key> \
  --expected-threshold <конец-диапазона> \
  --идентификатор-попытки <канонический-UUID> \
  --lease-id <тот-же-канонический-UUID> \
  --json
```

Успешный ответ содержит готовое назначение, замороженные проверяемые источники и относительные пути реестра и отчёта. Публичное тело этой претензии и назначение не содержат `selection_id`, UUID попытки, lease, `run_key`, host/thread identity или абсолютный путь рабочей копии.

Если heartbeat остановился после общей резервации либо после `претендовать`, но до перехода общей резервации через host-границу, специализированное состояние освобождается до общего `освободить`:

```bash
python3 Инструменты/fum-analitika-zavershyonnyikh-shagov/scripts/аналитика-завершённых-шагов.py \
  освободить \
  --корень-рабочей-копии . \
  --expected-branch-ref refs/heads/<ветка> \
  --expected-selection-head <selection_head> \
  --expected-job-id <job_id> \
  --expected-spec-generation <поколение-задания> \
  --expected-registry-generation <поколение-реестра> \
  --expected-run-key <run_key> \
  --expected-threshold <конец-диапазона> \
  --идентификатор-попытки <канонический-UUID> \
  --expected-lease-id <тот-же-канонический-UUID> \
  --json
```

Команда принимает только общую фазу `зарезервирован` без свидетельства среды, созданной задачи, FIFO-владения или результата. Exact претензия `зарезервирована` удаляется одной CAS-транзакцией с проверкой текущей ветки, OID общей резервации, management-ref и OID канонического обычного queue-ref; отсутствие претензии даёт идемпотентный `unclaimed`. Активный reset-marker закрывает мутацию, а после завершения сброса повтор использует новый OID обычной очереди независимо от наличия в ней иного владельца. Сдвиг ветки другой обычной задачей не превращает отсутствие эффекта в неоднозначность, но любое пересечение host-границы, `привязана`, `подтверждена`, `очищена`, `передана` или `завершена` закрывает освобождение. После `released` либо `unclaimed` общий `освободить` обязан в собственной CAS-транзакции повторно проверить отсутствие специализированной ссылки вместе с OID резервации, эпохи, управления и обычной очереди; иначе встречное создание претензии либо сброс могли бы оставить orphan-состояние.

## Ограждение FIFO-исполнителя

После собственного FIFO-допуска исполнитель сначала подтверждает общий `bind-run` и `verify-run` диспетчера, а затем вызывает специализированный `bind-run`:

```bash
python3 Инструменты/fum-analitika-zavershyonnyikh-shagov/scripts/аналитика-завершённых-шагов.py \
  bind-run \
  --корень-рабочей-копии . \
  --expected-branch-ref refs/heads/<ветка> \
  --expected-selection-head <selection_head> \
  --expected-job-id <job_id> \
  --expected-spec-generation <поколение-задания> \
  --expected-registry-generation <поколение-реестра> \
  --expected-run-key <run_key> \
  --expected-threshold <конец-диапазона> \
  --expected-lease-id <lease_id> \
  --task-id <точный-CODEX_THREAD_ID> \
  --json
```

`verify-run` принимает те же аргументы и добавляет `--generation <поколение-FIFO>`. Он одной транзакцией проверяет ветку, claim и точного владельца queue ref с `base_head = selection_head`. Только после обоих уровней `verify-run` разрешена содержательная работа.

Назначение требует назвать наблюдаемую способность, терминальную приёмку, отрицательные результаты и стоимость пройденной цепочки, сопоставив их с внешними критериями. Отчёт создаётся по пути из претензии и содержит одноимённые разделы и явное утверждение, что число шагов, коммитов или документов не является доказательством улучшения.

## Commit, handoff и терминальное подтверждение

В одном обычном локальном FIFO-коммите задача обязана одновременно:

- добавить новый детерминированный отчёт;
- изменить в реестре только курсор целевого задания: установить конец диапазона, последний идентификатор события, следующий порог `конец + N` и результат `{идентификатор, путь, content_sha256, конец_диапазона}`;
- сохранить обычные сессионные файлы происхождения, отчёты проверок, recency и review, когда они требуются правилами репозитория.

Обычная команда FIFO `commit` распознаёт exact аналитическую резервацию только вместе с канонической претензией в фазе `подтверждена`. Одна Git-транзакция проверяет прежние OID резервации и претензии, одновременно сдвигает ветку и очередь, переводит претензию в `передана` и записывает закрытое свидетельство `{base_head, commit, task_id, generation}`. Аналитическая резервация без exact verified-претензии даёт закрытый отказ до сдвига ветки; неаналитическая передача претензию не меняет.

После точного ответа FIFO `committed` исполнитель не вызывает `завершить`, ничего больше не пишет и не публикует. Следующий ограждённый терминализатор подтверждает специализированный результат:

```bash
python3 Инструменты/fum-analitika-zavershyonnyikh-shagov/scripts/аналитика-завершённых-шагов.py \
  завершить \
  --корень-рабочей-копии . \
  --expected-branch-ref refs/heads/<ветка> \
  --expected-selection-head <selection_head-до-коммита> \
  --expected-job-id <job_id> \
  --expected-spec-generation <поколение-задания> \
  --expected-registry-generation <поколение-реестра> \
  --expected-run-key <run_key> \
  --expected-threshold <конец-диапазона> \
  --expected-lease-id <lease_id> \
  --task-id <точный-CODEX_THREAD_ID-исполнителя> \
  --generation <поколение-FIFO-исполнителя> \
  --json
```

Команда читает устойчивое свидетельство из претензии, требует его exact задачу, поколение и `base_head`, проверяет, что засвидетельствованный commit является first-parent-потомком `selection_head` и first-parent-предком текущей ветки, а затем валидирует отчёт и курсор именно в этом commit. Перед compare-and-swap она дополнительно требует, что текущее дерево сохраняет exact байты реестра и отчёта из засвидетельствованного коммита; позднее удаление отчёта или откат курсора закрывают допуск. Текущее `queue.last_completion` не используется: следующий обычный handoff может безопасно его заменить. Compare-and-swap ограждает текущий OID ветки и OID канонического обычного queue-ref и помечает только аналитическую претензию `завершена`, сохраняя свидетельство, commit и детерминированный идентификатор анализа; общая резервация не меняется. Активный reset-marker закрывает переход, а после завершения сброса его можно повторить по новому обычному OID даже при ином владельце очереди. Повтор той же команды идемпотентен. Неверные свидетельство, отчёт, hash, курсор, ветка или identity дают закрытый отказ и оставляют claim в `передана`.

После `completed` heartbeat вызывает общую `подтвердить-завершение-исполнителя`. Она заново требует exact текущие байты реестра и отчёта, first-parent-положение засвидетельствованного коммита и каноническую завершённую претензию, затем одной CAS-транзакцией проверяет OID претензии и общей резервации вместе с текущей веткой и терминализирует общую резервацию. Exact claim `завершена` сохраняется для полного terminal/FIFO/specialized replay; только этот переход делает общий запуск успешным. Следующая резервация того же аналитического адаптера одной CAS атомарно поглощает сохранённый claim вместе с заменой terminal reservation и проверкой queue-, branch-, management- и epoch-guards; crash после reserve видит claim отсутствующим.

Штатный FIFO-reset сохраняет специализированную претензию и не вызывает внешний `release`. Пока reset-marker активен, специализированные `претендовать`, `освободить`, `bind-run` и `завершить`, а также общие переходы результата не меняют ограждения; после финала сброса они продолжаются по сохранённой претензии и новому обычному queue-ref. Для фаз до коммита общий терминализатор доказывает безопасный отказ по exact receipt/host/ledger/current queue/branch и прежним reservation/epoch; `передана` после сброса остаётся терминализируемой по свидетельству, а `завершена` ждёт общего terminal-success. Обычный FIFO `finish-clean` атомарно сохраняет фазу `очищена` вместе с точными `task_id`, поколением и `base_head`; поэтому поздний handoff, потерянный ответ или reset не стирают доказательство отсутствия коммита. Общий терминализатор проверяет его first-parent-положение, OID и обычный queue-ref, удаляет претензию и завершает резервацию как `безопасный_отказ_до_эффекта` одной транзакцией.

Следующий порог получает новую претензию лишь после terminal-success прежней общей резервации, проверки tracked cursor и атомарного поглощения её exact terminal claim новой резервацией того же адаптера. Поэтому рестарт после claim, commit, специализированного `completed`, общей terminal-CAS или reserve-cleanup не создаёт второй отчёт и не теряет незакрытый порог.

## Проверка

Автономные тесты используют временные Git-репозитории, не требуют сети и покрывают `N = 1`, дубликаты, несколько порогов, пропущенный тик, повреждённые cursor и обычную очередь, паузу, независимую блокировку публикации, приватность, общую резервацию, management-fence и их гонки, pre-host `released`/`unclaimed`, сдвиг ветки до эффекта, запрет освобождения после host-границы, долговечную `очищена`, bind/verify, атомарное свидетельство, fail-closed handoff, сохранение claim при reset, report+cursor commit, последующий FIFO handoff, рестарт и терминальный replay. В рабочей сессии запускай их только через [обёртку отчётов о проверках](../fum-otchyotyi-o-zapuskakh-proverok/SKILL.md) с текущим исходным запросом Журнала.
