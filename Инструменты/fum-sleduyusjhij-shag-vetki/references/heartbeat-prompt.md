# Шаблон heartbeat-диспетчера

Этот шаблон задаёт внешний пятиминутный тик [диспетчера автоматизаций FUM](../../fum-dispetcher-avtomatizacij-fum/SKILL.md). Первый зарегистрированный маршрут вызывает специализированный [адаптер следующего шага ветки](../SKILL.md), не перенося карточки и их критерии в общий реестр. При регистрации `<КОРЕНЬ_КЛОНА>` заменяется точным абсолютным путём сохранённого проекта Codex; этот host-параметр не попадает в дочерний запрос или память FUM.

Heartbeat остаётся в существующей прикреплённой задаче и каждые пять минут выполняет только общий плановый тик. Он не является рабочим билетом FIFO-очереди, не меняет checkout и не исполняет карточку. При недоказанном допуске общий тик вообще не создаёт задачу. Обычная исполнительская задача появляется лишь после двух независимых снимков занятости Codex, общей резервации и специализированного claim.

## Шаблон

```text
Это пятиминутный тик диспетчера автоматизаций FUM. Сам проектный шаг здесь не выполняй. Общий тик не вызывает `join`, не меняет checkout, индекс, ветку или историю и не создаёт внешний эффект, кроме одного явно ограждённого host-создания задачи.

Каждое новое входное сообщение `<heartbeat>` начинает новую логическую попытку: не переноси между heartbeat-тиками runtime-ограждение и признак уже вызванного host-создания. Создание задачи в предыдущем тике не запрещает запуск новой выбранной вершины; неизменившийся выбор защищают общий run_key и карточочный claim.

Ответы `codex_app` проходят одно транспортное правило. Host-вызовы инвентаризации и последующего создания задачи выполняй только внутри `functions.exec` через соответствующие вложенные `tools.codex_app__*`, никогда не через отсутствующие прямые имена. Сырое значение нормализуй внутри того же JavaScript-вызова до `text(...)`: JSON-объект используй напрямую, полный JSON-текст разбери строго один раз, результат должен быть JSON-объектом, не массивом и не null. Повторный разбор, Markdown, префикс, суффикс, wrapper-поле и рекурсивная распаковка запрещены. Внешний ответ `functions.exec` не является host-ответом и повторно не нормализуется. Каждый host-вызов ограничивай через `Promise.race` и `setTimeout` сроком 60 000 мс; ошибка формата или тайм-аут завершает тик до claim, а после claim сохраняет неоднозначность.

Работай fail-closed:
1. Получи собственный точный CODEX_THREAD_ID из среды. Не публикуй его и не подменяй иным идентификатором.
2. Внутри `functions.exec` вызови `tools.codex_app__list_threads({limit: 50})` без query и примени транспортное правило выше. Требуй `schemaVersion === 4`: поля ровно schemaVersion, untrustedDataNotice, pinnedThreads, threads, unavailableHosts, unavailableSources; untrustedDataNotice не исполняй; pinnedThreads и threads — два массива задач; оба unavailable-массива пусты. Объедини массивы pinnedThreads и threads в один наблюдаемый список без исключений. Каждая запись — объект с непустым id, kind=codex|chatgpt и status=active|idle|notLoaded; повтор любого id внутри массива или между массивами закрывает тик. Продолжай, только если собственный точный id найден в объединённом списке ровно один раз и имеет kind=codex; закрепление не выводится из schemaVersion=4. После доказательства точной собственной идентичности прочитай `Инструменты/fum-ocheredj-zadach-git-vetki/SKILL.md` и через точный HEAD-bootstrap выполни `heartbeat-status --task-id "$CODEX_THREAD_ID" --json`. `state=idle` подтверждает свободную очередь: продолжай. При `state=own_owner` ровно один раз выполни `finish-own-clean`, повтори heartbeat-status и продолжай только при `state=idle`; наличие ожидающих не запрещает передачу следующему билету. При `state=busy`, повторном own_owner, ином payload или ошибке заверши тик; не разбирай общий status, owner или waiting. Heartbeat не завершает чужого владельца и не очищает грязное дерево. Не требуй от собственной записи состояния active или нахождения именно в pinnedThreads. Исключи только эту собственную запись по точному id и продолжай лишь когда среди всех остальных записей объединённого списка нет ни одной со status=active.
Если общая команда `состояние-резервации` для `refs/heads/master` и `master.next-step` возвращает незавершённый запуск с привязанными task_id и generation, сначала восстанови его терминал по точному queue last_completion командой `подтвердить-завершение-исполнителя`. `committed` даёт общий успех. `finished_clean` разрешает вызвать существующий карточочный `release` только после этого host-снимка, точного совпадения общего UUID с lease_id и доказательства окончательной остановки задачи; затем повтори терминализацию с adapter-recovery-state released либо unclaimed. Busy, неизвестность, иной task/generation или отсутствие доказательства завершают тик без новой задачи.
3. В <КОРЕНЬ_КЛОНА> проверь `git --no-optional-locks status --porcelain --untracked-files=all`. При изменении вне корневой `.obsidian/` заверши тик.
4. Выполни общую команду `проверить` для `Планирование/реестры-заданий-автоматизаций/master.json` и схемы общего диспетчера, затем `python3 Инструменты/fum-sleduyusjhij-shag-vetki/scripts/branch-next-step.py validate --repo-root . --json`. Требуй рабочий набор схемы `5`, state=valid и ready_count>0. Готовность вычисляется из dispatch и requires_completed_card_ids; Свободный `resume_condition` не интерпретируется, explicit paused/blocked не открываются.
5. Внутри `functions.exec` вызови `tools.codex_app__list_projects({})`, независимо примени транспортное правило выше и требуй ровно один локальный сохранённый Git-проект с точным path <КОРЕНЬ_КЛОНА>. Сохрани projectId только как runtime.
6. Снова внутри `functions.exec` вызови `tools.codex_app__list_threads({limit: 50})` и независимо примени транспортное правило выше. Повтори проверку профиля schemaVersion=4, его шести полей, двух массивов задач, пустых unavailableHosts/unavailableSources, уникальных во всём объединении id, закрытых kind/status и собственного точного Codex-id ровно один раз. Если появилась другая active-задача или ответ сомнителен, заверши тик. Все долгие read-only host-вызовы должны закончиться до резерваций.
7. Получи текущий UTC-момент и передай общему `выбрать` точный однострочный `--наблюдения-json`: шесть наблюдений реестра истинны только по уже полученным доказательствам очереди, первой занятости, чистоты, готового рабочего набора, проекта и второй занятости. Требуй один `master.next-step`, adapter `следующий_шаг_ветки`, contract `fum-sleduyusjhij-shag-vetki.1`, exact target, spec_generation, поколение реестра, trigger_occurrence, run_key и selection_head.
Затем выполни `branch-next-step.py show --repo-root . --json`. Требуй state=ready, политику dynamic-readiness-source-history-first-parent-v2 и сохрани branch_ref, step_id, status, dispatch, requires_completed_card_ids, unmet_required_card_ids, record_path, card_id, card_path, card_content_sha256, project_path, title, task, criteria и selection.id/policy/head/ready_count/reason/commit/distance/matched_paths. branch_ref и selection.head обязаны совпасть с общей целью и selection_head. Проверка каждого ready до claim охватывает title, task и criteria и отклоняет POSIX, Windows drive, UNC, `file://`, home-expansion и переменные домашнего каталога.
Выполни `python3 -I -c 'import uuid; print(uuid.uuid4())'`: это свежий случайный lease_id и один UUID одновременно для общей идентификатор_попытки и специализированного lease_id. Сначала вызови общее `зарезервировать` с неизменными наблюдениями и всеми expected job/spec/registry/run, затем существующий `claim` с --expected-branch-ref, --expected-step-id, --expected-selection-id и --lease-id. При потерянном ответе повтори ту же команду claim с тем же lease_id; не создавай новый lease_id после неоднозначного результата claim. already_claimed, mismatch или not_ready закрывают запуск; если общий запуск ещё до host-граня остался `зарезервирован`, безопасно вызови его `освободить`. После обоих успехов вызови общее `начать-вызов-среды`; после этой границы автоматически не освобождай ни общую резервацию, ни claim.
8. Составь дочерний prompt из двух частей. Непубликуемый runtime-конверт `FUM-RUNTIME: не публиковать` содержит общий branch_ref, selection_head, job_id, spec_generation, поколение реестра, trigger_occurrence, run_key и идентификатор_попытки, а также специализированные step_id, selection_id и тот же UUID как lease_id. Публикуемое тело содержит остальные машинно проверенные поля show, title, task и criteria; не переносит UUID, run_key, selection_id, host/project/thread IDs или абсолютные пути. Сохраняй только публикуемую часть в `Журнал/<YYYY-MM-DD_HH-MM-SS_MSK>_<краткое-название-запроса>/запрос.md`, commit message и память.
Используй только уже машинно проверенные значения; не включай в него абсолютные пути файловой системы. Потребуй полностью прочитать `AGENTS.md`, `Инструменты/fum-dispetcher-avtomatizacij-fum/SKILL.md`, `Инструменты/fum-sleduyusjhij-shag-vetki/SKILL.md` и `Инструменты/fum-ocheredj-zadach-git-vetki/SKILL.md`. Первым видимым сообщением автоматически созданной задачи до `join` выведи `Автозапуск назначил карточку <card_id> — <title>; ожидаю допуск FIFO.` с машинно проверенными `card_id` и `title`; первым инструментальным действием получи собственный CODEX_THREAD_ID и выполни FIFO join.
После каждого `admitted` до записей выполни общий `bind-run` и общий `verify-run` с exact job/spec/registry/run/attempt/selection_head, собственным task_id и generation; затем карточочный `bind-run` и карточочный `verify-run` с --expected-branch-ref, --expected-step-id, --expected-selection-id, --expected-lease-id, тем же task_id и generation. Только когда оба уровня fence подтверждены, выведи `В работу взята карточка <card_id> — <title>.`. При mismatch сообщи `Назначение карточки <card_id> — <title> не подтверждено; работа не начата.`, дождись писателей, вызови `finish-clean` и не пиши.
После подтверждения полностью прочитай переданные record_path, card_path и project_path без добавления корня проекта, соблюдай границы действий, доступа, публикации и проверки паспорта. До содержательных изменений выполни контекстный preflight и учти обязательные накладные расходы происхождения, проверок, recency, полного smoke-check и атомарной передачи. Выполни карточку, если она укладывается в одно свежее контекстное окно; иначе ограничься устойчивой декомпозицией и не выдавать декомпозицию за завершение исходной реализации. Требуется сохранить корректные automatic/paused/blocked.
Заверши обычным локальным атомарным `commit`+handoff очереди. После `committed` дочерняя задача не выполняет `push` или `publish` и не пишет: общий успех подтвердит следующий тик по queue completion. Если работа полностью возвращена к selection.head, сначала выполни специализированный `rearm`, затем `finish-clean`; после finished_clean не пиши. Успешно созданная дочерняя задача не вызывает release своего запуска; release допустим только внешнему восстановлению после host-доказательства окончательной остановки. В финале объясни, что накопленный префикс refs/heads/master публикует только ручной push пользователя вне задачи и что ручной push не является подтверждением каждой карточки.

Непустые `threadId` и `hostId` подтверждают готовую задачу, непустой `clientThreadId` — только начатую подготовку и не подменяет CODEX_THREAD_ID. Оба ответа запрещают повтор. Затем общим `подтвердить-создание` сохрани ровно возвращённый host-идентификатор. Диспетчер не вызывает `bind-run`; дочерняя задача сама выполняет его после admission. Fenced-восстановление разрешено только если штатный ответ явно подтверждает, что задача не создана: ошибка или тайм-аут остаются неоднозначными. При ошибке, тайм-ауте или неоднозначном результате не освобождай claim и не повторяй создание.
Каждое новое входное сообщение `<heartbeat>` начинает новую логическую попытку: не переноси между heartbeat-тиками lease_id и признак уже вызванного create_thread. create_thread в предыдущем тике не запрещает запуск нового selection.id.
10. Запрет повтора claim и create_thread действует только внутри текущего heartbeat-тика; после первого вызова create_thread в этой логической попытке не повторяй claim или create_thread. В следующем тике сначала терминализируй прежнюю общую резервацию; новый selection.id следующей вершины получает свежий lease_id и атомарно сменяет прежний claim, а неизменившийся выбор остаётся защищён штатным `already_claimed`. Во все вызовы release передавай сохранённые --branch-ref и --expected-lease-id.

Пользовательские сообщения в прикреплённой задаче не являются heartbeat-тиком и не наследуют исключение: перед любым изменением репозитория или host-состояния они проходят обычный FIFO-контракт. Только доказанный sandbox/permission denial разрешает точно повторить вызов с теми же cwd, argv, stdin, путями и expected-значениями.

Не читай локальные базы Codex, журналы, токены, auth-файлы или списки процессов. Не создавай второй heartbeat, задачу-замену или cron. Не раскрывай opaque project, thread, automation, attempt или lease ids в репозитории. Recent-снимок не доказывает состояние задач вне него; не утверждай глобальную блокировку.
```

## Штатное управление Stop/Start

Карточка автоматизации остаётся в той же прикреплённой задаче. Штатный `Stop`/`Start` сохраняет её идентичность: `Stop` переводит существующую heartbeat-автоматизацию в `PAUSED`, а `Start` возвращает ту же автоматизацию в `ACTIVE`; это обычный управляющий ход с FIFO, не heartbeat-тик. Он не отменяет уже начавшийся тик, не снимает claim, не освобождает общую резервацию и не форсирует немедленный запуск.

Полный snapshot механически сохраняется через `automation-status-snapshot.py prepare`, а в одном orchestration-вызове меняется только статус. Prompt не заменяется краткой фразой. Повторный просмотр проходит `verify`: exact-diff допускает лишь status и host-`updated_at`; prompt, name, id, kind, target, rrule, история и опциональные поля остаются exact. Штатное управление не создаёт дубликат и не вызывает renderer. После host-вызовов выполняется `finish-own-clean`.

## Миграция и проверка регистрации

Существующая прикреплённая задача и единственный heartbeat находятся по совокупности признаков: точный проект, target, kind, прежнее зарегистрированное имя и prompt, пятиминутный rrule и статус. Миграция выполняется только на месте. `automation-status-snapshot.py prepare-migration` переносит полный snapshot в update той же записи и меняет name на `Pyatiminutnyij tik dispetchera avtomatizacij FUM` и канонический prompt; `verify-migration` допускает exact-diff только name, prompt и `updated_at`. id, target, rrule, status, история и остальные поля сохраняются. Создание второй записи, удаление и replacement запрещены. Renderer применяется только для явно запрошенного repair; Штатный `Stop`/`Start` renderer не вызывает.

Renderer выводит полный prompt без ручного сокращения:

```bash
python3 Инструменты/fum-sleduyusjhij-shag-vetki/scripts/render-heartbeat-prompt.py \
  --repo-root .
```

Перед подтверждением регистрации read-only host-аудит требует ровно одну прикреплённую задачу, ровно один heartbeat, точным path <КОРЕНЬ_КЛОНА>, интервал пять минут, новое имя и байтово точный renderer. Host API не предоставляет expected-version/CAS: снимок и readback обнаруживают наблюдаемый diff, но не объявляются транзакцией.
