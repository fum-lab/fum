# Шаблон heartbeat-диспетчера

Этот шаблон задаёт внешний пятиминутный тик [диспетчера автоматизаций FUM](../../fum-dispetcher-avtomatizacij-fum/SKILL.md). Он маршрутизирует [адаптер следующего шага ветки](../SKILL.md) и второй адаптер `master.completed-step-analysis`, не перенося карточки, диапазоны событий или критерии в общий реестр. При регистрации `<КОРЕНЬ_КЛОНА>` заменяется точным абсолютным путём сохранённого проекта Codex; этот host-параметр не попадает в дочерний запрос или память FUM.

Heartbeat остаётся в существующей прикреплённой задаче и каждые пять минут выполняет только общий плановый тик. Он не является рабочим билетом FIFO-очереди, не меняет checkout и не исполняет карточку или анализ. При недоказанном допуске общий тик вообще не создаёт задачу. Обычная исполнительская задача появляется лишь после двух независимых снимков занятости Codex, общей резервации и одной выбранной специализированной претензии.

Ручной push не является подтверждением каждой карточки.
```text
9. После этой проверки одним вызовом `functions.exec` выполни host-границу и создание. Сначала явно выполни `await tools.exec_command({cmd: полнаяКомандаНачатьВызовСреды, workdir: "<КОРЕНЬ_КЛОНА>", yield_time_ms: 30000, max_output_tokens: 2000})`, потребуй завершённый процесс с кодом 0 и разбери его полный JSON-output ровно один раз до точного `состояние=вызов_разрешён`. На успешной ветви сразу запусти `await Promise.race([tools.codex_app__create_thread({prompt: дочернийПромпт, target: {type: "project", projectId: идентификаторПроекта, environment: {type: "local"}}}), таймаутСоздания])`; не передавай `model` или `thinking`. Эти две явно ожидаемые операции выполни в одном вызове `functions.exec` без `text(...)`, возврата или перехода модели между ними. Неуспех либо неоднозначность команды границы запрещает create_thread; если нельзя доказать, что граница не пересечена, не освобождай резервацию или claim. Непустые `threadId` и `hostId` подтверждают готовую задачу, непустой `clientThreadId` — только начатую подготовку и не подменяет CODEX_THREAD_ID. Оба ответа запрещают повтор. Затем общим `подтвердить-создание` сохрани готовую пару только как `--thread-id <threadId> --host-id <hostId>`, а предварительный ответ только как `--client-thread-id <clientThreadId>`; старый неоднозначный флаг не используй. Диспетчер не вызывает `bind-run`; дочерняя задача сама выполняет его после admission, причём exact threadId запрещает привязку другой задачи. Fenced-восстановление разрешено только если штатный ответ явно подтверждает, что задача не создана: ошибка или тайм-аут остаются неоднозначными. При ошибке, тайм-ауте или неоднозначном результате не освобождай claim и не повторяй создание.
Каждое новое входное сообщение `<heartbeat>` начинает новую логическую попытку: не переноси между heartbeat-тиками lease_id и признак уже вызванного create_thread. create_thread в предыдущем тике не запрещает запуск нового selection.id; аналитический порог меняется только после подтверждённого результата прежнего диапазона.
10. Запрет повтора claim и create_thread действует только внутри текущего heartbeat-тика; после create_thread не повторяй их. Следующий тик сначала терминализирует прежнюю резервацию. Для нового selection.id общая `зарезервировать` одной CAS поглощает и удаляет exact старый terminal claim вместе с заменой terminal reservation; только затем отдельная CAS адаптера создаёт свежий claim с новым lease_id. Неизменившийся выбор остаётся защищён штатным `already_claimed`. Аналитический `претендовать` сохраняет прежний диапазон. В release передавай сохранённые branch/head/job/spec/registry/run/attempt/lease; для обоих адаптеров он допустим только из общего `зарезервирован` до host-границы и выполняется специализированным, затем общим CAS.

Только явный пользовательский запрос постоянной задаче начинает штатный сброс; heartbeat его не начинает. Полностью прочитай `Инструменты/fum-ocheredj-zadach-git-vetki/SKILL.md`, `Инструменты/fum-dispetcher-avtomatizacij-fum/SKILL.md`, `Инструменты/fum-sleduyusjhij-shag-vetki/SKILL.md`; следуй `план-сброса` → `подготовить-сброс` → `подтвердить-остановку-сессий` → `применить-сброс`. `active` без штатной остановки закрывает подготовку, handoff не заменяет stop. Финал сохраняет next-step claim схем 4/5/6 и аналитический claim, не вызывает release; common-terminal приоритетно принимает durable success/clean proof и exact receipt/host/ledger/current queue/branch. Success-claim остаётся для replay, clean-claim удаляется. После успеха не пиши.

Пользовательские сообщения в прикреплённой задаче не являются heartbeat-тиком и не наследуют его исключение: кроме описанного явного штатного сброса, перед любым изменением репозитория или host-состояния они проходят обычный FIFO-контракт. Только доказанный sandbox/permission denial разрешает точно повторить вызов с теми же cwd, argv, stdin, путями и expected-значениями.

Не читай локальные базы Codex, журналы, токены, auth-файлы или списки процессов. Не создавай второй heartbeat, задачу-замену или cron. Не раскрывай opaque project, thread, automation, attempt или lease ids в репозитории. Recent-снимок не доказывает состояние задач вне него; не утверждай глобальную блокировку.
```

## Штатное управление Stop/Start

Карточка автоматизации остаётся в той же прикреплённой задаче. Штатный `Stop`/`Start` сохраняет её идентичность: `Stop` переводит существующую heartbeat-автоматизацию в `PAUSED`, а `Start` возвращает ту же автоматизацию в `ACTIVE`; это обычный управляющий ход с FIFO, не heartbeat-тик. Он не отменяет уже начавшийся тик, не снимает claim, не освобождает общую резервацию и не форсирует немедленный запуск.

Полный snapshot механически сохраняется через `automation-status-snapshot.py prepare`, а в одном orchestration-вызове меняется только статус. Prompt не заменяется краткой фразой. Повторный просмотр проходит `verify`: exact-diff допускает лишь status и host-`updated_at`; prompt, name, id, kind, target, rrule, история и опциональные поля остаются exact. Штатное управление не создаёт дубликат и не вызывает renderer. После host-вызовов выполняется `finish-own-clean`.

## Миграция и проверка регистрации

Существующая прикреплённая задача и единственный heartbeat находятся по совокупности признаков: точный проект, target, kind, прежнее зарегистрированное имя и prompt, пятиминутный rrule и статус. Миграция выполняется только на месте. `automation-status-snapshot.py prepare-migration` переносит полный snapshot в update той же записи и меняет name на `Pyatiminutnyij tik dispetchera avtomatizacij FUM` и канонический prompt; `verify-migration` допускает exact-diff только name, prompt и `updated_at`. id, target, rrule, status, история и остальные поля сохраняются. Создание второй записи, удаление и replacement запрещены. Renderer применяется только для явно запрошенного repair; Штатный `Stop`/`Start` renderer не вызывает.

Renderer выводит полный prompt без ручного сокращения:

```bash
python3 Инструменты/fum-sleduyusjhij-shag-vetki/scripts/render-heartbeat-prompt.py \
  --repo-root .
```

Перед подтверждением регистрации read-only host-аудит требует ровно одну прикреплённую задачу, ровно один heartbeat, точным path <КОРЕНЬ_КЛОНА>, интервал пять минут, новое имя и байтово точный renderer. Host API не предоставляет expected-version/CAS: снимок и readback обнаруживают наблюдаемый diff, но не объявляются транзакцией.
