# [FUM](Глоссарий/FUM.md)

[FUM](Глоссарий/FUM.md) — `fraktaljnyij uzel myishleniya`, по-русски — [фрактальный узел мышления](Глоссарий/фрактальный-узел-мышления.md). Проект разрабатывается как открытый агент следующего поколения.

Сейчас этот репозиторий — [память проекта](Глоссарий/память-FUM.md) и его [документационный прототип](Глоссарий/документационный-прототип-FUM.md), а не готовое отдельное приложение. Практический интерфейс текущей формы — человек, внешняя задача Codex и локальная копия памяти в Git и Markdown. Obsidian можно использовать как удобный интерфейс чтения и навигации, но каноническим источником остаются файлы репозитория.

## Как использовать FUM сейчас

### 1. Подготовьте свою копию

Для личной или публичной работы создайте fork, замените `USERNAME` своим именем на GitHub, клонируйте fork и при необходимости подключите базовый репозиторий как `upstream`:

```bash
git clone https://github.com/USERNAME/fum.git FUM
cd FUM
git remote add upstream https://github.com/fum-lab/fum.git
```

После свежего клонирования инициализируйте закреплённую Git-зависимость LinguisticKit:

```bash
python3 Инструменты/fum-proverka-git-zavisimostej/scripts/proveritj-git-zavisimostj.py init \
  --repo-root . \
  --path Зависимости/LinguisticKit
```

Откройте корень репозитория как локальный проект в Codex Desktop. При желании откройте тот же каталог как хранилище Obsidian.

### 2. Сформулируйте обычный запрос

Напишите задаче Codex, что нужно понять, изменить, проверить или сохранить. Можно писать естественным языком, в том числе транслитом. Если запрос влияет на память проекта, его исходная формулировка сохраняется дословно, а производная память ведётся по-русски кириллицей. Если важны доступ, публикация, сеть, секреты, платные сервисы или другие внешние эффекты, укажите разрешённые границы явно.

Полезный запрос обычно содержит ожидаемый результат, исходные материалы и существенные ограничения. Знать внутреннее устройство памяти или специальные команды FUM для начала работы не требуется.

### 3. Дождитесь локального результата

Обычный новый чат сначала получает доверенный снимок плана, активных линий и FIFO. Агент оценивает роль задачи и выбирает один ограждённый маршрут. Read-only-запрос не занимает слот. Независимый писатель лениво получает или переиспользует linked worktree `Подузлы/слот-*` с отдельными checkout, индексом, ref и FIFO. Последовательное продолжение атомарно создаёт intent и билет прежних ref и worktree без второго checkout; `master` остаётся в первичном checkout. Рецензент и интегратор получают отдельные назначения.

Один слот допускает ровно одну одновременно активную сессию. Ожидающее продолжение не является вторым владельцем и после handoff последовательно использует тот же слот. После терминальной квитанции и чистого readback слот освобождается для другой задачи. После допуска писатель работает только в exact slot `repo-root`, читает принятую память, обновляет документы или код, запускает проверки и сохраняет происхождение изменения в `Журнал/`.

Промежуточная worktree-сессия заканчивается атомарным commit+handoff первому exact-билету прежних линии, FIFO, worktree и ref. Билетом может быть уже открытый чат; если его нет, владелец создаёт одно продолжение. Для `master` продолжение в первичном checkout всегда создаётся заранее. Терминальные commits результата, ревью и интеграционного кандидата замораживаются собственными квитанциями без продолжения.

Результат worktree-линии проходит автоматическое независимое агентское ревью, автоматическую агентскую интеграцию и, при конфликте, отдельное автоматическое агентское разрешение конфликта с обязательным повторным независимым ревью. Принятый результат меняет локальный `master` только точным compare-and-swap. GitHub fork и pull request в этом локальном маршруте не используются.

### 4. Проверьте результат

Прочитайте итог задачи, просмотрите изменённые файлы и Git-дифф, а при необходимости — соседние `запрос.md` и `отчёт.md` в новой папке `Журнал/`. Отчёт показывает смысл изменения, проверки, решения и известные ограничения; Git-коммит закрепляет точный принятый снимок.

После промежуточного коммита worktree-линии первый билет получает `reload_required`, подтверждает вершину и продолжает в прежнем слоте. Продолжение `master` перечитывает `HEAD`, повторяет публикации и запускает веточный селектор в первичном checkout. Если шага нет, обычная ветка чисто завершается. Терминальное назначение пула продолжения не создаёт; слот переиспользуется. Долговечные продолжения видны в [карточках шагов](Планирование/карточки-шагов/README.md).

### 5. Опубликуйте отдельно, если это нужно

В обычном маршруте вне worktree-пула пользователь публикует выбранный локальный результат отдельным действием, например:

```bash
git push origin master
```

Для другой ветки или точного ref используйте соответствующую явную команду. Ручной push публикует проверенный Git-префикс, но не расширяет разрешения на иные внешние эффекты.

У локального worktree-пула действует более узкий автоматический транспорт: каждый result-ref, включая заблокированный или пока несливаемый, после проверки публикационной чистоты отправляется без force в уже настроенный remote этого же репозитория и подтверждается точным readback. Ошибка сети или аутентификации оставляет локальный ref достижимым и переводит публикацию в `publication_pending`; она не превращается в потерю результата. Удалённый `master` обновляется только после принятой локальной интеграции и обязательного повторного независимого ревью.

## Автоматическое продолжение

Постоянного диспетчера и heartbeat больше нет. [Обязательное продолжение ветки](Документация/45-обязательное-продолжение-Git-ветки-после-коммита.md) относится к последовательной линии. До промежуточного worktree-коммита уже есть один первый билет: от пользовательского чата либо `create_thread` владельца. Для `master` владелец всегда создаёт новую задачу заранее. Терминальные result-, review- и integration-commits продолжения не требуют.

Коммит разрешён только после подтверждения exact continuation-intent и первого ожидающего билета на исходной вершине тех же ref и worktree. Атомарный commit+handoff двигает ветку и передаёт очередь. Worktree-продолжение подтверждает новую вершину в том же слоте; продолжение обычной ветки перечитывает новый `HEAD`, запускает селектор и берёт один допустимый шаг. Несовпавшая квитанция закрывает маршрут без резервного независимого выделения. `done`, отсутствие готового шага или чистый отказ заканчиваются `finish-clean`, поэтому пустой петли нет.

Задача следующей фазы существует до промежуточного коммита намеренно. Git-квитанции позволяют новой сессии после обрыва read-only восстановить тот же слот, ref, FIFO, intent и следующую допустимую команду без дубликата. Но ошибка, тайм-аут, один `clientThreadId` или потерянный ответ при создании ещё неизвестной host-задачи запрещают коммит и слепой повтор: host-поверхность не имеет идемпотентного ключа и авторитетного поиска такого результата. Это безопасная остановка, но не обещание безусловного прогресса после любого сбоя среды.

Если именно эти защитные ограждения не дают безопасно продолжить локальную работу, человек может использовать отдельный аварийный маршрут из корня репозитория:

```bash
./sbrositj.sh
```

Скрипт без `sudo` требует настоящие TTY одновременно на stdin и stdout, показывает точные текущие ветку, `HEAD`, удаляемые изменения и runtime-ссылки и запрашивает динамическую фразу полного плана. После подтверждения он возвращает индекс и рабочее дерево к этому `HEAD`, сохраняя ignored-данные и вложенные репозитории, архивирует и аннулирует прежнее scoped runtime-состояние и создаёт свежую пустую FIFO. Это сознательный `break-glass`, а не host-stop и не источник новой задачи-продолжения: дальнейшее исполнение начинает человек отдельным запросом. Ошибка фразы или изменение плана завершают вызов без сброса; скрипт не принимает неинтерактивный force-обход.

## Границы текущей формы

- Единого коробочного приложения, собственного самостоятельного runtime и готового GUI FUM пока нет; Codex и его host-оркестрация остаются внешней средой.
- Документарный и эталонный прототип проверяет exact slot `repo-root` содержательных команд, но Codex Desktop пока не даёт переноса workspace на уровне host с машинным ACK. Это не нативная изоляция host и не доказательство отсутствия чтений первичного checkout; граница дополнительно зависит от соблюдения сформированного маршрута агентом.
- Git, журнал и автоматические проверки подтверждают происхождение, структуру и воспроизводимые инварианты, но не доказывают истинность каждого содержательного вывода или преимущество FUM над другими агентами.
- Сеть, секреты, платные сервисы, публикация, получение данных из внешних источников и физические эффекты требуют отдельного явного разрешения.
- Исполняемые прототипы подтверждают только свои ограниченные сценарии и не являются обещанием готовности полного продукта.
