# [FUM](Глоссарий/FUM.md)

[FUM](Глоссарий/FUM.md) - `fraktaljnyij uzel myishleniya`, по-русски - [фрактальный узел мышления](Глоссарий/фрактальный-узел-мышления.md). Название фиксируется как аббревиатура латинскими буквами.

Этот репозиторий служит [памятью проекта FUM](Глоссарий/память-FUM.md) - открытого агента следующего поколения. Сейчас он является [документационным прототипом FUM](Глоссарий/документационный-прототип-FUM.md): память уже ведётся через требования, происхождение решений, проверки, журнал, индексы и наследуемую Git-историю, хотя [коробочная реализация FUM](Глоссарий/коробочная-реализация-FUM.md) ещё проектируется. Исполняемые Swift-прототипы проверяют отдельные механизмы; один узкий локальный одноагентный сценарий уже прошёл в собственном runtime через реальные model-only-шаги, разрешённое локальное действие, изолированный Git-кандидат, независимую приёмку и два межпроцессных возобновления. [Проверяемый многоагентный контур](Прототипы/проверяемый-многоагентный-контур/README.md) автономно проводит на записанных фикстурах четыре сквозных сценария, а сохранённый живой прогон и его преемник связывают две корневые сессии: новая сессия опубликовала от точного родителя закрытое 16-артефактное поколение с единственным `handoff_result`, семью успешными проверками входов и канонически совпавшими повторными replay. Тот же пакет проверяет паспорт репозиторной композиции версии `1`, узкий однопакетный пишущий исполнитель и сериализованный CAS-интегратор с реестром resolver версии 1: локальный клон от точного `base_oid` получает уникальные refs, один осмысленный commit и внешний канонический паспорт, исходный checkout остаётся неизменным, а совместимые кандидаты и результаты двух зарегистрированных resolver-классов сохраняют исходные commit прямыми родителями интеграционного commit и публикуются в отдельный локальный bare-ref только точным compare-and-swap. Отдельный автономный контур регистрирует один долговечный специализированный fork-подузел, передаёт его публикационно чистый кандидат вверх между локальными bare-репозиториями и обновляет точный gitlink assembly отдельным commit. Ещё один автономный контур создаёт самостоятельный проект в отдельном локальном bare-репозитории: дочерний commit хранит читаемый `README.md`, машинный паспорт, собственные правила, очередь, claim, диспетчер и следующий шаг, а родитель — только узкую композиционную регистрацию и точный gitlink; проектный commit и отдельный CAS-коммит обновления родителя восстанавливаются свежими клонами. Это подтверждает узкое межсессионное восстановление из сохранённой памяти, структурный контракт отдельного кандидатного commit, ограниченное локальное принятие и два самостоятельных межрепозиторных маршрута, но не реализует параллельный планировщик, универсальное разрешение конфликтов, несколько пишущих подузлов, совместную приёмку fork и проекта, реальный проектный submodule, внешний push или сквозной runtime и не доказывает отсутствие скрытого чтения, независимость моделей, внутренний многоагентный runtime или всю долговременную память FUM. [Сравнительная приёмка](Планирование/карточка-эксперимента-сравнительной-приёмки-преимуществ-FUM.md) предзарегистрирована, но ни один её измеряемый прогон не выполнен. Это не полный или универсальный агентский runtime, не живой многомодельный или распределённый FUM, не продуктовый релиз и не доказательство преимущества. Пригодность локальной Git-ориентированной памяти для долгоживущей агентной работы остаётся проверяемой гипотезой.

Канонический публичный upstream размещён в GitHub-репозитории [fum-lab/fum](https://github.com/fum-lab/fum). В наблюдаемой основной рабочей копии на 2026-07-21 Git-remote `origin` указывал на `https://github.com/fum-lab/fum.git`; в пользовательском форке `origin` обычно указывает на сам форк, а базовый репозиторий подключается как `upstream`. Незакоммиченная локальная правка не является опубликованной: обычная рабочая сессия `master` завершает локальный атомарный commit+handoff без `push` или `publish`, а публикацию точного проверенного префикса отдельно подтверждает ручной `push` пользователя. Готового продуктового релиза FUM это также не утверждает.

Долгий ориентир проекта - [FUM](Глоссарий/FUM.md)-агент полного цикла разработки и исследования: от выработки требований, постановки гипотез и [экспериментов](Глоссарий/эксперимент-FUM.md) до написания кода, проверки результатов, оформления [открытий](Глоссарий/открытие-FUM.md) и постепенного перехода к агенту, способному развивать самого себя.

Оба режима фактически завершают два процесса через `SIGKILL`, возобновляются с новыми PID и передают изолированный кандидат отдельному headless-процессу приёмки. ## Ключевые идеи

### Память и происхождение

[Память FUM](Глоссарий/память-FUM.md) строится как проверяемая, наследуемая и развиваемая среда. Каждый значимый запрос сохраняется в собственной [папке запроса](Глоссарий/папка-запроса.md) в [журнале работ](Журнал/), производные материалы живут в [Документация/](Документация/) и [Глоссарий/](Глоссарий/), а история изменений читается не только через Git, но и через соседство исходного текста, отчёта и принадлежащих запросу материалов.

Модель памяти ориентируется на живые организмы: от генома до накопленного опыта нервной системы. На каждом уровне должен работать цикл наследования, изменчивости и отбора.

### Фрактальная архитектура

[FUM](Глоссарий/FUM.md) рассматривается как сеть [FUM-узлов](Глоссарий/FUM-узел.md), где узлом может быть простой элемент, агент, человек, команда, организация или составная сеть узлов. Образец для архитектуры - повторяемые [модули](Глоссарий/модуль-FUM.md), способные объединяться в сеть из модулей того же рода.

На человеческом и агентском уровнях естественный язык является языком [синхронизации знаний FUM](Глоссарий/естественно-языковая-синхронизация-знаний-FUM.md). Люди, LLM-поддерживаемые агенты и гибридные узлы через весь строй языка обновляют локальные модели, выявляют расхождения и координируют совместное действие. Сам [агент человеческого образца FUM](Глоссарий/агент-человеческого-образца-FUM.md) должен повторять этот принцип рекурсивно: быть участником внешней сети и одновременно сетью внутренних подузлов, а не только монолитной LLM с чат-интерфейсом.

Исполняемый статус внутренних подузлов и создаваемых для них модельных сред ещё не выбран; эта граница сохраняется в [открытом вопросе о статусе внутренних FUM и модельных сред](Вопросы/2026-06-22_06-35-26_MSK_статус-внутренних-FUM.md).

В расширенной исследовательской рамке [многоуровневая языковая синхронизация FUM](Глоссарий/многоуровневая-языковая-синхронизация-FUM.md) связывает этот человеческий случай с клеточными сигналами, химическими реакциями, атомными взаимодействиями, уровнем элементарных частиц, другими субатомными масштабами и гравитационно-релятивистскими ограничениями. На нечеловеческих уровнях «язык» является проверяемой общей схемой взаимодействий, а не утверждением о словах, намерении или сознании.

[Сознание](Глоссарий/сознание.md) в проекте определяется как совместное знание: эмерджентное свойство сети элементов. Поэтому [FUM](Глоссарий/FUM.md) рассматривает сознание как многоуровневое сетевое свойство, а не как бинарный признак человеческого масштаба.

### Интерфейс и компьютерная среда

Важен не только сам [FUM-узел](Глоссарий/FUM-узел.md), но и [интерфейс FUM-узла](Глоссарий/интерфейс-FUM-узла.md). Внутренний интерфейс показывает узлу его состояния, память, подузлы и ограничения; внешний интерфейс связывает узел с человеком, другими узлами, сервисами и средой.

Отдельный целевой слой - связка [FUM](Глоссарий/FUM.md) и [MCP-серверов](Глоссарий/MCP-сервер.md) разных сервисов как [единая точка взаимодействия пользователя с компьютером](Глоссарий/единая-точка-взаимодействия-с-компьютером.md). Такой слой должен снижать [модальность приложений](Глоссарий/модальность-приложений.md), сокращать дублирование интерфейсного кода и уменьшать расстояние от идеи до воплощения.

### Наблюдаемость и обучение

[FUM](Глоссарий/FUM.md) должен иметь доступ ко всем своим [внутренним состояниям](Глоссарий/внутреннее-состояние.md), включая информацию, отображаемую пользователю в интерфейсе. [Навигация по памяти FUM](Глоссарий/навигация-по-памяти-FUM.md) считается [наблюдаемым входным сигналом](Глоссарий/наблюдаемый-входной-сигнал.md): открытия документов, переходы по ссылкам, поиск, прокрутка и выбор фрагментов должны быть видимы агенту как часть работы.

Для собственного обучения [FUM](Глоссарий/FUM.md) нужен [обобщённый алгоритм поиска повторяющихся последовательностей](Глоссарий/обобщённый-поиск-повторяющихся-последовательностей.md), пригодный для байтов, текста, структурированных событий, выявленных [паттернов](Глоссарий/паттерн-памяти.md) и последовательностей действий агента.

### Автоматизации и проверки

[Автоматизации FUM](Глоссарий/автоматизация-FUM.md), [устройства восприятия и действия](Глоссарий/устройство-восприятия-и-действия-FUM.md), визуализация и рабочие проверки входят в память проекта как воспроизводимые артефакты. Их исходные тексты, конфигурации, версии, тесты и ограничения должны быть локально проверяемыми; при развитии автоматизаций используется [TDD](Глоссарий/TDD.md).

[Язык автоматизаций FUM](Глоссарий/язык-автоматизаций-FUM.md) должен стать программным слоем, удобным для LLM: входы, выходы, эффекты, проверки, трассы, версии и происхождение фиксируются так, чтобы модель могла надёжно читать, генерировать, объяснять и точечно править автоматизации.

### Открытость и границы доступа

[Открытость FUM](Глоссарий/открытость-FUM.md) является частью идеи, а не только публикационным режимом. Репозиторий ведётся под [CC0 1.0 Universal](LICENSE.md), чтобы базовая память, требования и архитектурные решения могли проверяться, наследоваться и развиваться.

При этом личная память [персонального агента](Глоссарий/личный-FUM-агент.md) не публикуется автоматически. Для обмена [наработками](Глоссарий/наработка.md) между узлами нужны явные [уровни доступа](Глоссарий/уровень-доступа.md), а [децентрализация FUM](Глоссарий/децентрализация-FUM.md) и [границы власти](Глоссарий/граница-власти-FUM.md) должны сохранять координацию без тотального контроля.

Практические критерии допустимой координации, защиты общей памяти и остаточной автономии подузлов остаются в [частично прояснённом вопросе о границах власти узлов FUM](Вопросы/2026-06-22_07-51-48_MSK_границы-власти-узлов-FUM.md).

### Исследования и дальние контуры

[FUM](Глоссарий/FUM.md) должен не только выполнять инженерную работу, но и вести [научные исследования](Глоссарий/научное-исследование-FUM.md), ставить [эксперименты](Глоссарий/эксперимент-FUM.md) и оформлять [открытия](Глоссарий/открытие-FUM.md) как проверяемые [наработки](Глоссарий/наработка.md) памяти.

Дальние горизонты проекта включают [физическое действие FUM](Глоссарий/физическое-действие-FUM.md), [роботизированные системы FUM](Глоссарий/роботизированная-система-FUM.md), [производственные цепочки FUM](Глоссарий/производственная-цепочка-FUM.md), [космическую автономию FUM](Глоссарий/космическая-автономия-FUM.md) и [межзвёздное расселение FUM](Глоссарий/межзвёздное-расселение-FUM.md). Эти темы ведутся как проверяемые требования и открытые вопросы, а не как немедленное обещание автономного действия.

Переход от проектирования и симуляции к реальному исполнению ограничен отдельными открытыми вопросами о [границах аппаратной автономии](Вопросы/2026-06-22_07-28-43_MSK_границы-аппаратной-автономии-FUM.md) и [границах космической автономии FUM](Вопросы/2026-06-22_07-40-59_MSK_границы-космической-автономии-FUM.md).

## Форк памяти

[Публичный GitHub-репозиторий `fum-lab/fum`](https://github.com/fum-lab/fum) служит текущим базовым upstream [памяти FUM](Глоссарий/память-FUM.md). Внешний пользователь может форкнуть его, держать `master` своего форка близко к обновляющемуся upstream `master`, а личную память вести в отдельных ветках вроде `memory/<название>`.

Целевая [репозиторная композиция FUM](Глоссарий/репозиторная-композиция-FUM.md) отделяет общий upstream правил и инструментов от superproject конкретного составного узла. Долговечный специализированный подузел живёт в отдельном форке общего upstream, самостоятельный проект — в отдельном проектном репозитории, а композиционная память подключает проверенные опубликованные ревизии обоих видов как Git submodule. Gitlink фиксирует точный коммит; долговечная ветка остаётся в дочернем репозитории и не превращается в автоматически отслеживаемую ветку submodule.

Путь `Проекты/<название>` в композиции предназначен для gitlink проекта, а не для копии проекта внутри основной истории FUM. У каждого проектного репозитория есть собственные паспорт, очередь и [следующий шаг ветки](Глоссарий/следующий-шаг-ветки.md). FUM-STEP-0084 закрепляет схему паспорта на локальной Git-топологии, FUM-STEP-0085 — изолированное исполнение одного проверенного пакета до кандидатного commit, FUM-STEP-0086 — узкую бесконфликтную CAS-интеграцию в отдельный локальный bare-репозиторий, а FUM-STEP-0087 — версионированный реестр с полной пересборкой производного manifest и base-aware-объединением канонических записей по устойчивым ID. FUM-STEP-0088 добавляет автономный долговечный fork-подузел: отдельный живой клон публикует кандидат в собственный ref, явно синхронизирует его с точной новой вершиной ядра, передаёт общую пользу вверх через паспорт и обновляет родительский gitlink отдельным commit; свежие клоны восстанавливают оба сохранённых состояния. FUM-STEP-0089 отдельно замыкает автономный local-bare маршрут самостоятельного проекта: состояние допуска хранится в физическом checkout ребёнка, родитель сохраняет узкую регистрацию и точный gitlink, проектный commit предшествует отдельному родительскому CAS-коммиту, а свежий родительский клон сначала видит точную ревизию без materialized submodule и лишь затем явно восстанавливает чистый detached-снимок. Контур не создаёт настоящий проект, submodule или сетевой remote. До совместной приёмки FUM-STEP-0090 он не выдаётся за полную композицию fork и проекта или сквозной runtime; действующий resolver ограничен зарегистрированными классами и не является универсальным.

Базовая схема работы:

```bash
git clone <url-вашего-форка-FUM>
cd FUM
git remote add upstream https://github.com/fum-lab/fum.git
git fetch upstream
git switch -c memory/<название>
```

Когда upstream обновляется, сначала обновляется `master` форка, затем он сливается в собственную ветку:

```bash
git fetch upstream
git switch master
git merge --ff-only upstream/master
git push origin master
git switch memory/<название>
git merge master
```

Улучшения, полезные для общей памяти, выносятся в отдельную ветку от свежего `master` и передаются обратно через pull request без приватных материалов. Полный протокол форка, периодического слияния, обратной передачи улучшений и публикационный аудит зафиксированы в документе [Публичный upstream и форки памяти FUM](Документация/27-публичный-upstream-и-форки-памяти.md), а многорепозиторная передача и сохранение коммитов пишущих подузлов — в [репозиторном графе пишущих подузлов и проектов FUM](Документация/44-репозиторный-граф-пишущих-подузлов-и-проектов-FUM.md).
