# [FUM](Глоссарий/FUM.md)

[FUM](Глоссарий/FUM.md) — `fraktaljnyij uzel myishleniya`, по-русски — [фрактальный узел мышления](Глоссарий/фрактальный-узел-мышления.md). Проект разрабатывается как открытый агент следующего поколения.

Сейчас этот репозиторий — [память проекта](Глоссарий/память-FUM.md) и его [документационный прототип](Глоссарий/документационный-прототип-FUM.md), а не готовое отдельное приложение. Практический интерфейс текущей формы — человек, внешняя задача Codex и локальная копия памяти в Git и Markdown. Obsidian можно использовать как удобный интерфейс чтения и навигации, но каноническим источником остаются файлы репозитория.

## Как использовать FUM сейчас

### 1. Подготовьте свою копию

Для личной или публичной работы создайте fork, замените `USERNAME` своим именем на GitHub, клонируйте fork и при необходимости подключите базовый репозиторий как `upstream`:

```bash
git clone https://github.com/USERNAME/fum.git FUM
cd FUM
git remote add upstream https://github.com/fum-lab/fum.git
```

После свежего клонирования инициализируйте закреплённую Git-зависимость LinguisticKit:

```bash
python3 Инструменты/fum-proverka-git-zavisimostej/scripts/proveritj-git-zavisimostj.py init \
  --repo-root . \
  --path Зависимости/LinguisticKit
```

Откройте корень репозитория как локальный проект в Codex Desktop. При желании откройте тот же каталог как хранилище Obsidian.

### 2. Сформулируйте обычный запрос

Напишите задаче Codex, что нужно понять, изменить, проверить или сохранить. Можно писать естественным языком, в том числе транслитом. Если запрос влияет на память проекта, его исходная формулировка сохраняется дословно, а производная память ведётся по-русски кириллицей. Если важны доступ, публикация, сеть, секреты, платные сервисы или другие внешние эффекты, укажите разрешённые границы явно.

Полезный запрос обычно содержит ожидаемый результат, исходные материалы и существенные ограничения. Знать внутреннее устройство памяти или специальные команды FUM для начала работы не требуется.

### 3. Дождитесь локального результата

Обычная задача сначала входит в строгую FIFO-очередь общей рабочей копии. Поэтому несколько одновременно открытых задач могут видимо ожидать друг друга. После допуска задача читает принятую память и применимые локальные правила, обновляет нужные документы или код, запускает проверки и сохраняет происхождение изменения в `Журнал/`.

Сессия с осмысленным изменением заканчивается локальным атомарным commit+handoff: коммит и передача очереди происходят вместе. Обычная задача ветки `master` не выполняет `push` или `publish` автоматически.

### 4. Проверьте результат

Прочитайте итог задачи, просмотрите изменённые файлы и Git-дифф, а при необходимости — соседние `запрос.md` и `отчёт.md` в новой папке `Журнал/`. Отчёт показывает смысл изменения, проверки, решения и известные ограничения; Git-коммит закрепляет точный принятый снимок.

Если результат породил отдельное продолжение, его можно сформулировать новым обычным запросом. Долговечные продолжения также видны в [карточках шагов](Планирование/карточки-шагов/README.md).

### 5. Опубликуйте отдельно, если это нужно

После собственной проверки пользователь публикует выбранный локальный результат отдельным действием, например:

```bash
git push origin master
```

Для другой ветки или точного ref используйте соответствующую явную команду. Ручной push публикует проверенный Git-префикс, но не расширяет разрешения на иные внешние эффекты.

## Автоматическое продолжение

В уже настроенной среде Codex прикреплённая задача [диспетчера автоматизаций FUM](Документация/45-диспетчер-автоматизаций-FUM.md) получает пятиминутный heartbeat. При наблюдаемом простое она может выбрать разрешённый готовый следующий шаг и создать отдельную обычную задачу. Такая задача всё равно проходит FIFO и не вытесняет текущего владельца рабочей копии.

Состояние диспетчера можно читать сообщениями в его задаче. Изменяющее управление выполняется двухфазно: сначала формируется точное предложение, затем пользователь отдельно подтверждает его. Свежий clone репозитория сам по себе не устанавливает и не переносит host-автоматизацию Codex.

В этой же постоянной задаче можно отдельно запросить штатный сброс FIFO и рабочей копии к точному `HEAD` текущей локальной именованной ветки и подтвердить построенный план. Это не heartbeat: read-only-план закрепляет preimage/target изменённых tracked-путей и отклоняет специальный Git-видимый untracked-объект с `unsupported_untracked_type`; подготовка ограждает очередь, а применение очищает индекс и отслеживаемые изменения, удаляет точные Git-видимые неигнорируемые неотслеживаемые обычные файлы и символические ссылки, включая такие пути `.obsidian/`, сохраняет игнорируемые данные и отказывает при грязном submodule или неотслеживаемой границе вложенного репозитория. Частично применённый `read-tree` повторяется только из совместимого preimage/target-состояния, а поздний drift блокирует дальнейшее удаление. Пока Codex-host не предоставляет чистый stop произвольной живой задачи, любой прежний участник со статусом `active`, неизвестным или неоднозначным состоянием блокирует подготовку до первой мутации; `handoff` остановкой не считается, поэтому живая приёмка этого сценария остаётся открытой. До финала продолжение хранит reset-record, после финала — самодостаточная квитанция; после успешного применения тот же управляющий ход больше ничего не записывает и не запускает.

Если именно эти защитные ограждения не дают восстановить локальный автозапуск, человек может использовать отдельный аварийный маршрут из корня репозитория:

```bash
./sbrositj.sh
```

Скрипт без `sudo` требует настоящие TTY одновременно на stdin и stdout, показывает точные текущие ветку, `HEAD`, удаляемые изменения и runtime-ссылки и запрашивает динамическую фразу полного плана. После подтверждения он возвращает индекс и рабочее дерево к этому `HEAD`, сохраняя ignored-данные и вложенные репозитории, архивирует и аннулирует прежнее scoped runtime-состояние, создаёт свежую пустую FIFO и checkout-scoped tombstone прежних задач. Валидные official reset receipts сохраняются; повреждённые архивируются и удаляются, а квитанция ручного сброса хранится отдельно и позволяет без новой мутации восстановить уже состоявшийся терминальный исход. Валидный незавершённый переход на ветку цепочки сначала нужно идемпотентно закончить: сброс отказывает до подтверждения, чтобы не осиротить уже созданную целевую ветку и её карточочные метаданные. Это сознательный `break-glass`, а не host-stop: физически работающая задача не останавливается, прежняя задача не должна входить заново, а следующий запуск карточки возможен только на последующем heartbeat существующей `ACTIVE` автоматизации при наблюдаемом простое. Ошибка фразы или изменение плана завершают вызов без сброса; скрипт не принимает неинтерактивный force-обход.

## Границы текущей формы

- Единого коробочного приложения, собственного самостоятельного runtime и готового GUI FUM пока нет; Codex и его host-оркестрация остаются внешней средой.
- Git, журнал и автоматические проверки подтверждают происхождение, структуру и воспроизводимые инварианты, но не доказывают истинность каждого содержательного вывода или преимущество FUM над другими агентами.
- Сеть, секреты, платные сервисы, публикация, получение данных из внешних источников и физические эффекты требуют отдельного явного разрешения.
- Исполняемые прототипы подтверждают только свои ограниченные сценарии и не являются обещанием готовности полного продукта.
