# Git и рабочая сессия

Эти правила полностью читаются до изменения Git-состояния, подготовки коммита и любой пишущей работы после выбора маршрута.

- Постоянная ветка `refs/heads/planirovaniye` предназначена для согласованных пользователем планов FUM/FUMA и необходимых сопроводительных материалов. Её точное имя выбрано пользователем как исключение из обычной схемы `000058`. Работа ведётся в отдельном изолированном Git worktree с одним писателем дерева и ref. Согласованные этапы фиксируются последовательными проверяемыми коммитами по `FUM-ПРАВИЛО-000062`, каждый коммит публикуется по `FUM-ПРАВИЛО-000064`. Принятые результаты планирования интегрируются в постоянную `fuma`; последующая более редкая поставка в `master` проходит отдельную приёмку по его действующим правилам и явному запросу пользователя. [Согласованный порядок веток](../../Журнал/2026-09-16_13-52-17_MSK_закрепить-роли-веток-и-границу-параллельной-проверки/запрос.md). До принятой интеграции настоящая норма действует только в `refs/heads/planirovaniye` и не считается действующей в `master`.

Своевременное обновление постоянных постановок выполняется по `FUM-ПРАВИЛО-000149`, интеграция веток — по `FUM-ПРАВИЛО-000064`.

<!-- FUM-ПРАВИЛО: FUM-ПРАВИЛО-НОВОЕ-000023 -->
- Для согласованного узла и репозитория `fum-lab/fum` допускается только постоянная ветка состояния `refs/heads/fum-lab/fum` как узкое исключение из `000058`. ROOT назначает одного писателя в отдельном физическом worktree и видимом чате по `000162`; прежний писатель прекращает запись до смены владельца. ROOT остаётся в `refs/heads/fuma`, роль `000121` не передаётся. Принятые код и нормы проверяются до первой предметной записи; план или статический профиль её не разрешают.

Для первого этапа ROOT выдаёт конечный независимый ACT `fum.поручение-дочерней-контрольной-точки.2`, выбирающий ранее закреплённый A `fum.полномочия-ветки-состояния-узла.1` по полному коммиту, точному пути и сырому SHA. До выдачи ROOT сверяет буквальные ID узла и репозитория. A связывает координатора, настоящего владельца, хэш физического корня, полный ref, начальную постановку, базу текущего этапа, поколение, один expected и упорядоченный конечный состав служебных целей. ACT.исполнитель равен A.владелец, ACT.постановка.коммит равен A.начальный_коммит, ACT.область равна A.цели; коммит A предшествует ACT. Копия A из входа maker не заменяет независимый выбор.

Новому этапу или владельцу нужны новое адресное поручение и независимое контрольное поколение: отдельный назначенный полный ref по `000058` перед новым эффектом указывает на выбранный коммит A. Прежний `refs/heads/codex/...` сохраняется для чтения ранее закреплённых входов и квитанций; новый ref допустим только при подтверждённой поддержке выбранными схемами и сценариями, иначе эффект запрещён. Продвижение `fuma` не меняет эти полномочия. Для первого этапа используются версионные вход `fum.обновление-ожиданий-узла.2`, назначение `fum.назначение-писателя-ожиданий.3`, параметры `fum.создание-коммита.8` и подготовка `fum.подготовленный-коммит.10`. Старые схемы сохраняют прежние ограничения; похожий ref, иной узел и произвольная дополнительная цель не допускаются.

Для повторного этапа используется только согласованное семейство: план `fum.план-журнала-писателя-состояния.2`, полномочия `fum.полномочия-ветки-состояния-узла.3`, ACT `fum.поручение-дочерней-контрольной-точки.3`, назначение `fum.назначение-писателя-ожиданий.4`, вход `fum.обновление-ожиданий-узла.3`, параметры `fum.создание-коммита.11` и подготовка `fum.подготовленный-коммит.13`. План P.2 связывает историческое доверие к результату R с актуальной базой H: R является предком H, а выбранные expected-байты R сохранены в H без изменения. План задаёт новую пару Журнала, первоначальный запрос, предыдущий этап, точные экземпляры команд и ресурсы строителя; его чтение не разрешает установку.

ROOT независимо выбирает ранее закреплённые P.2, A.3 и ACT.3. A.3 содержит точный Git-источник `план_журнала`, сохраняет идентичности плана, первоначальную постановку и один expected; новое поколение полномочий отличается от поколения исторического доверия. Выполняется порядок R ≤ H ≤ P.2 < A.3 < ACT.3 по Git-происхождению; строгие границы не заменяются одинаковым коммитом. ACT.3 выбирает A.3 отдельно от копии maker; сохраняются точные равенства владельца, координатора, ref, физического корня, базы и упорядоченного T. U.3 и N.4 выбирают тот же ACT/A, прежнее доверие P.2 и новые байты кандидата; первое создание с повторным этапом не смешивается.

Maker.11 содержит отдельное поле `повторный_журнал` с единственным ключом `каталог`: собственный физический каталог 0700 вне Git. Установка создаёт только точную новую пару P.2 и сохраняет долговечные намерение и квитанцию с независимой цепью ACT/A/P; прежний запрос и RAW не переписываются. Новый запрос сохраняется побайтно; отчёт меняется только в проверяемых рабочих областях и служебных блоках с актуальной связностью, recency и терминальными RAW. Подготовка.13 сохраняет привязки поручения и повторной пары; READY и создание повторно сверяют их, весь конечный stage0-состав и выбранный исполняемый код. Частичная установка или неизвестный исход запрещают слепой повтор и обход новым UUID либо каталогом. Историческая квитанция проверяется отдельно без нового state-эффекта; новый этап требует нового независимого назначения.

Перед каждым новым эффектом повторно сверяются независимые A/ACT, актуальное контрольное поколение, нативное поручение, UUID, физическое дерево, HEAD/ref, конечный состав и индекс. При неизвестном исходе или дрейфе новая запись запрещена до установления фактического результата. Читающее восстановление того же проверенного входа и исторической квитанции использует исторические A/ACT, сохраняет все связи и не создаёт второй коммит; отсутствие активного control само по себе не отменяет исторический результат. Новое намерение не считается читающим повтором.

Этапы, коммиты и точная обычная доставка в одноимённый `origin` выполняются по `000062` и `000064`; локальный результат не доказывает удалённую доставку. Прежние контейнер RAW, expected и квитанции сохраняются. Приватные входы, намерение, доверие и квитанции хранятся в устойчивом физическом каталоге вне Git; временная фикстура не доказывает переживание перезапуска ОС. Полный ROOT-профиль `000062` и `НОВОЕ-000017` остаётся обязательным. Это исключение не активирует FIFO/pool/CAS, heartbeat, dispatcher, autostart, расписания, массовое возобновление или автоматические слияния.

- Новые назначенные ветки строятся по иерархии `refs/heads/<адрес-узла>/<путь>/master`: для FUM адрес узла — `fum-lab/fum`, для другого fork — точный адрес его узла без изменения регистра; при пустом пути используется `refs/heads/<адрес-узла>/master`. Сегменты `<путь>` и генерируемые сегменты имени дерева используют согласованные братиславские имена в нижнем регистре ASCII; назначение связывает их с точным каноническим каталогом или явно назначенным новым путём и физическим worktree без переименования каталогов. Для всех одновременно действующих назначений в пределах одного узла одному логическому пути соответствуют одна ветка, одно физическое worktree и один писатель дерева и ref; передача допускается после прекращения записи прежним писателем. Назначение связывает путь, область каталога, полный ref, физическое worktree и владельца; при неоднозначности соответствия или конфликте refs новая запись запрещена до разрешения. Существующие ветки и их историю сохраняют; чужие refs автоматически не переименовывают и не удаляют. [Позднее указание об иерархии веток](../../Журнал/2026-10-25_06-45-23_MSK_поддержать-композицию-принятых-вариантов-журнала/запрос.md).

Для согласованных слабо пересекающихся направлений корень вправе создавать долгоживущие постоянные ветки по этой схеме от точного принятого коммита постановки. Подходящие существующие ветки переиспользуются; их история не переписывается. В назначении фиксируются область направления, полный ref, владелец, отдельное пишущее worktree и видимый чат по `000058`–`000061` и `000162`. Братиславское имя получают существующей автоматизацией только при подтверждённой поддержке выбранной схемы; иначе поддержка `UNKNOWN` и требуется отдельное исправление. Постоянство относится к ветке и истории: поручения остаются ограниченными, а закрытому дочернему этапу требуется новый допуск.

Исключение `НОВОЕ-000023`, исторические контрольные refs и квитанции сохраняют свой точный контракт. Git не допускает одновременно `refs/heads/fum-lab/fum` и его потомков в одном пространстве refs; при конфликте создание запрещено до отдельно принятой изоляции либо перехода исключения. Прежние сценарии с ограничением `codex/` не становятся совместимыми с новой схемой от изменения текста: без проверенной реализации и отдельного допуска их для новых refs не выбирают.

В ветку направления преимущественно поступают согласованные точные снимки `fuma` и `planirovaniye`; их принимает её единственный писатель. Частота определяется необходимыми правилами, интерфейсами, исправлениями и зависимостями, а не каждым чужим коммитом. Общие изменения не правятся одновременно разными владельцами; необходимость чужой области передаётся её писателю. Обновление основы не разрешает автоматически продолжать закрытое поручение или менять чужой ref.

Обратно в назначенную принимающую ветку передаются периодические проверенные поставки направления. Поводы и оставшийся состав фиксируются в плане или отчёте: согласованный готовый этап, зависимость для другого направления либо изменение приоритета. Нужная другому исполнителю исправленная зависимость не откладывается только ради размера партии. Новые исходные сообщения и плановые записи сохраняются независимо от очереди интеграций. Приёмка охватывает весь фактически входящий состав от общего предка до выбранного OID; проверка последнего коммита не заменяет её. Частичный принятый объём выделяется и поставляется по `000064`, PR адресуется назначенной принимающей ветке по `000149`. Учитываются конфликты, стоимость проверки и устаревание основы; неготовая поставка сохраняется с конкретным остатком.

Настоящий порядок не активирует исторические FIFO/pool/CAS, heartbeat, dispatcher или автоматические слияния по `000066`. [Источник выбора долгоживущих веток](../../Журнал/2026-10-04_14-48-24_MSK_закрепить-долгоживущие-ветки-направлений/запрос.md).

- Для нового агентского коммита, созданного через Codex, `Author Name` имеет точный формат `FUM Codex [<model>; effort=<effort>]`, например `FUM Codex [gpt-6-astra; effort=max]`. Специализация исполнителя сохраняется отдельно в описании коммита и Журнале и не меняет имя агента. Автоматизация добавляет последние подтверждённые значения модели и усилия из native JSONL этой задачи и повторно сверяет наблюдение с подготовленным полным именем; неизвестные, неполные или изменившиеся значения не подменяются догадкой. Свежие prepare, READY и create отдельно требуют `FUM Codex`; prepare отказывает до записи истории модели, READY — до записи готовности, create — до `write-tree` и намерения коммита. Успешная сохранённая квитанция читается раньше нового допуска. Исторические роли остаются допустимыми только для исторических reader/compose и буквального replay; опубликованные коммиты, прежние подготовки и квитанции не переписываются. Имя обозначает последнее наблюдение, а не весь этап одной парой; полная история переключений сохраняется отдельно. Это правило не меняет email, данные committer и явно назначенные даты. [Поручение об однозначном авторе Codex](../../Журнал/2026-10-14_13-36-08_MSK_уточнить-автора-коммитов-Codex/запрос.md).

Для назначения полного имени меняй только `GIT_AUTHOR_NAME`; перед коммитом сравнивай `git var GIT_AUTHOR_IDENT` и `git var GIT_COMMITTER_IDENT` с исходными данными, после него проверяй фактические поля commit. Переопределение общего `user.name` ради роли затрагивает также committer и не соответствует этой норме. [Наблюдаемая ошибка и проверенное восстановление](../../Сбои/FUM-СБОЙ-0047-подмена-committer-при-выборе-роли-автора.md).

<!-- FUM-ПРАВИЛО: FUM-ПРАВИЛО-000201 -->
- Сообщение коммита пишется на русском языке и включает точный текст исходного пользовательского запроса, описание сделанного и последний Git trailer `Codex-Thread-ID: <UUID>` в теле сообщения. Значение trailer должно совпадать с разделом `## Идентификатор сеанса Codex` файла запроса и относиться к корневой пользовательской задаче Codex, а не к дочернему субагенту.

Только для конечной дочерней передачи по `НОВОЕ-000019` вместо чужого человеческого диалога включается точное нативное поручение с заголовком `Первоначальное поручение корня:`. Оно не считается сообщением человека; последний trailer сохраняет общий корневой UUID. Фактически наблюдённые модель и усилие относятся к дочернему исполнителю.

Для `дочерний-приём` по `НОВОЕ-000021` включается точное новое нативное поручение под заголовком `Адресное поручение приёма корня:`. Последний trailer сохраняет корневой UUID; модель и усилие относятся к ребёнку.

<!-- FUM-ПРАВИЛО: FUM-ПРАВИЛО-000202 -->
- Ссылкой на файл исходного запроса нельзя заменять сам текст запроса в сообщении коммита; ссылка может быть добавлена только как дополнительная справка.

В режиме `дочерняя-передача` это же требование относится к первоначальному поручению корня: ссылка на назначение или C дополняет дословный текст, но не заменяет его.

В `дочерний-приём` ссылки на поручение, план или C/H/S/A дополняют дословный текст адресного поручения, но не заменяют его.

<!-- FUM-ПРАВИЛО: FUM-ПРАВИЛО-НОВОЕ-000008 -->
- Внешний агент без допущенного локального checkout передаёт только недоверенное предложение изменения с точными базой, манифестом и хэшем и не становится писателем `master`. Проверка такого пакета не применяет его и не означает принятие: только действующая локальная корневая сессия в собственном рабочем дереве действующей схемы вправе выбрать содержательные строки, сформировать локальные `Журнал/`, recency, индексы и `Proyekcii/**`, выполнить проверки и создать локальный коммит по действующему допуску. Публикацию принятого коммита регулирует правило `FUM-ПРАВИЛО-000064` корневого ядра.
